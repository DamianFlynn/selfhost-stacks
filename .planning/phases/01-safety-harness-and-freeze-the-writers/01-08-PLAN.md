<objective>
Run the WRIT-04 ownership normalisation: one decided `uid:gid` across the whole library tree, with
directory and file modes normalised alongside it.

This is the last mutating plan in the phase and the one with the least margin for error. Everything
before it either created a recovery artifact or removed a writer; this one rewrites metadata on
1,244 files and thirteen directories in place. It is placed last deliberately, and the ordering is
load-bearing in both directions:

- **After the writer freeze (plans 01-05, 01-06, 01-07).** Lidarr carries `UMASK_SET: 002`. A
  recursive `chown` executed while any tagger-class process still holds rw simply re-drifts on that
  process's next write, and the run would prove nothing while looking like it had worked. This is
  the argument 01-02 makes for implementing the `ownership` subcommand there but not running it.
- **After the QUAL-01 capture (plan 01-04).** `ffprobe` records neither `uid:gid` nor mode, so the
  snapshot is provably invariant under this work — ordering cannot change its content. Ordering was
  therefore decided on risk instead: the field-level record of what the tags were predates every
  write the phase makes.

The script this plan runs already exists — `scripts/freeze-music-apply.sh ownership`, written and
syntax-proven in plan 01-02, gated behind the existence of `tank/media/Music@pre-project`. Nothing
new is authored here. What this plan adds is the judgement about *running* it: confirming the freeze
actually holds first, piloting one folder before thirteen, and naming what `aclmode=restricted` does
to a `chmod` rather than discovering it a thousand files in.

**The `aclmode=restricted` risk is the reason this plan has a pilot task.** `tank` is
`acltype=nfsv4` with `aclmode=restricted`. That combination is already known to reject `rsync -a`
here — `mkstemp ... Operation not permitted` on every file, while printing a stats block that looks
like success. The mechanism is the dataset refusing an operation that would alter a non-trivial ACL,
and `chmod` is squarely in that class: on a file carrying a non-trivial NFSv4 ACL, `aclmode=restricted`
causes the `chmod` to fail with `EPERM` rather than silently apply. The `chown` half is unaffected.
So the failure mode to plan for is a **partial** normalisation — ownership converges, modes do not —
and the honest response is to measure it on one folder first.

Output: one `uid:gid` across the tree, modes normalised or the exception explicitly named and
scoped, a recorded before/after census inside the fence, and `check-music-freeze.sh` passing in its
asserting mode for the first time.

Roadmap criterion 5 has two halves. This plan makes the first half true — `stat` returns one decided
value. The second half — "and that decided value is recorded in the repo" — is plan 01-09, together
with correcting `beets.md`'s `chown -R 568:545` (D-14). WRIT-04 is not closed until both have run.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| recursive `chown`/`chmod` → 1,244 library files | An in-place metadata rewrite across the whole library, run as root, whose only rollback is a dataset-wide `zfs rollback` |
| apply script → scope | One wrong constant expands the blast radius from `/mnt/tank/media/Music` to `/mnt/tank/media` or `/mnt` |
| normalisation → Jellyfin | Jellyfin is the sole remaining rw holder; changing ownership under a live consumer can break reads as easily as writes |
| decided `uid:gid` → Phase 2 | This value becomes `anonuid`/`anongid` on the NFS export; getting it wrong here surfaces as a Music Assistant permissions problem two phases later |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-01-45 | Tampering | Recursive `chown` with no rollback | mitigate | The `ownership` subcommand refuses to run unless `tank/media/Music@pre-project` exists (01-02 guard item 3); Task 1 confirms the snapshot independently of the script's own report |
