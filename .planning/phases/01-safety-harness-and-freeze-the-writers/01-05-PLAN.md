<objective>
Make WRIT-01 structurally true rather than true by good behaviour.

The roadmap names two writers. Eleven containers actually hold a read-write path that contains
`/mnt/tank/media/Music`. Narrowing every `/mnt/tank/media` mount to its own subtree is the only
option that leaves the library reachable by exactly one process by construction — a policy that
survives someone restarting a container, rebuilding a stack, or uncommenting an include line.

Purpose: WRIT-02 requires wrtag's library mount deleted, the mount and not merely the restart
policy. D-20 requires nobody to hold rw on Music during Phases 1-3, with the winner granted rw in
Phase 6. D-21 makes Jellyfin the single documented exception and requires the audit to say so
explicitly, because a bare count of one rw holder reads as a failure to whoever inherits this in
Phase 7.

Output: ten compose service files edited, applied on the host, and the audit re-run showing
tagger-class writers at zero across both audit classes.

**Discretionary decision resolved — soulbeet is frozen here, not left to Phase 4.** Its image is gone
from GHCR so it cannot run, and `soulbeet.yaml` is commented out of `arrs/compose.yaml`, which means
the running-container audit passes either way. But the declared-mount class of the audit sees its
`/mnt/tank/media/Music:/music` line, which carries no suffix and is therefore rw. Leaving it means
one uncommented include line re-arms a fifth writer against a library that by then holds the pilot.
The edit is a single suffix and carries zero runtime risk precisely because the container cannot
start. Deletion still belongs to Phase 4, which owns retirement and is deliberately independently
shippable — the same treatment D-22 gives wrtag.
</objective>

| Janitorr → media tree | A container whose declared job is deletion currently holds a rw path that contains the library |
| Jellyfin → Music | The one writer that survives, mitigated at the application layer rather than at the mount |
