<objective>
Build the recovery fence, and build it before anything in this phase writes.

There is no `beet undo` — verified against the live CLI. The ZFS snapshot is the only rollback for
the library tree, and rolling back the tree alone leaves a tagger's `incremental` state claiming the
work is done, which is why the `library.db` copies are taken in the *same step* rather than as a
separate chore. Everything else in Phase 1 that mutates — the ownership normalisation in plan 01-08,
the mount narrowing in 01-05, the Jellyfin and Lidarr changes in 01-06 — sits behind this plan in
the wave order for exactly that reason.

Purpose: SAFE-02, SAFE-03 and SAFE-04 protect assets with no other recovery path. The 54 cover scans
carry full tracklistings for 27 `dj-mixes` folders and are more reliable than any autotagger; they
exist nowhere else. The `TKEY` and `EnergyLevel` tags on the 794 `dj-mixes` files are DJ-tool output
that no metadata source will reproduce.

Output: `scripts/freeze-music-apply.sh` committed, the fence populated under
`/mnt/fast/safety/music-pre-project/`, a manifest with checksums, and an off-box copy of the two
irreplaceable artifact classes on the Mac Mini.

**Sequencing note (open question resolved).** This plan ships both the `fence` and the `ownership`
subcommands but runs only `fence`. `ownership` is run in plan 01-08, after the writers are frozen —
a recursive `chown` executed while Lidarr still holds a rw mount with `UMASK_SET: 002` simply
re-drifts. Shipping both subcommands in one file keeps D-27's "one idempotent apply script" literal
rather than scattering mutations across two scripts.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| workstation → LXC 100 / Proxmox host over ssh as root | `zfs snapshot`, recursive copies and mode changes all run with full root authority |
| apply script → ZFS pool `tank` | Snapshot creation is cheap and safe; snapshot *destruction* or *rollback* would be catastrophic and irreversible |
| apply script → `/mnt/fast/safety` | The fence itself has no snapshot behind it — a bug that writes into the wrong path here has no undo |
| LXC 100 → Mac Mini | The off-box copy crosses a machine boundary with root ssh on one side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Tampering / destruction | `zfs rollback` or `zfs destroy` reachable from an automated script | mitigate | Acceptance criterion asserts `grep -cE 'zfs (destroy\|rollback)'` returns 0. Rollback stays a deliberate human command |
| T-01-07 | Tampering | Silent zero-file copy via `rsync -a` on `tank` | mitigate | `rsync -a` is banned by acceptance criterion; `-rlt --no-p --no-o --no-g` is a named constant. Prior failure printed a success-shaped stats block and exited 23 |
| T-01-08 | Tampering | Torn SQLite WAL from copying a live `library.db` | mitigate | Use the SQLite online-backup mechanism where available; record which mechanism was used per file |
| T-01-09 | Denial of Service | Fence writes into `/tmp` (tmpfs on host RAM) | mitigate | All output under `/mnt/fast/safety`; acceptance criterion checks `/tmp` is untouched. Prior incident took the 28 GB box down and killed ssh on host and LXC |
| T-01-10 | Repudiation | Fence declared complete without verified copies | mitigate | Per-file sha256 spot-check (D-10), verified-over-total reported, run exits non-zero on mismatch |
| T-01-11 | Information Disclosure | `library.db` copies leaving the host | accept | Copies contain music metadata and local file paths, no credentials. Destination is the operator's own Mac Mini, recorded in the SUMMARY |
| T-01-12 | Elevation of Privilege | Root ssh to the Proxmox host for `zfs snapshot` | accept | Snapshot creation is the minimum privilege that satisfies SAFE-02, there is no non-root path, and the script issues only `zfs snapshot` and `zfs list` against the pool |
