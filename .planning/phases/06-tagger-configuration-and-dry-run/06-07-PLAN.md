<objective>
Build the standing assertion that CONF-01, CONF-02 and CONF-05 are true **of the process that will actually import**, and record the two arms of D-30 as the two different objects they are.

Purpose: rc6's `BeetsFlaskConfig.commit_to_beets()` calls `beets.config.set(self.to_dict(extra_fields=True))`, and `to_dict()` serialises the *whole* schema dataclass — defaults included — which confuse inserts at **highest** priority. So a key the vendored config leaves silent is not beets' default; it is rc6's. `import.duplicate_action` becomes `remove`, a delete with no prompt. `match.medium_rec_thresh` becomes `0.10`. `directory` becomes `/music/imported`. `beet config -d` shows none of that, because the injection happens only inside the server process — which is why a read from the CLI would be telling the truth about a different object.

Output: `scripts/check-beets-config.sh`, with a `--self-test`, and one transcript holding both arms side by side.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI confuse view → server-committed config | These are two different objects. Treating one as evidence for the other is how `duplicate_action: remove` stays invisible while the UI deletes duplicates. |
| workstation → LXC 100 → container | Every remote command must be bounded Linux-side; macOS has no GNU `timeout`. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-31 | Tampering | `import.duplicate_action` silently `remove` in the server-committed config, deleting duplicates with no prompt across a library with 828 measured duplicate groups | mitigate | Arm 1 asserts it is `ask`; task 2's verify greps the transcript and fails on `remove`. |
| T-06-32 | Spoofing | A dump that is NOT the server-committed object read as though it were, making every green reading unverified | mitigate | The S3(c) positive control: assert the dump contains a key that can only come from rc6's schema. Absent it, the run is `UNKNOWN, not green`. |
| T-06-33 | Information Disclosure | A credential surfacing in a config dump committed to a public repo | mitigate | Assert redacted and unredacted dumps are identical (no beets credential exists); any difference is treated as a credential and stops the plan. No `-e TOKEN=` on any `docker exec`. |
| T-06-34 | Denial of Service | A `docker exec` issued before the server is up, reading a false answer from an empty log | mitigate | Gate on the watchdog registration line, never on `.State.Status`; the verify command fails the script if `.State.Status` appears in executable lines. |

| T-06-SC | Tampering | npm/pip/cargo installs | accept | This plan installs nothing; the container's `/config/requirements.txt` install hook is provably absent (plan 06-04 task 3). |
