SECTION 3 — PINNED PROOF ROWS (D-22) AND THE DO-NOT-RESCAN SET (OQ-1)
================================================================================
Pinned in the same idiom as the PROOF_ALBUMS table at scripts/check-music-consumers.sh:245-294:
one canonical machine-checkable set, pinned in the artefact and in the script, with a WHY per
row rather than a fixture file nobody opens.

"Parsed correctly" (D-22) means N DISTINCT BROWSEABLE ARTIST ENTITIES with DISTINCT Ids in the
consumer's own API. It does NOT mean a matching count, and it does NOT mean one artist literally
named `A;B` — Phase 3 measured four tracks written onto entirely different songs with counts
looking perfectly plausible.

PRIMARY PROOF SET — the `ARTISTS` tag, because `ARTISTS` is the tag beets ACTUALLY WRITES
(C-2: beets cannot be configured to emit `;` in `ARTIST`; there is no write-delimiter key in
config_default.yaml at 2.12.0 or 2.13.1). These three are what task 2 rescans and what task 3
asserts forever after.

  # | file (Jellyfin-internal path)                                            | tag     | value                            | expect N | before N | before names
  --+--------------------------------------------------------------------------+---------+----------------------------------+----------+----------+-------------

  WHY row 1 — the 4-artist case, the widest N in the library, and the ONLY one that exercises
    a name containing a `$` (`Too $hort`) and a name containing dots (`T.I.`). Both are the kind
    of thing that breaks a naive splitter, and neither is exercised by any other row.
  WHY row 2 — the minimal 2-artist case on a track in a DIFFERENT album and a DIFFERENT artist
    folder, so a result that is really "the whole ARTPOP album re-probed" cannot masquerade as
    a pass on all three rows.
  WHY row 3 — the third album, and the one whose `ARTISTS` value puts the ALBUM ARTIST SECOND
    (`Nate Ruess;P!nk`). If Jellyfin ever re-derived the list from `ARTIST`/`AlbumArtist` rather
    than from `ARTISTS`, this row's ORDER would give it away where rows 1 and 2 would not.
  Rows 1 and 3 were chosen over the two remaining `ARTISTS` files in their own albums
    (`Do What U Want` = Lady Gaga;R. Kelly, `True Love`, `Here Comes the Weekend`) only because
    one row per album is enough; those files sit in the same directories and will be re-probed
    by the same Media/Updated call, so the after-census covers them anyway.

*** DO NOT RESCAN — the OQ-1 TRUSTFALL curiosity, recorded, deliberately left alone ***
These six files carry `;` in `ARTIST` (not `ARTISTS`) and Jellyfin ALREADY reads them as
separate artists with distinct Ids, which is exactly what `UseCustomTagDelimiters: false`
predicts it should NOT do. 10.11.11's prober splits on the custom delimiters only when that
flag is true (AudioFileProber.cs@v10.11.11:227-246), and ATL joins multiple same-named fields
with an internal separator on read — it does not split a single field on `;`
(atldotnet ATL/Track.cs:1079). There is no .nfo in that album directory. So this is almost
certainly STALE DB STATE from a pre-10.10 prober, and a targeted rescan could COLLAPSE these
six to one artist each — destroying evidence criterion 4 rests on, inside a phase whose premise
is that it writes nothing. It would not breach the `:ro` fence (the change is in Jellyfin's DB,
not the tree) but it is not reversible without work.
