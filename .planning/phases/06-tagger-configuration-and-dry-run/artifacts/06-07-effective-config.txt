A4 — "docker exec inherits the image ENV, so BEETSDIR=/config/beets applies"
VERDICT: **FALSIFIED AS WRITTEN — and the correction is load-bearing, not pedantic.**
  Measured from inside the container:

      BEETSFLASKDIR=/config/beets-flask

  A `docker exec` inherits the CONTAINER'S RESOLVED ENVIRONMENT - the image ENV overlaid with
  compose's `environment:` block - not the image ENV. flask.yaml deliberately sets
  BEETSDIR: /config so that $BEETSDIR/config.yaml resolves to the ONE vendored file both
  containers mount (D-03).
  WHY THE DISTINCTION MATTERS: had the image ENV actually applied, $BEETSDIR/config.yaml would
  be /config/beets/config.yaml - which is NOT the vendored file - and arm 2 would have been an
  honest reading of the wrong config. The CONSEQUENCE the research drew from A4 (that the
  vendored config loads underneath the -c overlay, which is what makes `beet config -d`
  meaningful) SURVIVES, and is independently confirmed by the source list in § 2.

A3 — whether a `-c` overlay passed to `beet` escapes rc6's eyconf validation
VERDICT: **CONFIRMED — it escapes, and the mechanism is stronger than "escapes".**
  Test: an overlay containing exactly
      import:
          copy: no
  was passed as `beet -c /tmp/p6-a3-copyno.yaml config -d`.
  Result: rc=0, EMPTY stderr (no validation refusal of any kind), and the overlay WON:
      copy: no
      move: no
  MECHANISM, read at source rather than inferred: /venv/bin/beet is a four-line entry point
  whose whole body is `from beets.ui import main`. It imports no beets_flask module at all, so
  eyconf is never constructed and there is nothing for it to refuse. eyconf validation lives in
  BeetsFlaskConfig.reload(), which only the SERVER calls.
  CONSEQUENCE FOR PLAN 06-08: the D-31 control MAY use a `-c` overlay. It does not need the
  fallback of copying into a /tmp tree.
  ⚠ ONE THING THE TEST ALSO SHOWED, WORTH CARRYING: an overlay setting `copy: no` leaves
  `move: no` alone. copy:no + move:no is beets' import-in-place mode, NOT a move. Anyone writing
  06-08's overlay should set what they mean rather than assume the pair is a toggle.

THE REDACTION NO-OP, ASSERTED RATHER THAN ASSUMED (T-06-33)
--------------------------------------------------------------------------------
`beet config -d` redacts fields marked sensitive unless -c/--clear is passed. This repo holds no
beets credential (Phase 4 D-24), so redaction must be a no-op. Measured by running both forms and
comparing byte-for-byte:
    beet -c <overlay> config -d        vs    beet -c <overlay> config -d -c
    VERDICT: BYTE-IDENTICAL. Redaction is a no-op.
Had they differed, the difference would BE a credential sitting in a config destined for a public
repo, and the standing script fails closed on exactly that.

24 of the 26 rows are `gui.*` keys present in arm 1 and absent from arm 2. That is the expected

their presence in arm 1 is precisely what proves the commit_to_beets() injection happened. Four
of them - `gui.inbox.folders.placeholder.*` - come from rc6's schema rather than from
flask-config.yaml, which is why they are the positive control.

THE TWO REAL ROWS are `import.duplicate_keys.album` and `.item`: a LIST in arm 1, a STRING in
arm 2. This is the row 06-RESEARCH.md:557 predicted ("Equivalent via str_seq; harmless"), and it
fired. Harmless is the right reading - beets coerces both through `str_seq` - but it is recorded
rather than dismissed, because it is a concrete demonstration that the injection changes the TYPE
of a key, not only its value, and a future key where type matters would look identical here.

⚠ THE FOUR LANDMINE KEYS DO NOT APPEAR IN THIS TABLE, AND THAT IS THE RESULT, NOT AN OMISSION.

§ 6. FINDINGS THAT ARE NOT FAILURES — RECORDED, NOT FIXED HERE
================================================================================================

⚠ FINDING 1 — `max_filename_length: 0` IS NOT "NO TRUNCATION". THE COMMENT IS WRONG.
  stacks/selfhosted/arrs/beets/config.yaml:263 says of `max_filename_length: 0`:
      "# No truncation. The target filesystem is ZFS on `tank`; a silent mid-name truncation
      #  would make the expected-tree diff (D-27) report a path difference that is really a
      #  length limit."
  Measured inside the container, against beets 2.12.0's own source:
      config max_filename_length    = 0
      effective max filename length = 200
  `util.get_max_filename_length()` reads the config value and RETURNS IT ONLY IF TRUTHY:
      if length := beets.config["max_filename_length"].get(int):
          return length
      limit = MAX_FILENAME_LENGTH           # 200
      ... return min(os.statvfs(directory)[9], limit)
  So `0` does not disable the limit - it falls through to min(statvfs NAME_MAX, 200), a real
  200-character-per-path-component cap. The stated intent (avoid a truncation that D-27's
  expected-tree diff would misread as a path difference) is NOT achieved by this value, and
  the number that would achieve it is a large explicit one, not 0.
  DELIBERATELY NOT FIXED IN THIS PLAN. Plan 06-07 asserts the effective config; it does not edit
  the vendored config, and quietly editing a file until a check goes green is the shape this
  project exists to avoid. This is a follow-up commit against plan 06-01's file, and it is
  material to plan 06-08/06-09's expected-tree diff: any component of
  `$albumartist/$album%aunique{}/$disc-$track $title` longer than 200 characters WILL be
  truncated, and 06-EXPECTED-TREE.txt was written without that constraint in view.

⚠ FINDING 2 — `import.write` IS `true` IN THE SERVER-COMMITTED CONFIG, AND IS REPORTED, NOT
  ASSERTED. That is deliberate and is stated in the vendored file itself (config.yaml:323-329):
  `write: yes` is Phase 7 behaviour, and EVERY Phase 6 invocation overrides it to `no` through
  its own `-c` overlay. So the effective value under a Phase 6 run is NOT the value in this
  artifact. The controls that do not depend on this key being right are the `:ro` mount (D-05)
  and the statefile sha256 (D-29), and both are independently evidenced above. The standing
  script prints this as a warning on every run rather than asserting it, because asserting
  `write: no` here would be asserting something false about the file and true only about an
  invocation.

⚠ FINDING 3 — A DEFECT IN THIS PLAN'S OWN `<verify>` BLOCK, RECORDED RATHER THAN WORKED AROUND.
  The task-2 verify contains:
      if grep -qE "\bUK\b" "$f" | grep -qi "countries"; then ...
  `grep -q` writes NOTHING to stdout, so the second grep always reads an empty stream, always
  exits 1, and the `if` can never be true. The guard is structurally incapable of firing - the
  same class of defect 06-06 hit with a poll predicate searching for a folder name in a payload
  that carried only a hash, and the same class as § 5's first sweep. It is left as written rather
  than edited: the assertion it was reaching for IS made, from arm 1, by the standing script, and
  is driven red by self-test case 4.

⚠ FINDING 4 — A DEFECT IN THIS PLAN'S INSTRUMENT, FOUND BY THE WIDER SWEEP AND FIXED IN BAND.
  The dump extractor's flow-sequence splitter was not quote-aware, so
  `gui.library.artist_separators: [',', ;, '&']` - whose first element is a QUOTED COMMA - was
  split into four entries instead of three. No key this script asserts carries a quoted comma,
  which is exactly why it would have sat unnoticed until one did. Fixed in commit ce4f6d7 with
  the reason recorded in the code. Post-fix reading: `[",",";","&"]`.
