A1 is "the running build matches the 2.10.4 source read: MA prefers the `ARTISTS`

The test, and why it cannot be satisfied by accident:

    row 2  file tags:  Artist  = "Katy Perry"          <- ONE name, no ";"
                       ARTISTS = "Katy Perry;Snoop Dogg"

**A1 VERDICT: CONFIRMED on 2.11.0b2**, behaviourally rather than by source read.

2.4  THE `summary` PARAMETER — A TRAP THAT WAS CHECKED, AND DID NOT FIRE
--------------------------------------------------------------------------------
The schema revealed a parameter neither the research nor the plan anticipated:

The script reads with the default. If the slim shape truncated `artists[]`, every

The default is therefore left in place deliberately, and the reason is recorded
in the script so nobody "fixes" it later.

2.6  ROW 1 CHARACTERISED — TWO CAUSES RULED OUT, ONE QUESTION LEFT OPEN
--------------------------------------------------------------------------------
The row is NOT dropped and NOT explained away. Three candidate causes were
tested; two are eliminated by measurement:

  RULED OUT — the `;` delimiter. Rows 2 and 3 prove the splitter works on this
  exact build, by the argument in § 2.2: a name that exists only in `ARTISTS`
  came back as its own entity. A delimiter failure cannot be selective.

  RULED OUT — the `mb_id_count == 1` short-circuit. The file carries FOUR
  `MUSICBRAINZ_ARTISTID` values
  (`0bc858a1…;650e7db6…;8e0fe7bd…;f7ba7fbe…`). The short-circuit fires only at
  exactly one id, and had it fired the answer would be 1 artist, not 3.

  LOCATED — the loss is at MA's artist-ENTITY stage, not at tag parsing.
  `music/artists/library_items` (provider-filtered) returns 66 artist entities,
  and **"Twista" is not among them** — nor is any name matching /wista/i. The
  other three names all resolved to real entities. "Lady GaGa" (item_id 209) is a
  PRE-EXISTING entity whose display name came from the `Artist` tag spelling,
  which is why MA shows "Lady GaGa" where the `ARTISTS` tag says "Lady Gaga" —
  a de-duplication artefact, not a parsing error.

  STILL OPEN, stated precisely instead of guessed: MA's artists-per-track
  distribution across this library is **1,220 tracks at 1, 22 at 2, 2 at 3, and
  none above 3** — and this file is the library's ONLY 4-value `ARTISTS` tag. So
  "MA caps the returned list at 3" and "Twista specifically failed to map" are
  BOTH consistent with every measurement available, and a sample of one cannot
  tell them apart. Manufacturing a fourth-artist test case would mean writing to
  the library, which D-25 forbids here for exactly the phantom reason. **Phase 7
  is where a second >=4-artist track first lands, and that is the measurement
  that discriminates.** Carried forward rather than resolved.
