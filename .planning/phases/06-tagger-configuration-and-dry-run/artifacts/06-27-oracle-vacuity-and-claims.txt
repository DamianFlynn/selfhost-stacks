2. GC-15 — THE LAST TWO UNQUOTED PATH INTERPOLATIONS, DRIVEN BY CAPTURING THE
   COMMAND STRING RATHER THAN BY RUNNING IT
--------------------------------------------------------------------------------
A CITATION CORRECTION INHERITED, NOT REDISCOVERED. The cross-family adjudication
says GC-15's three sites are at quick-health-check.sh:1515/:1728/:2196. Those are
GC-17's sites, in a different file, owned by plan 06-26. The labels were crossed.
GC-15's sites are the two `dex_cmd sha256sum` calls in THIS file. Nothing was
looked for in quick-health-check.sh, and that file is untouched by this plan.

WHERE THE FIX WENT, AND WHY NOT INSIDE `dex_cmd`. GC-15 recommends the call
sites; that recommendation was taken. `dex_cmd` renders with "$*", and eighteen
other call sites in this file already hand it `printf '%q'` output - quoting
inside `dex_cmd` would double-quote every one of them. Two call sites is also the
reviewable change: `git diff` shows exactly which two paths moved.

THE DRIVE. REAL_LIB_DB set to `/config/my library.db` - a value with a space,
which is what the finding is about. The command string is ECHOED and then PARSED
by bash (LXC 100's shell, per rsh()'s own comment) with an argv DUMPER standing in
for the `timeout … docker exec -u … ` prefix. NOTHING WAS RUN: no ssh, no docker,
no sha256sum, no estate contact. The prefix strip asserts it matched, and refuses
to report a result if it did not.

  BEFORE
    timeout 300 docker exec -u beetle beets-flask sha256sum /config/my library.db /config/state.pickle
      argv[1] = </config/my>
      argv[2] = <library.db>
      argv[3] = </config/state.pickle>
      argc = 3                      <- ONE path arrived as TWO arguments

  AFTER
    timeout 300 docker exec -u beetle beets-flask sha256sum /config/my\ library.db /config/state.pickle
      argv[1] = </config/my library.db>
      argv[2] = </config/state.pickle>
      argc = 2                      <- the space survives as one word

THE CONSUMER, CONFIRMED RATHER THAN ASSUMED. Two `awk -v p="$REAL_LIB_DB" '$2 == p'`
extractions read the output, and they key on the RAW value. The question the plan
required answering is whether the key still matches now that the COMMAND carries a
quoted form. It does, and the argv capture above is the proof: the remote shell
REMOVES the `\ ` quoting during word expansion, so sha256sum is exec'd with the
raw path in argv and prints that raw path. Quoted on the wire, raw in argv, raw in
the output, raw in the key - the two agree. The keys were therefore left alone;
changing them to a quoted form would have BROKEN the match.

STATED HONESTLY, the one thing quoting does NOT fix: `sha256sum` prints
`<hash>  <path>`, and awk's default field splitting makes `$2` the first
whitespace-delimited token, so a path containing a space still cannot be keyed by
`$2 == p`. That is a PRE-EXISTING limit of the consumer, not something this change
introduced, and it fails CLOSED - the very next lines are
`[ -n "$LIB_SHA_BEFORE" ] || { unknown "no sha256 line for …"; exit 3; }`, so such
a value produces UNKNOWN and exit 3. Before this fix the same value instead
word-split into a THIRD argument on the far side, where sha256sum would have
hashed two paths that were never asked for. Refusing beats mis-hashing. Both
defaults are fixed container paths with no whitespace, which is why GC-15 is INFO.
NOT DRIVEN: the space-carrying value against a REAL container - that needs a live
`--run`, and no live run happened. What is driven is the command string and the
argv it produces, which is where the finding lives.
