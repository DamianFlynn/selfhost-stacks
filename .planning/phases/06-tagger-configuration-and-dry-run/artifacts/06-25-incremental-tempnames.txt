WHAT THIS MEASURES:
  * /tmp is mode 1777 (world-writable, sticky). The sticky bit stops a
    non-owner UNLINKING or RENAMING an existing entry; it does NOT stop anyone
    CREATING a new entry — including a symlink — at an unused name.
  * The kernel's symlink/regular-file protections ARE on. But they only refuse
    a follow when the pre-placed name is owned by a uid that is neither the
    directory's owner nor the following process. Here the whole application —
    a redis, an HTTP server, five rq workers and their multiprocessing
    children — runs as uid 568, THE SAME UID the instrument's `docker exec -u
    beetle` uses. So the kernel mitigation does not cover this case.

WHAT COULD NOT BE MEASURED, stated rather than inferred:
  * `ps` is not installed inside the container (the in-container `ps -eo ...`
    returned nothing); the process picture above is `docker top` from the host
    and is therefore the host's view, which is sufficient for uid but not for
    anything requiring the container's own /proc.
  * Nothing here establishes whether beets-flask has ever been compromised, and
    no such claim is made. The measurement is about REACHABILITY of the name,
    not about a live adversary.

4. THE DECISION — one answer, two files. Plan 06-27 may quote this section
   verbatim for the oracle's RUN_TAG comment.
--------------------------------------------------------------------------------

  THE THREAT IS REAL ENOUGH TO TREAT, AND THE TREATMENT IS MINTING THE NAME
  INSIDE THE CONTAINER. But the property being relied on is CREATION, NOT
  SECRECY, and the difference is the whole of GC-07's objection. `mktemp`
  creates with O_EXCL: it FAILS rather than opening a name that already
  exists, and it will not follow a symlink into being. The template prefix
  stays greppable in the source and is not claimed to be a secret.
  Unpredictability is not the mitigation; refusing to open what is already
  there is. This is why `RUN_TAG="$$"` was the wrong mechanism for the right
  threat: a PID is small, sequential and enumerable, it is the WORKSTATION's
  bash PID and has no relationship to the container's namespace, and it is a
  LABEL chosen by the writer rather than a name minted by the kernel — so it
  narrows a window instead of closing a door. Both findings therefore resolve
  the same way: the threat is real, `$$` overstated what it bought, and the
  correct remedy in BOTH instruments is a container-minted name whose failure
  to mint is a REFUSAL and never a fallback.

Two supporting points, so the decision is not reopened from scratch:

  (a) GC-07's three objections are objections to `$$` AS A MECHANISM, not to
      the existence of the threat. Its own suggested fix names the same remedy
      chosen here ("make it true by having the container mint the name —
      SCRATCH_LIB=\"$(… mktemp \"$SCRATCH/lib.XXXXXX\")\"").
  (b) GC-07's third objection — that the oracle's step-1 probe, which refuses
      any non-empty $SCRATCH, is what actually refuses a pre-placed name — is
      true of the ORACLE and false of this file. The incremental control has no
      step-1 probe over these names at all. It did not even have the guard the
      oracle leans on, which is why it is the sibling that needed the code
      change rather than only a corrected comment.

    :522  echo "TAGHIST BLIND could not mint a program path with mktemp ..."; exit 2
    :525  trap 'case "${THPROG:-}" in /tmp/p6-taghist.*) rm -f "$THPROG" ;; esac' EXIT
    :526  printf '%s\n' "$PROG" > "$THPROG"
    :527  "$PY" "$THPROG" "$ROOT/state.pickle" 2>&1

CLEANUP: a TRAP, not a per-exit-path `rm`. Chosen because every `MANIFEST BLIND`
in that program exits early and the old `rm -f` sat only after the last of them,
so any could-not-look leaked all three files — and a MINTED leftover is worse
litter than a fixed one, because nobody knows its name. The trap re-tests the
variable against the template prefix with a `case`, so it can never remove
anything else, and `${MANDIR:-}` keeps it safe under `set -u`.

EXIT CODES ARE UNTOUCHED. A failed mint is a COULD-NOT-LOOK, so it takes 2
(UNKNOWN), joining the same `... BLIND ...; exit 2` ladder as every other blind
case in those programs. No code was renumbered; the numbering difference against
the oracle is a recorded deliberate non-finding and stays as it is.

CONTRACT PRESERVED: `PROBE-RC` and `STATEFILE-SHA` are emitted in the same order
by the same two lines, and the manifest sentinels MANIFEST-META-BEGIN /
MANIFEST-META-END / MANIFEST-SHA-BEGIN / MANIFEST-SHA-END / MANIFEST OK are
unchanged and in the same order.
