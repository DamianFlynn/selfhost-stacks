PART 1 — GC-03: THE ASSERTED SET CAN BE EMPTY, AND THE BLOCK TICKED GREEN OVER IT
================================================================================

THE COUNTER SUBTLETY, MEASURED RATHER THAN REASONED
---------------------------------------------------
All five D-04 counts are produced by `printf '%s\n' "$SET" | grep -c '^HEAD:'`, and
`printf '%s\n' ""` emits a single BLANK line, not nothing. The plan flagged this as a
place where a guard could be written against a condition that is never true. Measured:

    $ EMPTY=""
    $ printf '%s\n' "$EMPTY" | grep -c '^HEAD:'      ->  0
    $ printf '\n'            | grep -c '^HEAD:'      ->  0
    $ CNT=0; while IFS= read -r l; do [ -z "$l" ] && continue; CNT=$((CNT+1));
      done <<< "$EMPTY"; echo $CNT                   ->  0

So `D04_N_ASSERT` IS genuinely 0 on an empty asserted set — the blank line does not
survive the `^HEAD:` anchor — and `-eq 0` is the correct condition to guard on. The
`while … <<< "$EMPTY"` loop confirmed at ZERO iterations, which is why `D04_BAD`
stays 0 and the ladder falls through to its green condition.

THE FIXTURE
-----------
GC-03's own scenario, built mechanically rather than by hand: take the REAL scan of
this repository's HEAD (199 lines) and remove the three asserted invocations, exactly
as deleting or reshaping them would:

    $ grep -vF 'beet_exec "${BEET_BIN}' raw.txt > fixture-allexempt.txt

    removed:
      HEAD:scripts/check-beets-config.sh:892:    beet_exec "${BEET_BIN} -l ${THROWAWAY_DB} -c ${OVERLAY} config -d"
      HEAD:scripts/check-beets-config.sh:908:    beet_exec "${BEET_BIN} -l ${THROWAWAY_DB} -c ${OVERLAY} config -p -d"

    fixture: 196 lines -> executable 5, exempt 5, asserted 0.

Note what this fixture does NOT trip: raw is 196 (not 0, so guard 1 passes), raw 196 ≠
stripped 95 (so guard 2 passes), executable is 5 (not 0, so CONDITION K passes), the
exempt count is 5 = its pin, and the doc count is 2 = its pin. Every existing guard is
satisfied. That is the whole finding.

PART 2 — GC-16: THE FOURTH REGEX BRANCH'S MISSING ANCHORS
================================================================================

THE FINDING, AND THE CORRECTION THAT TRAVELS WITH IT
-----------------------------------------------------
`D04_INV_RE` has four alternatives. The three LITERAL-token branches each anchor in
three places: content start (with optional `sudo`), after a shell separator
(`[[:space:]](&&|;)[[:space:]]*`), and after a `docker` prefix. The FOURTH branch —
the variable-expansion branch added by plan 06-16 — anchored only on content start or
immediately inside an opening quote.

Recorded so the correction is not lost: the cross-family reviewer graded GC-16 BLOCKER
and justified it by claiming the block comment PROMISED separator anchoring. THAT
JUSTIFICATION IS FALSE. The comment said "content start, or immediately inside an
opening quote", which is exactly what the code did. There was no documentation
mismatch to fix. The substantive gap is real and is graded WARNING: a latent blind
spot with NO CURRENT INSTANCE IN THE TREE. Widening the code is therefore a behaviour
change, and the comment had to be brought FORWARD to the new behaviour — a different
edit from the one the reviewer asked for.

Why it ships alongside GC-03: GC-03's own text names this asymmetry as the silent
route by which the asserted set drops to zero without any counter leaving its pin.

THE EDIT
--------
Leading alternation of branch 4 only. The TRAILING requirement — a flag or a lowercase
subcommand word — is untouched, because that half is what holds the executable count at
8 rather than 26.

  OLD: (^HEAD:[^:]*:[0-9]*:[[:space:]]*(sudo[[:space:]]+)?|")
  NEW: (^HEAD:[^:]*:[0-9]*:[[:space:]]*(sudo[[:space:]]+)?|"|[[:space:]](&&|;)[[:space:]]*|docker[[:space:]][^`]*[[:space:]])

--------------------------------------------------------------------------------
ADDITIVITY — THE FULL PIPELINE, OLD REGEX vs NEW REGEX, IDENTICAL INPUT
--------------------------------------------------------------------------------
Pipeline reproduced exactly as the block runs it:

    git grep -n -I -w -E -e 'beet' -e 'BEET[A-Z_]*' HEAD -- scripts stacks

      | strip ^HEAD:path:line:<space>(#|//)      -> comment-stripped
      | D04_INV_RE                               -> invocation-shaped
      | split on \.md:                           -> documentation / executable
      | D04_EXEMPT_RE                            -> exempt / asserted

Input for both columns is the SAME scan of base commit bf509f4 (199 raw lines), so the
only variable is the regex.

    NEW  raw=199 stripped=98 inv=10 exe=8 assert=3 exempt=5 doc=2

⚠️  ONE FIGURE MOVES, FOR A REASON THAT IS NOT THE WIDENING, AND IT IS REPORTED RATHER
    THAN ABSORBED — THIS IS A DEVIATION FROM THIS PLAN'S OWN VERIFY BLOCK.
    `scripts/quick-health-check.sh` is itself inside D-04's scan scope (`scripts/`), so

    200 and 99, NOT 199 and 98. Measured after the task-1 commit:

    The cause is exactly one line — condition P's own message, at
    `scripts/quick-health-check.sh:1882`:

    That sentence carries the literal token BY REQUIREMENT (plan 06-23 task 1(a): the

    so it survives the comment strip and lands in both the raw and the stripped count.
    The FOUR EXISTING sibling guards each contribute the same line for the same reason

    WHAT DID NOT MOVE, checked rather than assumed: the line is not invocation-shaped

    invocation-shaped / executable / asserted / exempt / documentation all stay at

    neither of the block's two relational guards is affected: raw is still non-zero and

    The new exit-code notice and the rewritten block comment were both written to add

NEGATIVE CONTROLS — the narrowing that makes the stripped count meaningful is INTACT
--------------------------------------------------------------------------------
  fixture (mentions and argument passing, with no invocation anywhere on the line):
    HEAD:scripts/x.sh:14:    echo "see `$BEET_BIN` in the runbook"
    HEAD:scripts/x.sh:15:    remote_exec "$prog" "$root" "$BEET" "$PY"

    HEAD:scripts/x.sh:17:    printf %s "$BEETS_DB_COUNT"

  OLD regex: 0 of 4 matched
  NEW regex: 0 of 4 matched

Line 16 is the one worth naming, because it is where the NEWLY ADDED separator anchor
could plausibly have over-matched: the line contains a `;`. It does not match, and the
reason is that the ANCHOR half does the refusing here while the FOLLOWER half would
have admitted it — ` -eq` satisfies `[[:space:]]+(-|[a-z])` perfectly well. The
separator anchor requires WHITESPACE immediately before the `&&` or `;`, and this line
reads `]];`. That is the clearest single demonstration that both halves earn their
place: neither alone would hold this line out.

The follower requirement is what keeps the executable count at 8 rather than 26 — the
measurement the block comment records. Widening the ANCHOR set while dropping the
FOLLOWER test is how this edit would have become a regression, and the controls above
are what prove it did not.
