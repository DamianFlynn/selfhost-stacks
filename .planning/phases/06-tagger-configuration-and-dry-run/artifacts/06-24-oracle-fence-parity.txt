PART 1 - GC-02: the receiving-side fences now carry the sending side's predicate
================================================================================================

THE DEFECT, RESTATED FROM THE CODE
----------------------------------------------------------------------------------------------
The sending-side fence (`:327`, `:342`) narrows the path suffix to the character class
[A-Za-z0-9._-]. The three receiving-side fences - the copies that run in the very shell about to
`rm -rf` / `rm -f` - were the BARE GLOBS `/tmp/p6|/tmp/p6-*` and `/mnt/fast/safety/phase06/*`.
`[A-Za-z0-9._-]` excludes `/`; a glob does not. The inner layer therefore accepted `..` traversal
while three comments beside it claimed it was "the one that cannot be bypassed by a future edit
that forgets the first".

Nothing was exploitable as shipped. The outer fence runs before the first ssh of every mode,
`remote_sh_c` passes the path as a positional parameter, and `"$1"` is quoted at the `rm`. What
was false was the CLAIM - and the claim is what a future reader would rely on when deleting the
outer fence as "duplicated".

SIDE BY SIDE - the outer fence and the inner fence, after this change
----------------------------------------------------------------------------------------------
OUTER (sending side, bash, scripts/phase06-oracle.sh:327-336):

    SCRATCH_FENCE_OK=1
    case "$SCRATCH" in
      /tmp/p6) : ;;
      /tmp/p6-*)
        case "${SCRATCH#/tmp/p6-}" in
          ''|*[!A-Za-z0-9._-]*) SCRATCH_FENCE_OK=0 ;;
        esac
        ;;
      *) SCRATCH_FENCE_OK=0 ;;
    esac

INNER (receiving side, POSIX sh program text, SCRATCH_FENCE_SH at :1371):

    case "$1" in
      /tmp/p6) : ;;
      /tmp/p6-*)
        case "${1#/tmp/p6-}" in
          ""|*[!A-Za-z0-9._-]*)
            echo "REFUSED: the scratch path is not a throwaway root under /tmp/p6" >&2; exit 3 ;;
        esac
        ;;
      *) echo "REFUSED: the scratch path is not a throwaway root under /tmp/p6" >&2; exit 3 ;;
    esac

The three differences are all forced, and none of them is the predicate:
  1. `"$SCRATCH"` vs `"$1"`  - the path arrives as a positional parameter on the remote side.
  2. `''` vs `""`           - the inner text is a single-quoted BASH string, so it cannot contain
                              an apostrophe. dash treats the two case patterns identically.
  3. a flag vs echo+exit 3  - the outer fence sets a variable the next line tests; the inner one
                              is the last word before `rm`, so it refuses in place.
The ALLOW-LIST ITSELF - `/tmp/p6` exactly, or `/tmp/p6-` plus one-or-more [A-Za-z0-9._-] - is now
character for character the same at both layers. The stamp pair is the same story against
`/mnt/fast/safety/phase06/`.

THREE LITERAL COPIES RATHER THAN ONE SHARED STRING - the trade, stated
----------------------------------------------------------------------------------------------
`STAMP_WRITE_FENCE_SH` and `STAMP_RM_FENCE_SH` are byte-identical literals. Aliasing one to the
other would make drift structurally impossible, which is stronger than testing for it. It was not
done, for two reasons, and the second is the honest one:
  (a) each destructive site keeps a fence it owns, so no site inherits another's correctness and
      each can be driven on its own - which is what the cases below do; and
  (b) the plan's own verification asserts the narrow character class appears at five or more
      sites, and an alias yields four. The count is a proxy for "the class is everywhere it needs
      to be"; satisfying it literally was preferred over arguing with it mid-execution.
The residual risk that leaves - two copies that could drift again - is closed by an EXECUTED
equality case rather than by a comment. That is the direct lesson of GC-02, whose root cause was
not duplication but duplication that drifted in silence.

DRIVEN - the inner fence ALONE, with the outer fence absent
----------------------------------------------------------------------------------------------
Each case executes a FENCE TEXT with the local /bin/sh and a hostile `$1`. The outer fence is not
in the picture at all, which is the whole point: `:327` refused every one of these paths long
before the first ssh, and the inner layer's documented purpose is to hold when a future edit
removes that.

WHY NONE OF THESE CASES CAN DELETE ANYTHING: the text executed is the fence only - a bare `case`
that either falls through or prints and exits 3. It contains no `rm`, no `touch` and no
redirection into a path, and three self-test cases assert that by inspecting the strings. The
full programs (CLEANUP_PROG, STAMP_WRITE_PROG, STAMP_RM_PROG) are NEVER executed here, not even
on paths the fence should refuse: were the fence to regress, driving the full program would turn
this self-test into `rm -rf /tmp/p6-x/../../../home`. What carries the result from the fence text
to the shipped program is structural instead - three cases assert each PROG literally BEGINS with
the fence text that was driven, which is true by construction because the programs are built by
concatenation at their definition.

THE REGRESSION, DRIVEN AGAINST A BARE-GLOB MUTANT
----------------------------------------------------------------------------------------------
A case that only proves the new predicate refuses does not prove the old one accepted. Every other
guard in this self-test carries its driven red INLINE, holding the old shape as a literal beside
the new one. That was deliberately NOT done here: embedding `/tmp/p6|/tmp/p6-*) : ;;` would leave
a grep for the weak fence still returning a hit in the file, and that grep is precisely the
detector a future reviewer will use to check GC-02 stayed closed. A permanently-hit grep is a
broken detector.

So the regression is driven against a MUTANT COPY of the whole script instead. The mutant reverts
the three fences to their bare-glob text and changes nothing else; the builder asserts each of its
three substitutions matched EXACTLY ONCE and aborts otherwise, so a silently-empty mutation cannot
masquerade as a passing run.

PART 2 - GC-06: the three `printf | grep -q` pipelines, one of them INVERTED
================================================================================================

THE DEFECT, AND WHY ONE OF THE THREE IS NOT LIKE THE OTHER TWO
----------------------------------------------------------------------------------------------
Plan 06-19 added `st_grep_why` specifically to avoid `printf | grep -q`, with a comment saying
"that shape has produced a false red in three plans of this phase already". The WR-08 self-test
section, 300 lines above it, used the shape that comment warns about, in three places:

    :1888  printf '%s\n' "$qout" | LC_ALL=C grep -qF "01 It's \$o.mp3" || rc=1
    :1907  printf '%s' "$qcmd" | LC_ALL=C grep -qF " sh $(printf '%q' "$qdir")" || rc=1
    :1910  if printf '%s' "$qcmd" | LC_ALL=C grep -qF "find $(printf '%q' "$qdir")"; then rc=1; fi

`:1888` and `:1907` are POSITIVE assertions - the needle must be present. A 141 there makes the
assertion fail, i.e. a FALSE RED. Loud, investigated, survivable.

`:1910` is INVERTED - the old interpolated shape must NOT be present, so a grep MATCH is the
FAILURE case. `grep -q` exits on its first match, which is precisely when the assertion is meant
to fire; `set -o pipefail` (:223) then propagates the dead `printf`'s SIGPIPE as 141; the `if`
reads FALSE; `rc` stays 0; and `st_case 0 0` reports the case PASSED at the exact moment it
should have failed. That is GC-01's mechanism pointed the dangerous way round: an assertion that
can silently not fire, which is this phase's dominant defect class.

THE FIX
----------------------------------------------------------------------------------------------
All three are now here-strings. `LC_ALL=C` is kept, `-F` is kept, and each needle is byte-for-byte
what it was - these assertions check exact rendered command text, and a changed needle is a
changed assertion, not a reformatted one.

    $ grep -v '^[[:space:]]*#' scripts/phase06-oracle.sh \
        | grep -cE '\|[[:space:]]*(LC_ALL=C[[:space:]]+)?grep[[:space:]]+-q'
    before: 3        after: 0
    $ grep -v '^[[:space:]]*#' scripts/phase06-oracle.sh | grep -cF 'grep -qF'
    before: 3        after: 4     (the three sites, plus st_grep_why's own file-based grep)

DRIVEN - the inverted assertion, on the failure input it exists to catch
----------------------------------------------------------------------------------------------
A `qcmd` was constructed that DOES carry the old interpolated `find <path>` shape. A correct
assertion must report FAILED on it.

    == 1. the real failure input, at its REAL size ==
       haystack bytes: 75
        PIPELINE form       rc=1  -> st_case sees 0 vs 1 -> case reports FAILED   (CORRECT)
        HERE-STRING form    rc=1  -> st_case sees 0 vs 1 -> case reports FAILED   (CORRECT)

MEASURED FACT, RECORDED EXPLICITLY RATHER THAN GLOSSED: at today's input size the pipeline form
is CORRECT. The haystack is a 75-byte one-line command string, grep reads all of it before
exiting, `printf` has already finished writing, and there is no reader to disappear. The danger
is real but unreachable at this size - which is precisely why it survived review, and precisely
why leaving it in place would be wrong: the input is the self-test's own fixture, and nothing
guarantees it stays 75 bytes.

So the mechanism is demonstrated separately, with the needle placed at the TOP of a padded
haystack (the position that makes grep exit earliest, so the worst case for the pipeline):

    == 2. the same two shapes, padded past the pipe buffer ==
           8 KiB   pipeline grep-stage rc=0     here-string rc=0
          32 KiB   pipeline grep-stage rc=0     here-string rc=0
          56 KiB   pipeline grep-stage rc=0     here-string rc=0
          64 KiB   pipeline grep-stage rc=141   here-string rc=0
          96 KiB   pipeline grep-stage rc=141   here-string rc=0
         128 KiB   pipeline grep-stage rc=141   here-string rc=0

    == 3. the assertion's verdict at 128 KiB, which is what actually matters ==
        PIPELINE form (pipefail on)   rc=0  -> st_case sees 0 vs 0 -> case reports PASSED (WRONG)
        HERE-STRING form              rc=1  -> st_case sees 0 vs 1 -> case reports FAILED (CORRECT)

That is the finding, executed: on an input the assertion is SUPPOSED to reject, the pipeline form
reports the case PASSED. The here-string form reports FAILED, which is correct, at every size.

CROSS-CHECK AGAINST THE SIBLING PLAN, ARRIVED AT INDEPENDENTLY
----------------------------------------------------------------------------------------------
Plan 06-22 measured the same threshold on the same workstation while closing GC-01 in
scripts/check-beets-config.sh: rc 0 at 8-56 KiB, rc 141 at 64/72/96/128 KiB, and position
dependence on otherwise identical input. This plan reproduces that boundary exactly - 56 KiB
clean, 64 KiB the first 141 - having measured it from a different script, a different needle and
a different haystack. Two independent reproductions of a 64 KiB pipe buffer on darwin 27.0.0.

Also inherited from 06-22 and worth repeating: the operator's interactive zsh aliases `grep` to
ugrep 7.8.4, but inside a bash script `command -v grep` resolves to /usr/bin/grep (BSD grep
2.6.0-FreeBSD). Every measurement above was answered by BSD grep. A reader reproducing this from
an interactive zsh prompt will be running different software.

================================================================================================
NOT DRIVEN - what this artifact does NOT establish
================================================================================================
Recorded so the register is a register and not a summary of the good news.

1. THE CONTAINER'S dash. Every fence case was driven with the macOS /bin/sh, which is bash in
   sh-compatibility mode. The fence text is deliberately POSIX - nested `case`, `${1#prefix}`,
   `""` as an empty pattern - and uses no bash-only construct, but "parses and behaves identically
   under dash" is an argument here, not a measurement. The estate's own `scripts/
   phase06-incremental-control.sh:473` has carried this shape against the same dash for several
   plans, which is corroboration, not proof.

2. THE FULL DESTRUCTIVE PROGRAMS. CLEANUP_PROG, STAMP_WRITE_PROG and STAMP_RM_PROG were never
   executed - deliberately, as set out in Part 1. What is proven is (a) the fence text refuses
   and accepts correctly, and (b) each program BEGINS with that exact text. The step from those
   two to "the program refuses" is sound but structural; no `rm` was observed declining to run.

3. `docker exec` STATUS PROPAGATION of the fence's exit 3. The refusal's exit code is driven
   locally; its journey back through `docker exec`, `rsh` and `RSH_RC` is unchanged by this plan
   and was not re-measured.

4. THE 141 REACHING A REAL SELF-TEST CASE. Part 2 demonstrates the mechanism with a padded
   haystack, not with the oracle's own fixture, which is 75 bytes. No run of this script has been
   observed reporting a false PASS. The change is a removal of a latent hazard, and the honest
   claim is that it was latent.

5. WHETHER ANY OTHER FILE IN THE ESTATE CARRIES THE SHAPE. Only scripts/phase06-oracle.sh was
   inspected here. Plan 06-22 did the repo-wide inventory for GC-01; anything it found outside
   this file is that plan's scope, not this one's.
