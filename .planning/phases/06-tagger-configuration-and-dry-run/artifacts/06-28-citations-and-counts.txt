METHOD — REGEXES EXTRACTED, NEVER RETYPED
------------------------------------------
Plan 06-23 widened `D04_INV_RE` during this same round, so any copy of the
regex written into a plan is already old. Both regexes are extracted from the
shipping file, and the extraction is asserted non-empty AND unique before use:

    sed -n "s/^[[:space:]]*D04_INV_RE='\(.*\)'$/\1/p"    scripts/quick-health-check.sh
    sed -n "s/^[[:space:]]*D04_EXEMPT_RE='\(.*\)'$/\1/p" scripts/quick-health-check.sh
    # each must yield exactly 1 line; each must be non-empty

Then the block's own pipeline, verbatim:

    git grep -n -I -w -E -e 'beet' -e 'BEET[A-Z_]*' HEAD -- scripts stacks   > hits.txt
    /usr/bin/grep '^HEAD:'                                     hits.txt      > raw.txt
    /usr/bin/grep -vE '^HEAD:[^:]*:[0-9]*:[[:space:]]*(#|//)'  raw.txt       > kept.txt
    /usr/bin/grep -E  -f inv_re.txt                            kept.txt      > inv.txt
    /usr/bin/grep     '\.md:'                                  inv.txt       > doc.txt
    /usr/bin/grep -v  '\.md:'                                  inv.txt       > exe.txt
    /usr/bin/grep -E  -f ex_re.txt                             exe.txt       > exempt.txt
    /usr/bin/grep -vE -f ex_re.txt                             exe.txt       > assert.txt
    # count each with: /usr/bin/grep -c '^HEAD:' <file>

(`-f <file>` is used rather than an inline `"$RE"` so the extracted regex is
never re-quoted through a second shell expansion.)

AGREEMENT WITH PLAN 06-23 — AND WHAT THE TWO NUMBERS EACH MEAN
---------------------------------------------------------------
06-23's artifact records TWO pairs and they are not in conflict:

  * 199 / 98 is an OLD-REGEX vs NEW-REGEX comparison over IDENTICAL INPUT
    (the scan of base commit bf509f4). It is the correct historical pair, and
    the only pair that can prove the widening was additive, because there the
    regex is the sole variable.
  * 200 / 99 is a reading of HEAD after 06-23 landed. The +1 is exactly one
    line: condition P's own message, which carries a literal `beet`-invocation
    token BY PLAN REQUIREMENT and is an `echo`, so it survives the comment
    strip and lands in both raw and comment-stripped.

This plan's independent measurement at 456ad06 reads **200 / 99**, agreeing
with 06-23's post-merge reading and with plan 06-26's independent confirmation
at its own base and after all three of its tasks. Three agents, three
measurements, same answer.

The number this plan's OWN text quoted before execution — 191 / 90 in
beets.md, and 199 / 98 inherited in the plan body — was stale on arrival. That
is the finding, not a discrepancy to reconcile.

WHY THE TWO UNPINNED ROWS WERE DROPPED RATHER THAN RESTATED
------------------------------------------------------------
The plan offered two shapes and recommended the second. The second was taken.

`raw` and `comment-stripped` count the whole repository's `beet`/`BEET*`
mentions across `scripts` and `stacks`. They therefore move with EVERY commit
to either tree — including the commit that writes them down. beets.md is
itself inside the scan scope (`stacks`), so any value written into that table
is a value the act of writing it can change. Restating them as a transition
(`raw 200 -> 201`) would be honest but would need re-measuring and re-editing
on every future commit, and the failure mode when someone forgets is a page
that states a checkable-looking falsehood — which is exactly the state GC-10
found.

Neither figure is pinned. Nothing asserts on either. Dropping them costs no
coverage and removes the only two rows that could rot.

The five surviving rows are all either pinned or derived from pinned ones, and
none of them moves when prose is added anywhere in the repo.

THE SENTENCE THAT WAS REMOVED, AND WHY IT WAS THE ACTUAL FINDING
-----------------------------------------------------------------
Old: "**Measured counts on this plan's tree** (hand-reproduced from the host
      and compared against the block's own printed figures — agreement at every
      position, both trees)"

That parenthesis asserts a verification which the note's own presence
invalidates: the note's body quotes `D04_INV_RE` and `BEET[A-Z_]*`, which adds
`BEET`-matching lines to the raw and comment-stripped counts it claims
agreement on. It is not a typo — it is a claim of agreement that could not have
been true once the claim was written down.

The replacement states which figures are pinned, which are not, what was
measured, at which commit, on which tree, and names GC-10.

This file's own convention, applied correctly by the eleventh and twelfth
exit-code notices in quick-health-check.sh (`headers 10 -> 11`), is to state a
self-referential count as a transition measured before AND after the edit that
changes it. That convention was not applied here when the table was written.
