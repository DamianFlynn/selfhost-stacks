# 4. DNS IS VERIFIED, NOT CREATED — PASS, WITH THE WILDCARD CONTROL
################################################################################
>>> A TRAEFIK CERTIFICATE IS NOT EVIDENCE THAT DNS RESOLVES.
    That sentence belongs here, and on this estate it is not a generality. Traefik's runtime
    command line carries
        --entrypoints.websecure.http.tls.domains[0].main=deercrest.info
        --entrypoints.websecure.http.tls.domains[0].sans=*.deercrest.info
    a WILDCARD. A valid certificate would be presented for a hostname with no DNS record at
    all. The record has to be looked up, and a control name has to fail to resolve, or the
    lookup only proves that a wildcard cert exists.

      104.21.83.117
      172.67.175.143

    Both IPv4 answers and both IPv6 answers are Cloudflare proxy addresses
    (104.21.0.0/16 and 172.67.0.0/16; 2606:4700::/32). The record is real AND proxied.

    $ getent hosts zzz-nonexistent-test.deercrest.info      <-- THE CONTROL
      rc=2        (no output; did not resolve)
    $ dig +short zzz-nonexistent-test.deercrest.info
      (empty)

    The control is what distinguishes a real record from a wildcard. There is NO DNS wildcard
    for `deercrest.info`: an arbitrary name under the zone does not resolve, so
    `beets.deercrest.info` resolving is a specific record that someone created.

    $ dig +short CNAME beets.deercrest.info
      (empty)
    Recorded honestly: no CNAME is visible in DNS. That is expected for a Cloudflare PROXIED
    record — Cloudflare flattens and answers with its own anycast A/AAAA regardless of how
    the record is stored in the dashboard. So the correct claim is "the name resolves to
    Cloudflare proxy addresses", NOT "a CNAME was observed". Do not upgrade the claim.
