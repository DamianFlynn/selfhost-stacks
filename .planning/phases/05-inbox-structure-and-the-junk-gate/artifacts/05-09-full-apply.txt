2. DEFECT 1 — THE APPLY RECORD LANDED IN THE CONTAINER'S EPHEMERAL LAYER

.../phase05/05-09 SUBDIRECTORY and the proof FILE were bind-mounted. The parent directory was
not. Docker created the path inside the container's writable layer, the tool wrote 4,746 records
to it, and `--rm` discarded them.

  * The WRITES were unaffected. The collection was correctly mounted read-write and all 715 files
    were written; the tool exited 0 and its stderr summary is on disk. Only the EVIDENCE was lost.
  * This is my invocation error, not a defect in the tool. Recorded rather than quietly re-run,
    because "the artefact exists" and "the artefact was produced by the run it claims to describe"

RECOVERY, in two parts, neither of which is "run it again and pretend":

  (a) A corrected re-run, with .../phase05 mounted read-write. Because rule 4 is a fixed point,

        4,746 records, `written: false` on ALL 4,746, `noop` on all 4,746,
        files changed 0, failures 0, .failed 0 bytes, exit 0, 609.52 s

  (b) `now-album-apply.ndjson` was RECONSTRUCTED FROM MEASUREMENT — and the reconstruction is

3. DEFECT 2 — ATLANTIS REBOOTED MID-VERIFICATION
--------------------------------------------------
While the 45 GB after-capture (`ffmpeg` + `ffprobe`, two processes per file) was running, a full
ID3-header pass over the 4,746 snapshot twins was started CONCURRENTLY. ssh to LXC 100 then timed
out during banner exchange, and both hosts came back with `up 0 min` / `up 2 min`.

This is the documented atlantis memory-pressure signature, and running two whole-collection reads
at once is a fair reading of the cause. Recorded so the next plan does not repeat it: on this
estate, whole-collection passes over `tank` are run ONE AT A TIME.

WHAT WAS AT RISK, AND WHY THE ANSWER IS NOTHING:

  * No write was in flight. Both applies had completed and been fingerprinted before the capture
    started, and the corrected re-run had already proved 0 further mtimes moved.
  * Asserted rather than assumed: a fresh fingerprint after the reboot, compared to the one taken
    before it — **4,751 rows either side, 0 moved, 0 vanished, 0 appeared**. No torn write, no
    truncated file, no lost file.
  * `zpool status -x`: all pools healthy.
  * The interrupted work was READ-ONLY and resumable. The capture is ledger-based by design; it
    resumed from 1,237 and completed at 4,746 with 0 failed.

The resumed archive was VALIDATED rather than trusted, because a hard power-off during a
gzip-append is exactly when a container file goes bad quietly:

4. THE GATE — THE FULL-COLLECTION FIELD-LEVEL DIFF
----------------------------------------------------
  bash scripts/diff-music-tags.sh phase05-now-before.ndjson.gz phase05-now-after.ndjson.gz
  exit 0

  category                                    declared        observed    verdict
  ------------------------------------------- --------------- ----------- -------
  MATCHED                                     4,735           4,735       MATCH
  MISSING_AFTER                               0               0           MATCH
  NEW_AFTER                                   0               0           MATCH
  FIELDS_DROPPED                              0               0           MATCH
  FIELDS_GAINED                               0               0           MATCH
  FIELDS_CHANGED                              740, album only 740, album   MATCH
  matched files with ZERO tag fields BEFORE   0               0           MATCH

TWO NUMBERS IN THAT TABLE ARE NOT THE ONES THE PLAN TEXT PRE-DECLARED, AND BOTH ARE CORRECT.

  * The plan says "MATCHED equal to the collection's mp3 count", i.e. 4,746. The observed 4,735 is
    right and 4,746 was never achievable: `diff-music-tags.sh` joins on `audio_md5`, and plan
    05-07 measured 11 groups of files sharing one bitstream (9 of them inside `Vol 004`, a
    three-edition merge). 4,746 records collapse to 4,735 distinct keys on BOTH sides. MATCHED
    equals the distinct-key count, which is the correct form of the assertion.
  * FIELDS_CHANGED is 740, not 751, for the same reason and it reconciles exactly. All 22 files in
    the 11 duplicate groups fall inside the written set (the groups live in Vol 002/003/004, all
    of which were written), so 22 written paths collapse to 11 keys: 751 - 11 = 740. Measured, not
    argued: distinct changed keys = 740, duplicate groups in BEFORE = 11.

ASSERTED MECHANICALLY, NOT BY READING 740 ROWS:

  jq -r '.fields_changed[].field' | sort | uniq -c        ->   740 album

  One distinct field name across every changed row, and it is `album`. No `tracktotal`, no
  `artist`, no `title`, no `comment`, no `date`. D-10's exclusion of the volumes 4 / 8 / 9
  tracktotal repair is therefore discharged by measurement: `tracktotal` does not appear in the
  changed set at all. That repair belongs to Phase 6.

  distinct AFTER values among changed rows                22   (= the 22 written volumes)
  AFTER values failing ^Now That's What I Call Music! \d{1,3}$   0
  changed source_paths NOT among the 751 written paths    0    (a strict subset)

FIELDS_GAINED 0 is the other half of the safety statement: mutagen synthesised no
`COMM:ID3v1 Comment` frame from the ID3v1 block and translated no `TYER` into `TDRC`. The two
load-time defaults the tool sets explicitly against both held over 4,746 files.

MATCHED 4,735 with MISSING_AFTER 0 and NEW_AFTER 0 is the direct measurement that `audio_md5`
did not move on ANY of the 751 written files. Had `preserve_id3v1_trailer()` failed,
`save(v1=UPDATE)` would have regenerated the ID3v1 block, moved the key, and the written files
would have appeared as MISSING_AFTER plus NEW_AFTER instead of inside MATCHED. Phase 7's join key
survives this write. That is D-10's whole safety argument, measured rather than restated.

The vacuous-pass guard: ZERO matched files had an empty tag set on the BEFORE side. "No fields
dropped" here means fields were present and survived.

6. SCOPE — AND THE PLAN CRITERION THAT PASSES VACUOUSLY
--------------------------------------------------------
The plan's acceptance criterion is:

    "`zfs diff tank/downloads@pre-phase5 tank/downloads` from atlantis shows modifications
     confined to paths under the collection folder"

IT WAS RUN, AND IT PASSES, AND IT PROVES NOTHING. Recorded rather than quoted:

  total lines                                          28,845
  change types                       23,996 `+`, 88 `-`, 7 `M`, 4,754 `R`
  `M` lines on a REGULAR FILE                          0
  `M` lines on any .mp3                                0
  the 7 `M` lines                    all DIRECTORIES — /mnt/tank/downloads and six children
  inside the collection              115 `+`, 9 `-`, 4,750 `R`, 0 `M`

`zfs diff` collapses "renamed AND modified" into a single `R` record, and plan 05-07 renamed
EVERY mp3 in this collection relative to `@pre-phase5`. Driven directly: a file this plan
demonstrably wrote —

  R  F  .../VA-Now_.../01. U2 - Discotheque.mp3 -> .../VA-Now_.../Vol 036/01. U2 - Discotheque.mp3

— carries an `R` line and no `M` line at all. So this criterion would report the identical
"0 modifications on any mp3" whether this plan had written 751 files or zero. It is
non-discriminating, in the same family as 05-08's finding about its own plan's `jq` verify.

(The 23,996 `+` and 88 `-` outside the collection are SABnzbd's ordinary inflow since
2026-09-18T15:42 at roughly one job per 72 s. Not this plan's, and not new.)

REPLACED WITH AN INSTRUMENT THAT CAN FAIL IN BOTH DIRECTIONS — whole-file md5 against the
snapshot twin, on two arms:

  WRITTEN arm    25 files, spread over 22 volumes
     files whose content MATCHES the snapshot (must be 0)      0
  UNWRITTEN arm  25 files, spread over 25 volumes
     files whose content DIFFERS from the snapshot (must be 0) 0
  twins not found in the snapshot                              0
  VERDICT                                                      PASS

The written arm proves the instrument can SEE a write; without it, "the unwritten files are
identical" would be the same worthless statement `zfs diff` makes. The unwritten arm is the scope
claim. Bounded to 25 per arm deliberately: an unbounded pass over 45 GB x 2 is what caused § 3.
