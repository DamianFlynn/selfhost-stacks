== Why the negative control does not target the library ==
  Phase 1's D-20 says nobody holds rw on the library dataset (tank/media/Music) until
  Phase 6, and D-21 states the property under test as 'a different devid changes the
  inode', not 'the library specifically'. The target is LXC 100's ext4 root, which
  satisfies the property without touching anything D-20 fences. The library's MOUNT
  PATH is deliberately absent from every command this task runs, so that criterion
  stays mechanically checkable rather than defeated by prose about it.

== Why the assertion is on the PAIR (%d, %i), never %i alone ==
  Task 1 measured /mnt/tank/downloads and the library root BOTH reporting inode 34 on
  different filesystems. Inode numbers are only unique within a filesystem, so an
  instrument comparing %i alone would call two distinct objects identical. Both
  controls above assert the pair.

================================================================================
What this establishes, and what it does not
================================================================================

ESTABLISHES: a move between two _inbox directories preserves both devid and inode — it is a
rename(2), not a copy-then-unlink. The instrument has been observed BOTH holding (68/247882 ->
68/247882) and breaking (68/247882 -> 64519/1050087), so a future "INODE UNCHANGED" reading is
evidence rather than a tautology.

DOES NOT ESTABLISH: anything about moves into or out of the library dataset. Those remain
copy-then-unlink across the tank/downloads -> tank/media/Music boundary, as CLAUDE.md
§ Constraints already records. Nothing in this task measured that boundary.
