<objective>
Teach the existing tag tool one new rule, and prove it on paper before it writes anything.

D-10 is explicit that this is one field on one collection and that no second tool is written. The
measurement splits cleanly: `disc` and `track` are already correct — zero omissions across the
collection and the per-volume arithmetic lands exactly on the volumes that are complete — while `album`
is the one field that is wrong, and wrong in a way that breaks the deliverable. Volume 36's folder would
otherwise contain three different album strings and beets would not see one album.

The single riskiest line-change in this phase lives here. `normalise-dj-tags.py` sets
`SCRATCH_ROOT = "/mnt/tank/downloads/spike-03"` and `resolve_target_or_die()` fences to it, so the
Phase 5 target is refused as written. The wrong fix is to widen that constant to all of
`/mnt/tank/downloads`, which would make every file the download client writes reachable by a tag writer.
The right fix is a second, NARROWER named pair — a collection mode whose root is the Now! collection
folder itself.

Purpose: get the rule right and reviewed before a single byte is written.
Output: an extended `normalise-dj-tags.py`, a passing self-test, and a dry-run NDJSON.
</objective>

    THE INPUT IS THE FOLDER NAME, NOT THE ALBUM TAG. Rule 4 belongs to the same class as rule 1's
    derive_album_from_folder, not to rule 2's value-transform class. D-03 forbids deriving a volume
    number from the album string, and the reason is measured: volume 1 is tagged
    `Now That's What I Call Music` with no number at all; volume 2 is tagged
    `Now, That's What I Call Music II` with a Roman numeral and a comma; and volume 36 is split across
    three spellings — `...! Vol.36 CD1` on 16 files, `...! Vol.36  CD2` on 20 files WITH A DOUBLE SPACE,
    and `...! 36` on 4 files. `...Vol.36 CD1` ends in 1 and `...Vol.36  CD2` ends in 2, so a
    trailing-number regex silently misfiles 36 tracks into volumes 1 and 2. It exits 0 and it looks
    right. Put that paragraph in the rule's docstring verbatim, so the next editor meets it before
    writing the obvious regex.

    DERIVATION. Match the folder basename against an ANCHORED pattern of the literal `Vol ` followed by
    exactly three digits and nothing else — the form plan 05-07 created. Convert to an integer, strip
    leading zeros, and require the result to be between 1 and 115 inclusive. Any other folder name is a
    named refusal: not-a-volume-folder, out-of-range, or wrong-digit-count.

    CANONICAL FORM. The output is the literal `Now That's What I Call Music! ` followed by the unpadded
    volume number — so `Vol 001` yields `Now That's What I Call Music! 1` and `Vol 036` yields
    `Now That's What I Call Music! 36`. One consistent form across all 115. Two properties make this the
    right choice and both should be stated in the docstring: it carries the number on EVERY volume, so
    sanitise_derived's guard that rejects any value with no digit accepts all 115 — a form like a bare
    `Now That's What I Call Music!` for volume 1 would be refused outright; and it uses the majority
    punctuation, `Music!` on 96 of the 117 measured values, which makes the string a usable Discogs query
    for the CONF-05 disambiguation Phase 6 will need on this series.

    Pass the derived value through sanitise_derived exactly as rule 1 does. It is path-derived data
