<objective>
Fix the instrument that blocked ROADMAP Phase 4 success criterion 3, and prove it can fail — and
prove it refuses to guess — before a real music job is spent on it.

Criterion 3's behavioural half is OPEN (`04-VERIFICATION.md`, `04-D12-EVIDENCE.md` § 6) for a reason
that is structural and measured: SABnzbd moves a finished job into `complete/nzb/music/` and **then**
invokes the post-processing hook, so 04-12's watcher — which polled that destination tree — could
never sample before the hook. Job A's first sighting was 12:18:00.074Z against a `Matching` line at
12:17:59Z (already later); job B's snapshot fell inside the same one-second `Audio.txt` bucket as its
own `Matching` line (indeterminate). On top of that the contract's 2-second stability floor cannot
fit inside job A's 1-second hook.

Purpose: this plan replaces the timestamp race with a **structural ordering**. A snapshot taken while
the job folder is still under `incomplete/` is necessarily earlier than the move, and the move is
necessarily earlier than the hook — no sub-second comparison against a second-resolution log is
needed. But structural ordering alone is not enough, and cross-AI review round 2 found exactly why:
SABnzbd runs with `direct_unpack = 1`, so audio files appear **during** the download; `incomplete`
and `complete` are the same ZFS dataset (both device 68), so the move is an instant rename; and music
`postproc_time` is 1-3 s on recent jobs, with only **35 of 121** rows reaching 4 s. A mid-download
lull can therefore leave a *subset* of files stable and hashed, and the later-extracted files then
appear only at COMPLETION — which the old judge would have called a **FAIL**. So this plan also makes
the snapshot's **completeness** a published, testable property, and gives UNPROVEN precedence over
FAIL wherever the two are indistinguishable from bytes alone.

An instrument that has already produced one invalid measurement has earned a self-test, and real
music jobs are scarce (roughly one every 1-5 days, one chance each), so the fix is driven against
eight synthetic controls — including one that must return **FAIL**, four that must return
**UNPROVEN**, and one that proves the watcher does not self-exit on an empty window — before the
window is armed.

Output: two host-scratch scripts (`watch-d12b.sh`, `judge-d12b.sh`) with their sha256 recorded, an
eight-control self-test record, and a dated in-band amendment to `04-D12-EVIDENCE.md` §§ 1 and 5
written **before** any second job exists.
</objective>

- No SABnzbd or Lidarr API call, and no API key on argv (orchestrator decision carried from 04-12).
- This repo is public. Job folders and release names never enter a tracked file; they are identified
  by the first 12 characters of the sha256 of the folder basename, and the mapping lives only in host
  scratch (04-12 precedent, T-04-12-01).
- Remote commands are bounded **Linux-side** with `timeout` inside the remote string (macOS has no GNU
  `timeout`); any remote string containing a pipe starts `set -o pipefail`, and the ssh RC is taken on
  the very next line with no local pipe in the assignment.
- `wc -l` on a missing path prints nothing and exits 1, which a `$(...)` capture renders as `0`
  (04-12 deviation 2). Assert a path exists and is non-empty before reading an absence from it.
  `test -s FILE -o -f FILE` is **inert** — the `-f` disjunct passes on an empty file. Never use it.
- `pgrep -f <pattern>` matches the inspecting shell's own command line when that command line contains
  the pattern **or the path** (04-12 deviation 6). Building the pattern from concatenated pieces does
  **not** help if the path literal appears anywhere else in the same command string. To assert a
  process is gone: write the pattern to a file in one ssh invocation, then take the `ps` snapshot and
  match it with `grep -F -f` in a **second, separate** ssh invocation whose command string contains
  neither the watcher's name nor its path.
- The S5 containment fence (`scripts/spike03-wrtag-arms.sh:242-286`) resolves with **`realpath -m`**,
  not `-e`: `-m` resolves components that do not exist yet, which is required when fencing a path
  *before* creating it. `realpath -e` is correct only at deletion time, when the path must exist.
</conventions>

    every FAIL clause**. State the ladder in the script's own header in these words, because "FAIL
    first" turns "could not look" into "the estate rewrote bytes", which is invariant 1's mirror:
    1. `UNPROVEN reason=no-attributed-pre` — the attribution token is `none`, or no `pre.sha256` file
       exists for the attributed folder.
    2. `UNPROVEN reason=ordering-unproven` — `pre.time` is missing, or `vanished.time` is missing, or
       `pre.time` is not strictly earlier than `vanished.time`.
    3. `UNPROVEN reason=baseline-stale` — `pre.inv` differs from `last.inv`. The folder changed after

       **This clause is the round-2 row-2 fix and it is the reason it sits above the FAIL clauses:**
       under `direct_unpack = 1` a file that appears only at COMPLETION is equally consistent with
       late extraction and with a hook rewrite, and bytes alone cannot separate them. Recording that as
       FAIL would be a false accusation against a clean estate; recording it as UNPROVEN is the honest
       answer and is what § 5 already prescribes for an unprovable condition.
    4. `UNPROVEN reason=no-completion` — `post.sha256` is missing, `post.rc` is non-zero, or the
       manifest cannot be parsed. A failed acquisition is not an empty folder.
    5. `UNPROVEN reason=empty-intersection` — `files_in_both` is 0. "Every file present in both
       snapshots is sha256-equal" is vacuously true on an empty intersection and PRE-only files are
       explicitly exempt, so without this floor a two-file PRE manifest against a zero-entry COMPLETION
       manifest returns `BYTES-OK` having compared nothing at all (round 2 row 5).
    6. `FAIL reason=bytes-changed` — any file present in both snapshots whose sha256 differs.
    7. `FAIL reason=completion-only-unmatched` — any audio file present only at COMPLETION whose
       sha256 matches no PRE-HOOK file. Reachable only once clause 3 has established `pre_complete=yes`.
    8. `BYTES-OK` — everything else.
