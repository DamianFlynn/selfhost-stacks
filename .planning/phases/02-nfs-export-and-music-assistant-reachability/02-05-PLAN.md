<objective>
Mount the export on the NUC, decide Route A versus Route B on evidence, and prove criterion 2 —
that read-only is enforced at the export layer rather than by configuration politeness.

Purpose: the route is the one genuinely unresolved question in this phase. Primary sources contradict
each other — Music Assistant's own documentation states verbatim that a folder cannot be mounted from
Home Assistant into `/media`, while HA Supervisor's source shows the network-share path landing exactly
where MA needs it. RESEARCH.md resolves the contradiction (MA's sentence is about *local* bind mounts,
which genuinely are impossible), but a documentation reading is not a measurement. This plan runs the
decision procedure rather than assuming its outcome.

Criterion 2 is the other reason this plan exists, and it has a specific trap. Route A mounts with a
client-side `ro`, so a `touch` that fails proves only that the *client* is read-only. That test would
pass on a fully writable export. The criterion is about the **export**, so the test must bypass the
client-side `ro` — a hand-rolled `mount -o rw` from the NUC. That, and only that, tests CONS-01
criterion 2.

Output: a live, proven mount; a recorded route decision with the losing route's failure symptom; and
criterion 2's evidence.
</objective>

  </read_first>
  <action>
    Two independent write attempts, because a client-side `ro` and a server-side `ro` are different
    claims and **only the second is the requirement**.

    **4a — through the Supervisor mount.** Attempt to create a file under the mounted path on the NUC
    (`/mnt/data/supervisor/media/music/`). Expect failure with `Read-only file system` and a non-zero
    exit. This proves the *client* mount is read-only. It is necessary context, not the criterion.

    **4b — bypassing the client-side `ro`. This is criterion 2.** From the NUC, hand-mount the export
    read-write at a scratch path: `mount -t nfs -o rw 172.16.1.158:/mnt/tank/media/Music /tmp/ro_probe`,
    then attempt a `touch` inside it. **PASS is that the `touch` fails with `Read-only file system`
    despite `-o rw`** — that is the export enforcing it. **FAIL is that the file is created**, which
    means the export is `rw` and CONS-01 is not met.

    Unmount `/tmp/ro_probe` afterwards regardless of outcome.

    If a probe file *does* land, it is a criterion-2 failure. Record it as a failure, remove the file
    from the library, and stop — do not proceed to the MA plans with a writable export. A `rw` export
    plus the `0777` tree means every client on the LAN has full write access to 34 GB of curated
    library, and Route B has no client-side `ro` to fall back on.

    Note that the mount may already be refused if the NUC's source address differs from the export
    line's — that is 02-01 Task 3's measurement being wrong, not a criterion-2 result, and it must be
    diagnosed as such. Distinguish the two: a denied *mount* is an access-control mismatch; a
    successful mount with a refused *write* is criterion 2 passing.
  </action>
