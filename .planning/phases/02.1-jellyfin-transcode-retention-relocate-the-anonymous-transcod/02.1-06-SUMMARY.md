# Phase 02.1 Plan 06: Prove the Bounds Fire, and Reclaim the 12.55 GiB — Summary

**The 12.55 GiB is off `/`, and every control this phase installed has now been watched working
rather than read back.** `/` went from 20.21 GiB free to 33.12 GiB, the margin against the D-17
floor from **185 MiB at the phase head to 13.13 GiB**, and `check-jellyfin-transcode.sh` exits 0 in
default mode for the first time since 02.1-02 built it.

**Two of the plan's own assertions turned out to be unsatisfiable by a correctly-working system, and
one of my own proofs produced a confident, coherent, completely false result before being caught.**
Those three things are the substance of this summary, because the reclaim itself was routine.

## What was proven

**Segments land in the new place and nothing lands in the old one — measured twice, while the old
volume still existed.** Row 4 returned 44 new `.mp4` under `/mnt/fast/transcode` in a two-minute
window on the stream-copy session and 55 on the re-encode session. Row 5 returned **0** new files in
`/var/lib/docker/volumes/$OLD_VOL/_data/transcodes` during the same transcodes, with
`docker volume ls -q | grep -qx "$OLD_VOL"` recorded as exiting 0 at that moment. That last point is
what makes row 5 non-vacuous, and it is why the deletion is a separate task ordered after it (D-10).

**Segment deletion fires.** Eight `Deleting segment file(s) index 0 to N` lines per session from
`MediaBrowser.Controller.MediaEncoding.TranscodingSegmentCleaner`, with N advancing 4→7→10→14→17→20
on the copy branch and 7→13→20→27→33→40 on the re-encode branch.

**Throttling fires.** 89 `Throttling transcoder gap` plus 6 `Not throttling transcoder gap` on the
copy branch, 87 plus 8 on the re-encode branch, and **zero** `No throttle data` in either — so the
throttler was not merely constructed, it had real download-position data to act on. Better than the
row asked for: the log line reads `target gap 1800000000` ticks, which is **Jellyfin echoing
`ThrottleDelaySeconds = 180` back in its own words**. That is a configured value observed in effect,
which is precisely what CONS-04 asks for and what an API read-back cannot give.

**`-readrate 10` fires on the branch where it should and is correctly absent on the branch where it
should not.** Present with `-codec:v:0 copy`; absent with `-codec:v:0 libx264`. Both quoted from the
ffmpeg command line, both recorded as results rather than one being passed over.

**The quota refuses a write, and `/` does not move.** Refused on attempt **1** of 10 — enforcement
was synchronous here, not the several-second lag the plan defended against — and `/` moved by
**exactly 0 bytes** across a 1 GB ballast. That is the property the phase is buying.

**The volume is gone, and the invariant holds.** `docker volume rm` by explicit 64-character id,
never the bulk-removal subcommand. Row 8 (the id is absent) and row 7 (zero `Type: volume` mounts,
container proven to exist *first*) both pass. `/` avail 21674889216 → 35575803904 = **+12.95 GiB**,
matched to the byte by `stat -f`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] My own proof client produced a false all-zero result, and it read exactly like a product finding**

- **Found during:** Task 1, run 1
- **Issue:** The first pair of sessions reported **zero** deletion lines, **zero** throttling lines
  and **zero** `No throttle data`, on both codec branches, with a strictly-increasing download head
  and the ffmpeg pause key re-probed at `d=10000` as supported. Every discriminator the plan
  provided pointed at "the controls do not start on this estate".
- **Cause, and it was mine:** the client contains `printf … | head -10` pipelines. Under
  `set -o pipefail` the SIGPIPE returns 141, which fired the `ERR` trap in section 4 — the manifest
  fetch, before a single segment had been consumed. The handler worked perfectly and restored
  Jellyfin to Information. But `set +e` inside a trap handler is **global, not function-local**, so
  with errexit switched off the handler returned and the script ran on for another 200 lines,
  driving a full session and then grepping a log that had been back at Information throughout. Both
  target lines are Debug-level and were structurally unable to appear.
- **How close it came:** the null result was investigated as genuine for some time, including
  extracting the UTF-16 string tables from all 409 shipped assemblies to confirm the four log
  messages exist in this build (they do, in `MediaBrowser.Controller.dll`). A plausible mechanism
  had already been drafted — that Jellyfin excludes the throttler on the stream-copy path because
  `-readrate 10` substitutes for it. **That mechanism is false**; run 2 shows the throttler running
  on both branches. Committing run 1 would have recorded a fabricated limitation of Jellyfin with
  quoted assembly evidence beside it making it look thoroughly researched.
- **Fix:** three changes. Every unguarded `| head -N` became `| sed -n '1,Np'`, which reads to EOF.
  The handler now ends with `if [[ $rc -ne 0 ]]; then exit "$rc"; fi`, so an error path cannot
  restore state and continue. And the load-bearing one — a **Debug-liveness assertion at grep
  time**, asserting the effective level is still `Debug` and the overlay file still present, and
  recording the `[DBG]` line count for the whole window (2255 and 3063). An instrument that reads a
  log must prove the log was at the required level for the window it reads, or "zero matches" and
  "the control did not fire" are the same output — 02-08's `exportfs -v` in a new costume.
- **Run-1 vs run-2 on the identical title and identical settings:** 0/0/0 → 8/95/0.
- **Commit:** `f2b3546`

**2. [Rule 1 — Bug] The log file was selected by date arithmetic across a timezone boundary**

- **Found during:** Task 1, session B's first launch
- **Issue:** The client computed `log_$(date +%Y%m%d).log`. LXC 100 runs **UTC**; the Jellyfin
  container runs **+01:00**. At 23:02 UTC the host said `20260902` while Jellyfin had already rolled
  to `log_20260903.log`. The run read 0 `[DBG]` lines from a file Jellyfin had abandoned and
  correctly refused to proceed — but the symptom presented as "Debug did not take effect".
- **Fix:** select by mtime — `ls -1t "$LOGDIR"/log_*.log | sed -n '1p'`. The host date and the
  container's timezone are both recorded in the transcript so the trap is visible next time.
- **Silver lining, recorded because it is the only evidence that half the mechanism works:** this
  failure exercised the trap's **error path** for real, and it restored correctly
  (`TRAP restore_log_level FIRED ON : ERROR PATH (exit status 1)` … `ASSERT restored == captured
  original (Information) : PASS`). A trap only ever observed on the happy path is not known to work.
- **Commit:** `f2b3546`

**3. [Rule 1 — Bug] VALIDATION row 16's numeric ceiling cannot be satisfied by a working system**

- **Found during:** Task 1, both sessions
- **Issue:** The plan requires all three segment counts at or below
  `ceil(SegmentKeepSeconds / segment_duration) + 10`. Measured: session A 102, 92, 168 against a
  ceiling of 60; session B 178, 186, 192 against 110. All six above — in sessions where the cleaner
  is demonstrably working and says so eight times each.
- **Why:** the ceiling counts only the segments *behind* the download head that the cleaner has yet
  to reclaim. At any instant the dataset also holds the segments *ahead* of the head that the
  encoder has already produced, and that region is bounded by `ThrottleDelaySeconds = 180` — which
  is the throttler's entire purpose and is visible in its own log line as `target gap 1800000000`.
  Read off session B in steady state: head 159, cleaner had just deleted 0..40, surviving indices
  41..232, so 119 segments behind (357 s against 300 s plus a 20 s tick) and 74 ahead (222 s against
  180 s plus a 5 s poll) = 192, which is the measured count exactly.
- **Corrected form:** `ceil((SegmentKeepSeconds + max(ThrottleDelaySeconds,120)) / segment_duration)`
  plus slack for the cleaner's 20 s tick and the throttler's 5 s poll. Session A's 168 is the
  outlier and has a named cause: `-readrate 10` lets a stream copy emit fifty seconds of media
  between two five-second polls, so the forward region overshoots in bursts on the remux branch in a
  way it cannot on the re-encode branch.
- **Not waived.** What the ceiling was protecting is discharged three ways: the cleaner's own log
  lines with advancing ranges; the counts oscillating rather than climbing (session A **fell** from
  102 to 92); and, independently of Jellyfin entirely, the 50 G ZFS quota, which task 3 proves
  fires. Row 16 is left unedited — correcting a VALIDATION row is a planning change, and 02.1-10
  verifies against it. Same handling as 02.1-05 gave row 15.

**4. [Rule 1 — Bug] The errno is EDQUOT, not ENOSPC — and the plan's inference from that is false**

- **Found during:** Task 3
- **Issue:** Row 11 requires the ENOSPC phrase **present** and `Disk quota exceeded` **absent**.
  Measured: 0 and 2. Exactly inverted, on all ten attempts.
- **The plan's stop condition fired, and I tested its premise rather than accepting it.** The plan
  says *"If the EDQUOT form appears, refquota is in force rather than quota and plan 02.1-03's
  property is wrong."* Measured on atlantis at the moment of refusal: `refquota` = **0 / default**,
  `quota` = **53687091200 / local**, and no ancestor dataset carries either. **02.1-03 chose the
  correct property.** What is wrong is the *errno mapping the research recorded*, and therefore the
  stated rationale for the choice. On `zfs-2.4.3-pve1` a dataset `quota` refusal surfaces as EDQUOT;
  ENOSPC is what a genuinely full pool returns, and this pool is 22% allocated.
- **The risk the plan was trying to name is real, and worse than described.** The reasoning was
  "pick `quota` so refusals match the estate's ENOSPC-keyed greps". Both properties return EDQUOT,
  so **no** choice of property produces a match. Any monitoring keyed on the ENOSPC phrase is blind
  to a transcode-quota refusal. Switching to `refquota` would not fix it; adding the EDQUOT string
  to those greps would. Logged as a follow-up — out of scope for this plan.
- **What was NOT done:** the expectation was not adapted and no string was inserted to make the
  check pass. Row 11 is **not marked passed**. Because the stop condition's premise was measured
  false, the measurement was completed rather than abandoned — which is how `/` came to be measured
  at the moment of refusal at all.
