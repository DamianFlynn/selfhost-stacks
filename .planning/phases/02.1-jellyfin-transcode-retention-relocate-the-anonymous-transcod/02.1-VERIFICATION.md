# Phase 02.1: Jellyfin transcode retention — relocate the anonymous transcode volume off / and set a retention policy — Verification Report

**Phase Goal:** LXC 100's root filesystem is structurally unable to be filled by Jellyfin again. Every
cache byte Jellyfin writes lands on a *declared* bind mount to `/mnt/fast`, growth is capped by a ZFS
property that no UI edit and no container recreate can raise, Jellyfin's own retention levers are on
and proven to *fire* rather than proven to be set, and a standing fail-closed check would have caught
the incident before `/` reached zero. The unreferenced Docker images are reclaimed through the
existing approval gate in the same pass, and the estate's own amdgpu recovery script is hardened so it
cannot silently undo any of it.

   confirmed live: the admin-equivalent Jellyfin API is reachable from the whole LAN via its macvlan
   address, not confined to `t3_proxy` as both scripts and the accepted-risk note in `PROJECT.md`
   claim.

Neither gap threatens the mount/quota mechanism itself, which is real, live, and independently
re-verified. Both are documentation-and-assertion defects in the observability layer this phase built
specifically to prevent a repeat — which is precisely why they are scored as blocking rather than
cosmetic.

`scripts/quick-health-check.sh`) rather than in the mount/quota mechanism, which is real and
independently re-verified live in every particular the ROADMAP claims for it.

**Gap 1 (CR-01) is the more consequential one against this phase's stated purpose.** The phase goal's
own words are "a standing fail-closed check would have caught the incident before `/` reached zero."
The specific failure mode the original incident took — an unbounded cache path — has a second, cheaper

this phase built, on the exact green path an operator would trust. The fix is small (a string
comparison, no transcode required, exactly as CR-01's suggested patch shows) and does not require
re-running any of the "fires" proofs — those remain valid regardless.

acceptance for an administrator-equivalent, write-scoped API key rests on a false premise. The key is
reachable from the whole LAN, not from "a host that can route to t3_proxy" as both scripts and
`PROJECT.md` state. This should be corrected and the risk acceptance re-derived (or the exposure
closed by dropping `ports:`, which the review notes is a separable decision) before this is treated as
settled.

Neither gap requires re-running 02.1-06's driven playback sessions, 02.1-07's fault injections, or
02.1-09's reap — all of those are independently confirmed sound. Both gaps are narrowly scoped edits to
the two check scripts (plus a `PROJECT.md` correction for Gap 2) and are natural candidates for a short
closure plan (e.g., `02.1-11`) rather than a rework of the phase.

One outstanding human-verification item (transcode playback watchability) is also carried forward —
