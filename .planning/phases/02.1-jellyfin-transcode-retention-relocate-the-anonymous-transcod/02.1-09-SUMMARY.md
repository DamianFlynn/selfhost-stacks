# Phase 02.1 Plan 09: Reclaim unreferenced Docker images through the approval gate — Summary

Four superseded `keeper-sh` images reclaimed from LXC 100 through the existing two-process human
gate, freeing **1.45 GiB** and taking `/`'s margin over the D-17 floor from 13.11 to 14.49 GiB — with
the forecast-versus-measured gap chased to root cause rather than banked.

## What happened

This was a continuation. A prior agent completed task 1 (the read-only inventory) and halted
correctly at task 2, the blocking human approval gate — the one irreversible act in the whole phase.
The operator has since ruled. This session executed the reap and closed the plan.

**The operator's ruling, verbatim: "approved unchanged" — all 4 rows, no edits, no strikes.**

That phrasing matters and was asked for by name. `02.1-REAP-LIST.md` § *Approval* requested the
explicit words precisely so an unedited file could not be confused with an unread one, and the plan's
acceptance criterion allows an unchanged sha256 **only** on that condition. The gate was presented
with the full four-row list, per-row sizes and justifications, the corrected ≈1.02 GiB reclaim
estimate rather than the script's naive 1.61 GiB headline, and an explicit statement that the urgency
the plan was written under is gone — so declining any row cost nothing. All four were approved anyway.

The operator did **not** rule on the three unreferenced untagged digests raised in the transcript's
§ 4.4. They remain excluded and deferred, as that section recommended. **Scope was not expanded**:
the dangling image count is 9 before and 9 after.

## The gate held in both halves

**Re-validated before acting, not trusted from the approval message.** `reap-list.txt` was re-read on
LXC 100 immediately before the prune: 4 lines, sha256 `1eaa2049bb05cd96…` unchanged, mtime still the
inventory's own `00:45:03Z` write. Had either differed the run would have stopped — a mismatch means
the file changed under the approval and the approval no longer covers what is on disk.

**The script's own re-derivation found nothing.** `prune` rebuilds the referenced set from
`docker ps -a` with **no status filter** immediately before deleting — covering this estate's
documented `created`-state blind spot, where dispatcharr and teleport sat invisible for six weeks
behind a filtered check. Six hours after the list was built, all four rows still held: **0 conflicts**.

**The prune ran exactly once.** `FLOOR_GB=20 bash scripts/spike03-image-headroom.sh prune`, exit **0**:
removed 4, already reclaimed 0, rmi failures 0. `already reclaimed: 0` alongside `removed: 4` is the
positive evidence of a single run — a second invocation inverts the pair.

## The most interesting result: the forecast was right, in units nobody had reconciled

Task 1 forecast **≈1.09 GB** of realistic reclaim. `df` moved **1.45 GiB** — 42% more. An estimate
beaten by 42% is not self-evidently good news, so it was investigated.

**`docker system df` Images SIZE moved 66.54 → 65.45 GB — a delta of exactly 1.09 GB.** That figure
is deduplicated, so it is the correct instrument for how much image data left the store. The forecast
was right to three significant figures, and its *mechanism* was right too: the 211.7 MB base was
shared among the four candidates and freed once when all four went — confirmed because the surviving
`2.23` siblings still report `SHARED SIZE 205.4MB`, unchanged.

**The gap is units.** `docker system df` reports *apparent* bytes; `df` reports *allocated blocks*.
ext4 rounds every file up to 4 KiB, and these are Node applications. Measured on the surviving
siblings, which are the same application and therefore the right proxy:

| image | layers | files | apparent | allocated | ratio |
|---|---|---|---|---|---|
| `keeper-web:2.23` | 16 | **107,030** | 559452257 B | 750628864 B | **1.342** |
| `keeper-worker:2.23` | 14 | 25,034 | 277159880 B | 328757248 B | 1.186 |

107,030 files in one image; 191.2 MB of block-rounding overhead that Docker does not report and `df`
does. This reap's implied ratio is 1.430 — consistent. The `df` delta is still *below* the naive
1.61 GiB size sum, which is the direction the plan expected.

**Carry-forward:** forecast in `docker system df` Images-SIZE terms and expect `df` to move **more**,
by roughly 1.2–1.4× for many-small-file images.

**RECLAIMABLE misled again — in the opposite direction this time.** It fell only 0.21 GB (62.44 →
62.23) while 1.45 GiB of real disk was freed, where in 03-01 it *rose* 0.57 GB during an 18 GiB
reclaim. Two observations, opposite signs, same conclusion: it does not track real disk.

## Deviations from Plan

### 1. [Rule 1 — Bug, self-inflicted and reverted] A probe that pulled an image

- **Found during:** Task 3, verifying cal-web's health.
- **Issue:** The first cal-web probe used `curlimages/curl:latest` via `docker run --rm`. That image
  was not resident — 03-01 had reaped it — so Docker **pulled** it, directly contradicting this
  plan's own **T-021-SC**: *"No image is pulled; the plan only deletes."*
- **Why it mattered:** this plan's whole method is that the image inventory reconciles. An unremarked
  pull would leave the live host disagreeing with the recorded after-listing by one image and 23.9 MB,
  and the next reader would have no way to distinguish an accidental pull from an unlogged deletion.
- **Timing — no recorded figure was contaminated:** the pull happened *after* the after-listing, the
  after-counts, the `docker system df` reading, the removal diff and the container-state diff had all
  been captured. It was caught on the next check.
- **Fix:** `docker rmi curlimages/curl:latest`. This removed only an artifact created minutes earlier
  by this session — nothing the operator's gate protects, and nothing that existed before the prune.
  The live store was then re-diffed against the recorded after-listing: **identical**. The probe was
  re-run with `nginx:1.31.3-alpine`, already resident, and it is that run quoted as evidence.
- **Files modified:** none in the repo; host state restored.
- **Commit:** `8f6bb73` (documented in the transcript § 7.10 and the reap list § *After*).
- **Carry-forward:** `docker run --rm <image>` **is a pull** when the image is absent, and it looks
  identical to a local run once it succeeds. On a freshly reaped host the generic utility images are
  exactly the ones most likely to be gone. Probe with an image confirmed present in the
  before-listing, or `docker exec` into a running container.
