# Phase 02.1 Plan 04: The Copy and the Declaration — Summary

The structural fix. Jellyfin's cache is off the anonymous Docker volume on `/` and onto a declared
bind inside `fast/appdata/media`, and `stacks/selfhosted/media/jellyfin.yaml` now says so — both
mounts declared, the dead RAM-disk decoy deleted, and the reasoning written where the next reader
will actually look. **Nothing was recreated and nothing was deleted**: the container still runs on
the old volume, which is what makes every step here reversible. That is 02.1-05's and 02.1-06's
work, in that order, and the ordering is the rollback.

## This plan was finished by a continuation agent

Executor instance A ran the census, the probe and the copy at `21:54Z` and was then **killed by a
transient API server error** — a harness failure, not a plan defect and not quota — before any of it
was committed. Continuation instance B picked it up, **re-derived every assertion from live state**
rather than trusting the dead instance's narrative, and completed tasks 2 and 3.

**The one number instance B could not retake is the pre-copy source census**, which by definition
cannot be taken after a copy. Instance A's two census files survived on the host with their mtimes
intact (`21:54:17Z` and `21:54:48Z`) and are used as-is, labelled as such, with the drift between
them computed mechanically. Everything else in the census artifact is instance B's own measurement.

**A trap the failure exposed, and the most portable thing in this plan.** The post-failure damage
check read `/mnt/fast/transcode` (0 entries) and concluded the copy had never started. It had in
fact **completed**. An empty `/mnt/fast/transcode` is this plan's *success* condition, not evidence
of inaction — the copy's destination is `/mnt/fast/appdata/media/jellyfin/cache`, which nobody
looked at. After an interrupted plan, read the path the plan **writes** to, not the path it asserts
stays empty.

## What was built

**The cache is copied and proven.** 2,664 files, 410302255 bytes, from the anonymous volume's
`_data` to `/mnt/fast/appdata/media/jellyfin/cache`. Proven by structural completeness (0 top-level
directories missing), `images` and `xmltv` non-empty on the destination, a 99% count floor on
`images` (2285 against a floor of 2262), a 20-file sha256 sample (**20/20 match, 0 mismatch**), and
a missing-by-path list driven to **empty** by a reconciliation pass whose per-file exit status was
checked rather than a printed summary.

**Exact equality is deliberately not the pass rule**, and the artifact says so in words. Jellyfin is
live throughout and writes to the image cache on artwork fetch, xmltv sync and ordinary browsing, so
an exact count-and-byte match is a false-negative generator — both cross-AI reviewers reached that
from opposite sides. The exact figures are **reported** instead, and they happen to match to the
byte on every subtree, which is a quiet Tuesday night rather than a criterion. The automated verify
and the written acceptance criteria now assert the same thing; the reviewed version's did not.

**`jellyfin.yaml` declares the two binds and explains them.** `/cache` from
`/mnt/fast/appdata/media/jellyfin/cache` (D-08/D-09) and `/cache/transcodes` nested on top from
`/mnt/fast/transcode` (D-01/D-03). The dead shared-memory transcode mount is deleted **with its
comment** (D-02) — it had held zero bytes since the day it was added and read as "already solved",
which is plausibly part of why 19 GB accumulated with nobody looking.

**The runbook landed where a 9pm debugger will find it.** Both reviewers independently identified
`PROJECT.md`'s Key Decisions table as the wrong destination. The stopped-TV runbook (three literal
commands, ending in `zfs set quota=none fast/transcode` as a tourniquet with an explicit instruction
not to leave the bound off) and the Live TV latent gap (`/LiveTv/TunerHosts` returns `[]`, so
`LiveStream.TempFilePath` is latent; neither segment deletion nor throttling would bound it because
both gate on `RunTimeTicks`, which a live stream lacks) are both in the stack file.

**The stale VAAPI claim is gone.** The comment block asserted a hardware-acceleration configuration
that has not been live since `2026-08-31 18:27`, when `scripts/disable-jellyfin-hwaccel.sh` set
`HardwareAccelerationType: none` as amdgpu HMM mitigation. Corrected rather than deleted, with the
mitigation's reason, its date and its out-of-scope status recorded. The `/dev/dri` passthrough and
the `video`/`render` `group_add` are retained deliberately, so re-enabling stays a settings change
rather than a compose change.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] `transcodes/` excluded from the copy: 12.55 GiB, not the planned 472 K**

- **Found during:** Task 1
- **Issue:** The plan describes the volume as "392 MiB today … `transcodes` 472 K". `transcodes` is
  now **13473768858 bytes across 1,324 files** — 12.55 GiB, four orders of magnitude above the
  planned figure. It refilled since the container came up on `2026-08-31T18:27:41Z`. This is the
  incident the phase exists to fix, caught mid-refill. Copying `_data` wholesale, as the plan's
  words say, would have moved 12.93 GiB instead of 391 MiB.
- **Fix:** Copied `_data` **minus** `transcodes/` — 410302255 bytes across 2,664 files, which is
  exactly the "392 MiB" figure the plan repeatedly names and reasons about. Three independent
  reasons, any one sufficient: (a) anything under `DST/transcodes` is **shadowed** by the nested
  `/cache/transcodes` bind the moment the container is recreated, so it would be unreachable dead
  weight; (b) the whole volume is deleted in 02.1-06 anyway; (c) it would breach the plan's own
  headroom precondition outright — `21474836480 + 2 × 13884071113 = 49242978706` against
  `21658583040` available. `DST/transcodes` was created **empty** as the mountpoint for the nested
  bind.
- **Cost if wrong:** nothing. `transcodes/` is HLS segment cache — regenerable by definition, and
  the source copy is untouched until 02.1-06.
- **Files modified:** `/mnt/fast/appdata/media/jellyfin/cache` (host state), census artifact
- **Commit:** `1f0d2ba`

**2. [Rule 3 — Blocking] The plan's literal headroom precondition measures the wrong thing**

- **Found during:** Task 1
- **Issue:** The plan requires `df avail /` to exceed `21474836480 + (2 × source_size)`. Even at the
  reduced scope that demands `22295440990` against `21658583040` available — short by 607 MiB. Taken
  literally, the plan halts.
- **Fix:** The precondition, not the state, is what is wrong. The `2×` term exists to cover a
  **transient double** — both copies on the *same* filesystem. Measured with `stat -c %d`, that is
  not this copy's shape: `/` and `/var/lib/docker/volumes` are dev `64519` (ext4) but
  `/mnt/fast/appdata/media` is dev `63` (zfs, 1.31 TiB free). The copy **reads** from `/` and
  **writes** elsewhere, so `/` consumption is zero. Replaced with the orchestrator's numeric
  self-halt budget (no step > 2 GiB of `/`; `/` never below 10 GiB; halt if the cache stops being
  flat). **None fired**, and the outcome was measured rather than argued: `/` went from
  `21643157504` to `21657853952` across the copy — **up 14.0 MiB**.
- **Commit:** `1f0d2ba`

**3. [Rule 3 — Blocking] `rsync` is not installed on LXC 100**

- **Found during:** Task 1
- **Issue:** The plan names `rsync -a` for the A5 probe and `rsync -rlt --no-p --no-o --no-g` for
  the reconciliation pass. Neither exists on the host.
- **Fix:** **Deliberately did not install it.** A package-manager install is explicitly excluded
  from auto-fix, and pulling a package onto a production Docker host running 78+ containers to copy
  391 MiB that `cp` already copies correctly adds supply-chain surface and `/` consumption to buy
  nothing. Used the documented equivalence, stated flag-for-flag in the artifact:
  `cp -r -d --preserve=timestamps` ≡ `rsync -rlt --no-p --no-o --no-g`, and
  `cp -d -u --preserve=timestamps` for the reconciliation (`-u` = only missing or newer). Per-file
  exit status was branched on and failures counted separately — never a summary.
- **Commit:** `1f0d2ba`

**4. [Rule 1 — Bug] My own comment prose tripped the check asserting the path was gone**

- **Found during:** Task 2
- **Issue:** The acceptance criteria require `grep -c '/dev/shm'` and `grep -c '/data/transcode'` to
  return **0**. The first draft of the "why not the RAM disk" paragraph named both paths literally
  to explain their removal, so both greps returned 1 — a correctly-written explanation failing the
  very check it was explaining. Exactly the class of bug the D-32 watch artifact already documents
  in its own FORMAT block.
- **Fix:** Reworded to describe both paths in words rather than write them literally, with an
  explicit note saying that is deliberate and why, so the next editor does not helpfully "fix" it
  back. Both greps now return 0.
- **Commit:** `32f62a7`

**5. [Rule 2 — Missing] The stale VAAPI claim appears three times, not once**

- **Found during:** Task 2
- **Issue:** The plan scopes the VAAPI correction to the comment block at lines 34-55. The file
  header asserts the same untrue thing twice more — a feature bullet
  ("Hardware-accelerated transcoding (VA-API on AMD Radeon 890M)") and a `Hardware Acceleration:`
  section reading as a live description. Correcting only the block named would have left two stale
  claims for a reader who never scrolls to it.
- **Fix:** Corrected all three. The header now marks hardware acceleration **DISABLED** with a
  pointer to the full explanation, and distinguishes what the hardware is *capable* of from what
  Jellyfin is *configured* to do. No device passthrough or group configuration was touched — only
  the prose was wrong, exactly as the plan says.
- **Commit:** `32f62a7`

## What is still owed

**TRAN-01 is deliberately NOT marked complete, even though this plan's frontmatter claims it.**
TRAN-01 reads *"Every Jellyfin cache write, transcodes included, lands on `/mnt/fast`, not on
LXC 100's root filesystem — by declared bind mount"*. The **declaration** is done; the **writes**
are not. Every cache write still lands on the anonymous volume on `/`, because the container has
not been recreated — which this plan deliberately does not do. Marking it complete here would put a
green tick on a requirement the running system does not satisfy. It becomes true at 02.1-05's
recreate, and that is where it should be ticked. This mirrors 02.1-03's precedent, which marked
TRAN-07 complete but left TRAN-03 pending because TRAN-03 needs the bound proven *firing* rather
than proven *set*.

**The anonymous volume still exists and still holds 12.93 GiB on `/`.** This plan copied; it did not
reclaim. The 12.55 GiB is released by 02.1-06's `docker volume rm`, and only **after** 02.1-05
proves Jellyfin running on the new path. That ordering is the rollback and is not negotiable.

**The `/` margin against the D-17 policy floor is ~186 MiB**, eroding a few MiB per half-hour from
ordinary container churn across the other 78+ containers — not from transcoding, which has been flat
all evening. It is the reason not to let the phase idle.
