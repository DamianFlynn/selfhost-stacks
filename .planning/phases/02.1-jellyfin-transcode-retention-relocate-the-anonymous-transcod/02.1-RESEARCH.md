### Locked Decisions

Copied verbatim from `02.1-CONTEXT.md` § *Implementation Decisions*. The planner MUST honour every
one. Research below either supplies the mechanics to execute them or reports a measured hazard in
executing them — **it does not relitigate any of them.**

**Where transcodes land**

- **D-01: Transcodes go to the `fast/transcode` ZFS dataset, mounted in LXC 100 at
  `/mnt/fast/transcode`.** The dataset already exists, is **empty**, has 1.4 T available, is owned
  `apps:apps` with the setgid bit, is declared as `mp18` in `pct config 100` and at
  `infra/lxc-selfhost.tf:249` — and **nothing mounts it**. It was provisioned around Sep 2025 and
  never wired up. No new mount point is needed.

- **D-02: `/dev/shm` is REJECTED as the target, and the dead mount is deleted.** `jellyfin.yaml:143`
  binds `/dev/shm:/data/transcode` and the comment above it says "Transcode to RAM for better
  performance" — but `/dev/shm` holds **0 bytes** and always has, because `TranscodingTempPath` was
  never set to `/data/transcode`. Rejected on measurement: `/dev/shm` is sized 15 G against **24 G
  total RAM with only 4.7 G actually available**, so a 19 GB cache there is an OOM, not a full disk
  — and the estate has a documented incident where 1.1 GB in tmpfs took the whole box down
  (`lxc100-tmp-is-tmpfs`). **Delete the mount and its comment together.** Leaving it is a decoy: it
  reads as "already solved", which is plausibly part of why 19 GB accumulated unnoticed.

- **D-03: Belt and braces — bind AND set.** Bind `/mnt/fast/transcode` to `/cache/transcodes` (which
  is already Jellyfin's default path) **and** set `TranscodingTempPath` to it explicitly. If the
  setting is reverted from the UI or appdata is lost, the mount still catches the writes; if the
  mount is ever dropped, the setting still names a real path. Neither is silently load-bearing alone.

- **D-04: Transcode files stay owned `0:568`; record why.** Jellyfin runs as **`uid=0(root)`** — the
  `user:` line in `jellyfin.yaml:64` is commented out and `PUID`/`PGID` are an LSIO convention the
  official `jellyfin/jellyfin` image ignores. A live write probe confirmed container-root can write
  into the dataset (`CAP_DAC_OVERRIDE` inside the userns), landing files `0:568` — host uid
  **100000**, an unmapped id. **Do not "fix" this**: nothing but Jellyfin reads the dataset and every
  file is disposable within minutes, so Phase 1's `568:568` reasoning does not apply. Record it
  explicitly so the next reader seeing `100000` (or `65534` from a container-side listing) knows it
  is expected, not the drift Phase 1 spent 2,674 entries correcting. Setting `user: 568:568` was
  rejected — it would change `/config` and `/media` access and the video/render group membership for
  VAAPI, an enormous blast radius for a scratch directory.

- **D-05: Tune the dataset for scratch video.** Currently `recordsize=128K`, `compression=lz4`,
  `sync=standard`, `atime=off`. Set **`compression=off`**, **`sync=disabled`**, **`recordsize=1M`**.
  The dataset is **empty**, so there is nothing to migrate.

- **D-06: `fast/transcode` is Jellyfin's alone.** Single-tenant, so the quota bounds exactly one
  service and a runaway is unambiguously attributable. A future transcoder gets a **sibling dataset**,
  not a subdirectory here.

- **D-07: The dataset and its properties are declared in Terraform**, following the existing
  `infra/lxc-mpe.tf:50` `null_resource` pattern. Today `fast/transcode` is undeclared —
  `infra/host.tf:63` only `mkdir -p`s the path and `infra/lxc-selfhost.tf:249` mounts it. A
  `null_resource` adds **no attribute to the guarded LXC resource**, so it does not touch the destroy
  landmine. The residual cost is real and must be planned for: it means running `terraform apply` in
  `infra/` at all.

**Fix scope**

- **D-08: Bind ALL of `/cache` off `/`, not just the transcodes path.** The `jellyfin/jellyfin` image
  declares `VOLUME /cache`; it is unbound, so Docker put it on `/`. STATE.md names *"the volume being
  anonymous rather than a declared bind mount"* as the root cause, and the volume also holds the
  **image cache (370 MB)** — the other, slower grower — plus `xmltv` (16 MB) and shader caches.
  Binding only `transcodes` would leave the named root cause standing.

- **D-09: `/cache` binds to `/mnt/fast/appdata/media/jellyfin/cache`** — a **plain directory** inside
  the already-mounted `fast/appdata/media` dataset. This is decisive: `infra/lxc-selfhost.tf:163-167`
  requires every child ZFS dataset to have its own explicit `mount_point`, so a *new dataset* would
  mean editing the guarded LXC resource, while a plain directory needs nothing. It also sits next to
  `/config` where a reader expects Jellyfin's state. The transcodes bind then **nests on top** of it
  from `fast/transcode`. Note honestly: `fast/appdata/media` has **no snapshots and no auto-snapshot
  policy**, so the "don't back up regenerable cache" argument did not apply.

- **D-10: Copy the 392 MB across, then delete the anonymous volume by name — only after Jellyfin is
  proven running on the new path.** Preserves the image cache and the xmltv cache. Keeping the old
  volume as a fallback was rejected.

- **D-11: Jellyfin only — inventory the other five volumes and stop.** `docker system df` reports 6
  local volumes totalling 1.2 GB; Jellyfin's was the only one able to empty `/`. Run a one-time

**What bounds growth**

- **D-13: `quota = 50 G` on `fast/transcode`.** A backstop, not a working limit. 20 G was considered

- **D-14: Turn on BOTH `EnableSegmentDeletion` and `EnableThrottling`.** All three levers are

## Summary

The phase's mechanism is now fully characterised from Jellyfin's own source at the exact tag running
on the estate (`v10.11.11`), and three things turned out differently from the shape CONTEXT.md
assumed.

**First, the incident has a complete, arithmetic explanation.** The transcode Jellyfin was observed
running is `-codec:v:0 copy` — a *stream-copy HLS remux*, not a re-encode. The source file
(`Harry Potter and the Order of the Phoenix … (Bluray-1080p).mkv`) measures **18 GB at 17.93 Mbit/s
over 8,294 s**. An unbounded stream-copy HLS job writes essentially the whole source into
`/cache/transcodes` as fast as the disk allows. One such job accounts for the 19 GB on its own. And
the only thing that would have cleaned it up is `DeleteTranscodeFileTask` — a built-in scheduled task
that is enabled, fires at startup and every 24 h, and deletes files whose mtime is **older than one
day**. Worst-case orphan lifetime is therefore **~48 h**, which is precisely the ~36 h window the
incident occupied. The estate's existing safety net did not fail; it is simply sized in days.

**Second, `EnableSegmentDeletion` does more than delete.** In `EncodingHelper.cs:7258`, when segment
deletion is on *and* the output video codec is `copy` — exactly this estate's case — Jellyfin adds
`-readrate 10` to ffmpeg's input, capping the remux at 10× realtime. That single side effect is a
stronger bound on "an abandoned stream writes an entire film in minutes" than throttling is, and it
is delivered by the deletion switch, not the throttling switch. `EnableThrottling` is *also* live
here: the estate's `jellyfin-ffmpeg 7.1.4` was probed with Jellyfin's own detection command and does
carry the `p pause transcoding` runtime key, so `IsPkeyPauseSupported` is true and the throttler will
start. Both levers are real; neither is inert.

**Third, and most consequential for planning: the encoding config is a full-object POST, and the
object currently in it carries a deliberate incident mitigation that a naive write would destroy.**
`POST /System/Configuration/encoding` deserialises the entire body into `EncodingOptions` and saves
it; every property absent from the body reverts to the C# constructor default. `HardwareAccelerationType`
is live at `none` and `EnableHardwareEncoding` at `false` — set on **2026-08-31 18:27** by
`scripts/disable-jellyfin-hwaccel.sh` as the mitigation for the amdgpu HMM kernel oops that took the
whole estate down for six hours. The constructor default for `EnableHardwareEncoding` is **`true`**,
so a partial POST re-arms it. Read-modify-write is not a nicety here; it is the difference between a
config change and a repeat outage.

**Primary recommendation:** apply the three encoding settings with a strict GET → jq-merge → POST
round-trip against `/System/Configuration/encoding`, asserting in the same step that
`HardwareAccelerationType` is still `none` and `EnableHardwareEncoding` still `false` after the write;
set `SegmentKeepSeconds=300` and keep `ThrottleDelaySeconds=180`; use ZFS **`quota`** (not `refquota`)
because it is the only one of the two that a future snapshot or child dataset cannot escape **and**
because it returns `ENOSPC` — the errno the incident's 764 zero-byte files already signature — where
`refquota` returns `EDQUOT`, which a "No space left on device" grep would miss.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Where transcode bytes physically land | **Host / ZFS** (`fast/transcode` dataset) | Container runtime (bind mount) | The dataset is the only layer that cannot be changed from Jellyfin's UI or lost on a container recreate |
| Hard cap on transcode growth | **Host / ZFS** (`quota` property) | — | D-12: the quota is the asserted bound. It is a pool-level property; nothing inside the container can raise it |
| Graceful bound on a *live* transcode | **Application** (Jellyfin `EncodingOptions`) | — | `EnableSegmentDeletion` + `EnableThrottling` keep steady state orders of magnitude below the quota so playback never meets the ceiling |
| Cleanup of *orphaned* transcodes | **Application** (`DeleteTranscodeFileTask`, ≤48 h) | Host / ZFS quota | Segment deletion stops when the job exits; only the scheduled task and the quota cover a dead job |
| Cache location declaration | **Container runtime** (compose `volumes:`) | Host filesystem (plain dir) | D-09: a plain directory inside an already-mounted dataset needs no change to the guarded LXC resource |
| Dataset existence + tuning | **Terraform** (`null_resource` on atlantis) | — | D-07. A `null_resource` adds no attribute to `proxmox_virtual_environment_container.selfhost` |
| Detection that any of the above regressed | **Workstation** (`quick-health-check.sh`) → **LXC 100** (new standalone script) → **atlantis** (zfs queries) | — | Established three-hop convention: `check-music-freeze.sh:123-131` delegates zfs to atlantis because `zfs` is not resolvable inside the unprivileged LXC |
| Preventing an upstream release undoing it | **Renovate config** (`renovate.json5`) | Standing check (reads settings back) | D-23. Renovate is prevention; the check is detection |

Read the diagram as three concentric bounds on the same bytes: `-readrate` + segment deletion bound a
**live** job; `DeleteTranscodeFileTask` bounds an **orphaned** job on a 48 h horizon; the ZFS quota
bounds **everything**, including the case where all of the above have failed. D-12's "the quota is
what gets asserted" is correct, and the diagram shows why: it is the only box with no gating
conditions on it.

### Pattern 1: Read-Modify-Write against a Jellyfin named configuration

**What:** `POST /System/Configuration/{key}` is a **full-object replace**. The controller
deserialises the body into the registered configuration type and saves it wholesale; there is no
partial-update path.

```csharp
// Source: jellyfin v10.11.11 — Jellyfin.Api/Controllers/ConfigurationController.cs
[HttpPost("Configuration/{key}")]
[Authorize(Policy = Policies.RequiresElevation)]
public ActionResult UpdateNamedConfiguration(string key, [FromBody] JsonDocument configuration)
{
    var configurationType = _configurationManager.GetConfigurationType(key);
    var deserializedConfiguration = configuration.Deserialize(configurationType, _serializerOptions);
    if (deserializedConfiguration is null) throw new ArgumentException(...);
    _configurationManager.SaveConfiguration(key, deserializedConfiguration);   // ← whole object
    return NoContent();
}
```

**Why it matters concretely on this estate.** `EncodingOptions`'s constructor sets defaults for every
property. Two of the live values differ from those defaults:

| Property | Live value (measured 2026-09-02) | Constructor default | Effect of a partial POST |
|---|---|---|---|
| `EnableHardwareEncoding` | **`false`** | **`true`** | **Silently re-enables hardware encoding** |
| `HardwareDecodingCodecs` | `["h264"]` | `["h264","vc1"]` | Silently adds VC1 hardware decode |
| `HardwareAccelerationType` | `"none"` | *(enum default, `none`)* | Unchanged — but only by luck |

`EnableHardwareEncoding: false` and `HardwareAccelerationType: none` were written at **2026-08-31
18:27** by `scripts/disable-jellyfin-hwaccel.sh` as the mitigation for the amdgpu HMM kernel oops.
The `.bak` sitting next to `encoding.xml` proves the prior state:

```
$ diff encoding.xml.bak.20260831T182741Z encoding.xml
13c13
<   <HardwareAccelerationType>vaapi</HardwareAccelerationType>
---
>   <HardwareAccelerationType>none</HardwareAccelerationType>
41c41
<   <EnableHardwareEncoding>true</EnableHardwareEncoding>
---
>   <EnableHardwareEncoding>false</EnableHardwareEncoding>
```

**Two round-trip properties are safe by construction, and it is worth knowing why.** Jellyfin's
serializer is configured `DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull`
(`src/Jellyfin.Extensions/Json/JsonDefaults.cs:33`), so the GET response omits **only** null-valued
properties. On this server that is `EncoderAppPath`, `TranscodingTempPath`, `FallbackFontPath` and
`EncoderPreset` — 43 keys returned of 47 declared. Feeding the GET body straight back deserialises
those four to null, which is what they already are. No loss.

**But `EncoderAppPath` is a trap in the other direction.** `EncodingConfigurationStore.Validate`
throws `InvalidOperationException("Unable to update encoder app path.")` if a non-empty
`EncoderAppPath` differs from the stored one. It is absent from GET (null) — so a body built by hand
that helpfully copies `EncoderAppPathDisplay` into `EncoderAppPath` will **500 the POST**. Build the
body from the GET response, never from the XML and never by hand.

**Also in `Validate`:** if `TranscodingTempPath` changes to a new non-empty value, the store requires
`Directory.Exists(newPath)` **as the Jellyfin process sees it**. The bind must therefore already be
in place inside the container when the POST is issued — which orders D-03's setting *after* D-01's
mount, not alongside it.

### Pattern 2: Nested bind mounts in a compose `volumes:` list

**What:** Docker sorts container mounts by **the number of path segments in the destination**, not by
declaration order, before mounting.

```go
// Source: moby v28.3.2 — daemon/volumes.go
// Less returns true if the number of parts (a/b/c would be 3 parts) in the
// mount indexed by parameter 1 is less than that of the mount indexed by parameter 2.
func (m mountSort) Less(i, j int) bool { return m.parts(i) < m.parts(j) }
func (m mountSort) parts(i int) int {
    return strings.Count(filepath.Clean(m[i].Destination), string(os.PathSeparator))
}
// sortMounts ... This ensure[s] that when mounting, the mounts don't shadow other mounts.
// For example, if mounting /etc and /etc/resolv.conf, /etc/resolv.conf must not be mounted first.
```

`/cache` has 1 part; `/cache/transcodes` has 2. `/cache` therefore always mounts first regardless of
the order they appear in `jellyfin.yaml`. **Declaration order in compose is cosmetic here** — write
them in the order a reader would expect and rely on the sort, but say so in the comment block so a
future reader does not "fix" it.

One consequence to expect and not be alarmed by: runc creates a missing bind destination inside the
rootfs. Because `/cache` is mounted first, creating `/cache/transcodes` creates a real (and then
permanently shadowed) empty directory at `/mnt/fast/appdata/media/jellyfin/cache/transcodes` on the
host. It is inert. Do not delete it while the container is running.

### Pattern 3: The standing check's three-hop shape

`quick-health-check.sh` (workstation, macOS) → single `ssh -n root@172.16.1.159` → new host-resident
script → `ssh root@172.16.1.158` for `zfs`. That is exactly the shape of the two existing fold-ins
and the reasons are already written down in the files:

- **Host-resident** because the docker mount enumeration and the volume/du work are not one-liners
  (`check-music-freeze.sh:6-12`).
- **`ssh -n`** on the workstation side, inline `ssh host 'cmd'` only — never `bash -s` with a heredoc,
  which `-n` silently discards (`02-05` finding, recorded in STATE.md).
- **zfs delegated to atlantis** via a `zfs_query()` wrapper with a route variable
  (`check-music-freeze.sh:123-131`), reported in the summary so "could not look" and "nothing found"
  are distinguishable.
- **The summary heading is a literal contract.** Both existing fold-ins anchor on
  `^📊 N\. Summary` and both files say in capitals not to renumber it silently. The new script must
  declare its own anchor with the same warning, and `quick-health-check.sh` must treat a missing
  anchor as UNKNOWN, not green (the WR-09 defect, already fixed twice).

### Anti-Patterns to Avoid

- **Asserting `d98b2ff9…` is absent.** D-18 is right and the code confirms why: a fresh anonymous
  volume for `/cache` would be created automatically by any future `docker run`/compose that drops
  the bind, with a different id. Assert `Type: volume` count == 0 over `docker inspect jellyfin`.
- **Reading the encoding settings back as proof they fire.** Phase 2 established this failure mode
  twice (MA's `folder_name`; `exportfs -v` on a refused mount). `EnableThrottling: true` is inert
  unless `IsPkeyPauseSupported` **or** ffmpeg ≤ 6.1 — a gate the API cannot show you.
- **`docker volume prune`.** It reports `0B` reclaimable today because all 6 plain volumes are
  active, but after the recreate it would also be free to remove anything else that became dangling.
  D-10 says *by name*; keep it that way, and capture the name **before** the recreate.
- **Grepping ffmpeg/Jellyfin logs for `No space left on device` as the only quota signature.** That
  string is the `quota` (ENOSPC) form. Under `refquota` the errno is `EDQUOT` and the string is
  `Disk quota exceeded`. Pick `quota` and the grep is correct; pick `refquota` and it silently misses.
- **Using `df -BG` for the D-17 floor.** 03-01 already found this: `df -BG` rounds **up**, so 2.2 GiB
  free reports as `3G`. On a 20 GiB floor that is up to 1 GiB of optimism. Use `df -B1 --output=avail`
  and truncate, which is what `spike03-image-headroom.sh` was changed to in commit `b217ada`.

## Common Pitfalls

### Pitfall 1: `disable-jellyfin-hwaccel.sh enable` silently reverts every setting this phase applies

**What goes wrong:** the estate's amdgpu recovery script restores `encoding.xml` **in its entirety**
from the newest `.bak`, then restarts Jellyfin. The only `.bak` on disk was taken at
`20260831T182741Z` — before this phase exists. Running `enable` after this phase lands turns
`EnableSegmentDeletion`, `EnableThrottling` and `TranscodingTempPath` back to their pre-phase values
and reports success.

**Why it happens:** the script's job is one setting but its mechanism is the whole file. It even
knows: `do_enable` prints *"the ENTIRE encoding.xml is restored, not just this"* and the WR-07
comment says *"do_enable restores the WHOLE FILE, so a stale backup reverts everything else the
operator changed in Jellyfin's Playback settings too, and nothing reported it."* The post-restore
verification added in IN-06 checks **only** `HardwareAccelerationType`.

**How to avoid:** three options, in decreasing order of strength.
1. Make `set_hwaccel` and `do_enable` **surgical** — read the *live* `encoding.xml`, set only
   `HardwareAccelerationType` and `EnableHardwareEncoding`, write it back. The `.bak` then becomes a
   value source, not a whole-file source. This is a ~15-line change to the existing `python3`
   heredocs and it removes the class of defect, not the instance.
2. Extend `do_enable`'s post-restore verification to re-assert the three retention values and exit
   non-zero if any moved.
3. At minimum, add a `warn` naming the phase and the three settings.

**Warning signs:** `HardwareAccelerationType=vaapi` in the API while
`EnableSegmentDeletion=false` — the pair only co-occurs after an `enable` restore.

**This is TRAN-09 and it is a research finding, not a CONTEXT decision.** The operator should confirm
it is in scope.

### Pitfall 2: A partial POST to `/System/Configuration/encoding` re-arms the amdgpu outage

Covered in full under Pattern 1. The one-line version: `EnableHardwareEncoding`'s constructor default
is `true`, its live value is `false`, and `false` is a deliberate mitigation for an incident that took
the estate down for six hours on 2026-08-31. **The write must be a GET → merge → POST round-trip, and
the post-write assertion must include `HardwareAccelerationType == "none"` and
`EnableHardwareEncoding == false`.** Asserting only the three settings you meant to change is the
same shape as the 01-06 path-set diff: it passes while something else was rewritten.

### Pitfall 3: Jellyfin refuses to start if a foreign marker file is under the transcode path

`GetTranscodePath()` calls `CreateAndCheckMarker(transcodingTempPath, "transcode", recursive: true)`.
`CheckOrCreateMarker` enumerates `.jellyfin-*` **recursively** and throws
`InvalidOperationException($"Expected to find only {markerName} but found marker for {otherMarkers}.")`
on any other marker.

```csharp
// Source: jellyfin v10.11.11 — Emby.Server.Implementations/AppBase/BaseApplicationPaths.cs
public void CreateAndCheckMarker(string path, string markerName, bool recursive = false)
{
    Directory.CreateDirectory(path);
    CheckOrCreateMarker(path, $".jellyfin-{markerName}", recursive);
}
```

Two ways to trip it in this phase:

1. **Copying the anonymous volume with a plain recursive `cp -a`** brings `.jellyfin-cache` along —
   correct, it belongs at `/cache` — *and* `transcodes/.jellyfin-transcode`. If the copy target's
   `transcodes/` is then shadowed by the nested bind, the stray marker is harmless (unreachable). But
   if the bind order were ever wrong, or the bind were dropped, Jellyfin would find
   `.jellyfin-transcode` under `/cache` — non-recursive check on `CachePath`, so still safe.
   **Verified safe by the code, but say so in the plan rather than discovering it.**
2. **Copying into `/mnt/fast/transcode` from anywhere that carries a marker.** The transcode dataset
   is empty and should stay so; D-10's copy targets the *cache* directory, not the transcode dataset.
   Do not conflate them.

Secondary consideration, not a blocker: because the scan is recursive and `GetTranscodePath()` is
called on **every** HLS segment request (`HlsSegmentController:63,89,143`, `StreamingHelpers:380`), a
large transcode directory costs a full recursive directory walk per segment. A bounded transcode
directory is a latency property as well as a disk property.

### Pitfall 6: `EnableThrottling: true` can be configured and never start

`TranscodeManager.StartThrottler` gates on
`IsPkeyPauseSupported || EncoderVersion <= 6.1`. This estate runs ffmpeg **7.1.4**, so the version
arm is false and everything rests on `IsPkeyPauseSupported`.

**Probed live, replicating Jellyfin's own detection command verbatim** — result: **supported.**

```
$ printf "?" | docker exec -i jellyfin /usr/lib/jellyfin-ffmpeg/ffmpeg \
      -hide_banner -f lavfi -i nullsrc=s=1x1:d=10000 -f null - 2>&1 | grep "pause transcoding"
p      pause transcoding
u      unpause transcoding
```

Note the `d=10000`: that is not arbitrary, it is Jellyfin's own value for ffmpeg ≥ 7
(`EncoderValidator.cs:555`). At d=120 the null pipeline completes in under a second at ~14,000×
realtime and never reads stdin — a shorter duration returns a **false negative**. Any plan that
re-probes this must use `d=10000`.

Additional gates on the throttler that the plan's proof must satisfy: **File input, video, and
`RunTimeTicks >= 5 minutes`.** Music and short clips never throttle. The proof transcode must be a
film.

### Pitfall 7: Segment deletion stops the instant the job exits

```csharp
// Source: jellyfin v10.11.11 — TranscodingSegmentCleaner.TimerCallback
if (_job.HasExited) { DisposeTimer(); return; }
```

Segment deletion bounds a **live** job only. An orphaned job's residue is whatever the cleaner had
not yet deleted at the moment the job died — roughly `SegmentKeepSeconds + ThrottleDelaySeconds` of
content. That is the direct reason `SegmentKeepSeconds` sizes the *orphan* footprint as well as the
live one, and it is the strongest argument for lowering it (see below).

Orphan cleanup falls to `DeleteTranscodeFileTask` at ≤48 h, and below that to the ZFS quota. There is
no third layer.

pitfalls does not miss it: a bare apply was measured on 2026-08-31 to plan
`1 to destroy` on `proxmox_virtual_environment_container.selfhost` — LXC 100 and ~103 containers.

### `SegmentKeepSeconds` — recommend **300** (down from 720)

**Mechanism.** The cleaner deletes indices `0 … (downloadPositionSeconds − keep) / segmentLength`
every 20 s, measured against the client's **download** head. It deletes the whole prefix behind the
window, not a sliding sample.

**Arithmetic at this estate's measured bitrate (2.24 MB/s, 6 s segments):**

| `SegmentKeepSeconds` | Segments retained | Retained bytes per stream | + 180 s throttle lead | 4 concurrent streams |
|---|---|---|---|---|
| 720 (default) | 120 | 1.61 GB | 2.02 GB | 8.1 GB |
| **300 (recommended)** | **50** | **0.67 GB** | **1.08 GB** | **4.3 GB** |
| 120 | 20 | 0.27 GB | 0.67 GB | 2.7 GB |
| 20 (floor) | 3 | 0.04 GB | 0.44 GB | 1.8 GB |

**Failure mode if too HIGH.** Not "the quota is breached" — at 720 s even four concurrent streams of
this class fit inside 50 G. The real cost is **orphan residue**. Because the cleaner stops the moment
the job exits (Pitfall 7), a Jellyfin restart, a host wedge or a container recreate leaves
`keep + lead` worth of segments behind, and they live up to 48 h before
`DeleteTranscodeFileTask` reaches them. At 720 s each orphan leaves ~2.0 GB; at 300 s, ~1.1 GB. Over
a bad 48 h that is the difference between roughly 10 GB and 5 GB of dead weight inside a 50 G bound
that also has to accommodate live playback.

The default of 720 was chosen upstream for a world where a second of transcode output costs
2–4 Mbit/s of *re-encoded* video. Here the video codec is `copy`, so a second costs **17.93 Mbit/s** —
5–9× the assumption the default was sized against.

**Failure mode if too LOW.** A client seeking backwards past the keep window requests a segment index
below the current transcoding index. Jellyfin does **not** 404: it kills the job and starts a new
ffmpeg from that point.

```csharp
// Source: jellyfin v10.11.11 — Jellyfin.Api/Controllers/DynamicHlsController.cs:1512
else if (segmentId < currentTranscodingIndex.Value)
{
    _logger.LogDebug("Starting transcoding because requestedIndex={0} and currentTranscodingIndex={1}",
                     segmentId, currentTranscodingIndex);
    startTranscoding = true;
}
```

So the observable cost is a **transcode restart** — a few seconds of buffering — not a playback
failure. Two further notes: the old job is killed with a `p => false` delete predicate, so its
segments are left on disk (they get overwritten because the new job reuses the same output-name
prefix); and with `-readrate 10` in play the restart has to re-remux from the seek point.

**Why 300 specifically.** 50 segments is a comfortably larger seek-back window than any client UI
offers (10 s / 30 s skip buttons, resume-position restore) and covers a deliberate scrub back through
a scene. The 20 s cleaner tick plus one segment means the retained set overshoots by up to 26 s —
about 9% at 300 s, versus 33% at 60 s, so 300 keeps the configured number meaningful. And 300 is
15× the silent-clamp floor of 20, so there is no risk of configuring a number Jellyfin quietly
ignores.

**Confidence: MEDIUM.** The arithmetic and the code paths are HIGH confidence; the judgement that a
5-minute seek-back window is sufficient for this household is a reasoned assumption, recorded as A2.

### `ThrottleDelaySeconds` — recommend **keeping 180**

**Mechanism.** Every 5 s the throttler computes
`gap = transcodingPositionTicks − downloadPositionTicks` and pauses ffmpeg (writes `p` to stdin) when
`gap >= max(ThrottleDelaySeconds, 60)` seconds. It unpauses (`u`) as soon as the gap closes.

**Failure mode if too HIGH.** ffmpeg is allowed a larger lead, so more unwatched content is on disk
and more is left behind by an orphan. At 180 s the lead is 0.40 GB per stream at this bitrate.

**Failure mode if too LOW.** More frequent pause/resume cycles against a running ffmpeg. Clients
prefetch 2–3 segments (12–18 s) routinely; a threshold near the 60 s floor would put the throttle
close enough to normal client buffering behaviour that pause/resume churn becomes routine rather than
exceptional, and every pause is a write to a subprocess's stdin on a shared host. Values below 60 are
silently clamped to 60, so configuring 30 would be a lie in the config file.

**Why 180 stands.** It sits 3× above the hard floor and roughly 10× above typical client prefetch, so
the throttle engages only on genuine run-ahead — which is precisely the abandoned-stream case D-14
names. Combined with `SegmentKeepSeconds=300`, the steady-state on-disk set is bounded at about
`300 + 180 = 480 s` of content ≈ **1.08 GB per stream at 17.93 Mbit/s**, ~2.7 GB for a 60 Mbit/s 4K
remux. Four concurrent 4K streams ≈ 11 GB — comfortably inside 50 G with room for orphans.

**Do not treat throttling as the primary bound.** `EnableSegmentDeletion`'s `-readrate 10` side effect
is the stronger control on a stream-copy remux and it applies before any client has downloaded
anything (the throttler needs a non-zero download position to compute a gap at all — see
`IsThrottleAllowed`'s final `return false` for "No throttle data").


## `quota` vs `refquota` on `fast/transcode`

CONTEXT.md calls them identical for a childless, snapshotless dataset and hands the choice to the
planner. **Today they are identical — verified: `zfs list -r -t all fast/transcode` returns the
dataset alone, no children and no snapshots. But they are not equally safe, and the difference is
observable.**

| | `quota` | `refquota` |
|---|---|---|
| Bounds | *"the amount of space a dataset **and its descendants** can consume … includes all space consumed by descendants, including file systems and snapshots"* | *"the amount of space **a dataset** can consume … does **not** include space used by descendants, including file systems and snapshots"* |
| Property lives on | the DSL **directory** (`dd_quota`) | the DSL **dataset** (`ds_quota`) |
| Errno when exceeded | **`ENOSPC`** — `dsl_dir.c:1344 retval = SET_ERROR(ENOSPC);` | **`EDQUOT`** — `dsl_dataset.c:4337 error = SET_ERROR(EDQUOT);` |
| ffmpeg's message | `No space left on device` | `Disk quota exceeded` |
| A future snapshot / child dataset | counted — cannot escape the bound | **not counted — escapes the bound entirely** |
| Interaction if both set | operations exceeding *either* fail; `refquota` above `quota` has no effect | — |

**Recommendation: `quota=50G`. Do not set `refquota`.**

Three reasons, in order of weight:

1. **`refquota` does not bound what this phase exists to bound.** D-06 says a future transcoder gets a
   sibling dataset — but "sibling" is a convention, and a convention is exactly the kind of thing that
   drifts. If anything ever lands under `fast/transcode/…`, `refquota` lets it consume the pool while
   reading green. `quota` cannot be escaped that way. The phase's whole premise is a bound that
   survives someone not knowing the rule.
2. **`ENOSPC` is the errno the estate has already learned to recognise.** 03-01's forensic signature
   was *"764 zero-byte files (the ENOSPC signature)"*. A check or a log grep built on
   `No space left on device` is correct under `quota` and **silently blind** under `refquota`. Given
   this project's documented history of instruments that report green while the thing is broken, do
   not introduce a second errno.
3. **The snapshot downside of `quota` is not live here.** The classic argument for `refquota` is that
   a snapshot's held blocks steal headroom from live writes under `quota`. `fast/transcode` has no
   snapshots and no auto-snapshot policy, holds only disposable data, and D-06 makes it
   single-tenant. If a snapshot policy is ever added to `fast`, exclude this dataset — and record
   that as the reason.

**What actually happens when the bound fires** (relevant to D-15's "prove it"):

- ZFS refuses the write with `ENOSPC`. Enforcement is **not synchronous** — it "may be delayed by
  several seconds", so the dataset can slightly overshoot the quota before writes start failing.
  Do not assert `used <= 50G` exactly; assert `used <= quota × 1.02` or simply that writes fail.
- ffmpeg's muxer fails, ffmpeg exits non-zero. `TranscodeManager.StartFfMpeg` observes a non-zero
  exit and the job dies. The partially written segment is left at zero length — the observed
  signature.
- The client's next segment request finds no file, `GetSegmentResult` times out, and playback
  **errors** rather than hanging indefinitely. It is a failed playback, not a hung one, and it is
  scoped to that one stream.
- **`/` is untouched.** That is the property the phase is buying, and it is the thing the test should
  assert — not that playback survives, which it will not.
- The dead job's files are removed by `KillTranscodingJob` → `DeletePartialStreamFiles` once the
  60 s HLS kill timer expires, so the dataset self-heals.

**`df` inside LXC 100 reflects the quota.** ZFS's `statvfs` derives `f_blocks` from
`referenced + available`, and `available` is capped by the directory quota. That gives the standing
check an assertion it can make **from LXC 100 without reaching atlantis** —
`df -B1 --output=size /mnt/fast/transcode` should read ≈ 50 G, not 1.4 T. Treat that as a *second
independent instrument* alongside the authoritative `ssh atlantis zfs get -Hp quota fast/transcode`,
per the "verify with a second instrument" rule. **Prove it empirically in the plan** (read `df`
before and after setting the quota) rather than assuming it — this is A3 in the Assumptions Log.

### Copy safety — `rsync -a` and the NFSv4-ACL question

CLAUDE.md documents `rsync -a` failing on `tank` with `mkstemp … Operation not permitted` while
printing success-looking stats and exiting 23, caused by `acltype=nfsv4` + **`aclmode=restricted`**.

**Measured on the actual target, 2026-09-02:**

```
NAME                PROPERTY    VALUE
fast                acltype     posix         aclmode discard     aclinherit discard
fast/appdata/media  acltype     nfsv4         aclmode passthrough aclinherit passthrough
fast/transcode      acltype     posix         aclmode discard     aclinherit discard
```

`fast/appdata/media` **is** `acltype=nfsv4` — but `aclmode=passthrough`, not `restricted`. Under
`passthrough` a `chmod` is permitted and rewrites the ACL; the `EPERM` that breaks `rsync -a` on
`tank` is a property of `restricted`. So the constraint **probably does not apply** here.

**Do not rely on "probably".** The estate has been burned by exactly this shape (STATE.md 2026-09-01:
*"`ro` is forced, not a preference" is a property of the TrueNAS-era datasets, not of `tank`*).
Recommendation for the plan:

1. Prove it with a two-file probe before the real copy: `rsync -a` one file from the volume into a
   scratch dir under `/mnt/fast/appdata/media/jellyfin/`, check **exit status and** that the file
   arrived with the right size.
2. If it fails, fall back to the documented estate-safe form:
   `rsync -rlt --no-p --no-o --no-g` (CLAUDE.md), or plain `cp -R` — ownership is explicitly
   irrelevant here by the same reasoning as D-04 (regenerable, single-reader, Jellyfin runs as
   container root with `CAP_DAC_OVERRIDE`).
3. Either way, **assert the copy by byte count and file count**, not by rsync's summary. 03-01's
   lesson and CLAUDE.md's both say rsync's stats can look like success while it exits 23.

Two supporting facts that make the copy low-risk: the source is 392 MiB against 1.31 T available on
`fast`, and `/mnt/fast/appdata/media/jellyfin` is `apps:apps drwxr-xr-x` with `/config` already
proven writable by container-root today. The LXC idmap maps `568→568` identically
(`/proc/self/uid_map`: `568 568 1`), so a `chown 568:568` from inside LXC 100 would also work if the
plan wants ownership consistency with `/config` — but D-04's reasoning says it is unnecessary.

### Ordering hazards, as a sequence

The plan should treat these as ordered constraints, not as steps to be shuffled:

1. `TranscodingTempPath` cannot be POSTed before the bind exists — `EncodingConfigurationStore.Validate`
   requires `Directory.Exists(newPath)` from Jellyfin's own view.
2. The anonymous volume name must be captured **before** the recreate (Pitfall 5).
3. The copy must complete before the recreate, or the first `/cache` access on the new bind finds an
   empty directory and Jellyfin begins re-fetching 370 MB of artwork.
4. `docker volume rm` must come after Jellyfin is *proven* running on the new path (D-10), which is
   the only ordering CONTEXT.md already states explicitly.
5. The ZFS property changes (D-05) should land **before** the bind, because `recordsize` applies to
   newly written blocks only — the dataset is empty today, and it should still be empty when
   `recordsize=1M` takes effect.

Renovate evaluates all `packageRules` **serially in declaration order**; it does not stop at the
first match, and when two matching rules set the same option **the later one wins**. The
documentation's own guidance is to order rules in ascending importance so specific rules can override
broad ones. The new Jellyfin rule must therefore appear **after `packageRules[2]`** — appending to the
end of the array is both simplest and consistent with how the Mattermost rule (`[19]`) already sits
after `[2]`.

## Code Examples

### Applying the three encoding settings (the D-21 round-trip)

```bash
# Runs ON LXC 100. Jellyfin publishes no host port and is reachable only from here; the D-40 key
# lives at /mnt/fast/secrets/jellyfin-deercrest.env, mode 0600 root.
set -euo pipefail
. /mnt/fast/secrets/jellyfin-deercrest.env      # no `set -a`: in-process only

# NEVER an IP literal, NEVER the bare name `jellyfin` (resolves to Cloudflare's edge from LXC 100).
ADDR=$(docker inspect jellyfin \
       --format '{{(index .NetworkSettings.Networks "t3_proxy").IPAddress}}'):8096

jf() { curl -sS -H @<(printf 'Authorization: MediaBrowser Token="%s"\n' "$JELLYFIN_API_KEY") "$@"; }

# 1. GET the CURRENT object. Do this immediately before the POST — encoding.xml was last written
#    2026-08-31 18:27 by disable-jellyfin-hwaccel.sh, so a cached copy is not safe.
jf "http://${ADDR}/System/Configuration/encoding" > /mnt/fast/spike-021/encoding.before.json

# 2. Record the two values a partial POST would clobber. THESE ARE THE ASSERTION.
BEFORE_HW=$(jq -r '.HardwareAccelerationType'  /mnt/fast/spike-021/encoding.before.json)   # "none"
BEFORE_HE=$(jq -r '.EnableHardwareEncoding'    /mnt/fast/spike-021/encoding.before.json)   # false

# 3. Merge — never construct the body by hand. In particular NEVER set EncoderAppPath:
#    EncodingConfigurationStore.Validate throws InvalidOperationException if it changes.
jq '.EnableSegmentDeletion = true
  | .SegmentKeepSeconds    = 300
  | .EnableThrottling      = true
  | .ThrottleDelaySeconds  = 180
  | .TranscodingTempPath   = "/cache/transcodes"' \
  /mnt/fast/spike-021/encoding.before.json > /mnt/fast/spike-021/encoding.after.json

# 4. POST the WHOLE object. 204 No Content on success.
jf -o /dev/null -w 'HTTP %{http_code}\n' \
   -X POST -H 'Content-Type: application/json' \
   --data-binary @/mnt/fast/spike-021/encoding.after.json \
   "http://${ADDR}/System/Configuration/encoding"

# 5. Read back and assert BOTH the intended change AND the unintended non-change.
jf "http://${ADDR}/System/Configuration/encoding" > /mnt/fast/spike-021/encoding.readback.json
jq -e --arg hw "$BEFORE_HW" --argjson he "$BEFORE_HE" '
      .EnableSegmentDeletion  == true
  and .SegmentKeepSeconds     == 300
  and .EnableThrottling       == true
  and .ThrottleDelaySeconds   == 180
  and .TranscodingTempPath    == "/cache/transcodes"
  and .HardwareAccelerationType == $hw          # MUST still be "none" — the amdgpu mitigation
  and .EnableHardwareEncoding   == $he          # MUST still be false  — ctor default is TRUE
' /mnt/fast/spike-021/encoding.readback.json

# 6. A full diff, so anything else that moved is visible rather than merely unasserted.
diff <(jq -S . /mnt/fast/spike-021/encoding.before.json) \
     <(jq -S . /mnt/fast/spike-021/encoding.readback.json)
```

Step 6 is the 01-06 lesson applied: asserting the five fields you changed is a path-set diff. The
full diff is the content diff.

**No container restart is required.** Plan 01-06 established this for `LibraryOptions`
(*"No Jellyfin restart occurred or was required … the settings read back correctly from the API
immediately"*), and the same `SaveConfiguration` path applies here — `TranscodingSegmentCleaner` and
`TranscodingThrottler` both call `_config.GetEncodingOptions()` **inside their timer callbacks**, so
they pick up a change on the next tick without a restart.

### The five assertions the standing check makes

```bash

  '{{range .Mounts}}{{if eq .Destination "/cache/transcodes"}}{{.Type}} {{.Source}}{{end}}{{end}}' \

# C. The old volume is gone (D-10). Assert by name AND by count — an absent name is not a
#    guarantee that no anonymous volume exists (that is assertion B's job).
docker volume ls -q | grep -qx "$OLD_VOL" && fail "anonymous volume $OLD_VOL still exists"

# E. The three encoding values, read back (D-20) — REPORTED as a regression detector, and
#    accompanied by the two amdgpu values, because reverting THOSE is the higher-cost regression.
```

### Known Threat Patterns

| Pattern | STRIDE | Standard mitigation | Status here |
|---|---|---|---|
| Local resource exhaustion — an unbounded cache fills the Docker host's root filesystem and takes down 103 containers | **Denial of Service** | Hard filesystem-level quota, not an application setting | **This is the phase.** ZFS `quota=50G` on a dedicated dataset off `/` |
| Credential disclosure — the API key reaching a **public** repository | Information Disclosure | CLAUDE.md standing rule: credentials go in `~/.claude/secrets/` or `/mnt/fast/secrets/` by variable name only. The estate has a live example of this going wrong (the UCG-Max root password sat in this public repo for ~6 months and is still recoverable via `git log -S`) | **Mitigate:** the plan must screen any committed artefact with `grep -cE '(token\|api_key\|password\|secret)'` — the T-01-38 gate from 01-07 |
| Credential disclosure via process listing | Information Disclosure | `-H @<(printf …)` process substitution rather than `-H "…$KEY"` | Existing idiom; copy it |
| Privilege reintroduction — a full-object POST silently re-enabling hardware encoding | **Tampering** | Read-modify-write with an explicit post-write assertion on the values you did *not* mean to change | **This is Pitfall 2.** `EnableHardwareEncoding` ctor default is `true`; live value is `false` and is an incident mitigation |
| Supply-chain — an upstream minor release silently reverting a resource-exhaustion control | Tampering | Pin the update class that can carry breaking behaviour to manual review | **D-23.** Also note 10.11 already reworked encoding once |
| Unverified package execution during a health check | Tampering / Elevation | Never `npx --yes`; guard on `command -v` and report UNVALIDATED | § *Renovate Rule Shape* |
| Destructive infrastructure change — a bare `terraform apply` destroying the Docker host | **Denial of Service** | `prevent_destroy` + `ignore_changes` + saved-plan discipline with a mechanical zero-destroys assertion | § *Terraform* |
| Fail-open detection — a check reporting green because it could not look | Repudiation | D-19 fail-closed, with **negative controls executed** rather than asserted | TRAN-05's two negative-control rows |

**One residual risk to record rather than fix:** the D-40 API key is administrator-equivalent by

by `check-music-consumers.sh`; this phase widens its use from read to write. That is a real change in
what a leak of that file costs. Recommend the plan states it explicitly rather than leaving it
implicit, in the same style as 02-09's `sec=sys` "accepted residual risk, recorded as a CHOICE".
