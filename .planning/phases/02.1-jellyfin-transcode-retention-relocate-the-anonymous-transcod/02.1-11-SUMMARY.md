# Phase 02.1 Plan 11: Assert the Five Encoding Values Fail-Closed Summary

Converted `check-jellyfin-transcode.sh`'s five encoding read-backs from `info()` prints into
fail-closed assertions against env-overridable `EXPECT_*` expectations, proved each one able to fail
individually with five per-field negative controls that mutated no file, and made a drifted value
legible on `quick-health-check.sh`'s green path — closing GAP 1 / CR-01.

## What Was Built

**The defect.** ROADMAP Success Criterion 6 claimed the standing check *asserts* "the transcode
quota **and the five encoding values**". It did not. Lines ~562-573 printed all five through
`info()`, so `FAILURES` never incremented on drift, and `quick-health-check.sh`'s selector omitted
both tokens, so on the branch that prints a tick the five values were **neither asserted nor
displayed**.

The consequence was specific and cheap: set `TranscodingTempPath` back to Jellyfin's own default
`/config/transcodes` and the transcode cache moves onto `fast/appdata`, **off the quota'd dataset**,
while the binds, both mount instruments and the `/` headroom floor all stay green and the script
prints `✅ Jellyfin transcode retention intact`. That is the cheapest route straight back to the
incident this phase exists to prevent, and it directly contradicted the phase Goal's claim that "a
standing fail-closed check would have caught the incident before `/` reached zero".

**The fix, in three parts:**

1. An `EXPECT_*` block of five `${VAR:-default}` constants (the values 02.1-05 applied and 02.1-06
   proved firing), documented as (i) the only knobs, so a policy change is a one-line edit and a red
   names the line; (ii) the device that lets a control avoid mutating live state; (iii)
   override-can-only-make-it-RED — there is no value that suppresses an assertion.
2. `assert_enc()`, calling `fail()` with `expected=`/`found=` on mismatch, with an extra explanation
   on the `TranscodingTempPath` branch because it is not like the other four.
3. A `transcode target:` summary line, a truthful `encoding values:` tally, and the fold-in selector
   widened so both are legible on the green path.

## The SC6 Resolution Actually Taken — Recorded So It Is Not Re-Litigated

The verification report offered two ways out: **assert all five**, or **assert two and reword SC6
down to two**. **All five was chosen.** The reasons, restated here because this is the document a
future reader will find:

1. **The CONS-04 objection applies to none of the five.** The in-code justification ("a standing
   check cannot prove a setting FIRES") is sound but answers a different question. Comparing
   `SegmentKeepSeconds` to `300` is the same class of operation as comparing `TranscodingTempPath`
   to `/cache/transcodes` — a deterministic read-back of a value 02.1-05 wrote, needing no
   transcode, no API mutation and no log.
2. **Asserting two leaves a subtler copy of the same defect.** `SegmentKeepSeconds` drifting to
   `86400` is a plausible UI edit that silently deletes the retention policy this phase installed,
   and under a two-value scheme the check stays green. Same shape as CR-01, one field over. This was
   driven as control 3.
3. **The 01-09 permanently-red trap is handled by construction**, not by hope: one block, named
   constants, `${VAR:-default}`.
4. **It keeps SC6's substantive commitment.** Reducing "five" to "two" would be a scope reduction of
   a ROADMAP commitment, which is not this plan's to make. SC6 got a *clarifying* amendment
   instead — assert-not-drifted, with criterion 4 named as the sole firing proof.

## ⚠️ Limitation: the fold-in's RED path was NOT driven end-to-end

Stated plainly rather than implied, because this is exactly the distinction 02.1-10 was careful
about.

`quick-health-check.sh` **hard-codes its remote command**, so an `EXPECT_*` override cannot reach
the check through it. The fold-in's `❌ BROKEN` branch was therefore **not** exercised by this plan.
What was done instead:

- **The GREEN path was driven end-to-end**, from the workstation: exit 0, with
  `transcode target: /cache/transcodes` and `encoding values: 5 asserted, 0 drifted` printed inside
  the `✅ Transcode retention intact` block.
- **The coupling was proven mechanically**: the `grep -E` alternation was read *out of the file*
  (not retyped — retyping would test my transcription) and each of its **nine** tokens asserted to
  appear verbatim in the check's emitted section 6. All nine returned ≥ 1. A **negative control**
  (`transcode elephant`) returned 0, so the test discriminates.
- **The RED path was driven at the check level** in task 2, five times.

So: drift *will* reach the operator's screen, and each token *does* select something. Whether the
fold-in's BROKEN branch renders a drift correctly is inferred from the identical branch being
proven for the other reds, not observed for this one.

## Deviations from Plan

### [Rule 3 — Blocking] The plan's delivery mechanism is unexecutable under worktree isolation

**Found during:** Task 2.
**Issue:** The plan specifies commit → push → `git pull --ff-only` on LXC 100 → assert host-side
`git rev-parse HEAD` == `origin/main`. This plan ran as a **parallel worktree agent** on branch
`worktree-agent-a5a14f3f7b75e2c18`; the orchestrator merges to main after the wave. Pushing to main
from the worktree would bypass that merge, so it was not done.
**Fix:** The edited script was staged to `/mnt/fast/spike-021/02.1-11/scripts/` — **outside** the
repo — and delivery was asserted by **sha256 equality** between the committed worktree file and the
host-side copy (`7ea3c84b…` both sides). On the point these controls depend on, this is *stronger*:
a matching HEAD proves the right commit is checked out, a matching sha256 proves the exact bytes
under test are the bytes committed. Delivery half (ii) was executed as written (`grep -c
EXPECT_TRANSCODING_TEMP_PATH` → 3, `grep -c assert_enc` → 9, both non-zero).
**Consequence, stated so nobody overreads the artifact:** these runs prove the assertions
discriminate. They do **not** prove the standing check *on LXC 100* is the amended one — it is not
until the orchestrator merges and the host pulls. `/mnt/fast/stacks` still hashes `d33356c5…`, the
pre-02.1-11 version. **Open follow-up: after merge, `git pull --ff-only` on LXC 100 and re-run
`quick-health-check.sh` once** to confirm the `transcode target:` line appears against the real
standing check. One line, no risk.
**Also:** task 3's acceptance criterion asks for a `.planning/STATE.md` edit. STATE.md is **owned by
the orchestrator** in worktree mode and was deliberately **not touched**. ROADMAP edits were confined
to the SC6 wording deliverable — no progress tables, checkboxes, plan counts or tracking fields.
**Staging cleaned up:** `/mnt/fast/spike-021/02.1-11` removed; host repo left at `780ada8` with
`scripts/` clean and both script hashes unchanged.
