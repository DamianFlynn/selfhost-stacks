# Phase 02.1 Plan 07: Disarm the Silent Revert — Summary

**The one-command silent revert of this entire phase is disarmed, and the disarming was proven able
to fail twice.** `disable-jellyfin-hwaccel.sh enable` now captures phase 02.1's five transcode-
retention values from the live config *before* the whole-file `.bak` restore, re-asserts them into
the restored file, and verifies them on both sides of the container restart — naming any moved field
with its **before and after** values and exiting non-zero.

The substance of this plan is not the hardening. It is that the hardening's **negative control
actually fires**, which the reviewed design could not have achieved.

## The finding this plan closes

The cross-AI review raised it HIGH against plan 04: *"perturb one retention value after a restore,
re-run the verification path, confirm non-zero"* is **structurally unable to fail**. The verification
lives *inside* `do_enable`, and `do_enable` **re-captures the live values before restoring**. It
would have captured the perturbed values, carried them across faithfully, compared them against
themselves, and **passed** — emitting a transcript that reads exactly like a discharged negative
control. That is the same failure class as 02.1-06's log-level bug and 02-08's `exportfs -v`: an
instrument that cannot report the thing it exists to detect.

Two genuine fault-injection paths replace it, and **both were executed**:

**(a) A standalone `verify-retention` sub-action.** Read-only, invocable against an arbitrary
`JELLYFIN_CONFIG`, taking its expectations from the **caller** (`$TRAN09_EXPECT`) rather than
re-deriving them from the file it is checking. Taking the expectations from outside is precisely what
makes it able to fail. Exercised **both ways**: with `EnableSegmentDeletion` flipped `true→false` it
exited **1**, named the field, and printed `expected='true' found='false'`; with the value restored
it exited **0**.

**(b) A `TRAN09_FAULT=1` hook.** Skips the re-assert while still capturing and **still verifying**,
so the comparison genuinely finds the restored pre-phase values. It exited **1** and named four of
the five fields with both values:

```
✗ pre-restart TranscodingTempPath: FAIL - MISMATCH before='/cache/transcodes' after='absent'
✗ pre-restart EnableSegmentDeletion: FAIL - MISMATCH before='true' after='false'
✗ pre-restart SegmentKeepSeconds: FAIL - MISMATCH before='300' after='720'
✗ pre-restart EnableThrottling: FAIL - MISMATCH before='true' after='false'
✓ pre-restart ThrottleDelaySeconds: PASS (180)
```

**That fifth line is the most informative one in the transcript.** `ThrottleDelaySeconds` was `180`
on both sides, and it correctly passed inside a failing run. A blanket failure would have failed it
too. The comparison is proven genuinely per-field, not a switch that flips the whole block.

The hook is documented in the script header as **test-only**, names this plan and the VALIDATION row
it discharges, states plainly that setting it in production restores the silent revert, and prints
four loud warning lines whenever active — so it cannot be on without appearing in any transcript.

Executed on LXC 100 from `/mnt/fast/stacks`, against a throwaway `encoding.xml` at
`/mnt/fast/spike-021/tran09/` and a disposable container, with **both** `JELLYFIN_CONFIG=` and
`JELLYFIN_CONTAINER=` overrides on every invocation.

| 3 simulated phase write | the five values written into the fixture, contents recorded verbatim |

Step 2 exited **0**, so the "a non-zero step 2 is recorded, not a stop" allowance was never needed —
but the `.bak`'s existence was asserted **directly** rather than inferred from that exit code anyway,
which is the point of the allowance.

## The delivery was the precondition, not the tidy-up

`disable-jellyfin-hwaccel.sh` runs **on LXC 100** by its own header, while task 1 edited the
**workstation** copy. Without D-26 first, every invocation would have hit a script with neither
`verify-retention` nor `TRAN09_FAULT` — and in the worse of the two cases would have emitted a
transcript that *looks* like discharged evidence (T-021-84).

## Deviations from Plan

### Auto-fixed / design calls made during execution

**1. [Rule 2 — Missing] The retention verification runs twice, not once**

- **Found during:** Task 1, reconciling the plan's own text.
- **Issue:** `key_links` says *"capture before the whole-file copy, re-assert after it, **verify
  before the container restart**"*; the `<action>` says *"widen `do_enable`'s **post-restore**
  verification (lines 372-393)"*, which is after the restart. Those are different placements.
- **Fix:** both. A **pre-restart** gate compares immediately after the re-assert and returns 1
  *without restarting* — restarting a service the house is watching onto a config that has silently
  lost this phase's settings is strictly worse than not restarting at all. A **post-restart**
  comparison then runs inside the widened post-restore block, which catches the case the pre-restart
  gate structurally cannot: a Jellyfin that rewrites `encoding.xml` on startup.
- **Consequence visible in the transcript:** negative control 2 fails at the *pre-restart* gate, so
  the container is never restarted onto the reverted config — asserted (`State.Status = running`,
  unchanged).
- **Commit:** `2021d0f`

**2. [Rule 1 — Bug] `current_retention` could still have returned an empty string**

- **Found during:** Task 1, writing the read-back helper.
- **Issue:** Copying `current_hwaccel`'s shape faithfully copies its remaining hole. Its `UNREADABLE`
  sentinel is emitted **by the python heredoc**, so it covers a parse failure — but it cannot cover
  `python3` being absent, or the heredoc producing nothing at all. In that path the function returns
  `""`, and a caller could read five empty fields as five measured values. That is IN-04's exact
  bug (`"VAAPI is ON ()"`) in a new place.
- **Fix:** `current_retention` checks its own output and substitutes an explicit
  `UNREADABLE (no output - python3 missing, or <path> could not be opened)`. `compare_retention`
  then treats an `UNREADABLE` or empty value **on either side** as UNKNOWN and therefore a failure,
  never a pass — CR-02's rule applied to a different instrument. Proven locally against a
  non-existent config: exit 1, reported as UNKNOWN.
- **Commit:** `2021d0f`

**3. [Rule 2 — Missing] The credential screen got a positive control**

- **Found during:** Task 2, screening the push range and then the artifact.
- **Issue:** The first screen printed "0 matches" — and 0 is exactly what a pattern that can never
  match also prints. 02.1-06 paid for this shape already.
- **Fix:** the same pattern is run against a scratch file **known** to contain `api_key=<24 hex>`
  first. It returns 1. Only then is the 0 against the push range and the artifact meaningful. Both
  screens are recorded in the artifact.
- **Commit:** `fb1ea68`
