# Phase 02.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.
> Derived from `02.1-RESEARCH.md` § *Validation Architecture* (35 test rows), amended 2026-09-02
> against `02.1-REVIEWS.md` (3 rows repaired, 3 rows added).

**The governing rule for this phase (CONS-04, D-15):** a control that *reads back* is not a control
that *fires*. Every bound in this phase has two separate proofs — a cheap read-back that joins the
standing check, and a one-time firing proof executed with its transcript recorded. Neither
substitutes for the other. This project has been burned twice by the substitution: 01-06's path-set
diff passed while 83 `.nfo` were rewritten in place, and 02-08's `exportfs -v` kept printing a line
for a mount the client was refusing.

**Corollary added 2026-09-02 (review finding C):** *a proof that cannot fail is worse here than
elsewhere, because it produces a recorded transcript that looks like evidence.* Two rows were found
to be structurally unfireable as originally written — row 35's negative control (the verification
lived inside `do_enable`, which re-captures live values before restoring, so perturb-then-rerun would
capture the perturbed values and **pass**) and rows 16/18 (segment deletion and throttling both key
off the **client's download position**, so "force a transcode" without a client that fetches segments
sequentially proves nothing). Both now carry an explicit fault-injection path or proof-client recipe,
and both carry a **harness-defect stop condition** distinguishing "the control did not fire" from
"the test never drove the control".

## Sampling Rate

- **After every task commit:** `ssh root@172.16.1.159 'bash /mnt/fast/stacks/scripts/check-jellyfin-transcode.sh'` — targeted, < 20 s, starts no transcode.
- **After every plan wave:** `bash scripts/quick-health-check.sh` — the full estate check including both existing fold-ins, so a regression in Phase 1/2 coverage surfaces here too.
- **At the head of every plan (D-32):** append one timestamped watch line to `artifacts/02.1-D32-watch.txt` — `df -B1 --output=avail /` plus `du -sb` of the anonymous volume while it exists. Observation only; it asserts nothing and writes nothing into live transcode data.
- **Before `/gsd-verify-work`:** full suite green **AND** the D-15 firing proofs executed once with transcripts recorded — TRAN-03 quota-fires, TRAN-04 deletion-fires, TRAN-04 throttling-fires, TRAN-09 revert-fires.
- **Max feedback latency:** 20 s (quick), 90 s (full).

### Discharge — "Playback sanity after the cutover" (TRAN-01, TRAN-04)

**Discharged 2026-09-03 by plan `02.1-14`.** Evidence:
`artifacts/02.1-14-playback-verification.txt`.

Two operator-driven sessions on the Jellyfin web client, both on
*The Kid Who Would Be King (2019)* (h264/MKV/DTS-HD MA, ~29.9 Mbps), each **pinned to its
codec path by ffmpeg's own live command line** rather than a UI label:

- **Session A — REMUX.** `-codec:v:0 copy`, no `libx264`, `-readrate 10` **present**
  (row 17's stream-copy marker), `-map -0:s` so no PGS burn-in. Seek-back from ~10:00 to
  ~01:00 produced a **RESTART** — new ffmpeg PID carrying `-ss 00:01:01.088` — with a 2-3 s
  spinner. Operator verdict, verbatim: *"Session A was perfect, no issues at all great
  picture quality"*.
- **Session B — RE-ENCODE.** `-codec:v:0 libx264 … -maxrate 2616000`, `-readrate 10`
  **absent** (the mirror of session A, as row 17 predicts), no VAAPI or `/dev/dri` so the
  D-30 amdgpu mitigation held. Seek-back after ~10 min of unbroken watching produced a
  **RESTART** — new ffmpeg PID carrying `-ss 00:01:18.078`. Operator verdict, verbatim:
  *"this one is also perfect, no problem with the picture or sound quality"*.

Both sessions were proven to be transcodes (live ffmpeg, non-zero segments); **neither
direct-played**, so the 2026-09-02 trap that left this row open did not recur. `/` free
moved **−4.15 MiB** across the whole exercise, and the standing check exited `0` with
`FAILURES total: 0` both before and after against a byte-identical script.

Two caveats, recorded rather than smoothed: (1) session B's first capture had PGS subtitles
burning in, making the re-encode over-determined — the operator then disabled subtitles
unprompted, giving an A/B in which `libx264` persisted with the cap held constant, which
resolves the attribution; (2) the segment counts do **not** independently prove
`EnableSegmentDeletion` fired — 02.1-06 remains the evidence for that mechanism. This row's
contribution is the perceptual verdict and the seek-back restarts.
