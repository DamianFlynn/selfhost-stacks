## What actually bounds growth

### Q1 — What is the load-bearing bound?

| Option | Description | Selected |
|--------|-------------|----------|
| ZFS quota, Jellyfin retention as the graceful layer | Quota is structural — a ZFS property, not flippable from a UI, survives a recreate | ✓ |
| Jellyfin retention settings, no quota | Graceful cleanup — but lives in an appdata XML one UI click from off, the shape of failure that produced this phase | |
| Quota only | One control to assert — but the first symptom is a broken playback rather than a cleanup | |

**User's choice:** ZFS quota, with Jellyfin retention as the graceful layer

### Q2 — What quota value?

| Option | Description | Selected |
|--------|-------------|----------|
| 50 G | Backstop not a working limit; steady state far below it, total runaway is 4% of the pool's free space | ✓ |
| 20 G | Bounds it at "no worse than the incident" — but a few 4K transcodes could legitimately reach it | |
| 100 G | Only a catastrophe guard; catches less than a quota that catches a regression | |

**User's choice:** 50 G

### Q3 — Throttling as well as segment deletion?

| Option | Description | Selected |
|--------|-------------|----------|
| Both on — deletion + throttling | An abandoned stream stops growing rather than transcoding a whole film nobody is watching — the likely explanation for 19 GB with no ffmpeg running | ✓ |
| Segment deletion only | Fewer moving parts; throttling has a history of playback stalls on some clients | |
| You decide | | |

**User's choice:** Both on

### Q4 — Prove the bound, or is configuring enough?

| Option | Description | Selected |
|--------|-------------|----------|
| Prove it — play something, watch the dataset | Project standard is CONS-04; Phase 2 proved reading a setting back is not proof it fires | ✓ |
| Configured and asserted is enough | Faster on an insertion blocking Phase 3 — but is exactly the "configured setting is not a firing setting" trap | |
| You decide | | |

**User's choice:** Prove it

## Renovate pinning

> Raised by the operator mid-discussion: *"jellyfin is running a lot of new builds as it gets closer
> to the next major release, so pinning needs to be addressed."* Investigated during the session and
> treated as in-scope for durability, because an unreviewed release can silently revert this phase's
> controls. Broader estate-wide Renovate policy was kept out.

### Q1 — How should jellyfin/jellyfin be pinned?

| Option | Description | Selected |
|--------|-------------|----------|
| Treat minor as major: manual review on minor, patch still automerges | Matches how Jellyfin actually versions (10.MINOR is its major); mirrors the existing Mattermost and Immich rules | ✓ |
| Manual review for everything | Immich app-image treatment — but a steady stream of PRs to hand-merge, and Renovate backlogs are a documented failure here | |
| allowedVersions ceiling below 11.0 | Strongest guarantee — but rule 3 (the wrtag pin) is the cautionary tale | |

**User's choice:** Treat minor as major
**Notes:** Investigation found **no jellyfin rule at all** — it falls through to `packageRules[2]`
(minor automerge, `platformAutomerge: true`, `schedule: at any time`), while `packageRules[5]`
(manual review) fires only on major. Jellyfin has been on `10.` since 2019, so 10.9 (segment
deletion), 10.10 (lyric saving) and 10.11 (encoding rework) all present to Renovate as minor.

### Q2 — Fix the broken check-renovate.sh?

| Option | Description | Selected |
|--------|-------------|----------|
| Fix it — one line, and this phase adds a Renovate rule | A config error silently stops the whole repo run, which is what the validator exists to catch and currently cannot | ✓ |
| Record it, fix elsewhere | | |
| You decide | | |

**User's choice:** Fix it
**Notes:** `scripts/check-renovate.sh:22` tests for `renovate.json`; the repo has `renovate.json5`, so the validator `exit 1`s before checking anything.
