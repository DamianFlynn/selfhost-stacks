# Phase 02.1 Plan 10: Standing Coverage, Proven To Fail Closed — Summary

**The estate's routine health check now covers the thing that emptied `/`, and every one of its
fail-closed branches has been DRIVEN rather than read.** `scripts/quick-health-check.sh` gained a
third fatal block; six proofs were executed against it and against the check it calls; every test
that broke something restored it and verified the restore by sha256; and both repos' `scripts/` are
clean at the end.

**The two most useful things in this plan are both places where the plan was wrong.** The row-23
propagation test does not work by the mechanism the plan describes, and two of the task-2 acceptance
greps were already failing against the file before this plan touched it. Neither was massaged into
passing. That is the substance below, because the fold-in itself was a copy of a block that already
existed twice.

## What was proven

**The check fails closed on all four routes, and none of it was staged by mutating anything.**

|---|---|---|---|
| 1 — unroutable ZFS host | `ZFS_HOST=192.0.2.1` (RFC 5737) | **1** | quota and mounted are each their own red; summary reads `UNKNOWN` for both. **No** `!= 53687091200` mismatch, which a reader would parse as drift |

| — final unmodified run | none | **0** | FAILURES 0, transcript ends green |

Controls 1–3 are pure environment overrides. **Nothing was created, edited, moved, deleted, chmod'd,
chown'd, started or stopped**, and that is asserted rather than claimed: `jellyfin running healthy`,
host `scripts/` clean, the check script's sha256 unchanged, no `no-such-container-021` in
`docker ps -a`, and `/mnt/fast/secrets/jellyfin-deercrest.env` still `600 root`.

**Control 1's most informative line is a green one.** The container-side device-id instrument
(`stat -c %d`, which never reaches atlantis) kept answering while instrument 1's route was severed,
so the mounted state degraded from *asserted twice* to *asserted once, and the reader is told which
half is missing* — `zfs=UNKNOWN devid=47 parent=64519`. That is the entire reason VALIDATION row 36
specifies two instruments, and this is the first time the second one has been observed carrying the
assertion alone.

**Control 2 found no defect, which was not a foregone conclusion.** `docker inspect` on a missing
container produces empty output and the zero-volume-mounts test is literally `result == ""`, so an
absent container *could* have satisfied the phase's central invariant. The guard at
`check-jellyfin-transcode.sh:338-349` held: the three bind assertions were not printed at all, green
or red, and the summary said UNKNOWN.

**Control 3 was executable only because `JELLYFIN_SECRETS` is env-overridable** — the cross-AI
review's Plan-02 finding. Without it the control had two forms and both are wrong: skip it, or
chmod the real credential file and break an invariant `check-music-consumers.sh` asserts in order to
test this one.

**Row 24 — the anchor break — is the cleanest result in the plan.** The heading was renumbered

separately. The fold-in printed `⚠️ UNKNOWN — the audit exited 0 but its '📊 6. Summary' block was
not found` and exited 1, rather than the tick it would have printed before the WR-09 guard existed.
Restored, sha256 matched, re-run green.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug] The plan's row-23 mechanism is factually wrong, and the branch it wanted driven
was driven by a different means**

- **Found during:** Task 2, control 5
- **Issue:** The plan states *"The ssh returns non-zero with **empty output**, which drives the
  empty-output UNKNOWN branch."* It does not. The fold-in's redirection is
  `ssh host "bash /path/script 2>&1"` — the `2>&1` is **inside the remote command string**, so it
  captures the remote bash's own `No such file or directory`. Measured:
  output non-empty, `rc=127`, and the **BROKEN** branch fires.
- **What still holds:** row 23's actual claim. The remote failure propagates and
  `quick-health-check.sh` exits **1**, without any edit to that file — which was the review's whole
  point in rewriting the row.
- **Fix:** the empty-output branch was then driven by a mechanism that actually drives it — a
  **zero-byte** script at the same path. And that exposed the branch's most important property:
  a zero-byte script **exits 0**, so `TRANSCODE_RC` was `0` — a clean success — and the block still
  refused to print a tick, because `[ -z "$OUT" ]` is tested **before** the return code. Had the
  order been reversed, a silently truncated check would report green on a successful exit.
- **Not edited:** the plan text stands. Same handling 02.1-05 gave row 15 and 02.1-06 gave rows 11
  and 16.
- **Commit:** `4b5cffb`

**2. [Rule 1 — Bug] Two of task 2's acceptance greps are non-discriminating, and were already
failing before this plan touched the file**

- **Found during:** Task 2, first verification
- **Issue:** `grep -c 'bash -s'` must return 0 and `grep -c 'x1b'` must return 0. Measured against
  `git show HEAD:scripts/quick-health-check.sh` at the **parent commit**: **1** and **2**. The
  prohibitions are written down in the file — line 177 explains that the shape to avoid is `bash -s`
  plus a heredoc, and the ANSI-strip comments explain that `\x1b` is a GNU sed extension. A literal
  grep matches the notice explaining the prohibition, so a correctly-written file fails its own check.
- **Fix, and what was deliberately NOT done:** the explanatory comments were **not** deleted to make
  the greps pass — that would remove real documentation to satisfy a mechanical string test, which is
  the exact anti-pattern this phase has now documented four times. A **comment-stripped** substitute
  was used instead, the same device VALIDATION row 34 uses for the prune prohibition:
  `sed 's/#.*//' … | grep -c` returns **0** for both, against raw counts of 1 and 3. The control is
  discriminating rather than vacuous — the raw and stripped counts differ, so the strip is doing work.
- **Commit:** `4b5cffb`

**3. [Rule 3 — Blocking] The file's own notice convention was not greppable, so the third acceptance
grep was unsatisfiable without touching the second notice**

- **Honest count:** `grep -c` now returns **4** — three notice headers plus one occurrence inside
  that explanatory parenthetical. Recorded explicitly, because "prose mentioning the string satisfies

- **Commit:** `5ccc367`

The manual-only notice states the thing a reader is most likely to get wrong: **the fold-in closes

hours" half.** Scheduling is deferred with its reason named — Phase 2 closed with a mount-failure
notification that was never proven to deliver, and an unproven notification path is worse than a
known-manual check because it *feels* covered.

The API-key entry is recorded as an accepted residual risk stated as a **choice**, in the style of
02-09's `sec=sys` row: the key is administrator-equivalent **by Jellyfin's design**
(`CustomAuthenticationHandler.cs:53-57` maps any API key to `UserRoles.Administrator`, and 10.11 has
no scoped-key mechanism), it already existed and was already read by `check-music-consumers.sh`, and
**this phase widened its use to write** against `/System/Configuration/encoding`. Nothing to
implement; what changes is the documented cost of a leak.

`PROJECT.md` gained **three short entries, 3 insertions and 0 deletions** — an addition, not a
transplanted section. Both reviewers flagged the reviewed plan for pushing all three limits into a
document already around 240 lines.

## What is NOT covered — the honest list

Recorded in full in `artifacts/02.1-10-negative-controls.txt`, in four groups. The headlines:

**Six defective assertions in this phase's own contract**, all left failing rather than edited,
because this plan verifies against the plan text and editing it would destroy the evidence:
VALIDATION rows **15** (unsatisfiable — `ThrottleDelaySeconds` was already 180), **11** (errno pair
inverted: a ZFS `quota` refusal is **EDQUOT**, not ENOSPC), **16** (ceiling omits the
`ThrottleDelaySeconds` forward buffer), **33** (near-vacuous), 02.1-06's own task-3 `<verify>`, and
two of this plan's task-2 greps. **Five of the six are the same shape** — a mechanical check
satisfied or defeated by *prose about* the thing rather than by the thing. This phase now carries the
workaround in four separate places.

**Five factual errors in plan text**, found and not edited — including that the plan's *inference*
from the errno finding was also wrong: 02.1-03 chose the **right** ZFS property, and it is the
research's errno mapping that is incorrect.

**Seven open items worth doing.** The load-bearing ones:

1. **The estate's ENOSPC-keyed log greps are blind to a transcode-quota refusal.** Worse than
   described: **both** `quota` and `refquota` return EDQUOT, so no choice of property produces a
   match. Adding the quota-exceeded string to those greps would fix it; switching property would not.
2. **`renovate.json5` is UNVALIDATED.** `renovate-config-validator` is not installed. 02.1-08 proved
   syntax and shape, not semantic validity — and in this repo a single bad key has silently jammed
   the entire Renovate run while everything looked idle.
3. **`check-renovate.sh` has three latent `set -e` aborts (115/138/157), and line 157 is INVERTED** —
   it aborts when there are **zero** pending Renovate PRs, i.e. exactly when the estate is healthy,
   which also makes its own "no pending PRs" branch unreachable. Hidden today only because 27
   branches are open. Remedy is `|| true` ×3.
4. **The Jellyfin Renovate rule has never been observed refusing anything** — discharged by
   construction, and the observation cannot be manufactured.
5. `do_inventory` enumerates without `-a`, hiding nine untagged images.
6. Two dangling 0-byte anonymous volumes from the 02.1-05 recreate remain, inventory-only.
7. Nine dangling images remain after the reap, in scope by design.

**Three instrument traps to carry forward:** `docker system df` RECLAIMABLE has now misled in **both
directions**; `docker run --rm <img>` is a **pull** when the image is absent; and a log-reading
instrument must assert **log-level liveness at grep time**.

**On that last one — does the coverage added here inherit the hazard? Asserted, not assumed: no.**
Neither `check-jellyfin-transcode.sh` nor the fold-in reads a log. The check's evidence is `df`,
`docker inspect`, `stat -c %d`, `zfs get` over ssh and one HTTP GET — every one a direct query whose
failure is distinguishable from an empty result, which is why all six sections have explicit UNKNOWN
paths. The fold-in reads the check's own stdout and treats *both* "nothing came back" and "the anchor
is missing" as UNKNOWN, and **both branches were driven on purpose**. The hazard is recorded anyway,
because the next thing folded in may well read a log.

**And what real playback did and did not prove.** The operator watched a full episode at ~22:20–22:40Z
on 2026-09-02, after the cutover. It **direct-played**: zero segments, zero ffmpeg, zero bytes on `/`.
That is real evidence the cutover does not break playback. It is **not** transcode evidence — an empty
`/mnt/fast/transcode` after a direct-play session is the *absence of a test*. The firing proofs come
from 02.1-06's two driven sessions.
