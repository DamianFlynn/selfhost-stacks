## Summary

Three of the four things this review was asked to be suspicious of came back **clean**, and I
verified them mechanically rather than by reading the comments that assert them (see *Verified
Sound* below). The `EXPECT_*` overrides genuinely cannot disable an assertion. `02.1-12` genuinely

expired/not-expired bound.

The fourth — "unbounded ssh sites that were missed" — is where the defects are, and one of them is
this phase's own named central failure mode.

**The blocker:** `02.1-13` bounded seven legacy remote commands by prefixing `timeout N` inside a
**pipeline** whose second stage is `wc -l`. `timeout` kills the first stage; `wc -l` still runs and
still prints `0`; the pipeline exits `0`. I confirmed this against real coreutils `timeout`

`quick-health-check.sh:267` is that a wedged or slow dockerd produces **`✅ No unhealthy
containers`** with `EXIT_CODE` untouched — a green tick printed while blind, which is precisely
what this phase exists to stop. The guard immediately below it (line 268, "a non-numeric result
here is still UNKNOWN rather than zero") cannot fire for the docker-wedge case its own comment
names, because `wc -l` guarantees a number.

The rest are real but lesser: an unbounded-hang window that survives `02.1-13` at the two probes it
deliberately exempted (with a stated justification that is factually wrong about what
`ConnectTimeout` covers), a `transcode target` token coupling whose detector only catches total

There is no credential by value in any of the three files. `02.1-12`'s reachability correction is

## Critical Issues

### CR-01: `timeout N cmd | wc -l` renders a bound expiry as `0`, printing `✅ No unhealthy containers` while blind — BLOCKER

**File:** `scripts/quick-health-check.sh:267-277` (primary), `scripts/quick-health-check.sh:261-262` (same defect, informational blast radius)

**Issue:**

Line 267 is:

```bash
UNHEALTHY=$(ssh $SSH_OPTS root@172.16.1.159 "timeout $REMOTE_TIMEOUT docker ps --format '{{.Names}}' --filter health=unhealthy | wc -l" | tr -d ' ')
```

`timeout` binds to `docker ps` only. When the bound expires, `docker ps` is killed having emitted
nothing, `wc -l` runs on the empty stream and prints `0`, and the **pipeline's** exit status is
`wc`'s, i.e. `0`. `ssh` therefore returns `0` and `UNHEALTHY="0"`.

Verified against real coreutils `timeout` on this workstation:

```
$ gtimeout 1 sh -c 'sleep 5; echo hi' | wc -l ; echo "rc=$?"
0
rc=0
$ gtimeout 1 sh -c 'sleep 5' ; echo "rc=$?"      # no pipe, for contrast
rc=124
```

Control flow that follows:

- line 268 `if ! echo "$UNHEALTHY" | grep -qE '^[0-9]+$'` — `0` **is** numeric, so the UNKNOWN
  branch is skipped;
- line 272 `elif [ "$UNHEALTHY" -gt 0 ]` — false;
- line 276 prints **`✅ No unhealthy containers`** and leaves `EXIT_CODE` at `0`.

The comment at lines 264-266 states the intent exactly — *"dockerd can still be wedged behind the
amdgpu mmap_lock while sshd is fine (that is exactly the Aug 31 signature), so a non-numeric result
here is still UNKNOWN rather than zero"* — and the code cannot deliver it. With `| wc -l` on the
remote side the result is **always** numeric. The only way the guard fires is if `ssh`'s stdout is
empty, i.e. transport failure, and the probe at line 211 already exits on that. The guard is
effectively dead code for the failure mode it names.

**Failure scenario (green tick, exit 0, wrong answer):** `docker ps --filter health=unhealthy` on
this 78+-container host exceeds `REMOTE_TIMEOUT` (degraded dockerd, slow disk, a container whose
health probe is hung) while the three folded-in audits happen to complete inside their own bounds.
The transcript reads `✅ No unhealthy containers`, `EXIT_CODE` stays 0, and the script exits 0 —
green, on a host with unhealthy containers, having never looked.

**Secondary instance, same root, line 261:** `RUNNING=$(... "timeout $T docker ps -q | wc -l" ...)`
prints **`Containers running: 0`** on a bound expiry. This one is reported rather than asserted so
it does not affect the exit code, but it is misinformation on the transcript of exactly the kind
the WR-10 comment at lines 153-168 was written to eliminate (*"a confident and WRONG diagnosis
rather than UNKNOWN"*).

**Note on attribution:** the `| wc -l` shape predates `02.1-13` — before the change, a `docker ps`
that *failed* (daemon down) already produced `0` here. What `02.1-13` did was add a **new and
likely** route into it (bound expiry) while adding a comment claiming the case is handled. Both
halves need fixing.

**Fix:** capture the remote exit status instead of letting `wc` launder it, and count locally so
the empty stream stays distinguishable from a zero count:

```bash
# Count containers — status captured before any pipe, count done locally so that an empty
# stream (killed by the bound / failed docker) can never be laundered into "0" by `wc -l`.
RUNNING_RAW=$(ssh -n $SSH_OPTS root@172.16.1.159 "timeout $REMOTE_TIMEOUT docker ps -q")
RUNNING_RC=$?
if [ "$RUNNING_RC" -eq 124 ]; then
    echo "⚠️  UNKNOWN — 'docker ps' exceeded its ${REMOTE_TIMEOUT}s bound. NOT 'zero containers'."
    EXIT_CODE=1
elif [ "$RUNNING_RC" -ne 0 ]; then
    echo "⚠️  UNKNOWN — 'docker ps' failed (exit $RUNNING_RC). NOT 'zero containers'."
    EXIT_CODE=1
else
    echo "Containers running: $(printf '%s\n' "$RUNNING_RAW" | grep -c . )"
fi

UNHEALTHY_RAW=$(ssh -n $SSH_OPTS root@172.16.1.159 \
    "timeout $REMOTE_TIMEOUT docker ps --format '{{.Names}}' --filter health=unhealthy")
UNHEALTHY_RC=$?
if [ "$UNHEALTHY_RC" -eq 124 ]; then
    echo "⚠️  UNKNOWN — the unhealthy-container query exceeded its ${REMOTE_TIMEOUT}s bound."
    echo "  dockerd may be wedged. This is NOT 'no unhealthy containers'."
    EXIT_CODE=1
elif [ "$UNHEALTHY_RC" -ne 0 ]; then
    echo "⚠️  UNKNOWN — could not query unhealthy containers (exit $UNHEALTHY_RC)."
    echo "  This is NOT 'no unhealthy containers'."
    EXIT_CODE=1
elif [ -n "$UNHEALTHY_RAW" ]; then
    echo "⚠️  Unhealthy containers: $(printf '%s\n' "$UNHEALTHY_RAW" | grep -c .)"
    printf '%s\n' "$UNHEALTHY_RAW" | sed 's/^/    /'
else
    echo "✅ No unhealthy containers"
fi
```

Note this also removes the second `ssh` at line 274 (it re-queried the same thing) and adds `-n`,
per IN-03.

## Warnings

### WR-01: the two exempted probes are genuinely unbounded, and the stated justification for exempting them is factually wrong

**File:** `scripts/quick-health-check.sh:206-232`

**Issue:** The comment at lines 206-210 exempts both probes with:

> *"`true` and `command -v` are shell builtins that return immediately or not at all, and the
> not-at-all case is a dead transport, which ConnectTimeout above does cover."*

`ConnectTimeout` bounds the **TCP connect** (and, in some OpenSSH versions, the banner exchange).
It does not bound authentication, session setup, PAM, or the fork of the remote shell. A host that
completes the TCP handshake but cannot fork a shell — PID exhaustion, memory pressure, a full `/`
(which is *the incident this phase exists to fix*), the 2026-08-31 amdgpu signature where the box
was up and pingable for ~6 hours while services died — will leave both `ssh` invocations hanging
indefinitely with no local wall-clock bound.

So the unbounded-hang failure mode that `02.1-13` exists to eliminate survives at exactly the two
call sites `02.1-13` exempted. The same hole exists in miniature at all ten bounded sites too:
`timeout` cannot start until the remote shell has been forked, so the pre-`timeout` window is
unbounded everywhere.

I am rating this WARNING rather than BLOCKER because the *dominant documented* cause (wedged
dockerd, transport and sshd healthy, shell forks fine) **is** covered by the change — this is a
residual window, not a no-op. But the in-file justification should not be left standing as written,
because a future reader will trust it.

**Fix:** bound the probes in pure bash (no local `timeout` needed, so the macOS constraint is
respected):

```bash
# Bound an ssh with a pure-bash watchdog: the workstation is macOS and has no coreutils `timeout`,
# and ConnectTimeout does NOT cover session setup — only the TCP connect.
bounded_ssh() {
    local secs="$1"; shift
    "$@" & local p=$!
    ( sleep "$secs"; kill -TERM "$p" 2>/dev/null ) & local w=$!
    wait "$p"; local rc=$?
    kill -TERM "$w" 2>/dev/null; wait "$w" 2>/dev/null
    return $rc
}
if ! bounded_ssh 20 ssh $SSH_OPTS root@172.16.1.159 true 2>/dev/null; then ...
```

and correct the comment at 206-210 to say what `ConnectTimeout` actually covers.

### WR-03: `|| echo 'no healthcheck'` converts a bound expiry into a benign-looking health string

**File:** `scripts/quick-health-check.sh:246`

**Issue:**

```bash
STATUS=$(ssh $SSH_OPTS root@172.16.1.159 "timeout $REMOTE_TIMEOUT docker inspect traefik --format='{{.State.Health.Status}}' 2>/dev/null || echo 'no healthcheck'")
```

`timeout` exits 125/124 on expiry, `2>/dev/null` swallows its diagnostic, and the `||` fires,
producing `Health: no healthcheck`. A hung `docker inspect` is rendered as a benign, expected
configuration fact. Reported-only, so no exit-code impact — but it is transcript misinformation on
the exact scenario the bound was added for.

**Fix:** distinguish the statuses rather than collapsing every non-zero into one string:

```bash
STATUS=$(ssh -n $SSH_OPTS root@172.16.1.159 \
    "timeout $REMOTE_TIMEOUT docker inspect traefik --format='{{.State.Health.Status}}' 2>/dev/null")
case $? in
  0)   echo "  Health: ${STATUS:-no healthcheck}" ;;
  124) echo "  Health: ⚠️  UNKNOWN — inspect exceeded its ${REMOTE_TIMEOUT}s bound"; EXIT_CODE=1 ;;
  *)   echo "  Health: no healthcheck (or inspect failed)" ;;
esac
```

### WR-04: `REMOTE_TIMEOUT` is interpolated unvalidated into ten remote shell command strings

**File:** `scripts/quick-health-check.sh:202`, consumed at 243, 246, 254, 261, 267, 274, 281, 299, 375, 456

**Issue:** `REMOTE_TIMEOUT="${REMOTE_TIMEOUT:-120}"` is never checked to be a number and is then
spliced unquoted into strings executed by a remote shell as root:

```bash
ssh ... "timeout $REMOTE_TIMEOUT docker ps ..."
```

Two consequences:

1. **Metacharacter injection.** `REMOTE_TIMEOUT='1; rm -rf /mnt/fast/transcode'` executes on LXC
   100 as root. This is *self*-injection — the person setting the variable already has the ssh key
   — so it is not a privilege boundary crossing and I am not rating it Critical. It matters
   because this is a public repo whose scripts get copy-pasted into wrappers and CI, where the
   variable may stop being operator-controlled.
2. **Fail-closed but mislabelled on a typo.** `REMOTE_TIMEOUT=5m` is accepted by coreutils
   `timeout`, but `REMOTE_TIMEOUT="5 m"` or `REMOTE_TIMEOUT=abc` yields exit 125, which lands in
   the generic `❌ BROKEN (check-... exit 125)` branch and reads as *"the check failed an
   assertion"* — the exact conflation the 124 branch was added to prevent.

**Fix:** validate once, next to the assignment:

```bash
REMOTE_TIMEOUT="${REMOTE_TIMEOUT:-120}"
case "$REMOTE_TIMEOUT" in
  ''|*[!0-9]*)
    echo "REMOTE_TIMEOUT must be a whole number of seconds; got '$REMOTE_TIMEOUT'" >&2
    exit 2 ;;
esac
```

### WR-05: the `transcode target` token coupling has no per-token detector — only a total-anchor-loss detector

**File:** `scripts/quick-health-check.sh:513-523`; contract comment at `scripts/quick-health-check.sh:511-512` and `scripts/check-jellyfin-transcode.sh:730-745`

**Issue:** The coupling is **correct today** — `check-jellyfin-transcode.sh:756` emits
`  transcode target:        ...` and the selector at line 514 includes `transcode target`. I
verified all nine tokens against what section 6 actually emits and they all match.

The defect is that the coupling cannot detect its own partial breakage. `grep -E 'a|b|c'` returns 0
if **any** alternative matches. If someone renames `transcode target` in the emitting script, the
other eight tokens still match, `SUMMARY` is still non-empty, the `[ -z "$SUMMARY" ]` guard at 515
does not fire, and the script prints `✅ Transcode retention intact` with the transcode-target line
silently gone. That is the same failure shape as the CR-01 defect this fold-in was fixing (a value
neither asserted nor displayed on the tick branch), at reduced blast radius.

The comment at 511-512 states the requirement precisely — *"The alternation below must equal the
token set that check-jellyfin-transcode.sh's section 6 actually emits; a token that selects nothing
looks exactly like a check with nothing to say"* — and then relies on a human to maintain it. The
file's own doctrine ("a documented coupling with no detector is a coupling that will break") applies
to itself here.

**Mitigating fact, stated so this is not over-read:** post-`02.1-11`, a *drifted*
`TranscodingTempPath` makes the remote script exit 1, so the operator lands in the `❌ BROKEN`
branch regardless of the selector. The selector is now display, not gate. That is why this is
WARNING and not BLOCKER.

**Fix:** make the token set data, and assert each one individually:

```bash
TRANSCODE_TOKENS=( '/ headroom' 'volume mounts' 'transcode quota' 'transcode mounted' \
                   'transcode target' 'encoding values' 'unreachable' 'toolchain missing' \
                   'FAILURES total' )
BODY=$(echo "$TRANSCODE_OUT" | sed -n '/^📊 6\. Summary/,$p')
MISSING=()
for tok in "${TRANSCODE_TOKENS[@]}"; do
    printf '%s\n' "$BODY" | grep -qF "$tok" || MISSING+=("$tok")
done
if [ "${#MISSING[@]}" -gt 0 ]; then
    echo "⚠️  UNKNOWN — the audit exited 0 but these summary tokens were not emitted:"
    printf '    %s\n' "${MISSING[@]}"
    echo "  The cross-file token contract has drifted. State is UNKNOWN, not green."
    EXIT_CODE=1
else
    echo "✅ Transcode retention intact"
    printf '%s\n' "$BODY" | grep -F -f <(printf '%s\n' "${TRANSCODE_TOKENS[@]}") | sed 's/^/  /'
fi
```

The same applies to the freeze block (346-347) and consumers block (407-408), which have the
identical OR-alternation shape.

### WR-06: `timeout` is used without `-k`, so it cannot guarantee termination on the very wedge it was added for

**File:** `scripts/quick-health-check.sh:243, 246, 254, 261, 267, 274, 281, 299, 375, 456`

**Issue:** coreutils `timeout` sends `SIGTERM` on expiry and then **waits for the child**. Without
`-k DURATION` there is no follow-up `SIGKILL`. A process blocked in an uninterruptible kernel
operation (`D` state) does not act on a pending `SIGTERM` until the syscall returns, and `timeout`
blocks with it. The estate's documented amdgpu incident is characterised in this very file (lines
332-336, 487-491) as dockerd blocked on `/proc/*/smaps` behind a dead `mmap_lock`.

**Honest scoping:** the process `timeout` actually kills here is the `docker` *client* (or `bash`),
which blocks on an interruptible unix-socket read — `S` state, `SIGTERM` works. So the primary
documented scenario is covered. This is hardening against the adjacent case (a remote script
touching `/proc`, or a `bash` with a signal-deferring foreground child), and it costs one flag.

I also confirmed the concern I initially had about orphaned grandchildren holding the ssh channel's
stdout open past the kill is **not** a problem: coreutils `timeout` places the child in its own
process group and signals the whole group by default, so grandchildren die with it. Measured, not
assumed.

**Fix:** `timeout -k 10 $REMOTE_TIMEOUT ...` at all ten sites; update the `WHY 120 s` comment at
196-201 to name the kill grace.

### WR-07: `TTP_VALUE=""` is used as the "did not look" sentinel, but empty string is a legitimate API value

**File:** `scripts/check-jellyfin-transcode.sh:265-271` (comment and initialisation), `scripts/check-jellyfin-transcode.sh:756` (consumer)

**Issue:** Line 268 asserts:

> *"TTP_VALUE likewise: the empty string means 'did not look', never 'the path is empty'."*

`enc_val` renders a JSON `""` as the empty string (`.[$k]|tostring` of `""` is `""`), and an empty
`TranscodingTempPath` is Jellyfin's own "use the built-in default" sentinel — the value you get if
the field is cleared in the admin UI, which is exactly the drift this assertion exists to catch.
Line 756 then does `${TTP_VALUE:-UNKNOWN}` and prints **`transcode target: UNKNOWN`** for a value
that was read successfully.

The gate itself is unaffected — `assert_enc` compares `"" != "/cache/transcodes"` and goes red — so
this is a rendering defect, not a false green. But it is the "could not look" / "the value moved"
conflation this file is built to refuse, in the one summary line `02.1-11` added specifically so a
drifted target would be legible.

Note the script already computes the correct discriminator two lines later and uses it for the
neighbouring row: `ENC_ASSERTED -eq 0` means "section 5 never ran". The target line does not use it.

**Fix:**

```bash
TTP_VALUE="UNKNOWN"    # sentinel that cannot collide with any value the API can return
...
echo "  transcode target:        ${TTP_VALUE}  (target $EXPECT_TRANSCODING_TEMP_PATH)"
```

and correct the comment at 265-271.

### WR-08: `assert_enc` has no sentinel guard, so an `EXPECT_*` override *can* turn "could not look" into a pass

**File:** `scripts/check-jellyfin-transcode.sh:219-223` (the claim), `scripts/check-jellyfin-transcode.sh:626-643` (`assert_enc`)

**Issue:** I verified the main concern and it is **clean**: all five expectations use `${VAR:-default}`,
so `EXPECT_SEGMENT_KEEP_SECONDS=` (empty) falls back to `300` rather than producing a vacuously
true comparison, and the `[[ "$got" == "$want" ]]` RHS is quoted so it is a literal comparison, not
a glob (confirmed by test: `want='*'` does **not** match). An empty or unset override cannot
disable an assertion.

What is not clean is the absolute form of the claim at 219-223:

> *"There is no value of these five variables that suppresses an assertion, skips a key, or turns a
> mismatch into a pass"*

`enc_val` returns three reserved sentinel strings — `<absent>`, `null`, `<unparsed>`. Setting e.g.
`EXPECT_TRANSCODING_TEMP_PATH='<absent>'` makes a *missing key* compare equal and print
`✅ ... NOT DRIFTED`; `'<unparsed>'` does the same for a jq failure. That is a could-not-look
rendered as green — the one outcome this file exists to refuse — reachable through the documented
override mechanism.

This requires deliberate misuse, so it is a hardening item rather than an exploit. It earns a
WARNING because the sentinel/value distinction is the load-bearing invariant of `enc_val` (the
comment at 674-691 spends 18 lines on it) and `assert_enc` does not honour it, and because the
absolute claim will stop a future reader from adding the guard.

**Fix:** refuse a sentinel expectation at the top of `assert_enc`:

```bash
assert_enc() {
  local key="$1" want="$2" got
  case "$want" in
    '<absent>'|'null'|'<unparsed>')
      ENC_ASSERTED=$((ENC_ASSERTED + 1)); ENC_DRIFTED=$((ENC_DRIFTED + 1))
      fail "$key expectation '$want' is an enc_val SENTINEL, not a value — refusing to compare."
      echo "         A sentinel expectation would turn 'could not look' into a green tick."
      return ;;
  esac
  ...
```

and soften 219-223 to name the one exception now that it is guarded.

### IN-01: dead assignment before `exit`
