# Phase 02.1 Plan 13: Bound every remote command in the health check Summary

Put a `REMOTE_TIMEOUT` wall-clock bound on all ten remote commands in `quick-health-check.sh`,
enforced by coreutils `timeout` **on LXC 100** so it works from a macOS workstation with no new
dependency, gave a timed-out command its own UNKNOWN branch distinct from `❌ BROKEN`, and drove
it against a real 30-second sleeping remote script — the script returned in 8s with exit 1 instead
of hanging, then returned green at the same budget once the real script was restored.

## Why this plan existed at all

`SSH_OPTS` carried `ConnectTimeout=10`, which is easy to mistake for a bound on the whole call and
is not one. A wedged dockerd **accepts the connection instantly and then never returns** — this
estate's documented 2026-08-31 amdgpu signature, where `dockerd` blocked reading `/proc/*/smaps`
behind a dead `mmap_lock`. The health check would have sat there indefinitely: no tick, no red, no
exit.

The coupling that made it worth closing now: **02.1-11's fix has no value unless the check
terminates.** A check that never *returns* produces not even a transcript to disbelieve, which is
strictly worse than the false green CR-01 described.

## What was done

**Task 1 — the bound (commit `10be13a`).** One file, `scripts/quick-health-check.sh`.

- `REMOTE_TIMEOUT="${REMOTE_TIMEOUT:-120}"`, defined once in overridable form.
- A comment block stating the three things a reader gets wrong: `ConnectTimeout` bounds the connect
  only; `ServerAliveInterval`/`ServerAliveCountMax` do not help because **sshd answers keepalives
  happily while the command it spawned is blocked** — the transport is healthy, the command is not;
  and therefore the bound goes on the remote side, with an explicit cross-reference to
  `disable-jellyfin-hwaccel.sh:172` explaining that *that* script wraps locally because it runs on
  Linux. The asymmetry is documented so it does not get "corrected" later.
- A second one-shot probe (`command -v timeout`) beside the WR-10 reachability gate. Absent binary
  → an UNKNOWN-shaped refusal, `EXIT_CODE=1`, exit. Nothing is fetched.
- Ten remote command strings prefixed. On piped remotes the prefix binds to the first command,
  which is exactly the one that can hang (`docker` talks to the daemon; `grep`/`wc` are local to
  the remote shell) — stated in-band at the first such site so it does not read as a quoting slip.
- Three exit-124 branches, one per fold-in, naming the budget, the likely cause and the
  distinguishing diagnostic (`/proc/pressure/io` `full` near 100% **with an idle CPU**).
- The third header notice extended with a seventh EXIT-1 condition.

**Task 2 — the driven control (commit `8259f96`).** Transcript at

## The numbers the plan asked to be recorded

**Bounded-call count vs ssh-call count, raw:**

| Count | Value |
|---|---|
| `grep -c 'ssh .*root@172\.16\.1\.159'` raw, pre-edit | 14 |
| `grep -c 'ssh .*root@172\.16\.1\.159'` raw, post-edit | **15** |
| real ssh call sites (raw minus 3 `echo` re-run hints) | **12** |
| deliberately unbounded probes (`true`, `command -v timeout`) | 2 |
| `grep -c 'timeout $REMOTE_TIMEOUT'` | **10** |

12 − 2 = 10. Balances. The plan's own form of this criterion (raw − 2) gives 15 − 2 = 13 and does
not balance; see "Things the plan text got wrong" below.

**Wall clock — the driven hang and the healthy run at the short budget:**

| Run | Budget | Wall clock | Exit |
|---|---|---|---|
| driven against a `sleep 30` stub | `REMOTE_TIMEOUT=5` | **8 s** | **1** |
| healthy, real script restored | `REMOTE_TIMEOUT=5` | **4 s** | 0 |
| healthy, default | 120 s | **4 s** | 0 |
| healthy, unqualified final | 120 s | 4 s | 0 |

**The second number is the headroom figure and nothing in this repo previously recorded it.** A
whole healthy run — all ten bounded calls including three fold-ins — is **4 s** (4.362 s by
`time`). The slowest single remote call therefore passes at a 5 s budget. The 120 s default is
**~30x the observed worst case**: generous enough that a slow-but-working estate is never cut off
(the 01-09 permanently-red trap), short enough that a wedge is caught in the same sitting.

The driven run took 8 s rather than 5 s because the seven ad-hoc docker calls and two healthy
fold-ins ahead of the transcode block cost ~3 s between them; the transcode call itself was cut at
5 s.

## Why the bound is remote-side and not `timeout ssh …`

Recorded here as well as in the file, because it is the first question a reader will ask.

`scripts/disable-jellyfin-hwaccel.sh:172,234` wraps its ssh calls as `timeout 15 ssh …`. That
script **runs on Linux** and can bound locally. `quick-health-check.sh` runs on the **macOS
workstation**, which does not ship coreutils `timeout` at all — Homebrew's coreutils provides it as
`gtimeout` — so a workstation-side wrapper would be an undeclared dependency that fails on the one
machine this file is meant to be typed on. LXC 100 is Linux and has it (`/usr/bin/timeout`,
verified), so the bound executes there, inside the command string. The pattern is **adapted, not
copied**, and both scripts now say so.

`ServerAliveInterval` was considered and rejected on the merits, not overlooked: it measures the
transport, and the transport is fine. It would have kept the script alive rather than ended it.

## Deviations from Plan

### [Rule 1 — Bug] The plan's 124 branch placement would have been unreachable on the very case it exists for

**Found during:** Task 1(e).
**Issue:** The plan says to insert the 124 branch before `elif [ "$RC" -eq 0 ]` while the
`[ -z "$OUT" ]` empty-output test "must stay first". Both are individually right and together they
are broken: **a command killed by `timeout` usually produces no output** — the `sleep 30` stub the
plan itself specifies produces none — so on a real hang both conditions are true and an unmodified
empty test wins. Implemented literally, the driven control would have printed
`⚠️ UNKNOWN — 172.16.1.159 unreachable or the audit produced no output` for a host that answered
ssh perfectly, failing the plan's own task-2 criterion and reintroducing the exact "could not look"
vs "the value moved" conflation this plan exists to remove, merely relocated.
**Fix:** the empty test stays textually and logically first and gains one qualification — it defers
when, and only when, the remote status was 124: `if [ -z "$X_OUT" ] && [ "$X_RC" -ne 124 ]`.
**02.1-10's finding is fully preserved:** a zero-byte remote script exits 0, not 124, so it still
lands in the empty branch. Verified live — the `unreachable` string appears 0 times in the driven
transcript.
**Files modified:** `scripts/quick-health-check.sh`. **Commit:** `10be13a`.

### [Rule 3 — Blocking] The plan's "deliver first" step is not executable under worktree isolation

**Found during:** Task 2. Same root cause 02.1-11 recorded.
**Issue:** The plan asks for commit → push → `git pull --ff-only` on LXC 100 → assert host-side
`HEAD == origin/main`. This ran as a **parallel worktree agent** on branch
`worktree-agent-ac91560e4fc8f1a76`; the orchestrator merges after the wave, and pushing to main
from the worktree would bypass that merge.
**Fix / why it is moot here anyway:** 02.1-11 amended a **host-resident** script, so delivery was
load-bearing for its controls. **02.1-13 amends only `quick-health-check.sh`, which is
workstation-resident and executes on the workstation** — the copy under test *is* the copy in the
worktree, and the control ran it directly. Host state was recorded regardless (HEAD `780ada8` ==
`origin/main`, `scripts/` clean, before and after) because a divergent host tree has bitten this
phase before.
**Consequence, stated so nobody overreads the artifact:** these runs prove the bound works in the
committed copy. They prove nothing about a bounded `quick-health-check.sh` *on LXC 100* — that copy
is not the one anybody executes and is not this plan's payload.

2. **The bounded-call count criterion does not balance.** `raw ssh count − 2 == bound count` gives
   15 − 2 = 13 against 10 bounds. The gap is three `echo` lines that *print* a suggested
   `ssh root@172.16.1.159 'cd /mnt/fast/stacks && …'` re-run hint to the reader. They are
   remediation text, not call sites. Raw (15) and corrected (12) are both recorded so the
   subtraction is checkable.
3. **`grep -c 'apt\|apt-get\|install'` cannot return 0 on this file and never could.** It returns

   pipe before capturing this`, repeated at three call sites. It is a substring match with no word
   boundary. The claim it was reaching for, tested properly:
   `grep -cE '(^|[^[:alnum:]])(apt|apt-get|pip|npm|install)([^[:alnum:]]|$)'` → **0**.
4. **The plan's line numbers are all stale**, citing 143/156/159/167/174/180/187/194/211/257/308.
   The file has since been rewritten by 02.1-11 and 02.1-12; the real sites are
