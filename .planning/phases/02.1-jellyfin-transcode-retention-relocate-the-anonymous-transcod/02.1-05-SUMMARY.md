# Phase 02.1 Plan 05: The Cutover — Summary

**At 2026-09-02T22:19:52Z Jellyfin stopped writing its cache to `/`.** The container was recreated
onto the binds 02.1-04 declared, and every cache byte since lands on `fast/appdata/media` while
every transcode byte lands on the 50 G quota-bounded `fast/transcode`. Then its own retention
levers went on — segment deletion, throttling, and a transcode path that finally points at the
bounded dataset — through a full-object-replace API that would have silently re-armed a six-hour
outage if the write had been done carelessly. It was not.

**What this plan did NOT do: reclaim anything.** The 12.55 GiB is still sitting on `/` in the
anonymous volume, deliberately, because that volume is the rollback and D-10 keeps it until the
thing it protects is proven. It is proven now. 02.1-06 may delete it.

## What was built

**The mount shape is real, not declared.** Deleting a mount line from a yaml file does not remove
the mount from a running container — that is the entire reason this plan exists separately from
02.1-04. All four mount rows pass on the *runtime*: zero `Type: volume` mounts (asserted as D-18's
invariant, not as the absence of one id), `/cache/transcodes` → `bind /mnt/fast/transcode`, `/cache`
→ `bind /mnt/fast/appdata/media/jellyfin/cache`, and `/data/transcode` in no destination at all. The
container was proven to exist *before* any of them were enumerated — without that, "Jellyfin has zero
volume mounts" and "Jellyfin does not exist" are the same output.

**Assumption A4 is CONFIRMED, by probe rather than by reading the sort.** A uniquely named file
written into `/cache/transcodes` from *inside* the container appeared at `/mnt/fast/transcode/` on
the host and did **not** appear under the cache bind. Both halves matter: present at the nested
source proves the bind is live, absent under the parent proves it is the *nested* bind and not the
parent absorbing the write.

**An unplanned and stronger piece of evidence turned up in the same section.** The dataset was empty
before the recreate and holds exactly one entry after it: `/mnt/fast/transcode/.jellyfin-transcode`,
written at 22:20Z. That is *Jellyfin's own marker*, from `CreateAndCheckMarker`. The server — not
just the daemon — resolves its transcode path onto `fast/transcode`, and it did so before task 2 set
`TranscodingTempPath`, because Jellyfin's default is already `<cache>/transcodes`. It also proves the
start-refusal guard did not fire.

**The ZFS bound did not notice the container being destroyed and rebuilt.** Rows 10 and 36 re-read
from atlantis at 22:21:42Z, one minute fifty after the container Started: `quota=53687091200`,
`mounted=yes`, plus the container-side second instrument (`stat -c %d` = 47 vs `/mnt/fast`'s 64519).
This is exactly why D-12 makes the ZFS property load-bearing rather than an application setting — a
Jellyfin setting would have had to be re-asserted; a ZFS property did not.

**The five retention settings are live and the amdgpu mitigation survived.** `POST
/System/Configuration/encoding` returned 204. `TranscodingTempPath` = `/cache/transcodes`,
`EnableSegmentDeletion` = true, `SegmentKeepSeconds` 720 → 300, `EnableThrottling` = true,
`ThrottleDelaySeconds` = 180. `HardwareAccelerationType` still `none` and `EnableHardwareEncoding`
still `false` — asserted against both the captured pre-write values and the literals. Its constructor
default is `true`, so a partial POST would have silently re-armed the amdgpu HMM hazard that cost the
estate roughly six hours on 2026-08-31. No restart occurred; `StartedAt` is byte-identical either
side of the write.

**Jellyfin is serving, not merely `running`.** `GET /System/Info/Public` returned 200 with
`StartupWizardCompleted: true`, addressed the only correct way — via `docker inspect` on the
`t3_proxy` network, never an IP literal, never the bare name (which resolves to Cloudflare's public
edge from LXC 100 and would return 200 from the *website* with the container down). No errors in the
log, restart count 0.

**The standing check went 5 failures → 1.** The single red is section 3, "the anonymous volume STILL
EXISTS", and it is supposed to be red here. A green section 3 at this point would mean the rollback
had been destroyed before the cutover was proven.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing] The recreate could have taken the rollback with it, and nothing prevented it**

- **Found during:** Task 1, before the recreate
- **Issue:** The plan's acceptance criteria require the anonymous volume to still exist when the plan
  ends, and D-10 makes that ordering non-negotiable — the volume is the fallback copy of the cache.
  But nothing in the plan *prevents* its loss. Whether `docker compose up -d --force-recreate` passes
  `RemoveVolumes` when it removes the old container is undocumented for compose v5.0.2, and compose
  *does* have anonymous-volume inherit logic that behaves differently once a destination gains an
  explicit bind — which is exactly the transition this plan performs. Discovering the answer
  empirically means discovering it by losing the rollback.
- **Fix:** Docker refuses to remove a volume any container references. A single **stopped** holder
  container (`jf-oldvol-guard`, created from the already-resident jellyfin image so no pull, never
  started) was created before the recreate and removed immediately after — without `-v`, so the
  volume outlives it. The volume read `1` before the recreate, `1` after it, and `1` after the guard
  came off.
- **The answer, recorded so nobody needs the guard next time:** compose v5.0.2 did **not** take the
  volume. The guard turned out to be unnecessary, which is the outcome you want from insurance and
  is not a reason to skip it.
- **Cost if wrong:** the guard is a stopped container for ~2 minutes. Note it would have been
  visible to the estate's documented `created`-state blind spot had it been left behind; it was not.
- **Commit:** `c69bfd9`

**2. [Rule 1 — Bug] VALIDATION row 15's key-set equality is unsatisfiable, and it failed on a correct outcome**

- **Found during:** Task 2, step 6
- **Issue:** The plan asserts that the set of top-level keys differing between `encoding.before.json`
  and `encoding.readback.json` equals exactly five names including `ThrottleDelaySeconds`. The
  derived set has **four**: `ThrottleDelaySeconds` was already `180` before the write, so setting it
  to `180` changed no value. The assertion conflates *"keys SET in the POST body"* with *"keys whose
  VALUE CHANGED"*. The plan disagrees with itself here — its own task-2 prose says
  *"`ThrottleDelaySeconds` **180**, unchanged"*, 02.1-RESEARCH.md § *The Two Discretion Values* says
  the same, and `jellyfin.yaml`'s comment block delivered by 02.1-04 reads
  *"ThrottleDelaySeconds 180 -> 180 (UNCHANGED, and deliberately so)"*. It could only ever have
  passed if the live value had been something other than 180, which the research says it was not.
- **This is NOT the full-object-replace hazard firing.** That hazard is the *superset* direction — a
  key moving that nobody intended — and it was measured directly and separately:
  `changed_keys − intended_five` = `[]`. Nothing outside the five moved.
- **Fix:** Row 15's protective content was split into two checks that are each satisfiable and that
  together cover more than the equality did:
  - **(a)** `changed_keys − intended_five == []` — the subset direction, which *is* the hazard.
  - **(b)** every one of the intended five holds its intended **value** in the readback — which is
    the step-5 assertion, already run and passing.
  **(b) is doing work the equality never did.** A key-set comparison is silent on values: a POST that
  set `SegmentKeepSeconds` to 999 would have satisfied the plan's equality perfectly, because the
  *key* changed. Only the value assertion catches that. The equality's unique contribution was always
  (a), and (a) is what has been kept.
- **The round-2 review finding still stands and is not weakened by this.** Replacing a
  `grep -cE '^[<>]' … -le 12` diff-line count was correct, and the *direction* of the fix — a set,
  not a count — was correct. The set was simply populated with the wrong five names. Worth noting
  that a count of 4 would have passed `-le 12` here, so the old check would have gone green for the
  wrong reason on the very first run.
- **Files modified:** the artifact records both the plan's literal verify output and the corrected
  one, so a reader can check the reasoning rather than take it.
- **Commit:** `e8e70cb`

**3. [Rule 3 — Blocking] `rsync` is still absent on LXC 100**

- **Found during:** Task 1, the pre-cutover reconciliation
- **Issue:** The plan names `rsync -rlt --no-p --no-o --no-g` for the reconciliation pass. rsync does
  not exist on LXC 100 — 02.1-04's finding, unchanged.
- **Fix:** Deliberately did **not** install it. Used the equivalence 02.1-04 documented, stated flag
  for flag: `cp -d -u --preserve=timestamps` ≡ `rsync -rlt --no-p --no-o --no-g`. Exit status was
  branched on **per file**, never a printed summary — which is the whole point, since CLAUDE.md
  records `rsync -a` exiting 23 with `mkstemp … Operation not permitted` on `acltype=nfsv4` *while
  printing stats that look like success*. 10 files transferred, 0 failures, and the second
  enumeration was empty outright.
- **Commit:** `c69bfd9`

**4. [Rule 1 — Bug] The credential screen tripped on its own explanation**

- **Found during:** Task 2, pre-commit screening
- **Issue:** The acceptance criterion requires
  `grep -cEi '(token|api_key|password|secret)[[:space:]]*[=:]'` to return **0** over every committed
  artifact. `02.1-05-encoding-diff.txt` returned **1** — on a line reproducing the Authorization
  header format string to explain how the key is passed safely. The value in it was `%s`, a printf
  *placeholder*, not a credential. A correctly-written explanation of a safe practice failing the
  check that asserts the practice was followed. Exactly the class of bug 02.1-04 hit with `/dev/shm`
  and that the D-32 watch's FORMAT block documents.
- **Fix:** Reworded to *describe* the process substitution rather than write the header literally,
  with an explicit note in section 9 saying that is deliberate and why, so the next editor does not
  helpfully "fix" it back. Both patterns now return 0 over all four artifacts.
- **Commit:** `e8e70cb`
