# Phase 02.1: Implementation Plan Review

## 1. Summary
The proposed implementation plans for Phase 02.1 are exceptionally thorough, structurally sound, and technically rigorous. They demonstrate a deep, precise understanding of underlying system mechanics—including moby's mount-sorting depth algorithms, OpenZFS quota semantics, Jellyfin's HLS stream-copy remux limits, and Proxmox container-recreation lifecycle quirks. By combining proactive configuration pinning (Renovate) with surgical, read-modify-write application config updates (REST API) and a robust, fail-closed validation harness, the plans successfully address both the immediate crisis (root-disk exhaustion) and the systemic configuration drift that allowed it to occur. The sequence of execution is perfectly ordered, prioritizing backups, sandboxed validation, and dry runs before any destructive actions (such as volume deletion) are executed.

---

## 2. Strengths
*   **Exemplary Safety-First Engineering on Terraform (Plan 03):** Sourcing and applying Terraform changes in a directory that manages a live Proxmox container running ~103 containers is a high-risk operation. The saved-plan discipline with a **mechanical, automated JSON-assertion pass** (`terraform show -json | jq` verifying zero destroys and single-resource focus) is a brilliant mitigation against the highly destructive `bpg/proxmox` provider mount-point replacement bug. This is a masterclass in pipeline protection.
*   **Surgical REST API Configuration Mutation (Plan 07):** Recognizing that Jellyfin's `/System/Configuration/encoding` endpoint is a full-object replace rather than a partial update is a critical catch. The proposed read-modify-write (GET $\rightarrow$ `jq` merge $\rightarrow$ POST $\rightarrow$ readback assert) successfully prevents the silent reversion of the critical 2026-08-31 amdgpu kernel-oops mitigation (`HardwareAccelerationType: none` and `EnableHardwareEncoding: false`), which carries a constructor default of `true`.
*   **Durability Preservation & Runbook Hardening (Plan 04):** Hardening `scripts/disable-jellyfin-hwaccel.sh` (D-29 / TRAN-09) to capture, preserve, and re-assert the transcode retention and path values across a whole-file `.bak` restore is an outstanding catch. It successfully disarms a silent-revert loop that would have otherwise undone this entire phase during the next routine amdgpu recovery incident.
*   **Robust Standalone and Aggregated Testing (Plans 02 & 09):** Creating `check-jellyfin-transcode.sh` as a host-resident script that mirrors the exit-code and routing conventions of `check-music-freeze.sh` ensures highly consistent tooling. Aggregating it into the workstation-resident `quick-health-check.sh` with double `UNKNOWN` branches (handling empty outputs and broken summary anchors) ensures the shared health check fails closed on parse or connection failures.
*   **Proactive Renovate Pinning Strategy (Plan 01):** Adding the `jellyfin/jellyfin` package rule to treat minor releases as major upgrades is highly intuitive. It stops unattended auto-merges of feature-rich releases (e.g., 10.9, 10.10, 10.11) that frequently alter lyric-saving, transcode-paths, or encoding structures, while preserving the safe flow of security patch updates.
*   **Empirical Validation of Hypotheses (Plan 08):** Sizing the two discretion parameters (`SegmentKeepSeconds=300` and `ThrottleDelaySeconds=180`) using real-world HLS copy bitrates (17.93 Mbit/s) and verifying their actual execution in logs (rather than trusting API feedback) is superb. Testing the quota to prove it yields `ENOSPC` instead of `EDQUOT` is highly thorough.

---

## 3. Concerns

*   **Image Cache Census Race Condition (Plan 07 Task 1 / VALIDATION.md row 6) — [Severity: MEDIUM]**
    *   *Risk:* In Plan 06 Task 1, a pre-copy file census (size and count) is taken from `/var/lib/docker/volumes/<id>/_data/images`. In Plan 07 Task 1, after the container is recreated with the new bind mounts, the census is re-run on `/mnt/fast/appdata/media/jellyfin/cache/images` to prove cache integrity. However, because Jellyfin is live and serving, it is highly likely that upon starting up, Jellyfin or an active client session will immediately write, delete, or modify files in the image cache or shader cache. If any background artwork fetching, TV guide sync (`xmltv`), or client browsing occurs during the brief window between container start and census verification, the file count and total bytes will mismatch, resulting in a false-negative test failure.
*   **JSON5 Parse Compatibility in Verification (Plan 01 Verification) — [Severity: LOW]**
    *   *Risk:* The automated validation script for `renovate.json5` in Plan 01 uses `JSON.parse(s.replace(/^\s*\/\/.*$/gm,""))`. While this strips standard single-line `//` comments, standard JSON5 files can contain multi-line block comments (`/* ... */`), trailing commas, and unquoted keys. If the workstation's `renovate.json5` contains trailing commas or block comments, a standard `JSON.parse()` will throw a syntax error, causing the verification task to fail even if the Renovate configuration is perfectly valid.
*   **Credential Ownership Check Brittleness (Plan 02 Task 1) — [Severity: LOW]**
    *   *Risk:* Sourcing the credential `/mnt/fast/secrets/jellyfin-deercrest.env` asserts that `stat -c '%a %U'` is exactly `600 root`. While this is an excellent security measure, if the environment runs under an unmapped user namespace or if the file is owned by another admin user on Proxmox, this check might fail. However, because this is an established project convention (`check-music-consumers.sh` already uses it), the risk is low, but worth keeping in mind.

---

## 4. Suggestions

*   **Mitigate Image Cache Census Race (Plan 07):** To prevent transient background cache modifications from causing a false test failure, do one of the following:
    1.  Introduce a small file-count/size tolerance in the post-recreate comparison (e.g., allow additions but fail on massive deletion or missing subdirectories).
    2.  Simply restrict the check to validating that key directories (like `/cache/images`) are non-empty and accessible, rather than expecting an exact byte-level match on highly volatile cache structures.
*   **Robust JSON5 Parser for Verification (Plan 01):** To prevent standard JSON parser syntax errors over JSON5 files containing trailing commas or block comments, use Node's native module evaluation which handles JSON5 syntax natively without needing external packages:
    ```bash
    node -e "const fs = require('fs'); const content = fs.readFileSync('renovate.json5', 'utf8'); const data = eval('(' + content + ')'); ..."
    ```
*   **Document Live TV and Orphaned Cleaner Edge Case:** Ensure that the documentation added to `jellyfin.yaml` explicitly highlights that if Live TV is ever enabled in the future, HLS stream buffers for live streams (`LiveStream.TempFilePath`) will bypass segment deletion limits and rely solely on the ZFS quota as the hard backstop.

# Cross-AI Plan Review — Phase 02.1 (Jellyfin Transcode Retention)

## 1. Summary

This is an unusually well-evidenced plan set. The research underneath it is read from Jellyfin source at the exact running tag, the ZFS errno claims come from OpenZFS source rather than a man page, and nearly every assertion is paired with a stated instrument and a stated way that instrument has previously lied. The read-back-vs-fires distinction (CONS-04 / D-15) is applied consistently and correctly, and the highest-blast-radius action (the Terraform apply) is guarded mechanically rather than by a visual plan review. That said, the phase has three structural problems that no individual plan owns: **the root filesystem is not actually protected until wave 4**, **the headline "~62 GB reclaim" in plan 05 is very probably not real and 03-01's own data proves it**, and **two of the phase's "fires" proofs (plan 04's negative control, plan 08's segment-deletion proof) are not executable as written**. Several smaller command-level defects would stall execution.

---

## 2. Strengths

- **The fires/read-back split is real, not rhetorical.** Every bound has two proofs and the plans repeatedly refuse to let one substitute for the other. Plan 08 task 1 explicitly orders the "nothing lands in the old volume" observation *before* the deletion that would render it vacuous, and states why — this is the correct handling of a genuinely irreversible measurement.
- **Plan 07's read-modify-write discipline is the standout.** Identifying that `EnableHardwareEncoding`'s constructor default is `true` against a live `false` that is an incident mitigation — and then asserting the *non*-change plus a full `jq -S` diff rather than only the five intended fields — is exactly the 01-06 lesson applied correctly. The `EncoderAppPath` trap (absent-because-null, 500s if set) is the kind of detail that normally surfaces as a failed run.
- **Plan 03's Terraform guard is mechanical and the apply consumes the same saved plan that was asserted.** "Applying the saved plan is what makes 'I read it' and 'that is what ran' the same claim" is the right framing, and the stop-on-drift precondition (`-detailed-exitcode` before adding anything) prevents pre-existing drift being swept in.
- **`triggers` on the `null_resource`, and the deviation from D-07's cited analog, is correctly reasoned and auditable.** The plan names why `lxc-mpe.tf` is the wrong precedent (inert after first apply; no `set -e`) rather than silently substituting.
- **D-18's invariant-not-instance choice is right and is carried consistently** through plans 02, 07 and 08 — including plan 09 control 2, which exists precisely because an empty `docker inspect` would otherwise *satisfy* the zero-volume-mounts test.
- **Rollback tables are per-plan, concrete, and honest** about the one irreversible act (the image reap) and about the `null_resource` destroy semantics (state and host diverge).

## 3. Concerns

### Cross-cutting

- **HIGH — `/` is unprotected for the entire phase, and wave 1 contains a blocking human gate.** The anonymous volume keeps receiving transcodes until plan 07's recreate (wave 3), and is not removed until plan 08 (wave 4). If the operator sits on plan 05's reap approval for a day, the phase itself is exposed to a repeat of the incident it exists to fix. `DeleteTranscodeFileTask` bounds an orphan at ~48 h, which is the same window the 19 GB accumulated in. No plan clears the existing transcode cache or watches it during the phase, and the new check is deliberately not folded into `quick-health-check.sh` until plan 09.
- **HIGH — the "~62 GB reclaimable" figure that justifies plan 05 is almost certainly an accounting artifact.** 03-01 removed 27 images and `/` went 18 → 36 GiB (18 GiB real), yet `docker system df` reclaimable went **61.87 GB → 62.44 GB — it went up**. A 95-image / 66.54 GB total with 62.44 GB "reclaimable" implies ~4 GB of active image size across 103 running containers, which is not credible. Docker's RECLAIMABLE double-counts shared layers and counts images referenced only by non-running containers — exactly the set `spike03-image-headroom.sh` deliberately protects. Plan 05's objective ("Reclaim the ~62 GB") will therefore very likely be read as a failed task when the conservative diff yields a small list.
- **MEDIUM — total scope against a phase described as urgent and blocking.** Plans 01 (docs + Renovate + validator), 04 (hwaccel hardening) and 05 (62 GB reap) roughly double the phase relative to the minimal cut that actually protects `/` (03 → 06 → 07 → 08). D-28 and D-29 are explicit operator rulings so the *decision* is settled, but the *ordering* is not, and CONTEXT itself names scope-growth-then-abandonment as this project's failure mode twice.
- **MEDIUM — nothing asserts that `fast/transcode` is actually mounted.** If the dataset is unmounted at LXC boot, `/mnt/fast/transcode` is a plain directory, the bind still works, and the quota does not apply — while `zfs get quota` from atlantis still returns `53687091200` and reads green. This is precisely the boot-race that Phase 2 spent a plan proving with the `mountpoint` export option, and there is no equivalent guard here. The `df -B1 --output=size` second instrument would catch it, but plan 02 makes that line REPORTED, not asserted.
- **LOW — filename/frontmatter off-by-one.** `gsd-review-02.1-plan-00.md` carries `plan: 01`, through to `-08.md` carrying `plan: 09`.

## 4. Suggestions

1. **Re-order the waves so the cutover is the critical path.** Run 03 → 06 → 07 → 08 first; 01, 04, 05 and 09 afterwards. `/` is then protected in four plans rather than nine, and the blocking human gate stops standing between the incident and its fix. If the reap must stay in wave 1, put it *last* in the wave.
2. **Add an interim guard for the phase's own duration** — either clear the anonymous volume's `transcodes/` now (as 03-01 did, under the same authorisation) or add a one-line `du` watch, so the phase is not exposed to the failure it is fixing.
3. **Restate plan 05's target.** Replace "~62 GB" with "whatever the auditable diff yields", and record the 03-01 evidence (18 GiB removed, `docker system df` reclaimable unchanged) so a small list reads as the method working rather than as a shortfall.
4. **Replace the 49.5 GB ballast with a temporary quota shrink.** `zfs set quota=1G` → ballast 1 GB with `dd … conv=fsync` in a short retry loop → observe ENOSPC → `zfs set quota=50G` → assert 53687091200. Same code path, same errno, ~1/50th the IO, seconds instead of minutes. Plan 03 already asserts the literal 50 G value, so nothing is lost.
5. **Give plan 04 a real fault-injection path.** Either add a `verify-retention` sub-action to the script (invocable standalone against a given `JELLYFIN_CONFIG`), or an env-gated `TRAN09_FAULT=1` that skips the re-assert so the post-restore comparison genuinely fails. Without one, the negative control is theatre.
6. **Specify the proof client in plan 08.** Name the exact sequence — obtain a `PlayNow`/`PlaybackInfo` response, fetch `main.m3u8`, then GET segments sequentially at roughly realtime — and state that the download head must advance or rows 16/18 prove nothing.
7. **Assert the transcode dataset is mounted, not just quota'd.** Add `findmnt -no FSTYPE,SOURCE /mnt/fast/transcode` (expect `zfs fast/transcode`), or a device-id comparison against the parent, to `check-jellyfin-transcode.sh` section 4. This closes the same class of boot-race the `mountpoint` export option closed in Phase 2.
8. **Add `JELLYFIN_SECRETS="${JELLYFIN_SECRETS:-…}"` to plan 02's script requirements** so plan 09 control 3 is executable without touching the real credential.
9. **Fix the two literal command defects:** use `zfs get -Hp` in plan 03's property criterion (or expect `1M`), and resolve the saved-plan path to a workstation-local location.
10. **Budget for `check-renovate.sh` lines 26–173 failing on first execution.** Add a task step: run it, capture what breaks, fix only what blocks completion, and record anything deferred — rather than asserting exit 0 as a precondition.
11. **Extend plan 01's REQUIREMENTS.md task** to cover the Traceability table, the by-category arithmetic line and the coverage totals, or place the TRAN block in its own clearly-subtotalled section so the milestone's v1=39 denominator stays meaningful.
12. **Consider whether plan 01 should run first in wave 1**, since every other plan's frontmatter cites TRAN IDs that do not yet exist anywhere authoritative.

## 5. Risk Assessment

**Overall: MEDIUM-HIGH.**

The *design* risk is low — the controls are correct, the layering (quota → application retention → orphan sweep) is sound, and the guards on the two genuinely dangerous actions (the Terraform apply, the image deletion) are appropriate and mechanical. The Terraform blast radius, which is objectively the worst thing in this phase, is handled better than most production change processes handle it.

What raises the rating is **execution risk concentrated in the proofs and the ordering**. Three of the phase's "fires" proofs have defects that will surface only at run time: plan 04's negative control cannot fail, plan 08's segment-deletion proof depends on a client behaviour never specified, and plan 08's ENOSPC test may not observe the errno it asserts. Because this phase's entire epistemology is "reading it back is not evidence", a proof that cannot fire is worse here than elsewhere — it produces a recorded transcript that looks like evidence.

Separately, the phase leaves `/` exposed for its own duration behind a five-plan wave containing a human gate, while the headline justification for one of those plans (~62 GB) is contradicted by the project's own prior measurement. Neither is dangerous, but both work against the stated urgency, and the second risks a plan being recorded as failed when it in fact behaved correctly.

None of this argues against executing the phase. It argues for re-ordering so the cutover lands first, fixing the four executable-command defects before wave 1 starts, and repairing the two unfireable proofs before their transcripts are treated as discharge.

## Summary

The revised plan set is unusually rigorous and largely achieves the phase goal: Jellyfin cache writes move off `/`, ZFS provides a durable bound, application retention is exercised, and regression checks are added. However, several execution-level defects remain—most importantly an unencoded Wave 1 dependency, nondeterministic retention proof criteria, unsafe cleanup around the temporary quota, possible credential leakage in playback artifacts, and a destructive verification that runs the image reap twice.

## Strengths

- Cutover is correctly placed on the critical path; `/` is protected before the human image-reap gate.
- Terraform uses a saved plan with a mechanical zero-destroy assertion.
- Mount validation checks runtime state, nested-bind write-through, and `mounted=yes`, not merely Compose or ZFS configuration.
- Encoding changes use GET–merge–POST and preserve the amdgpu mitigation.
- Quota enforcement, segment cleanup, throttling, and failure paths are treated as “fires” proofs.
- Anonymous-volume deletion is correctly delayed until the old path is observed during real playback.
- Negative controls distinguish unavailable instruments from configuration drift.
- The image-reap accounting correctly rejects Docker’s misleading “reclaimable” figure.
- Security handling is generally thoughtful: no runtime package download, API key mode checks, and explicit public-repository screening.

## Concerns

- **HIGH — Wave 1 contains a real but unencoded dependency.** Plan 02 appends to an artifact created by Plan 01, yet both have `depends_on: []`. `parallelization: false` is mutable executor configuration, not dependency semantics. The text even incorrectly calls the plans “formally parallel-safe.” A different runner or future configuration can start 02 first.

- **HIGH — The image-reap verification executes the destructive operation twice.** Plan 09 Task 3 already runs `… spike03-image-headroom.sh prune`; its automated `<verify>` runs the same prune command again. The second invocation may fail because approved images are already absent, distort evidence, or perform additional behavior. Verification should never repeat the destructive action.

- **HIGH — The playback transcript may expose the Jellyfin API key.** Plan 06 requires recording `MediaSources[0].TranscodingUrl` and manifest content verbatim. Jellyfin transcode URLs commonly contain authentication query parameters. This conflicts with the requirement that no key appear in committed artifacts. A later grep is not sufficient protection if the artifact is staged or committed during execution.

- **HIGH — Quota restoration is not mechanically guaranteed.** Plan 06 says the 50 G restore happens “unconditionally, even on failure,” but provides no `trap`/finally mechanism. With `set -e`, interruption, failed SSH, failed `dd`, or an executor abort can leave `quota=1G`, breaking subsequent playback.

- **MEDIUM — The segment-deletion assertion is nondeterministic.** Sampling begins after roughly 360 seconds with a 300-second retention window. By then production and deletion may be in steady state; counts may stay flat or oscillate rather than “stop rising and then fall” across three one-minute samples. A valid cleaner can fail this criterion.

- **MEDIUM — Concurrent/shared watch-artifact mutation is poorly modeled.** Every plan appends to the same tracked file while omitting it from `files_modified`; Plans 07 and 08 share a wave. This risks lost appends, dirty-tree conflicts, or one plan committing another plan’s evidence. The explanatory note does not eliminate the race.

- **MEDIUM — Plan 06 is marked autonomous despite a mandatory human playback check.** Its `<human-check>` requires a person to play two titles and assess seeking. Either the phase can finish without that result, or this needs a checkpoint and `autonomous: false`.

- **MEDIUM — Debug logging and quota cleanup lack interruption-safe restoration.** Raising Jellyfin logging, creating ballast, and changing quota all require traps that restore state on `ERR`, `INT`, and `TERM`, not just happy-path instructions.

- **MEDIUM — Plan 08’s JSON5 tolerance test is ambiguously invalid.** “Append a trailing comma and a block comment” to a complete file would normally place a comma after the closing object, which is invalid JavaScript/JSON5. The mutation must insert the comma inside an object or array.

- **LOW — Live cache copy verification remains partly subjective.** Files appearing in the source after the copy may be absent from the destination. “Enumerated and explained” is not a reproducible pass rule; a final short reconciliation pass would be stronger.

- **LOW — A disposable image is not necessarily capable of `sleep`.** Plan 07 should verify the selected resident image has a usable shell/sleep binary and override its entrypoint explicitly.

## Suggestions

- Encode `02.1-02 depends_on: ["02.1-01"]`; renumber waves if necessary. Correct dependencies matter more than preserving cosmetic wave numbers.
- Replace Plan 09’s destructive verify command with assertions over the transcript, approved IDs, after-inventory, and free-space delta.
- Redact authentication parameters before recording `TranscodingUrl`; record a sanitized URL plus a hash of the original if correlation is needed.
- Wrap quota shrink, ballast cleanup, and debug-level changes in explicit traps. Verify restoration inside the trap and again on normal exit.
- Prove deletion using log evidence and bounded footprint over time, rather than requiring a particular three-sample rise/fall shape.
- Give each plan its own D-32 sample artifact and merge them in Plan 10, or serialize every writer with explicit dependencies.
- Convert the playback sanity check into a blocking human checkpoint, or clearly mark it as post-phase optional validation.
- Define the JSON5 mutation precisely: insert a block comment and trailing comma inside a scratch object/array.
- Run a final `rsync` reconciliation before cutover so late cache writes are copied deterministically.

## Risk Assessment

**Overall risk: MEDIUM.**

The architecture and rollback thinking are strong, and the root-filesystem protection is likely to succeed. The remaining risks are concentrated in orchestration and proof correctness rather than the core design. The duplicate destructive reap, missing hard dependency, credential-bearing transcript risk, and lack of guaranteed quota restoration should be fixed before execution.

## Consensus Summary

Two reviewers, so "consensus" here means *both* rather than a majority. They agree the phase is
well-evidenced and that the two genuinely dangerous actions — the Terraform apply and the image reap —
are guarded properly. They diverge sharply on overall risk (**Gemini: LOW**, **Claude: MEDIUM-HIGH**),
and the divergence is entirely about *execution* risk in the proofs and the wave ordering, not about
the design.

### Agreed Strengths

- **Plan 07's read-modify-write on `/System/Configuration/encoding`.** Both reviewers independently
  singled this out as the standout: catching that the endpoint is a full-object replace, and that
  `EnableHardwareEncoding`'s constructor default is `true` against a live `false` that is the
  amdgpu-oops incident mitigation, prevents a silent revert of a safety control.
- **Plan 03's mechanical Terraform guard.** Both call the `terraform show -json | jq` zero-destroy
  assertion on a *saved plan that is then applied* the correct mitigation for the known
  `bpg/proxmox` mount-point replacement landmine on LXC 100.
- **Plan 04's hardening of `disable-jellyfin-hwaccel.sh` (D-29 / TRAN-09)** as a real catch — it
  disarms a silent-revert loop that would otherwise undo the whole phase during the next amdgpu
  recovery.
- **Reversibility until the final step.** Both note the old anonymous volume survives copy, recreate
  and transcode proofs, and is deleted only in plan 08 after everything has passed.

### Agreed Concerns

Only one concern was raised by both reviewers:

- **MEDIUM — the JSON5 verify command in plan 01 is fragile.**
  `s.replace(/^\s*\/\/.*$/gm,"")` + `JSON.parse` strips only line-leading `//` comments. Block
  comments, inline comments, trailing commas or unquoted keys anywhere in a ~40-rule
  `renovate.json5` will throw a syntax error and fail the verification for reasons unrelated to the
  change. Gemini suggests `eval('(' + content + ')')` via `node -e`; Claude just flags the fragility.
  Either fix works — the point is that a valid JSON5 file must not fail the check.

Two further items are *near*-agreements worth treating as shared, because they are the same underlying
worry expressed at different scopes:

- **Cache-integrity census is over-strict (Gemini MEDIUM / Claude LOW).** Gemini's is the stronger
  form: Jellyfin writes to the image cache immediately on start (artwork fetch, client browsing), so
  an exact file-count/byte match between plan 06's pre-copy census and plan 07's post-recreate census
  will produce a **false-negative failure**. Claude independently notes the plan-06 verify compares
  counts only while the acceptance criteria demand bytes. Both point at the same soft spot from
  opposite sides: the census needs a tolerance (or a directory-non-empty check) rather than
  byte-exactness on a live, volatile cache.
- **Live TV / `LiveStream.TempFilePath` is an unbounded path.** Gemini asks for it to be documented in
  `jellyfin.yaml`; Claude notes the same gap sitting in plan 09's "known limits" but argues it belongs
  in `jellyfin.yaml` rather than `PROJECT.md`. They agree on the content and on the destination —
  fold it into `jellyfin.yaml`.

### Divergent Views

The reviews are highly asymmetric: Gemini raised **3 concerns** (1 MEDIUM, 2 LOW) and rated the phase
**LOW risk**; Claude raised **~25** across every plan, four of them HIGH, and rated it **MEDIUM-HIGH**.
Gemini did not contradict any of Claude's findings — it simply did not surface them. That is a
coverage difference, not a disagreement, which means **the Claude-only HIGH findings are unconfirmed
by a second reviewer and should be verified against the plans directly rather than accepted or
dismissed on reviewer count.** In particular:

1. **Two proofs may be unfireable (Claude HIGH, Gemini silent).**
   - Plan 04's negative control: verification lives inside `do_enable`, which re-captures live values
     before restoring — so perturb-then-rerun would capture the perturbed values and *pass*. There is
     no standalone verification entry point.
   - Plan 08's segment-deletion proof: `TranscodingSegmentCleaner` deletes behind the client's
     download position, and `IsThrottleAllowed` returns false with "No throttle data" at position
     zero. "Force a transcode" without a client that fetches segments sequentially proves nothing.
   This matters more than usual **because the phase's entire epistemology is "reading it back is not
   evidence"** — a proof that cannot fail produces a transcript that looks like evidence.

2. **`/` is unprotected for the phase's own duration (Claude HIGH, Gemini silent).** The anonymous
   volume keeps receiving transcodes until plan 07 (wave 3) and is removed in plan 08 (wave 4), while
   wave 1 contains a **blocking human gate** (plan 05's reap approval). Claude's suggested re-order —
   03 → 06 → 07 → 08 first, then 01/04/05/09 — protects `/` in four plans rather than nine.

3. **The "~62 GB reclaimable" justification for plan 05 (Claude HIGH, Gemini silent).** 03-01 removed
   27 images and `/` went 18 → 36 GiB, yet `docker system df` reclaimable went **61.87 → 62.44 GB — it
   rose**. Docker's RECLAIMABLE double-counts shared layers and counts images referenced by
   non-running containers. The risk is not damage; it is that plan 05 gets recorded as *failed* when
   it behaves correctly.

4. **The 49.5 GB ballast (Claude MEDIUM-HIGH, Gemini silent).** `compression=off` means it really
   allocates ~49.5 GB on a host with a documented whole-estate wedge at `/proc/pressure/io full ≈ 96%`.
   Claude's alternative — temporarily `zfs set quota=1G`, ballast 1 GB with `conv=fsync` in a retry
   loop, observe ENOSPC, restore `quota=50G` — exercises the identical code path at ~1/50th the IO.

5. **Four literal command defects (Claude only, all independently checkable):**
   - plan 03: `zfs get -H -o property,value recordsize` returns `1M`, not `1048576` — needs `-Hp`.
   - plan 03: `-out=/mnt/fast/spike-021/phase021.tfplan` is an LXC path but Terraform runs on the
     workstation.
   - plan 02/09: `JELLYFIN_SECRETS` is not env-overridable, but plan 09 control 3 requires overriding it.
   - plan 01: the `grep -q 'TBD (run /gsd-plan-phase 02.1'` acceptance criterion is vacuous — the real
     placeholder is `**Requirements**: TBD`.

6. **Where Gemini is more cautious than Claude:** the plan-07 image-cache census race (above) and the
   `stat -c '%a %U'` credential-ownership assertion in plan 02, which Gemini flags as brittle under
   unmapped user namespaces. Claude did not mention either.

### Suggested triage before execution

- **Fix first (cheap, mechanical, both-or-single-source but independently verifiable):** the four
  literal command defects, the JSON5 verify (the one agreed concern), and the census tolerance.
- **Decide before wave 1:** the wave re-ordering, and whether plan 05's objective is restated away
  from "~62 GB".
- **Repair before their transcripts are treated as discharge:** plan 04's fault-injection path and
