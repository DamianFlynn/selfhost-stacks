# 02.1-14 — Playback verification (human gate)

## What this closed

`02.1-VALIDATION.md`'s manual-only row, **"Playback sanity after the cutover" (TRAN-01,
TRAN-04)** — the one question no assertion in this phase answers: *is it watchable?*

The row was still open for a specific and instructive reason. The operator's one recorded
playback session (2026-09-02, ~22:20-22:40Z) **direct-played**: zero segments, zero ffmpeg,
zero bytes on `/`. `02.1-10-SUMMARY.md` records it honestly as *"not transcode evidence — an
empty `/mnt/fast/transcode` after a direct-play session is the absence of a test."* That was
a real result about the cutover not breaking playback, and it was not the result this row
asked for.

## What was proven

Two operator-driven sessions on the Jellyfin **web client**, both on *The Kid Who Would Be
King (2019)* — h264 High 1080p in MKV with DTS-HD MA 7.1, ~29.9 Mbps, chosen by `ffprobe`
rather than by filename because the codec combination is what forces each path.

| | Session A | Session B |
|---|---|---|
| Intended | remux | re-encode |
| **Evidenced** | `-codec:v:0 copy`, no `libx264` | `-codec:v:0 libx264 … -maxrate 2616000` |
| `-readrate 10` | **present** (row 17's marker) | **absent** (the mirror) |
| Intent vs evidence | **agree** | **agree** |
| Real transcode | 51 → 191 segments, live ffmpeg | 52 → 263 segments, live ffmpeg |
| Seek-back | **RESTART**, 2–3 s | **RESTART**, "super fast" |
| Corroboration | new PID 4142192, `-ss 00:01:01.088` | new PID 25069, `-ss 00:01:18.078` |
| Operator verdict | *"perfect, no issues at all great picture quality"* | *"also perfect, no problem with the picture or sound quality"* |

**Neither session direct-played.** The 2026-09-02 trap did not recur and no session had to
be re-driven for that reason.

Both seek-backs were performed after **continuous watching** — A ran 10:47→11:00, B ran
11:08→11:18 — so each rollback to ~01:00 landed roughly nine minutes back, comfortably
outside the 300 s `SegmentKeepSeconds` window rather than inside it where retained segments
would have served the seek without a restart and taught nothing.

## `/` did not move

```
before (10:46:37)  36,849,016,832
after  (11:20:10)  36,844,666,880
delta                  -4,349,952  =  -4.15 MiB
```

Two transcode sessions, three restarts, ~25 minutes of encoding — and `/` moved 4.15 MiB,
ordinary churn on a box running 78+ containers and three orders of magnitude below what
transcode output would cost. Well inside the "few hundred MiB" tolerance the plan set. Every
segment byte landed on `/mnt/fast/transcode` under the 50 G quota.

This is the phase's central claim, and it now rests on a real client rather than a synthetic
HLS fetcher.

## The standing check comparison is valid, and that was deliberate

`bash /mnt/fast/stacks/scripts/check-jellyfin-transcode.sh` exited `0` with
`FAILURES total: 0` **both before and after**, against a script whose sha256 was
`d33356c5…` at both readings.

That equality is not luck. Plan 02.1-11 landed its CR-01 fix during this exercise and its
own SUMMARY flagged that the host copy was still un-deployed. The redeploy was **held back
on purpose** until this row closed. Had it been pushed mid-exercise, the before-run and the
after-run would have executed different programs and their agreement would have meant
nothing.

## Deviations from Plan

**Executed inline, not via a worktree subagent.** This is a blocking human gate. The
checkpoint protocol spawns a *continuation* agent, and a continuation agent receives a fresh
worktree at base — which would strand the first agent's commits. Running on the main tree
was the only shape that survives a human round-trip.

**Deferred from its declared Wave 1 to last.** It has no `depends_on` and nothing depends on
it, and its two files are touched by no other plan. Running it in Wave 1 as declared would
have parked plans 02.1-12 and 02.1-13 behind a human watching a film for half an hour. Stated
before execution rather than done quietly.

**Session B was over-determined, then wasn't.** The first session-B capture (11:07:49) showed
`-filter_complex [0:3]…overlay` — a PGS subtitle track burning in. Burn-in forces `libx264`
independently of the bitrate cap, so the re-encode had two sufficient causes and the path
could not be attributed to the quality cap. This was **recorded as a limitation at the time**,
not discovered later.

The operator then disabled subtitles unprompted. The recapture (11:08:54) shows `-map -0:s`,
a plain `-vf` filter with no overlay — and **`libx264` persisting with `-maxrate 2616000`
unchanged**. That is an unplanned but genuine A/B: same title, same session, same cap,
burn-in removed as a variable. The 3 Mbps cap against a ~29.9 Mbps source is therefore
sufficient on its own, and session B's path *is* attributable to it. The operator's incidental
action produced a better-controlled result than the plan designed.

It also demonstrated a third restart for free: toggling a stream forces a new ffmpeg
(`-ss 00:01:00.060`, new session hash) and it recovered cleanly with nothing surfaced to the
client.

## What is NOT claimed

**The segment counts do not prove `EnableSegmentDeletion` fired.** Counts ran 51→191 and
52→263, more than a strict 300-second window would retain. That is consistent with
`-readrate 10` racing the encode ahead of the playback head while deletion trails the
*playback* position — but that is an explanation, not a measurement, and it is not offered as
one. 02.1-06 proved deletion firing from Jellyfin's own Debug log with advancing ranges; that
remains the evidence for the mechanism (CONS-04).

**The at-rest 263 → 0 drop is session cleanup on stop**, not mid-session retention. Recorded
as an observation, not as proof of the retention lever.

This plan's contribution is exactly two things: the perceptual verdict no assertion covers,
and the seek-back **restarts**, which are proven outright by `-ss` arguments on three distinct
new ffmpeg processes.

## Verification

- Artifact contains a during-playback ffmpeg command line for **each** session, both non-empty.
- Session B's capture contains the literal `libx264` (29 occurrences in the artifact);
  session A's contains `-codec:v:0 copy` and **no** `libx264`.
- Post-seek-back capture exists for each session and differs from the pre-seek one by new PID,
  changed `-ss`, and advanced `-start_number`.
- Segment counts during each session **> 0**; at-rest reading after both sessions recorded (0).
- `/` delta computed in bytes: **−4,349,952** — well within tolerance.
- Standing check exits `0`, `FAILURES total: 0`, matching the task-1 reference point against a
  byte-identical script.
- `02.1-VALIDATION.md`: `grep -c '02.1-14'` returns **2**; `git diff --numstat` returns
  **32 additions, 0 deletions** — additions only, no row's assertion text changed.
- Credential screen: positive control returns **2** against known secret-shaped text; the real
  sweep over the artifact returns **0**. No `Authorization`, no `MediaBrowser Token`, no
  `api_key`, no bearer token.

## What in this plan's text turned out to be wrong

**The operator card's "watch **or seek forward**" is not a neutral choice**, and the plan
presents it as one. Seeking forward restarts the transcode by itself, so the later seek-back
would show a restart regardless of whether `SegmentKeepSeconds` deleted anything — the
restart could not be attributed to the retention window. This was surfaced to the operator
*before* they chose, and they chose continuous watching. A future revision of this row should
not offer seek-forward as equivalent.

**The plan does not warn about image-based subtitles**, and it should. The PGS burn-in path is
a silent converter of a remux test into a re-encode test. The operator card written by task 1
added the warning; the plan text did not contain it. Session A avoided the trap only because
the warning was added.

## Authentication gates

None. Every command was a read-only `ssh` to LXC 100 or a browser action by the operator. No
Jellyfin REST API call was made, and no credential was read or written.
