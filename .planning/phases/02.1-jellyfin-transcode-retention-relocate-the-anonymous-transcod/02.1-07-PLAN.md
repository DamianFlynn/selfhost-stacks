<objective>
Disarm a one-command, silent revert of this entire phase — and make the disarming provably able to
fail.

`scripts/disable-jellyfin-hwaccel.sh` is the estate's amdgpu recovery runbook for a fault that
**recurred on 2026-08-31** and cost ~6 hours of downtime. Its `do_enable` action restores the **whole**
`encoding.xml` from the newest `.bak` — and the only `.bak` on disk is
`encoding.xml.bak.20260831T182741Z`, taken *before* this phase's settings exist. Running `enable` after
this phase lands therefore turns `TranscodingTempPath`, `EnableSegmentDeletion` and `EnableThrottling`
back to their pre-phase values **and reports success**.

The script already knows. `do_enable` prints *"the ENTIRE encoding.xml is restored, not just this"* and
its WR-07 comment says *"do_enable restores the WHOLE FILE, so a stale backup reverts everything else
the operator changed in Jellyfin's Playback settings too, and nothing reported it."* The post-restore
verification added in IN-06 checks `HardwareAccelerationType` **only**.

D-29 rules this in scope. Detect-only — letting the standing check catch the reverted state after the
fact — was rejected because it leaves a known revert path armed, and because the check is manual
(D-22) so "after the fact" could be weeks. Deferring was rejected on this project's own documented
failure mode: a deferred known-bad config rule is how the wrtag `<0.30.0` pin survived for months.

**The cross-AI review found the reviewed version's negative control structurally unable to fire, and
that is what this plan's design changes.** The reviewed proof said "perturb one retention value after
a restore, re-run the verification path, confirm non-zero". It cannot work: the verification lives
*inside* `do_enable`, which **re-captures the live values before restoring**. Re-running `enable` after
perturbing would capture the perturbed values, carry them across, and **pass**. There was no
separately-invocable verification entry point and no fault-injection hook, so the plan's own "prove the
verification can fail" requirement was unsatisfiable — and would have produced a transcript that looked
like a discharged negative control.

Two real fault-injection paths replace it, and both must be exercised:

- **A `verify-retention` sub-action** — invocable standalone against a given `JELLYFIN_CONFIG`,
  read-only, comparing that file against expected values supplied by the caller and exiting non-zero on
  any mismatch. This is the entry point the reviewed design lacked.
- **A `TRAN09_FAULT=1` env hook** that makes `do_enable` skip the post-restore re-assert while still
  capturing and still verifying, so the comparison genuinely finds the restored (pre-phase) values and
  genuinely fails.

**Scope call, made here and recorded so it is not rediscovered:** take the *minimal* change. Preserve
and re-assert the retention values across the restore, widen the post-restore verification, and add the
two fault-injection paths. Do **not** convert the mutation mechanism from direct XML editing to the
REST API in this plan, even though line 72-76's comment says *"Once 02-04 lands, prefer the API"* and
02-04 **has** landed. The file-based route works when Jellyfin is down, which is exactly the condition
this script exists for; converting it is a separate change with its own failure modes, and this plan is
already touching a live incident-recovery runbook. The comment must be updated so it stops claiming
something untrue, and the conversion recorded as explicitly deferred.

**Ordering constraint (D-31, constraint 2).** This plan runs **before** the image reap in 02.1-09, and
02.1-09 `depends_on` it for exactly that reason. Task 2's sandboxed proof needs a resident container
image, and the reap may delete precisely the generic utility images you would reach for — `alpine:3`
and `curlimages/curl:latest` were rows 9 and 2 of 03-01's approved list. The ordering removes the
collision; this plan additionally asserts its chosen image is already present and never pulls.

Purpose: TRAN-04's durability. Everything else in this phase is protected by a ZFS property or a
Renovate rule; this is the one revert path that lives inside the estate's own tooling.
Output: a hardened `do_enable` with two fault-injection paths, and an executed transcript proving both
the positive case and that the verification can genuinely fail.
</objective>
