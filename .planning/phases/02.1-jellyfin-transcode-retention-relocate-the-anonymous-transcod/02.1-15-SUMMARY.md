# Phase 02.1 Plan 15: Make the Bound Actually Bind Summary

**One-liner:** `set -o pipefail` plus a status captured with no local pipe in front of it makes a
`timeout`-killed remote pipeline fail closed at both container-count sites, proven by driving the
real script into a 60-second hang; the two probes that gate the whole check are bounded by a
bash-3.2 watchdog with a sentinel; and eight stale cross-file pointers become grep-able anchors.

## What Was Built

**CR-03 — the bound did not bind, and `wc -l` laundered the kill into a zero.**
`timeout T docker ps -q | wc -l` signals only the first stage. `wc -l` then counts the empty
stream, prints `0` and exits 0, so with no `pipefail` in the remote shell the pipeline exited 0 and
ssh returned 0. On a wedged dockerd — the 2026-08-31 amdgpu signature that plan 02.1-13 exists to
defend against — the script printed `Containers running: 0` and `✅ No unhealthy containers` and
exited 0. A green tick while blind: this phase's own named central failure mode, reintroduced by
the plan written to prevent it.

Both count sites now carry `set -o pipefail` in the remote command string **and** capture ssh's
status with no local pipe in front of it, branching on 124 explicitly. The dead `! grep -qE
'^[0-9]+$'` guard is kept as the catch for a malformed answer, but it is no longer first and no
longer alone.

**WR-01 — the two exempted probes.** Bounded by a pure-bash watchdog (`PROBE_TIMEOUT`, default
20 s), and the false justification withdrawn.

**WR-09 — eight stale cross-file pointers**, six of them cited by the review or found by
re-verification, plus two more that nothing had noticed. All now grep-able anchors.

## The Driven Controls

Everything below was executed, not reasoned about. Full transcripts in
`artifacts/02.1-15-pipefail-control.txt`.

**Mechanism, against the real LXC 100:**

| | stdout | ssh rc |
|---|---|---|
| `timeout 2 sleep 20` (no pipe) | — | 124 |
| `timeout 2 sleep 20 \| wc -l` | `0` | **0** ← the bug |
| `set -o pipefail; timeout 2 sleep 20 \| wc -l` | `0` | **124** ← the fix |

Note stdout is `0` in both the broken and the fixed case. `pipefail` alone is not a fix, because
the script consumed the value; only the status carries the truth. That is why the fix has two
halves.

**A/B on the count sites** — two copies of the real file, base and working tree, each with the
payload replaced by `sleep 60`, both at `REMOTE_TIMEOUT=10`:

- **before:** `Containers running: 0`, `✅ No unhealthy containers`, `SITE_EXIT_CODE=0`, 21 s
- **after:** two UNKNOWN blocks naming the bound, `SITE_EXIT_CODE=1`, 21 s

Both took 21 s against a 60 s sleeper. The bound was firing correctly in the broken version too —
the script simply threw the answer away.

**The real script, end to end**, in place under a trap, `REMOTE_TIMEOUT=10`, only the two count
payloads substituted: **exit 1 in 25 s, with all three fold-in blocks printing ✅**. The fold-ins
had the same 10 s budget and completed inside it, so the exit 1 is attributable to the count sites
and nothing else. Restore from a pristine copy under a bash EXIT trap, sha256 verified equal.

**WR-01, all five branches driven** on the real script under the same discipline: healthy (exit 0);
probe 1 hang (exit 1, 5 s, timed-out wording); probe 1 against a genuinely dead host (exit 1, 10 s,
**different** wording); probe 2 hang; probe 2 genuinely absent (the original branch preserved).
Restore hash-verified.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The plan's suggested `${PIPESTATUS[0]}` capture does not work**

- **Found during:** Task 1, before writing any code
- **Issue:** The plan suggests `RUNNING=$(ssh ... | tr -d ' ')` followed by
  `RUNNING_RC=${PIPESTATUS[0]}`. Driven, that reports `PIPESTATUS[0]=0` with `PIPESTATUS[1]` unset,
  while the remote really exited 124. Confirmed independently: `V=$(sh -c "exit 7" | cat)` gives
  `PIPESTATUS` one element holding 0, whereas the bare pipeline gives two elements holding `7 0`.
  **An assignment is a simple command, not a pipeline** — the pipe lives inside the command
  substitution, in a subshell. Had this been adopted as written, CR-03 would have been "fixed" into
  a shape that still reads green on a hang, and the plan's own verify would have passed.
- **Fix:** dropped the local pipe entirely; `$?` is read on the very next line and the whitespace
  strip is a separate statement afterwards. The code carries a comment saying why, because folding
  it back silently reintroduces the defect.
- **Files modified:** `scripts/quick-health-check.sh`
- **Commit:** `83ca4b5`

**2. [Rule 1 — Bug] The script's own tail message pointed at the wrong blocks, caused by this change**

- **Found during:** Task 1, by the driven run — not by reading
- **Issue:** The final `❌ Health check FAILED` line named only the three fold-ins. Making the count
  sites fatal made a previously-correct message wrong: the driven run failed on the counts while all
  three named blocks printed ✅.
- **Fix:** the message now names every block that can set `EXIT_CODE`, counts included.
- **Files modified:** `scripts/quick-health-check.sh`
- **Commit:** `83ca4b5`

**3. [Rule 2 — Missing critical functionality] The watchdog needed a sentinel, not just an exit status**

- **Found during:** Task 2, by driving the first version
- **Issue:** `ssh` exits **255** when the watchdog TERMs it — the same 255 an unreachable host gives.
  A watchdog returning only the exit status would have collapsed "the bound expired" and "the
  transport is dead" into one verdict. That is precisely the conflation this file exists to prevent,
  reintroduced by the fix for it.
- **Fix:** the watchdog writes a sentinel file immediately before it kills; its existence afterwards
  is proof the bound ended the call. Both probes branch on it and print different text. Driven: hang
  → `rc=255 timed_out=1`, dead host → `rc=255 timed_out=0`.
- **Files modified:** `scripts/quick-health-check.sh`
- **Commit:** `a26310d`

**4. [Rule 2 — Missing critical functionality] Withdrew the false comment that caused CR-03**

- **Found during:** Task 1
- **Issue:** The comment above the Traefik block asserted that bounding the whole pipeline "would
  need a subshell and would buy nothing". That sentence is the proximate cause of CR-03 — it told
  the next reader the case had been considered and dismissed. It is wrong twice.
- **Fix:** withdrawn and **paraphrased, never quoted**, per the convention plan 02.1-12 set when it
  withdrew the reachability claim, so a mechanical grep for the false claim keeps returning zero.
  Same treatment applied to WR-01's withdrawn justification — which also means the plan's own verify
  command (`! grep -q 'which ConnectTimeout above does cover'`) passes for the right reason.
- **Files modified:** `scripts/quick-health-check.sh`
- **Commits:** `83ca4b5`, `a26310d`

## Answers to the Questions the Plan Asked

**Which of `:243`/`:254`/`:281` were changed, and why:** none.

All three end in `grep -q`, which exits 1 on an empty stream, so a killed first stage lands in the
`else` branch and prints `❌ Not running` / `❌ Not accessible`. That is a **wrong red**, not a
**false green** — no branch reports health it did not measure, and none touches `EXIT_CODE`. It is
still a defect (a confident wrong diagnosis sends the reader to look at a healthy container) and it
remains filed as WR-01/open in the review's warning list. It was left alone for three reasons: no
exit-code claim depends on it; the correct fix changes what a *genuinely stopped* container prints,
which deserves its own control against a deliberately stopped container; and `:281`'s pipe is
**local**, not remote, so it needs a different treatment from the other two. The reasoning is now
written at the sites so the next reader does not re-derive it. `:281`'s local pipe is worth
flagging separately — `pipefail` would be a complete no-op there, since the remote command is not a
pipeline at all.

**Which WR-01 resolution, and why:** bound them, *and* correct the justification — the plan offered
these as alternatives but they were not. Bounding, because these two probes gate everything below,
so a hang here hangs the whole check with no transcript at all, and the uncovered case is literally
this phase's incident (a full `/` lets a host complete a TCP handshake and still fail to fork).

Mechanism: a pure-bash watchdog, **not** `ServerAliveInterval`/`ServerAliveCountMax`, which the plan
listed first. sshd answers keepalives from its own process, so whether they fire when a *session
fork* is stuck depends on where inside sshd the block lands — and that could not be driven safely on
a live 103-container host. A bound whose behaviour under the exact failure it targets is untestable
is not a bound. The watchdog bounds wall clock unconditionally and its behaviour *was* driven.

**What in the plan's text turned out wrong:**

1. **`${PIPESTATUS[0]}` does not carry the 124** in the shape the plan suggests. See deviation 1.
   This is the significant one: it would have produced a passing verify over a still-broken script.
2. **`ServerAliveInterval` is offered as an acceptable bound** for WR-01. It is at best unproven for
   the fork-failure case, and the file's own reasoning (point 2 of the `REMOTE_TIMEOUT` block)
   already rejects keepalives for the analogous case one layer down.
3. **The WR-09 table's credential-route line number was off** — 483, not 509-522.
4. **The plan's `<output>` block has a duplicated closing tag** (`</output>` twice). Cosmetic.

## Known Limits, Stated Rather Than Left Implicit

- **The watchdog kills the ssh *client*, not the remote command.** Confirmed by driving it: the
  `sleep 300` processes outlived their ssh clients on LXC 100 and expired on their own (verified
  clear afterwards). Harmless for `true` and `command -v`, which have either finished or never
  started — and the file says not to reach for this function to bound a remote command with side
  effects. `REMOTE_TIMEOUT`, which runs on the far side, is the right instrument for those.
- **The residual pre-fork window at the ten `REMOTE_TIMEOUT` sites is unchanged.** `timeout` cannot
  start until the remote shell has been forked. What the bounded probes now guarantee is that the
  script *detects* a host that cannot fork and refuses before reaching any of them. That is a gate,
  not a bound on every site, and the file does not claim otherwise.
- **`check-jellyfin-transcode.sh` and `check-music-consumers.sh` run on LXC 100**, so this plan's
  edits to them are not exercised by a local run and take effect on the orchestrator's deploy. Both
  edits are comment-only and both files pass `bash -n` under `/bin/bash` 3.2.57.
- **The script is still manual.** Nothing here changes the `KNOWN LIMIT` at the top of the file:
  it only ever fires when somebody types it.
