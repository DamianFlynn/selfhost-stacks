guards, the Terraform blast radius, or the secret handling:

  either literal over the file returns zero. No `tmpfs:` and no `shm_size:` were introduced.

## Critical Issues

### CR-01: `TranscodingTempPath` drift produces a fully GREEN check, and is invisible on the green path

**Files:** `scripts/check-jellyfin-transcode.sh:52-58, 562-573`; `scripts/quick-health-check.sh:331-332`

**Issue:** The 50 G ZFS quota — described throughout this phase as "the load-bearing bound" — bounds
exactly one path: `/mnt/fast/transcode`, reachable in the container as `/cache/transcodes`. It bounds
that path **only if Jellyfin is configured to write there.** `TranscodingTempPath` is what decides
that, and nothing asserts it:

- `check-jellyfin-transcode.sh:562-565` reads the five retention values into `info()` calls, which
  are explicitly REPORTED-not-asserted. `FAILURES` is never incremented for a drifted value.
- Section 2's `assert_bind` proves the *mount* exists. Section 4's two instruments prove the
  *dataset* is quota'd and mounted. Neither can tell whether Jellyfin is writing into it.
- Set `TranscodingTempPath` to `/config/transcodes` (a real, plausible value — it is Jellyfin's own
  default location, and `/config` is bound at `jellyfin.yaml:109`) and the cache moves to
  `fast/appdata`, entirely outside the quota. Every assertion in the script still passes. Exit 0.
  `✅ Jellyfin transcode retention intact`.

It is worse than unasserted — on the success path it is **unreadable**. `quick-health-check.sh:332`
selects the summary with:

```
grep -E '/ headroom|volume mounts|transcode quota|transcode mounted|unreachable|FAILURES total'
```

`encoding values` is not in that list, and the seven `info` lines from section 5 are in the body,
not the summary, so `quick-health-check.sh:339-340` prints `✅ Transcode retention intact` plus six
summary lines and nothing about the encoding values at all. The header at
`quick-health-check.sh:82-85` calls them "a REGRESSION DETECTOR". On the branch that prints a tick
they detect nothing and display nothing.

The stated justification does not cover this. `check-jellyfin-transcode.sh:53-55` argues "a standing
check cannot start a transcode, so it cannot prove a setting FIRES; it can only prove the value has
not drifted." Correct — and then it does not prove the value has not drifted. Comparing a string to
`/cache/transcodes` requires no transcode and no API mutation.

**Fix:** Assert `TranscodingTempPath` (and, at minimum, `EnableSegmentDeletion`) rather than
reporting them. Keep the numeric/boolean values reported if you like the distinction, but the path
is a mount-shape invariant in the same class as section 2, not an efficacy claim:

```bash
# after the enc_val loop, in place of the info() for TranscodingTempPath
TTP="$(enc_val TranscodingTempPath)"
if [[ "$TTP" == "/cache/transcodes" ]]; then
  pass "TranscodingTempPath = $TTP — the quota'd dataset is the transcode target (TRAN-04)"
else
  fail "TranscodingTempPath = '$TTP', want '/cache/transcodes' — the 50 G quota bounds NOTHING while"
  echo "         this is wrong. The bind and the dataset below can both be green and irrelevant."
fi
```

and add the selector to the fold-in so it is legible on the green path:

```bash
# scripts/quick-health-check.sh:332
| grep -E '/ headroom|volume mounts|transcode quota|transcode mounted|transcode target|encoding values|toolchain missing|unreachable|FAILURES total'
```

(emitting a `transcode target: <value> (target /cache/transcodes)` line from section 6 alongside it).

### CR-02: "Jellyfin publishes NO host port" is false — the stated compensating control for an admin-equivalent API key does not hold

**Files:** `scripts/check-jellyfin-transcode.sh:10-11`; `scripts/quick-health-check.sh:252, 299-301`
(contradicted by `stacks/selfhosted/media/jellyfin.yaml:85-93`)

**Issue:** Both scripts state, as load-bearing justification for being host-resident, that Jellyfin
"publishes NO host port" and "is reachable only from a host that can route to its t3_proxy address".
The compose file in the same review scope says otherwise:

```yaml
    networks:
      iot_macvlan:
        ipv4_address: 172.16.1.76     # a LAN address
      t3_proxy:                        # bridge (stacks/selfhosted/media/compose.yaml:12)
    ports:
      - "8096:8096"                    # published on LXC 100's host interface
      - "8920:8920"
      - 7359:7359/udp
      - 1900:1900/udp
```

Two independent routes exist that the comments deny:

1. `172.16.1.76:8096` — the macvlan address is a first-class LAN IP. Jellyfin's HTTP listener answers
   on it from anywhere on `172.16.1.0/24` (and, via the two subnet routers, from the tailnet).
   `check-jellyfin-transcode.sh:268` correctly notes this address is unreachable **from LXC 100**
   under macvlan host isolation — that is a statement about one host, and the file's own header at
   line 10 generalises it into a claim about every host, which is wrong.
2. `172.16.1.159:8096` — `ports:` on a service attached to a bridge network publishes on the LXC's
   host interface. `docker-proxy` binds `0.0.0.0:8096`.

Why this is Critical rather than a stale comment: this exact claim is the last item in the
compensating-control list that `.planning/PROJECT.md:215` uses to accept the residual risk of the
**administrator-equivalent** Jellyfin API key, whose use this phase widened from read to write
(`POST /System/Configuration/encoding`). Jellyfin 10.11 maps *any* API key to
`UserRoles.Administrator` unconditionally and has no scoped-key mechanism. The accepted risk was
sized against an endpoint believed to be unreachable outside one container; the endpoint is in fact
LAN-wide. The other controls in that list (mode `600 root`, process substitution, no key in the
repo) are real and were verified. This one is not.

**Fix:** Correct the claim in both scripts and re-state the true reachability, then re-derive the
risk acceptance from it. The scripts' host-residency argument survives intact on its other legs
(GNU `df --output`, the credential lives on LXC 100, the docker mount enumeration is not one
command) — only the port claim needs removing:

```
#   ON LXC 100 (root@172.16.1.159), from /mnt/fast/stacks, after a `git pull`.
#   Host-resident because: (a) the docker mount enumeration and the API call are not one ssh'd
#   command, (b) `df -B1 --output=avail` is GNU coreutils only, and (c) the credential file lives
#   at /mnt/fast/secrets/ on this host.
#   NOTE ON REACHABILITY — do not repeat the old claim that Jellyfin publishes no host port. It
#   publishes 8096/8920/7359/1900 (jellyfin.yaml:89-93) AND holds the LAN macvlan address
#   172.16.1.76, so the admin-equivalent API surface is reachable from the whole 172.16.1.0/24.
#   The correct statement is narrower: 172.16.1.76 is unreachable FROM LXC 100 under macvlan host
#   isolation, which is why this script resolves the t3_proxy address via `docker inspect`.
```

If LAN exposure of an unauthenticated-by-default admin API surface is not wanted, the separable
remediation is to drop `ports:` (Traefik already fronts it via the `t3_proxy` service label at
`jellyfin.yaml:329`) — but that is a behaviour change and should be its own decision, not folded in
here.

### WR-01: The Terraform file's `quota`-over-`refquota` rationale is inverted against this phase's own measured evidence

**Files:** `infra/jellyfin-transcode-dataset.tf:57-63`; `infra/variables.tf:341`

**Issue:** The file states as reason 2 of 2 for choosing `quota`:

> refquota returns EDQUOT ("Disk quota exceeded"); quota returns ENOSPC ("No space left on
> device"). ENOSPC is the errno the incident's 764 zero-byte files already signature, and it is the
> string every log grep in this estate is built on. Do not set refquota here.

Commit `da877a5` from this same phase is titled *"the transcode quota REFUSES a write and / does not
move — **errno is EDQUOT, not ENOSPC**"*. The measured behaviour is the opposite of the stated
rationale. `variables.tf:341` compounds it by pointing readers at this text: *"D-15/CONS-04 choose
quota over refquota — see the file header for the ENOSPC-vs-EDQUOT reasoning."*

The *decision* survives — reason 1 (refquota does not count descendants or snapshots) is independent
and correct — but the errno half is false, and it is precisely the half a future maintainer will act
on when closing recorded known-issue #3 ("ENOSPC-keyed greps are blind to a ZFS transcode-quota
refusal"). Known-issue #3 records that the greps are blind; it does not record that `infra/` still
carries the claim that they should not be.

**Fix:**

```hcl
#   2. refquota does not count descendants (reason 1 above) is the whole of the case.
#      NOTE ON THE ERRNO — CORRECTED 2026-09-03 by plan 02.1-06's measurement (commit da877a5).
#      An earlier draft of this comment claimed `quota` yields ENOSPC and `refquota` yields EDQUOT,
#      and used that as a second reason. IT IS THE WRONG WAY ROUND FOR THIS CASE: a write refused by
#      the dataset quota surfaces as EDQUOT ("Disk quota exceeded"). ENOSPC is what the ORIGINAL
#      incident produced, because that was a genuinely full `/`, not a quota refusal.
#      CONSEQUENCE: any ENOSPC-keyed log grep is BLIND to a transcode-quota refusal. Detection for
#      this bound must key on EDQUOT (or on `zfs list -o used,quota fast/transcode` directly).
```

### WR-02: `chmod 2775` is not represented in `triggers` — the exact inert-provisioner defect this file was written to avoid

**File:** `infra/jellyfin-transcode-dataset.tf:78-91, 134`

**Issue:** The file's own comment is explicit: *"EVERY VALUE THE PROVISIONER INTERPOLATES MUST APPEAR
HERE. The reviewed version of this plan had the uid/gid pair in `inline` only, reproducing the same
defect for two of them."* The mode `2775` is still `inline`-only. `triggers` contains
`properties` (the five ZFS properties) and `owner` (uid:gid) — nothing about the mode.

Consequence: editing `chmod 2775` to `chmod 2755` (or to anything else) changes no trigger, so the
resource is already-applied, Terraform plans clean, and the mode change silently does nothing. That
is the `lxc-mpe.tf` behaviour the file's header (lines 30-33) names as "fatal to THIS file's
purpose". The comment at 130-133 elevates the setgid bit to "a stated invariant rather than a hope" —
it is a hope, because the statement is not in the plan graph.

**Fix:** move the mode into a trigger and interpolate it:

```hcl
  triggers = {
    properties = join(",", [ ... ])
    owner      = "${var.apps_uid}:${var.apps_gid}"
    mode       = "2775"
    revision   = "1"
  }
  ...
      "chmod ${self.triggers.mode} /mnt/fast/transcode",
```

### WR-03: `var.jellyfin_transcode_quota` is interpolated unvalidated into a root shell on the Proxmox host

**Files:** `infra/variables.tf:337-343`; `infra/jellyfin-transcode-dataset.tf:83, 118`

**Issue:** The variable is `type = string` with no `validation` block, and lands in two places that
both execute on atlantis as root:

```hcl
"quota=${var.jellyfin_transcode_quota}",                 # triggers
"zfs set quota=${var.jellyfin_transcode_quota} fast/transcode",   # remote-exec inline
```

A value containing `;`, `&&` or a newline executes arbitrary commands as root on the host that owns
the pool — e.g. `50G; zfs destroy -r fast/appdata`. This is operator-supplied config, not attacker
input, so likelihood is low; but a typo'd multi-word value is the realistic case and the guard costs
four lines. The estate's other quota variables (`ha_backup_refquota`, `variables.tf:329-333`) have
the same shape, so this is not a regression — it is an opportunity the new file should have taken,
given it is the one carrying "the load-bearing bound of phase 02.1".

**Fix:**

```hcl
variable "jellyfin_transcode_quota" {
  description = "..."
  type        = string
  default     = "50G"

  validation {
    condition     = can(regex("^(none|[0-9]+(\\.[0-9]+)?[KMGTP]?)$", var.jellyfin_transcode_quota))
    error_message = "Must be a ZFS size literal (e.g. 50G, 1T) or the string 'none'. It is interpolated into a root shell on the Proxmox host."
  }
}
```

**File:** `scripts/check-renovate.sh:79-80, 90-91, 100-106, 189-191`

**Issue:** Three counts are computed as `$(echo "$VAR" | wc -l)` with no empty guard:

**File:** `scripts/check-renovate.sh:79, 90, 100`

### WR-08: `quick-health-check.sh` has no timeout on any ssh, so a wedged dockerd hangs it forever

**File:** `scripts/quick-health-check.sh:143, 156, 159, 167, 174, 180, 194, 211, 257, 308`

**Issue:** `SSH_OPTS="-o BatchMode=yes -o ConnectTimeout=10"`. `ConnectTimeout` bounds only the TCP/
auth handshake. Once connected, every remote command runs unbounded. The file's own comment at
lines 177-179 names the failure mode:

> dockerd can still be wedged behind the amdgpu mmap_lock while sshd is fine (that is exactly the
> Aug 31 signature)

In that state `ssh root@… "docker ps -q | wc -l"` connects instantly and then blocks indefinitely,
because `docker ps` blocks on the dead lock. The gate at line 147 passes (it runs `true`, not
`docker`), and the script hangs at line 174 with a bare `Containers running: ` prefix printed and no
newline. Nothing recovers it.

The estate already knows the fix: `disable-jellyfin-hwaccel.sh:172` wraps the *same host* with
`timeout 15 ssh -o ConnectTimeout=8 …` and the comment there says why. The convention exists in one
script and not the other.

**Fix:** bound every remote call, and treat 124 as UNKNOWN rather than as a container verdict:

```bash
SSH_OPTS="-o BatchMode=yes -o ConnectTimeout=10"
rssh() { timeout 60 ssh -n $SSH_OPTS root@172.16.1.159 "$@"; }   # 124 == the dockerd wedge
```

(the three audit fold-ins need a longer bound — the transcode check alone can spend 6 s in its
retry loop — but "longer" is not "unbounded").

### WR-09: `RUNNING` has no numeric guard while `UNHEALTHY` six lines later does

**File:** `scripts/quick-health-check.sh:174-175` vs `:180-190`

**Issue:**

### WR-11: `encoding.xml` is rewritten in place, non-atomically, while Jellyfin is running

**File:** `scripts/disable-jellyfin-hwaccel.sh:287, 363` (`tree.write(path, …)`)

**Issue:** Both `set_hwaccel` and `set_retention` end with `tree.write(path, encoding="utf-8",
xml_declaration=True)`. `ElementTree.write` opens the live path with `"wb"`, truncating it, then
streams. If the process dies mid-write — SIGKILL, the host wedging, an OOM, an `ssh` drop —
`encoding.xml` is left truncated or empty. Jellyfin is running throughout `do_disable` (the restart
is at line 479, after the write), so it can also read a half-written file.

This is the one script in the estate explicitly designed to run *during* an incident on a host that
may be seconds from wedging. Truncating the live config is the worst possible write pattern for that
context. `do_disable` takes a `.bak` first (line 472) so recovery exists; `set_retention` in
`do_enable` (line 602) writes over a file that was just `cp`'d from the backup, so the backup still
covers it — but neither path *says* so, and neither survives a truncation without operator action.

**Fix:** write to a sibling temp and `os.replace` (atomic within a filesystem):

```python
import os, tempfile
d = os.path.dirname(os.path.abspath(path)) or "."
fd, tmp = tempfile.mkstemp(dir=d, prefix=".encoding.xml.")
os.close(fd)
tree.write(tmp, encoding="utf-8", xml_declaration=True)
os.chmod(tmp, os.stat(path).st_mode & 0o7777)
os.replace(tmp, path)
```

(note `os.replace` creates a new inode, so the mode copy above is needed — `tree.write` on the
original path preserves owner/mode by keeping the inode, and that property must be replaced
deliberately, not lost).

### WR-12: `enable` can only prove the retention values were *carried across*, never that they are *correct*

**File:** `scripts/disable-jellyfin-hwaccel.sh:576, 617, 655`

**Issue:** `do_enable` captures `pre_ret` from the live config (line 576), re-asserts it (602), and
then compares the file against `pre_ret` twice (617, 655). Every comparison is against a value
derived from the same file. So the action's final message —

```
✓ verified: the five transcode-retention values survived the whole-file restore
```

— is true whatever those values are. If the five had already been reverted before `enable` ran (a
Jellyfin upgrade rewriting `encoding.xml`, a UI edit, a prior `enable` run with `TRAN09_FAULT=1`, or
a restore-from-`.bak` done by hand), `enable` faithfully preserves the wrong values and reports
success. The header at line 101 promises the stronger reading: *"a mismatch names the field with its
before and after values and exits non-zero (TRAN-09 / D-29)"*.

The script already contains the correct instrument — `do_verify_retention` takes its expectation
from `$TRAN09_EXPECT` rather than from the file, and the block at lines 398-409 explains at length
why that independence is what makes a proof able to fail. Nothing in `do_enable` calls it.

**Fix:** when `TRAN09_EXPECT` is set, gate on it too — an absolute check alongside the relative one:

```bash
  # after the post-restart compare_retention at :655
  if [ -n "${TRAN09_EXPECT:-}" ]; then
    if ! compare_retention "$TRAN09_EXPECT" "$post_ret" "post-restart vs TRAN09_EXPECT" "expected" "found"; then
      bad "the values survived the restore but do NOT match TRAN09_EXPECT — they were already wrong"
      bad "BEFORE this run. 'survived' and 'correct' are different answers."
      return 1
    fi
  else
    warn "TRAN09_EXPECT is unset: the checks above prove the values were CARRIED ACROSS, not that"
    warn "they are CORRECT. Set it to assert the absolute values."
  fi
```

### WR-13: The Jellyfin Renovate rule labels MINOR updates `major-update`

**File:** `renovate.json5:493-497` (packageRules index 38)

**Issue:**

```json5
"matchUpdateTypes": ["minor", "major"],
"addLabels": ["stack:media", "major-update", "manual-review-required"]
```

Every Jellyfin *minor* PR now arrives tagged `major-update`. The rule's description carefully
documents the additive-label wart it inherits from `packageRules[2]` (`automerge`, `safe`) and calls
those "decoration" — but the misleading label this rule *adds itself* is not mentioned. In this
estate the Dependency Dashboard and label filters are how the backlog is worked (recorded incident:
the real backlog lived on the dashboard, not the PR list), so a wrong label is not cosmetic.

`major` in `matchUpdateTypes` is also redundant — `packageRules[5]` already sets
`automerge: false` + `["major-update","manual-review-required"]` for every docker major.

**Fix:** split the rule, or drop the redundant `major` and the wrong label:

```json5
      "matchUpdateTypes": ["minor"],
      "automerge": false,
      "addLabels": ["stack:media", "manual-review-required", "jellyfin-minor-is-a-major"]
```

(`packageRules[5]` continues to handle Jellyfin majors correctly and unchanged.)

### WR-14: The Jellyfin rule matches one exact literal, and silently stops guarding if the image reference is ever registry-qualified

**File:** `renovate.json5:485-487`

**Issue:** `"matchPackageNames": ["jellyfin/jellyfin"]` is an exact string match against the depName
Renovate derives from `jellyfin.yaml:76`. Rewrite that line to `docker.io/jellyfin/jellyfin`, or

**Fix:** match the family, as the neighbouring rules do:

```json5
      "matchPackageNames": [
        "jellyfin/jellyfin",
        "docker.io/jellyfin/jellyfin",

      ],
```

(the trailing regex form is Renovate ≥ 37 syntax and is already used at `packageRules[9]` for
`/immich-server/`, so it is an established pattern in this file).
