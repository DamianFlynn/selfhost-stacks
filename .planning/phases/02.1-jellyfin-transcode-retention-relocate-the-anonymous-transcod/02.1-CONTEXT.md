# Phase 02.1: Jellyfin Transcode Retention - Context

**Gathered:** 2026-09-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the Jellyfin cache structurally unable to fill LXC 100's root filesystem again: a **declared**
write target off `/`, a **bound** on growth that survives a container recreate and a UI edit, and a
**standing check** that would have caught the incident before `/` hit zero.

This phase exists because 03-01 measured the real cause. `/` fell from 2.2 GiB free to **0 bytes**
while an unrelated approval gate was open, and the consumer was **19 GB of Jellyfin transcodes in an
anonymous Docker volume** (`d98b2ff9…/_data`), accumulated over ~36 hours with no `ffmpeg` running.
That is larger than the entire 18.1 GiB image reap 03-01 performed, and **unlike images it refills**.
Phase 3 is halted behind this.

**In scope:** the Jellyfin `/cache` volume and everything under it; the `fast/transcode` dataset and
its properties; Jellyfin's own retention settings; a standing headroom/retention check; the
`jellyfin/jellyfin` Renovate pinning that governs whether a release can silently undo the above;
and — **added by operator decision during discussion** — reclaiming the ~62 GB of unreferenced
Docker images still on `/`, through the existing approval gate.

**Out of scope:** the other five local Docker volumes beyond a read-only inventory; scheduling or
alerting for `quick-health-check.sh`; anything about the music library, tagging or Phase 3's
evidence protocol.

<decisions>
## Implementation Decisions

### Where transcodes land

- **D-01: Transcodes go to the `fast/transcode` ZFS dataset, mounted in LXC 100 at
  `/mnt/fast/transcode`.** The dataset already exists, is **empty**, has 1.4 T available, is owned
  `apps:apps` with the setgid bit, is declared as `mp18` in `pct config 100` and at
  `infra/lxc-selfhost.tf:249` — and **nothing mounts it**. It was provisioned around Sep 2025 and
  never wired up. No new mount point is needed.

- **D-02: `/dev/shm` is REJECTED as the target, and the dead mount is deleted.** `jellyfin.yaml:143`
  binds `/dev/shm:/data/transcode` and the comment above it says "Transcode to RAM for better
  performance" — but `/dev/shm` holds **0 bytes** and always has, because `TranscodingTempPath` was
  never set to `/data/transcode`. Rejected on measurement: `/dev/shm` is sized 15 G against **24 G
  total RAM with only 4.7 G actually available**, so a 19 GB cache there is an OOM, not a full disk
  — and the estate has a documented incident where 1.1 GB in tmpfs took the whole box down
  (`lxc100-tmp-is-tmpfs`). **Delete the mount and its comment together.** Leaving it is a decoy: it
  reads as "already solved", which is plausibly part of why 19 GB accumulated unnoticed.

- **D-03: Belt and braces — bind AND set.** Bind `/mnt/fast/transcode` to `/cache/transcodes` (which
  is already Jellyfin's default path) **and** set `TranscodingTempPath` to it explicitly. If the
  setting is reverted from the UI or appdata is lost, the mount still catches the writes; if the
  mount is ever dropped, the setting still names a real path. Neither is silently load-bearing alone.

- **D-04: Transcode files stay owned `0:568`; record why.** Jellyfin runs as **`uid=0(root)`** — the
  `user:` line in `jellyfin.yaml:64` is commented out and `PUID`/`PGID` are an LSIO convention the
  official `jellyfin/jellyfin` image ignores. A live write probe confirmed container-root can write
  into the dataset (`CAP_DAC_OVERRIDE` inside the userns), landing files `0:568` — host uid
  **100000**, an unmapped id. **Do not "fix" this**: nothing but Jellyfin reads the dataset and every
  file is disposable within minutes, so Phase 1's `568:568` reasoning does not apply. Record it
  explicitly so the next reader seeing `100000` (or `65534` from a container-side listing) knows it
  is expected, not the drift Phase 1 spent 2,674 entries correcting. Setting `user: 568:568` was
  rejected — it would change `/config` and `/media` access and the video/render group membership for
  VAAPI, an enormous blast radius for a scratch directory.

- **D-05: Tune the dataset for scratch video.** Currently `recordsize=128K`, `compression=lz4`,
  `sync=standard`, `atime=off`. Set **`compression=off`** (segments are already-compressed
  H.264/HEVC; lz4 burns CPU on a host running 103 containers), **`sync=disabled`** (disposable data),
  **`recordsize=1M`** (large sequential segment writes). The dataset is **empty**, so there is nothing
  to migrate.

- **D-06: `fast/transcode` is Jellyfin's alone.** Single-tenant, so the quota bounds exactly one
  service and a runaway is unambiguously attributable. A future transcoder gets a **sibling dataset**,
  not a subdirectory here.

- **D-07: The dataset and its properties are declared in Terraform**, following the existing
  `infra/lxc-mpe.tf:50` `null_resource` pattern. Today `fast/transcode` is undeclared — `infra/host.tf:63`
  only `mkdir -p`s the path and `infra/lxc-selfhost.tf:249` mounts it. A `null_resource` adds **no
  attribute to the guarded LXC resource**, so it does not touch the destroy landmine. The residual
  cost is real and must be planned for: it means running `terraform apply` in `infra/` at all.

### Fix scope

- **D-08: Bind ALL of `/cache` off `/`, not just the transcodes path.** The `jellyfin/jellyfin` image
  declares `VOLUME /cache`; it is unbound, so Docker put it on `/`. STATE.md names *"the volume being
  anonymous rather than a declared bind mount"* as the root cause, and the volume also holds the
  **image cache (370 MB)** — the other, slower grower — plus `xmltv` (16 MB) and shader caches.
  Binding only `transcodes` would leave the named root cause standing.

- **D-09: `/cache` binds to `/mnt/fast/appdata/media/jellyfin/cache`** — a **plain directory** inside
  the already-mounted `fast/appdata/media` dataset. This is decisive: `infra/lxc-selfhost.tf:163-167`
  requires every child ZFS dataset to have its own explicit `mount_point`, so a *new dataset* would
  mean editing the guarded LXC resource, while a plain directory needs nothing. It also sits next to
  `/config` where a reader expects Jellyfin's state. The transcodes bind then **nests on top** of it
  from `fast/transcode`. Note honestly: `fast/appdata/media` has **no snapshots and no auto-snapshot
  policy**, so the "don't back up regenerable cache" argument did not apply.

- **D-10: Copy the 392 MB across, then delete the anonymous volume by name — only after Jellyfin is
  proven running on the new path.** Preserves the image cache (no burst of artwork re-fetching on a
  server the house watches) and the xmltv cache (no blank TV guide on first load). Keeping the old
  volume as a fallback was rejected: it leaves 392 MB on the filesystem this phase exists to protect,
  and an undeleted anonymous volume is the exact artefact being removed.

- **D-11: Jellyfin only — inventory the other five volumes and stop.** `docker system df` reports 6
  local volumes totalling 1.2 GB; Jellyfin's was the only one able to empty `/`. Run a one-time
  **read-only** inventory of the rest so nothing is unknown, record it, stop. Scope growth followed by
  abandonment is this project's documented failure mode.

### What bounds growth

- **D-12: The ZFS quota is load-bearing; Jellyfin's retention settings are the graceful layer.** The
  quota lives in a ZFS property — it cannot be flipped from a UI, survives a container recreate, and
  caps the blast radius at one dataset. The Jellyfin settings go on too so the normal case never
  approaches the quota, but **the quota is what gets asserted**.

- **D-13: `quota = 50 G` on `fast/transcode`.** A backstop, not a working limit: with segment
  deletion on, steady state should sit orders of magnitude below it, so playback never meets the
  ceiling. A total runaway is then 4% of the pool's 1.31 T free rather than an outage. 20 G was
  considered (the incident's own size) but risks a legitimate multi-stream 4K working set failing on
  the family TV; 100 G was rejected as catching only a catastrophe.

- **D-14: Turn on BOTH `EnableSegmentDeletion` and `EnableThrottling`.** All three levers are
  currently off: `EnableSegmentDeletion: false`, `EnableThrottling: false`, `SegmentKeepSeconds: 720`.
  Deletion prunes segments the client has passed; throttling stops `ffmpeg` racing ahead of the
  viewer. Together they mean an abandoned stream stops growing rather than transcoding a whole film
  nobody is watching — **which is the most likely explanation for 19 GB accumulating with no `ffmpeg`
  still running at the end.**

- **D-15: Prove the bound fires; do not exit on "configured".** Start a real transcode, confirm
  segments appear under `/mnt/fast/transcode` and **nothing** appears in the old anonymous volume,
  then confirm the set is cleaned rather than growing monotonically. The project standard is CONS-04
  ("never exit on tool configured"), and Phase 2 spent a plan and a half establishing that **reading
  a setting back is not proof it fires** — MA's `folder_name` read back correctly while silently not
  applying.

### Durability and detection

- **D-16: A `/` headroom check joins `quick-health-check.sh` and CAN exit non-zero.** That script is
  217 lines and today contains **no disk check of any kind** — which is why 19 GB accumulated over
  ~36 hours with nothing saying so. 01-09 already established the script is allowed to exit non-zero.

- **D-17: Floor is 20 GiB on `/`** (126 G disk, 33 G free today). At the incident's observed burn rate
  — 19 GB in ~36 h — that is roughly a day and a half of warning, which is enough runway to act. OD-1's
  8 GiB was considered for consistency but gives about six hours, i.e. notification after the fact.
  Green today with 13 GiB of margin, so it does not start red — the 01-09 trap.

- **D-18: Assert Jellyfin has ZERO `Type: volume` mounts**, rather than asserting the specific id
  `d98b2ff9…` is absent. That is the actual invariant, and it catches a *new* anonymous volume as well
  as the old one returning. Asserting the id would pass forever once deleted while a fresh anonymous
  volume grew unnoticed — the same shape as the path-set diff that returned a false pass in 01-06.

- **D-19: Fail closed.** Unreachable LXC 100, unreachable atlantis, stopped Jellyfin, unmounted
  dataset — all are **failures**, not skips. This is the convention `check-music-consumers.sh` already
  uses, and the estate's worst outage (dispatcharr and teleport down six weeks) was silence being read
  as clean.

- **D-20: New standalone script, folded into `quick-health-check.sh`.** Matches the established
  shape exactly — `check-music-freeze.sh` and `check-music-consumers.sh` are each standalone with
  their own assertion contract and exit-code convention, and `quick-health-check.sh` calls both. The
  new one covers `/` headroom, the absent anonymous volume, the transcode quota, and the three
  encoding values read back — and stays runnable alone when debugging. Extending
  `check-music-freeze.sh` was rejected: transcode headroom is not a music-library concern.

  > **Superseded on the encoding-value count only (2026-09-03, plan 02.1-11):** the standing check
  > asserts **five** values, not three. D-20's decision stands; only the count was wrong. See
  > `02.1-11-SUMMARY.md` and ROADMAP SC6.

- **D-21: Settings applied by REST API, documented in `jellyfin.yaml`, asserted in the check.**
  `encoding.xml` lives in appdata, not git, and a UI edit silently reverts it. This is exactly the
  Phase 1 pattern — the Music metadata freeze was applied via REST and explained in the comment block
  at `jellyfin.yaml:93-140`, which is where the next reader actually looks. Vendoring `encoding.xml`
  was rejected: Jellyfin rewrites it on setting changes and across upgrades, so a vendored copy either
  fights the application or goes stale.

- **D-22: `quick-health-check.sh` stays MANUAL; record the gap explicitly.** It only fires when
  someone runs it. Making the estate's health check scheduled and alerting is a real capability with
  its own delivery, deduplication and notification-channel decisions — and Phase 2 closed with a
  mount-failure notification that was **never proven to deliver**. An unproven notification path is
  worse than a known-manual check, because it feels covered. Record as a known limit, not an assumed
  capability.

### Renovate pinning (raised by the operator mid-discussion)

- **D-23: Add a `jellyfin/jellyfin` rule treating MINOR as major — manual review on minor, patch
  still automerges.** Today there is **no Jellyfin rule at all**. It falls through to `packageRules[2]`
  (*"Auto-merge minor updates for all Docker images"*) with `automerge: true`,
  `platformAutomerge: true`, `schedule: ["at any time"]`. `packageRules[5]`
  (`manual-review-required`) fires only on **major** — and Jellyfin has been on `10.` since 2019, so
  its *de facto* major releases all present to Renovate as minor: **10.9 introduced segment deletion,
  10.10 changed lyric saving, 10.11 reworked encoding.** The exact settings this phase configures sit
  behind a rule that lets Jellyfin's biggest releases through unattended. Mirrors the existing
  Mattermost (`packageRules[19]`) and Immich (`packageRules[9]`) shapes. Patch flow is deliberately
  preserved — there is a stream of pre-11.0 builds shipping right now, and the estate's documented
  failure is a Renovate backlog nobody works through.

- **D-24: An `allowedVersions` ceiling was REJECTED.** `packageRules[3]` — the wrtag `<0.30.0` pin —
  is the cautionary tale: added on a misdiagnosis (2026-06-24), it has been enforcing a broken state
  ever since, and Phase 4 criterion 2 exists partly to remove it.

- **D-25: Fix `scripts/check-renovate.sh`.** Line 22 tests for `renovate.json`, but the repo has
  **`renovate.json5`** — the validator `exit 1`s before checking anything. Proportionate to fix here
  because this phase edits `renovate.json5`, and the estate's own documented lesson is that a
  Renovate config error **silently stops the whole repo run**, which is precisely what this validator
  exists to catch and currently cannot.

### Delivery and blast radius

- **D-26: Push to `origin`, then `git pull --ff-only` at `/mnt/fast/stacks`.** The path proven in
  Phase 2 after the `scp` workaround was retired. Make the push an **explicit step**, not an
  assumption: STATE.md records the tree sitting 5 commits ahead of `origin` while the host checkout
  was behind, and the estate has a documented failure where merged Renovate PRs never touch the host
  and `docker ps` disagreed with git.

- **D-27: No approval gate on the Jellyfin recreate — treat it as a routine compose change.**
  Operator decision. Accepts that in-flight playback is interrupted and that rollback is improvised.
  *(Planner note: the `docker volume rm` in D-10 is still explicitly ordered after the recreate is
  proven, and the image reap in D-28 keeps its own gate — D-27 covers the recreate only.)*

- **D-28: The ~62 GB image reclaim is IN SCOPE — via `scripts/spike03-image-headroom.sh`'s existing
  approval gate.** Operator decision, expanding the insertion. `docker system df` still reports
  61.87 GB (77%) reclaimable across images, so 03-01's audited 27 were always the conservative subset.
  Reuse the existing script: its `inventory`/`prune` split is **joined by a file on disk** specifically
  so the gate cannot be branch-skipped, and it builds the referenced set from `docker ps -a` with **no
  status filter**, covering the estate's documented `created`-state blind spot. `docker image prune -a`
  and `docker system prune` remain **prohibited by name**, with the prohibition asserted by a
  comment-stripped grep. 03-01's known limit still stands and the list still needs reading: a
  `compose down`'d stack's image looks orphaned to `docker ps -a`.
  *(Amended 2026-09-02 by the cross-AI review, without changing scope: the "~62 GB" figure is a
  `docker system df` RECLAIMABLE reading and is very probably an accounting artifact — see the note
  under D-31 below. The reclaim stays in scope; only how its success is **measured** changes.)*

### Raised by research, ruled by the operator (2026-09-02, during plan-phase)

- **D-29: Harden `scripts/disable-jellyfin-hwaccel.sh` — IN SCOPE.** Operator decision, taken after
  research found that its `do_enable` restores the **whole** `encoding.xml` from a `.bak` predating
  this phase, and its post-restore verification checks `HardwareAccelerationType` only. As written it
  is a one-command, silent revert of `TranscodingTempPath`, `EnableSegmentDeletion` and
  `EnableThrottling` — i.e. of this entire phase — and it sits in the amdgpu recovery runbook for a
  fault that **recurred on 2026-08-31**. `do_enable` must preserve or re-assert the three retention
  values, and its verification must widen to cover them. Detect-only (letting the standing check
  catch the reverted state after the fact) was rejected: it leaves a known revert path armed.
  Deferring was rejected on this project's own documented failure mode — a deferred known-bad
  config rule is how the wrtag `<0.30.0` pin survived for months. Tracked as **TRAN-09**.

- **D-30: `HardwareAccelerationType: none` / `EnableHardwareEncoding: false` are PRESERVED verbatim,
  and the reason is written down.** Operator decision. These are the amdgpu HMM mitigation applied
  2026-08-31 18:27, not drift. Because the encoding endpoint is a **full-object replace** (research
  Pitfall 2 — `UpdateNamedConfiguration` deserialises the whole body and saves it, and
  `EnableHardwareEncoding`'s constructor default is `true`), the phase must write both values back
  deliberately and **assert them after the write**. A partial POST here silently re-arms a hazard
  with a measured ~6 h outage. Re-enabling VAAPI as part of this phase was rejected: orphaned VAAPI
  `ffmpeg` is a confirmed contributor to the 2026-08-31 oops and belongs to its own investigation.

### Raised by cross-AI plan review, ruled by the operator (2026-09-02, during plan-phase --reviews)

- **D-31: Re-order the waves so the cutover is the critical path.** Operator decision, taken after
  the cross-AI review's top HIGH finding: `/` stayed unprotected for the *entire* phase. In the
  reviewed plan set the anonymous volume kept receiving transcodes until the recreate (wave 3), was
  not removed until wave 4, and **wave 1 contained a blocking human gate** (the image-reap approval).
  A day spent sitting on that gate exposed the phase to a repeat of the incident it exists to fix —
  `DeleteTranscodeFileTask` bounds an orphan at ~48 h, the same window the original 19 GB
  accumulated in.

  The new order puts the **Terraform dataset → cache copy/compose → recreate/encoding →
  fires-proof** chain in the leading waves, so `/` is structurally protected at the end of **wave 6**
  instead of behind a human gate. The docs/Renovate policy work, the `disable-jellyfin-hwaccel.sh`
  hardening, the image reap and the negative-controls/fold-in all follow afterwards.

  > **Wave number corrected in cross-AI review round 2 (Codex, 2026-09-02): originally written here
  > as "end of wave 5" over an eight-wave phase; it is now the end of wave 6 over nine waves.**
  > Nothing about the decision changed. Round 1 declined to encode `02.1-02`'s real dependency on
  > `02.1-01` — 02 appends a sample to the D-32 watch artifact 01 creates — specifically because the
  > edge cascades every later wave +1 and would falsify the "wave 5" wording above, and that wording
  > sits inside a locked operator decision. Codex raised the omission independently at HIGH and
  > supplied the argument the decline had not answered: **`parallelization: false` is mutable
  > executor configuration, not dependency semantics**, so a different runner — or anyone flipping
  > that flag — could start `02.1-02` first. The operator ruled that correctness wins. **D-31's
  > substance is "the cutover is the critical path"; the wave number is a consequence of that
  > decision, not the decision itself**, so updating the description to stay true is not overriding
  > the ruling. The edge is now encoded, the phase runs to nine waves, and the run-time `OLD_VOL=`
  > header guard in `02.1-02` is retained as defence in depth rather than as the primary control.
  > Recorded here so the record shows the change was deliberate.

  **D-28 and D-29 remain fully IN SCOPE — only their position in the wave order changes.** Neither is
  dropped, deferred, or shrunk.

  Two ordering constraints this creates, both resolved explicitly rather than left implicit:

  1. **The TRAN-01…09 requirement IDs are landed by the docs plan, and every other plan's frontmatter
     cites them.** If that plan runs late, the IDs are referenced before they exist anywhere
     authoritative. **Resolution: the docs plan is SPLIT.** The REQUIREMENTS.md / ROADMAP.md
     TRAN-block landing is a small, zero-risk, documentation-only step and becomes plan **02.1-01**,
     the first thing that runs. The Renovate rule and the `check-renovate.sh` repair — the actual
     policy work, and the part carrying real execution risk (lines 26-173 of that script have never
     executed under `set -euo pipefail`) — move to the tail as plan **02.1-08**.
  2. **The hwaccel-hardening plan's sandboxed proof needs a resident container image, and the image
     reap may delete exactly the generic utility images (`alpine:3` and `curlimages/curl:latest` were
     rows 9 and 2 in 03-01's approved list) you would reach for.** Resolution: the reap plan
     (**02.1-09**) `depends_on` the hardening plan (**02.1-07**), so the proof runs first while its
     image is still resident. The hardening plan additionally asserts its chosen image is already
     present and never pulls.

  **Also amended under this ruling — how the reap's success is measured (review finding E).** The
  project's own prior measurement contradicts the "~62 GB" headline: 03-01 removed 27 images and `/`
  went 18 → 36 GiB (**18 GiB real**), yet `docker system df` reclaimable went **61.87 GB → 62.44 GB —
  it rose**. A 95-image / 66.54 GB total with 62.44 GB "reclaimable" implies ~4 GB of *active* image
  size across 103 running containers, which is not credible. Docker's RECLAIMABLE double-counts shared
  layers and counts images referenced only by non-running containers — exactly the set
  `spike03-image-headroom.sh` deliberately protects. Plan 02.1-09's objective is therefore
  **"reclaim whatever the auditable diff yields"**, not "reclaim the ~62 GB", and the 03-01 evidence
  is recorded in the plan so a short approved list reads as *the method working* rather than as a
  shortfall. D-28's scope is unchanged.

- **D-32: A passive `/` watch runs for the phase's own duration — observation only.** Operator
  decision, choosing a passive guard over actively clearing the anonymous volume's `transcodes/`.
  A `du` of the anonymous volume plus a `/` headroom reading in **bytes** is recorded at phase start
  (plan **02.1-01**) and re-observed cheaply at the head of each subsequent plan, appending a
  timestamped line to a single watch artifact. If `/` starts filling mid-phase there is then an early
  signal instead of a surprise.

  **The watch never writes to or deletes live transcode data.** It is `du`, `df` and `docker inspect`
  and nothing else. The existing 19 GB-class cache is removed by the normal cutover path — the copy,
  the recreate, and the `docker volume rm` in **02.1-06** — not by this guard.

  purely cosmetic defect. The condition is documented in the new rule's `description` instead, and
