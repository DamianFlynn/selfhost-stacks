# Phase 02.1 Plan 08: Renovate Policy and the 148 Dead Lines — Summary

An upstream Jellyfin release can no longer automerge itself past a human, and the script that was
supposed to be watching Renovate has executed for the first time in its life.

## What Was Done

### Task 1 — the `jellyfin/jellyfin` rule (commit `3baec0c`)

`renovate.json5` had **no** Jellyfin rule of any kind. Jellyfin fell through `packageRules[2]`
("Default: Auto-merge minor updates for all Docker images", `automerge: true`,
`platformAutomerge: true`, `schedule: ["at any time"]`). Jellyfin has been on `10.` since 2019, so
its *de facto* major releases — 10.9 segment deletion, 10.10 lyric saving, 10.11 encoding — all
present to Renovate as **minor** and merged unattended. `packageRules[5]` catches only `major`,
which for Jellyfin means never.

One rule appended at index **38**, after `packageRules[2]` at index 2, so it wins on `automerge`:

| Field | Value | Why |
|---|---|---|
| `matchPackageNames` | `["jellyfin/jellyfin"]` | bare literal, **not** a `/…/` regex; equals the package portion of `jellyfin.yaml`'s `image: jellyfin/jellyfin:10.11.11` |
| `matchUpdateTypes` | `["minor", "major"]` | `major` named too so one rule owns the package's behaviour |
| `automerge` | `false` | the whole point |
| `patch` | **absent** | D-23: pre-11.0 builds ship constantly and this estate's documented failure is a backlog nobody works |
| `allowedVersions` | **absent** | D-24 |
| `platformAutomerge` | **absent** | inert when `automerge` is false; Mattermost's `[19]` omits it for the same reason |

**The `description` states the threat accurately, which is a correction the review asked for.** The
reviewed version implied an upgrade could revert the settings. It cannot — they live in
`encoding.xml` under `/mnt/fast/appdata` and swapping the image does not touch appdata. The two real
mechanisms are named instead: **semantic change across releases** (10.9 introduced
`EnableSegmentDeletion` in the first place; 10.11 reworked encoding, so a value that still reads back
correctly can stop meaning what it meant) and the estate's **documented Renovate deploy drift**
(a merged PR that never reaches `/mnt/fast/stacks`, leaving git and `docker ps` describing different
software). The five settings at risk are named. The additive-`addLabels` wart is documented rather
than fixed, with `manual-review-required` named as the label to filter on.

**The diff is purely additive: 19 insertions, 0 deletions.** Beyond eyeballing that, all 38
pre-existing rules and the top-level keys were compared **parsed**, not textually:
`JSON.stringify(before.packageRules) === JSON.stringify(after.packageRules.slice(0, 38))` → `true`.
`packageRules[1]`, the patch/digest automerge rule the plan required to survive byte-identical, is
individually asserted identical and still reads `automerge: true`, `["patch","digest"]`.

## Deviations from Plan

### 1. [Rule 3 — blocking] The plan's own candidate list made the plan's own assertion unsatisfiable

- **Found during:** Task 2, after applying the detection block exactly as the plan and RESEARCH.md
  specified it (`for f in renovate.json5 renovate.json .renovaterc.json5 .renovaterc.json`).
- **Issue:** the acceptance criterion and the `<automated>` verify both require
  `grep -v '^[[:space:]]*#' scripts/check-renovate.sh | grep -cE '\brenovate\.json\b'` to return
  **0**. It returned **2** — the candidate loop and its failure message, both of which contain the
  bare literal `renovate.json` as a legitimate candidate name. Brace expansion (`renovate.json{5,}`)
  does not help: `{` is a non-word character, so `\b` still matches.
- **Fix:** compose the candidate names from `basename × extension` instead of writing them out:
  `for base in renovate .renovaterc; do for ext in json5 json; do cand="${base}.${ext}"`. This is
  not a dodge of the assertion — it is what makes the assertion *honest*. A hard-coded filename is
  the exact defect being repaired; writing four more of them into the replacement reintroduces it in
  a new shape. The reasoning is recorded in a comment in the file so nobody "simplifies" it back.
- **Verified:** the composed loop was run in isolation and enumerates exactly the four candidates in
  the specified order, selecting `renovate.json5`. Executable-line count is now 0.
- **Files modified:** `scripts/check-renovate.sh`. **Commit:** `5c13899`.

### 2. [Rule 1 — bug] The plan under-counted the stale literals: four, not two

- **Found during:** Task 2. The plan said *"the two known occurrences are lines 22 and 81, but assert
  the count rather than assuming it."* Asserting found **four** in executable lines: 22 (the test),
  23 (the failure message), 27 (the success message) and 81. Two of them were inside the very block
  being replaced.
- **Fix:** all four gone; count is 0. No extra work — the instruction to assert rather than assume is
  what caught it, and it is recorded because the plan's number was wrong.

### 3. [documentation] The plan cites `jellyfin.yaml:59`; the `image:` literal is at line **76**

- The literal itself is correct and unchanged — `image: jellyfin/jellyfin:10.11.11`. Only the line
  number in the plan text and threat model is stale. Not edited (plan text is verified against by
  02.1-10); recorded here so the next reader is not sent to the wrong line.

### 4. RESEARCH.md says `renovate.json5` has 40 `packageRules`; it had **38**

- All six indices RESEARCH.md and CONTEXT.md actually rely on — `[2]`, `[3]`, `[5]`, `[9]`, `[19]`,
  `[28]` — are **correct**, verified by parse. Only the total was off. After this plan: 39.

- **What:** a four-line stub `renovate-config-validator` placed ahead of `PATH`. **Nothing was
  installed and no network call was made** — `command -v` cannot tell the difference. Created, used,

## What Is NOT Proven — stated plainly, per CONS-04

**1. `renovate.json5` is UNVALIDATED.** `renovate-config-validator` is not installed on this
workstation and installing it is out of scope (T-021-SC; the plan takes the guarded-skip route
explicitly). A config error **silently stops the whole repo run** — Renovate does not fail loudly —
so this is a real open gap, not a formality.

What *was* done instead, and its exact limit: `node v26.7.0` parsed the file as a JavaScript object
literal and the new rule was asserted structurally. **That proves the file is syntactically
well-formed JSON5 and that the rule has the intended shape. It does not prove the config is
semantically valid to Renovate** — an unknown key, a misspelled option or a deprecated field would
parse cleanly and still jam the pipeline. Routes A and B above were driven by a *stub*: they prove
the script's plumbing, nothing about the config.

**2. The rule has not been observed refusing to automerge anything.** There is **no
`renovate/jellyfin-*` branch** among the 27 open ones — no pending Jellyfin update exists in either
direction. The rule is proven present, correctly shaped and correctly ordered; it is **not** proven
*firing*. That observation is only available when upstream next ships a Jellyfin minor and it cannot
be manufactured here. Under CONS-04 the distinction is the whole point, so TRAN-06 is ticked with
this caveat attached rather than hidden.

## The Tolerance Probe

The one concern both round-1 reviewers raised independently: `JSON.parse` over a line-comment strip
throws on block comments, inline comments, trailing commas and unquoted keys — all legal JSON5.
Today's file contains none of those, so the fragile command would have *passed*, which is worse:
it would keep passing until someone added an ordinary JSON5 construct.

Probe run against `renovate.json5.tolerance-probe` in the repo working tree (never `/tmp` — tmpfs on
LXC 100), with **both mutations inside a container**, per round 2's finding that a comma after the
file's final `}` is invalid JSON5 and would fail a working parser:

1. `      /* tolerance probe */` inserted as the **first line inside** the new rule object's opening
   `{`, before its first key (probe file line 479).
2. A **trailing comma** after the object's **last** key/value pair — `"manual-review-required"\n      ],`
   — still inside its closing `}` (probe file lines 495–497).

**Tolerant parse against the mutated copy: exit 0.**

And the probe was proven to *discriminate*, which the plan did not require but without which "exit 0"
is unfalsifiable: the reviewed-fragile `JSON.parse(s.replace(/^\s*\/\/.*$/gm,""))` was run against the
**same** file and **exit 1**, throwing at line 479 on `/* tolerance probe */`. The tolerant parse is
not passing because the mutations are inert — it is passing because it tolerates them.

The copy was deleted; `git status --porcelain` confirms it is absent and it was never committed.
