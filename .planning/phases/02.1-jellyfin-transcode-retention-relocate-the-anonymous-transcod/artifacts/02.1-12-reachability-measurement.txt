$ ss -tlnp | grep -c ':8920' || true

    The `|| true` is load-bearing: a grep that matches nothing exits 1, and

    listeners is a successful measurement, not a failed command.

    THIS IS THE CONTRAST THAT THE CORRECTED WORDING RESTS ON. The workstation
    and atlantis both get 200 from 172.16.1.76:8096. LXC 100 — the container
    host itself — cannot reach it at all. That is macvlan host isolation: a
    macvlan sub-interface is deliberately not reachable from its own parent
    host. It is NOT evidence that the address is unreachable generally, and
    reading it that way is exactly the mistake that produced the false claim.

$ curl -s -o /dev/null -w '%{http_code}\n' --max-time 5 http://192.168.90.25:8096/health || echo curl-exit=$?
200

    The t3_proxy route works from LXC 100, which is why the check script
    resolves that address via docker inspect and uses it. The reason is
    "172.16.1.76 is unreachable FROM HERE", not "there is no other route from
    anywhere".

================================================================================
FINDINGS
================================================================================

(i)  WHICH ROUTES REACH THE ADMIN API SURFACE

     - 172.16.1.76:8096 — the container's iot_macvlan LAN address — answers 200
       to any host on 172.16.1.0/24. Confirmed from two independent LAN hosts
       (the macOS workstation and atlantis). Because the estate runs two
       Tailscale subnet routers advertising 172.16.1.0/24 (the UCG-Max gateway
       and the HA/NUC), it is also reachable from the tailnet.
     - 192.168.90.25:8096 — the t3_proxy docker network address — answers 200
       from LXC 100. This is the route check-jellyfin-transcode.sh uses.

     Jellyfin 10.11 has no scoped API keys: every key maps to
     UserRoles.Administrator. So "the API surface is LAN-reachable" means an
     administrator-equivalent surface is LAN-reachable.

(ii) WHICH ROUTES DO NOT, AND WHY

     - 172.16.1.159:8096 (LXC 100's own interface) — nothing listens. Zero
       sockets in `ss -tlnp`, docker reports every port unpublished, and curl
       fails to connect from the workstation, from atlantis and from LXC 100's
       own loopback. The `ports:` mapping in jellyfin.yaml is inert.
     - 172.16.1.76:8096 FROM LXC 100 — fails, by design. macvlan host
       isolation: the parent host cannot reach an address on a macvlan
       sub-interface it hosts. Every other host on the LAN can.

(iii) DID THE REVIEW'S docker-proxy / HOST-INTERFACE MECHANISM REPRODUCE?

     NO. It did not reproduce, on any of four separate instruments: `ss -tlnp`
     shows zero listeners on 8096 and 8920; `docker inspect .NetworkSettings.Ports`
     reports every port bound to null; `docker ps` shows no host-port arrow; and
     curl to 172.16.1.159:8096 fails with exit 7 from three different vantage
     points including LXC 100's own loopback. The code review was RIGHT ABOUT
     THE CONCLUSION (the admin API surface is reachable far beyond one
     container) and WRONG ABOUT ONE OF ITS TWO STATED MECHANISMS. The exposure
     is SOLELY the macvlan address. Writing "it publishes 8096 on the host
     interface" into the scripts would replace one false claim with another.

     This measurement agrees with all three prior independent readings (code
     review's primary claim, verifier, orchestrator) on the conclusion, and
     with the verifier and orchestrator on the mechanism.

(iv) CORROBORATION FROM LIVE USE

     A human operator was streaming from Jellyfin in a LAN browser at
     172.16.1.76:8096 during this measurement. That is direct live evidence
     that the endpoint serves LAN clients and is not confined to t3_proxy —
     and it is why detaching iot_macvlan is a behaviour change, not a cleanup.

(v)  WHAT THIS DOES AND DOES NOT CHANGE

     CHANGED: the blast radius of an API-key leak is estate-wide (the whole
     LAN, plus the tailnet via the two subnet routers), not confined to a host
     an attacker must already own. The "you must already be on LXC 100 to use
     it" mitigation does not exist and never did.

     NOT CHANGED: endpoint reachability is not key disclosure. Obtaining the
     key still requires root on LXC 100 — /mnt/fast/secrets/jellyfin-deercrest.env
     is mode 600 owned by root, and that mode/owner pair is asserted on every
     sourcing by both check-music-consumers.sh and check-jellyfin-transcode.sh,
     which refuse to source on anything else.

     ALSO NOT CHANGED BY THIS PHASE: 172.16.1.76:8096 being LAN-reachable is a
     PRE-EXISTING estate condition that long predates phase 02.1. What this
     phase changed is that the key is now used for WRITE
     (POST /System/Configuration/encoding), not that the port opened.
