3. THE CLEANUP MECHANISM -- INSTALLED AFTER THE PRECONDITIONS, BEFORE THE
   FIRST MUTATION
================================================================================
  The handler, verbatim from this script:

    set -Eeuo pipefail
    _cleaned=0
    cleanup() {
      local rc=$?
      if [[ $_cleaned -eq 1 ]]; then return 0; fi   # IDEMPOTENT: EXIT fires after ERR
      _cleaned=1; trap - ERR
      set +e                                        # NON-ABORTING: attempt every step
      local fails=0
      lxc 'rm -f .../.quota-ballast .../.quota-probe' || fails=$((fails+1))   # (2) files FIRST
      atl 'zfs set quota=50G fast/transcode'                    || fails=$((fails+1))   # (1) then quota
      sleep 5
      q=$(atl 'zfs get -Hp -o value quota fast/transcode')      # SELF-VERIFYING: re-read INSIDE
      [[ "$q" == 53687091200 ]] || { loud banner naming the dataset and the exact
                                        command to run by hand; fails++ }
      [[ $fails -gt 0 ]] && exit 1
    }
    trap cleanup EXIT ERR INT TERM

  Three properties, each of which is a way this pattern usually fails:
    IDEMPOTENT     -- a _cleaned guard, because EXIT fires after ERR and the
                      handler is therefore entered TWICE on any failure path.
    NON-ABORTING   -- set +e inside, failures collected rather than short-
                      circuited. A cleanup handler that stops at its own first
                      error is the failure mode it exists to prevent.
    SELF-VERIFYING -- the quota is re-read INSIDE the handler and required to
                      equal the literal 53687091200, with a loud banner and a
                      non-zero exit otherwise. A silently failed restore is far
                      worse than a noisy one.

  ORDERING MATTERS: the ballast and probe are removed BEFORE the quota is
  re-set. The reverse order would briefly leave 1 GB of junk inside a 50 G
  bound, which is harmless, but removing them first means a partial failure
  leaves the dataset small-and-clean rather than large-and-dirty.

  THE JELLYFIN DEBUG LOG LEVEL RAISED IN TASK 1 HAS ITS OWN TRAP, IN ITS OWN
  SCRIPT, HELD TO THESE SAME THREE PROPERTIES. Its error path was exercised for
  real -- see the run-1 section of 02.1-06-transcode-proof.txt.
