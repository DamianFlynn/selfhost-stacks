Two mechanisms account for it, both visible in this estate's own numbers:

      1724683251 bytes, but 211.7 MB of that is a base they share with each
      other and is counted four times over.

  (b) IT COUNTS IMAGES REFERENCED ONLY BY NON-RUNNING CONTAINERS. `ACTIVE 83`
      against `TOTAL 95` means twelve images are "inactive" by Docker's
      reckoning. Docker's notion of active is attachment to a RUNNING container.
      This estate has a documented `created`-state blind spot — dispatcharr and
      teleport sat in `created`, existing and never having run, for six weeks
      behind a status-filtered check. An image referenced only by a `created`,
      `exited` or `dead` container is load-bearing and Docker's RECLAIMABLE
      sweeps it in. `spike03-image-headroom.sh` deliberately protects exactly
      that set.

The numbers this plan IS measured against are the recorded `df -B1` byte delta

2.1  ⚠ A CORRECTION TO THE PLAN'S OWN STATED PREMISE, MEASURED NOT ASSUMED
--------------------------------------------------------------------------------

THE PLAN SAYS: "`docker image ls -q` DEDUPES BY ID, so a multi-tagged image
contributes one line no matter how many tags point at it. 03-01 hit exactly this
case with `audiobookshelf:2.35.1` and `audiobookshelf:latest`."

MEASURED ON THIS HOST, TODAY: IT DOES NOT DEDUPE.

  docker image ls -q | wc -l           = 89
  docker image ls --format tag | wc -l = 89     <-- IDENTICAL
  docker image ls -q | sort -u | wc -l = 86     <-- the dedupe only happens if you ask

`-q` emits ONE LINE PER REPOSITORY:TAG ROW, repeating the short ID for each tag.
Three images on this host carry two tags each, and each contributes two `-q`
lines:

  34ad5ee005b6   getmeili/meilisearch:v1.51   and  :v1.51.0
  af8d9cd069a7   pgvector/pgvector:0.8.3-pg18 and  :pg18
  d57d4a0c18b3   jellyfin/jellyfin:10.11.11   and  :latest

89 - 3 = 86. The arithmetic closes exactly.

WHY THIS MATTERS RATHER THAN BEING PEDANTRY. The plan's stated hazard — "an
accounting built on the ID count alone silently UNDER-reports a multi-tagged
removal" — is real but its MECHANISM IS INVERTED. Because `-q` tracks tags,
untagging one of two tags on an image moves the `-q` count by 1 while NO IMAGE
LEAVES THE STORE at all. The raw count therefore OVER-reports, not under-reports.
03-01's audiobookshelf pair produced TWO `-q` lines, not one; removing the first
tag would have moved the count without freeing a byte.

THE PLAN'S REMEDY IS CORRECT REGARDLESS, WHICH IS WHY THIS IS RECORDED AND NOT
ESCALATED: diff the FULL LISTING, not either count. Both the raw and the `sort -u`
figures are recorded above so a later reader can reconcile whichever way they
read it. `docker system df` TOTAL 95 reconciles against IDS_A_BEFORE_UNIQ = 95,
which is the true count of distinct images in the store.

7.5  Removed-size sum vs the measured `df` delta — the gap, explained not glossed
--------------------------------------------------------------------------------

  SUM OF REMOVED `.Size` VALUES (naive):   1724683251 B = 1.61 GiB
  MEASURED `df` DELTA (attributable):      1558175744 B = 1.45 GiB
  GAP:                                     - 166507507 B

THE DIRECTION IS THE EXPECTED ONE. The plan states that a `df` delta SMALLER than
the size sum is expected, because the sum counts shared layers once per image.
1.45 GiB < 1.61 GiB. It holds.

BUT THE MAGNITUDE NEEDS EXPLAINING, BECAUSE § 4.3 PREDICTED ≈1.02 GiB AND THE
MEASURED FIGURE IS 1.45 GiB — 0.43 GiB MORE THAN FORECAST. An estimate beaten by
42% is not self-evidently good news and was investigated rather than banked.

STEP 1 — DOCKER'S OWN DEDUPLICATED ACCOUNTING SAYS THE FORECAST WAS RIGHT.
`docker system df` reports Images SIZE as a DEDUPLICATED total, so its before/after
movement is the correct instrument for "how much image data left the store":

  Images  TOTAL  ACTIVE  SIZE      RECLAIMABLE
  before    95      83   66.54GB   62.44GB (93%)
  after     91      83   65.45GB   62.23GB (95%)
                         ^^^^^^^
  SIZE delta: 66.54 - 65.45 = 1.09 GB

§ 4.3 FORECAST ≈1.09 GB (877.96 MB unique + 211.7 MB shared base counted once).
THE MEASURED DEDUPLICATED DELTA IS 1.09 GB. The forecast was right to three
significant figures, and its mechanism was right too: the four candidates' 211.7 MB
base was shared AMONG THEMSELVES, so it was freed once when all four went. Direct
confirmation — the surviving 2.23 siblings still report SHARED SIZE 205.4 MB after
the reap, unchanged from before it, so none of the freed base belonged to them.

STEP 2 — SO WHY DOES `df` SHOW MORE? BECAUSE THE TWO TOOLS MEASURE DIFFERENT
QUANTITIES. `docker system df` reports APPARENT size — the sum of file sizes.
`df` reports ALLOCATED BLOCKS. ext4 rounds every file up to a 4 KiB block, so a
layer full of tiny files occupies materially more disk than its apparent size. The
keeper images are Node applications, and node_modules is the pathological case.

7.10  DEVIATION, SELF-INFLICTED AND REVERTED — a pull that should not have happened
--------------------------------------------------------------------------------

RECORDED IN FULL BECAUSE THE ALTERNATIVE IS AN UNEXPLAINED IMAGE COUNT, and this
plan's whole method is that the image inventory reconciles.

WHAT HAPPENED. In first probing cal-web's HTTP response (§ 7.9), the executor
reached for `curlimages/curl:latest` via `docker run --rm`. That image was NOT
resident — it had been reaped by 03-01 — so Docker PULLED it. This directly
contradicts this plan's own T-021-SC: "No image is pulled; the plan only deletes."

WHY IT MATTERS RATHER THAN BEING TIDINESS. The measurement in § 7.4 asserts that
the only change to the image store was the removal of four tags. An unremarked
pull would have left the live host disagreeing with the recorded after-listing by
one image and 23.9 MB, and the next person to reconcile them would have had no
way to tell an accidental pull from an unlogged deletion.

TIMING — IT DID NOT CONTAMINATE ANY RECORDED FIGURE. The pull happened AFTER the
after-listing, the after-counts, the `docker system df` reading, the removal diff
and the container-state diff had all been captured. Every number in §§ 7.1-7.5 was
read before it. It was caught on the next check.

REVERTED. `docker rmi curlimages/curl:latest` removed it and the two layers it
brought. This deletes only an artifact created minutes earlier by this session; it
touches nothing the operator's gate protects, and nothing that existed before the
prune. Verified by re-diffing the live store against the recorded after-listing:

  $ diff <(sort after-listing.txt) <(live docker image ls -a | sort)
    IDENTICAL to recorded after-listing
  TAGS_A now: 94   (recorded after-listing: 94)

THE PROBE WAS THEN RE-RUN WITH A RESIDENT IMAGE, `nginx:1.31.3-alpine`, and it is
that second run whose output is quoted in § 7.9. The evidence for cal-web's health
therefore does not rest on the mistake.

CARRY-FORWARD FOR ANY PLAN THAT PROHIBITS PULLS: `docker run --rm <image>` is a
PULL if the image is absent, and it looks identical to a local run when it
succeeds. On a host that has just been reaped, the generic utility images are
exactly the ones most likely to have been removed. Probe with an image confirmed
present in the before-listing, or with `docker exec` into a running container.
