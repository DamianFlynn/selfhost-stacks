1. MECHANISM — the micro-controls, run against the real LXC 100
================================================================================================

Remote shell identity (pipefail is a bash/ksh option, NOT POSIX sh — so this matters):
  /usr/bin/bash
  GNU bash, version 5.2.37(1)-release (x86_64-pc-linux-gnu)

  A. no pipe, no pipefail — baseline sanity, the bound is real:
       ssh ... "timeout 2 sleep 20"
       ssh rc=124

  B. THE BUG — pipe, no pipefail. `wc -l` counts the empty stream, prints 0, exits 0:
       ssh ... "timeout 2 sleep 20 | wc -l"
       ssh rc=0   captured stdout='0'

  C. THE FIX — pipe WITH pipefail. The 124 propagates:
       ssh ... "set -o pipefail; timeout 2 sleep 20 | wc -l"
       ssh rc=124 captured stdout='0'

     NOTE WHAT DID NOT CHANGE BETWEEN B AND C: stdout is `0` in BOTH cases. pipefail alone is
     therefore NOT a fix, because the script consumed the VALUE. Only the STATUS carries the
     truth, which is why the fix has two halves and not one.

  D. THE LOCAL-PIPE TRAP the plan warns about:
       OUT=$(ssh ... "set -o pipefail; timeout 2 sleep 20 | wc -l" | tr -d ' ')
       $? = 0        <-- tr's status. The 124 is gone.

  E. THE PLAN'S SUGGESTED RESCUE DOES NOT WORK — and this is the one thing in the plan text that
     is wrong. 02.1-15-PLAN.md task 1 suggests `RUNNING_RC=${PIPESTATUS[0]}` for that same shape.
     Measured:
       OUT=$(ssh ... "set -o pipefail; timeout 2 sleep 20 | wc -l" | tr -d ' ')
       PIPESTATUS[0]=0   PIPESTATUS[1]=<unset>   stdout='0'

     while the remote really had exited 124. Reason, confirmed independently:
       V=$(sh -c "exit 7" | cat)   -> PIPESTATUS[0]=0 PIPESTATUS[1]=  count=1
       sh -c "exit 7" | cat        -> PIPESTATUS[0]=7 PIPESTATUS[1]=0 count=2

     An ASSIGNMENT is a SIMPLE COMMAND, not a pipeline. The pipe lives inside the command
     substitution, in a subshell, so bash sets PIPESTATUS in the parent to a single element
     holding the assignment's own status. Reading `${PIPESTATUS[0]}` there returns 0 — silently,
     with no error — on exactly the failure it was added to catch. Had this been adopted as
     suggested, CR-03 would have been "fixed" into a shape that still reads green on a hang.

  F. THE SHAPE ACTUALLY ADOPTED — no local pipe, `$?` read on the very next line:
       OUT=$(ssh ... "set -o pipefail; timeout 2 sleep 20 | wc -l")
       RC=$?
       OUT=$(printf '%s' "$OUT" | tr -d '[:space:]')
       RC=124   stdout after local strip='0'

     The whitespace strip is a separate statement, AFTER the status has been taken. The code
     carries a comment saying so, because folding it back into the assignment silently
     reintroduces D.

6. AUDIT OF THE OTHER PIPED REMOTE SITES — :243, :254, :281 (line numbers at the plan base)
================================================================================================

The plan required a verdict on these three whether or not they were changed.

  :243  Traefik    ssh "timeout T docker ps --format '{{.Names}}' | grep -q '^traefik$'"
  :254  Authelia   ssh "timeout T docker ps --format '{{.Names}}' | grep -q '^authelia$'"

                   — note this pipe is LOCAL: the grep is outside the double quotes, so the
                     remote command is not a pipeline at all and pipefail would be a no-op there.

VERDICT: NOT the CR-03 defect, and DELIBERATELY LEFT UNCHANGED in this plan.

  Why they are not CR-03. All three end in `grep -q`, which exits 1 on an empty stream. A killed
  first stage therefore lands in the `else` branch and prints `❌ Not running` /
  `❌ Not accessible`. No branch reports health it did not measure — the reader is shown a red,
  not a tick. That is the whole difference: CR-03 was a FALSE GREEN, these are a WRONG RED.

  Why they are still a defect. `❌ Not running` on a hang is a CONFIDENT WRONG DIAGNOSIS. It sends
  the reader to look at a container that is in fact running fine. This is filed as WR-01 in the
  02.1 code review's warning list (the review's WR-02) and is NOT closed here.

  Why not fix them anyway. Three reasons, in order of weight:
    1. None of them touches EXIT_CODE, so no exit-code claim in this file depends on them. The
       fix is a legibility fix, not a fail-closed fix.
    2. The correct fix changes what a GENUINELY STOPPED container prints — it has to, since
       "stopped" and "could not look" currently share the `else`. That is a behaviour change to a
       line an operator reads every time, and it deserves its own control run against a
       deliberately stopped container, which this plan does not have.
    3. It needs a `case` over a captured status at each of three sites, and :281's local pipe
       needs a different treatment from the other two. Doing that half-way inside a plan whose
       control is about something else is how the 02.1-13 comment came to claim a case it did not
       handle — which is the mistake this plan exists to undo.

  Instead the reasoning is now written at those sites in the file, naming them as WR-01/open, so
  the next reader is not left to re-derive it. A known limit you can read is safer than an assumed
  capability you cannot test.

CONSEQUENCE FOR THE FILE'S GREPPABLE RULE. The new point 4 in the REMOTE_TIMEOUT block states it:
every remote command string containing a `|` must carry `set -o pipefail` AND have its status
captured, UNLESS its last stage is a `grep -q` (documented at the site). At this commit the piped
remote command strings are exactly the two count sites (both now pipefail'd and status-checked),
:243 and :254 (grep -q, documented), and :281 (local pipe, not a remote pipeline, documented).

9. ESTATE-SAFETY NOTE ON THE METHOD CHOSEN
================================================================================================

The obvious way to make the real `docker ps` hang is to stage a sleeping stub at
/usr/local/bin/docker on LXC 100. That was CONSIDERED AND REJECTED: it would put a sleeping
shim in front of every `docker` invocation on a 103-container host for the duration of the

site under a trap proves the identical property — the first stage of the same remote pipeline is
killed by the same `timeout`, and the same capture and branch see the result — with a blast
radius of one file on the workstation.

10. WR-01 — BOUNDING THE TWO EXEMPTED PROBES (same plan, task 2)
================================================================================================

RESOLUTION CHOSEN: BOUND THEM. The plan offered "bound them" or "keep them unbounded and replace
the false justification with a true one". Bounding was chosen because these two probes GATE
EVERYTHING BELOW — a hang here is a hang of the whole check with no transcript at all, which
plan 02.1-13 itself named as worse than a wrong answer — and because the uncovered case is
literally this phase's incident: a host with a full `/` can complete a TCP handshake and still
fail to fork a shell. The justification was corrected as well; the two were not alternatives.

MECHANISM CHOSEN: A PURE-BASH WATCHDOG, NOT ServerAliveInterval/ServerAliveCountMax.
The plan lists ServerAlive as the primary suggestion. It was rejected, for a reason that is worth
stating precisely rather than borrowing: sshd answers keepalives from its own process, so whether
they fire when a SESSION FORK is stuck depends on where inside sshd the block lands — and that
could not be driven safely on a live 103-container host. A bound whose behaviour under the exact
failure it targets is untestable is not a bound. The file's own point 2 already rejects keepalives
for the wedged-dockerd case; this is the same argument one layer earlier. The watchdog bounds
wall clock unconditionally, wherever the hang is, and its behaviour WAS driven.

THE FINDING THAT SHAPED THE IMPLEMENTATION — ssh EXITS 255 WHEN THE WATCHDOG KILLS IT, WHICH IS
THE SAME 255 AN UNREACHABLE HOST GIVES. A first version returned only the exit status, which
would have collapsed "the bound expired" and "the transport is dead" into one verdict — the exact
conflation this file exists to prevent, reintroduced by the fix for it. A sentinel file, written
by the watchdog immediately before it kills, separates them. Driven under /bin/bash 3.2.57 (the
macOS system bash, which is what `#!/bin/bash` gets — the first control run used bash 5.3 and was
re-run, because a bash-4-only construct would fail on the one machine this file is typed on):

  1 fast success   ssh true          : rc=0   timed_out=0 elapsed=0s
  2 fast success   ssh command -v    : rc=0   timed_out=0 elapsed=0s
  3 real failure   ssh 'exit 3'      : rc=3   timed_out=0 elapsed=0s   <- a real answer is never masked
  4 THE HANG       ssh 'sleep 300'   : rc=255 timed_out=1 elapsed=6s   <- bound 6
  5 unreachable    ssh 172.16.1.199  : rc=255 timed_out=0 elapsed=10s  <- ConnectTimeout, inside the bound

KNOWN LIMIT, RECORDED IN THE FILE TOO: the watchdog kills the ssh CLIENT, not the remote command.
Confirmed by driving it — the `sleep 300` processes from rows 4 and 6 and from runs B and D
outlived their ssh clients on LXC 100 and expired on their own schedule. That is harmless for
these two probes (`true` and `command -v` have either already finished or never started) and it
is why the file says not to reach for this function to bound a remote command with side effects;
REMOTE_TIMEOUT, which runs on the far side, is the right instrument for those. The two bounds
solve different problems and neither substitutes for the other.

RESIDUAL WINDOW, STATED HONESTLY: the ten REMOTE_TIMEOUT sites still have an unbounded pre-fork
window of their own — `timeout` cannot start until the remote shell has been forked. What the two
bounded probes now guarantee is that this script DETECTS a host that cannot fork, and refuses,
before it reaches any of them. That is a gate, not a bound on every site, and the file does not
claim otherwise.
