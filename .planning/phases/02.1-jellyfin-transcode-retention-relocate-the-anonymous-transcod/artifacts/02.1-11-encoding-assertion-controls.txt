WHAT IS BEING PROVEN, AND WHY IT NEEDED FIVE RUNS RATHER THAN ONE
--------------------------------------------------------------------------------
Until this plan, section 5 of check-jellyfin-transcode.sh printed all five
retention values through info(). FAILURES never incremented on drift, so the
script printed "✅ Jellyfin transcode retention intact" no matter what those
values said. Plan 02.1-11 converted them to assertions via assert_enc().

An assertion that has never been observed to fail is not evidence. Worse, a
single run with all five expectations perturbed would prove only that the
BLOCK can go red — it would not distinguish "five independent assertions" from
"one switch that flips them all". So each field is driven separately, and the
informative measurement in each run is not the red line: it is the FOUR GREEN
LINES BESIDE IT. That is the same shape as 02.1-07's TRAN09_FAULT control,
whose most useful output was the fifth field passing inside a failing run.

THE CONTROLS MUTATE NOTHING. Each expectation is a ${VAR:-default} constant, so
a control perturbs the EXPECTATION and never the value. This is deliberate and
load-bearing: /System/Configuration/encoding is a FULL-OBJECT REPLACE, and
POSTing a wrong value to stage a control would risk silently re-arming the
amdgpu hazard that cost ~6 hours on 2026-08-31 (D-30). No POST was made by any
run below; section 5 is a GET only. Same device as $TRAN09_EXPECT in
scripts/disable-jellyfin-hwaccel.sh.

WHAT THE PLAN TEXT GOT WRONG — recorded, not massaged
================================================================================
This phase's two most useful results were both places a plan was wrong. Keeping
the habit.

1. THE DELIVERY ASSERTION IS UNEXECUTABLE UNDER WORKTREE ISOLATION. The plan
   specifies commit → push → `git pull --ff-only` on LXC 100 → assert host HEAD
   == origin/main. A parallel worktree agent must not push to main; the
   orchestrator merges. Half (i) of the delivery assertion was therefore
   replaced by sha256 equality (see the DELIVERY block above). This is not a
   defect in the assertion's intent — it is a plan written for sequential
   execution and then run in a worktree. Any future plan whose proof requires
   host-side delivery should either state the sha256 form directly or be marked
   as not-worktree-safe.

2. TASK 3's ROADMAP EDIT WAS PARTLY ALREADY DONE. The plan instructs
   "append entries for 02.1-11-PLAN.md … 02.1-14-PLAN.md under new wave headings
   after Wave 9 … and update the `**Plans**: 10 plans in 9 waves` line". Both
   were already applied by the gap-closure planning commit (7a8b579 / 260fd93):
   the ROADMAP already carries Waves 10-12 with all four plans listed, and the
   line already reads "14 plans in 12 waves". `grep -c "10 plans in 9 waves"`
   returns 0. Nothing was done for this instruction and nothing needed to be.

3. THE `encoding values:.*REPORTED not asserted` STRIP-GREP DOES NOT
   DISCRIMINATE AT THIS COMMIT. The plan's acceptance criterion expects the
   comment-stripped count to be 0 while allowing the raw count to be non-zero,
   and asks for both to be reported. BOTH ARE 0 — no surviving comment mentions
   the old wording in that exact form, so the strip is doing no work here. What
   DOES discriminate is the same grep across the change:
     $ git show HEAD~1:scripts/check-jellyfin-transcode.sh | grep -c '…'  -> 1
     $ grep -c '…' scripts/check-jellyfin-transcode.sh                    -> 0
   Reported rather than quietly presented as a passing strip test, per the
   02.1-09/02.1-10 precedent that a non-discriminating check is worth naming.

4. shellcheck IS NOT INSTALLED ON THE WORKSTATION. Task 1's <verify> block
   handles this (`|| echo "shellcheck unavailable — syntax check only"`), and
   that is the branch that ran. `bash -n` passed. Recorded so a later reader
   does not assume the script has been shellcheck-clean-verified: it has not.

Nothing else in the plan text was found to be wrong. The five expectations, the
five control values, the predicted exit codes and the predicted per-field
discrimination all matched exactly.
