WHAT THIS IS
  The evidence that the compose file plan 02.1-04 delivered is now the RUNNING
  container. Deleting a mount line from a yaml file does not remove the mount
  from a running container; only the recreate does, and this is the record of
  that recreate and of everything asserted either side of it.

  THE ONE-LINE OUTCOME: Jellyfin now holds ZERO `Type: volume` mounts, its
  `/cache` and `/cache/transcodes` both resolve to declared binds on `/mnt/fast`,
  and a file written into `/cache/transcodes` from inside the container lands on
  the quota-bounded `fast/transcode` dataset. Every new cache byte Jellyfin
  writes from 2026-09-02T22:19:52Z onward is off `/`.

WHAT THIS IS NOT
  This does NOT delete the anonymous volume. It is still present, still holding
  13885711901 bytes (12.93 GiB) on `/`, and that is DELIBERATE -- D-10 orders its
  removal AFTER Jellyfin is proven running on the new path, which is plan
  02.1-06. The volume IS the rollback, and it stays until the rollback is no
  longer needed. The standing check's one remaining red is exactly this, and it
  is supposed to be red here.

4. ASSUMPTION A4  --  CONFIRMED BY WRITE-THROUGH PROBE, NOT BY READING THE SORT
--------------------------------------------------------------------------------

  THE ASSUMPTION. moby's `mountSort.Less` compares
  `strings.Count(filepath.Clean(destination), "/")`, so `/cache` (1 separator)
  mounts before `/cache/transcodes` (2) regardless of declaration order. That was
  read at moby v28.3.2 while this estate runs a newer daemon -- hence A4, and
  hence a probe. The correction a reader is most likely to get wrong: the sort is
  on SEPARATOR COUNT, not on string length and not on declaration order.

  THE PROBE. A uniquely named file written from INSIDE the container:

    probe_name                              .a4-probe-20260902T222123Z-1084920.txt
    write command                           docker exec jellyfin sh -c '… > /cache/transcodes/<name>'
    probe_write_exit                        0
    seen inside the container               YES
    on the host at /mnt/fast/transcode/     YES   <-- MUST be YES
    on the host under …/cache/transcodes/   NO    <-- MUST be NO
    content read back on the host           a4-write-through-probe 2026-09-02T22:21:24Z

    A4 = CONFIRMED

  Both halves matter. Present at /mnt/fast/transcode proves the nested bind is
  live; ABSENT under …/cache/transcodes proves it is the nested bind and not the
  parent one absorbing the write. One reading without the other would not
  distinguish the two.

    probe removed afterwards                YES

  THE SHADOWED DIRECTORY, RECORDED SO NOBODY TIDIES IT AWAY. runc creates a
  missing bind destination inside the rootfs, so an empty, permanently shadowed
  /mnt/fast/appdata/media/jellyfin/cache/transcodes now exists on the host.

    shadowed_dir_exists                     YES
    shadowed_dir_entries                    0

  IT IS INERT AND IT MUST NOT BE DELETED WHILE THE CONTAINER RUNS. Nothing can
  reach it from inside the container -- the nested bind covers it -- and removing
  it under a running container is how you get a mount referring to a deleted
  inode.

  AN UNPLANNED BUT STRONGER PIECE OF EVIDENCE, FOUND IN THE SAME SECTION. The
  dataset was empty before the recreate and holds exactly one entry after it:

    /mnt/fast/transcode/.jellyfin-transcode   0 bytes, root:apps, 22:20Z

  That is JELLYFIN'S OWN MARKER, written by `CreateAndCheckMarker(path,
  "transcode", recursive: true)` during startup. It is independent confirmation
  that the SERVER -- not just the daemon -- resolves its transcode path onto
  `fast/transcode`, and it appeared BEFORE task 2 set TranscodingTempPath,
  because Jellyfin's default transcode path is already <cache>/transcodes. It
  also proves the marker guard did not fire: had a foreign `.jellyfin-*` marker
  been present beneath the transcode path, this would have been a start refusal
  rather than a start.

7. JELLYFIN IS SERVING, NOT MERELY 'running'
--------------------------------------------------------------------------------

  `State.Status == running` is a daemon fact, not an application fact. The
  container could be running and the server refusing requests -- the marker-file
  guard, for instance, is a start refusal that would show as a crash loop, but a
  half-initialised server would not.

  Address resolved the only correct way:

  move it again), NEVER the bare name `jellyfin` (LXC 100's resolv.conf carries
