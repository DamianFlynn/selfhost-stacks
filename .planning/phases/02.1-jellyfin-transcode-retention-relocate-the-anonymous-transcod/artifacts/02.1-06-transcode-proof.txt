THE HARNESS DEFECT IN RUN 1, AND WHY IT IS RECORDED RATHER THAN QUIETLY FIXED
--------------------------------------------------------------------------------

  The first pair of runs produced a transcript in which rows 16 and 18 read as
  hard configuration failures: ZERO deletion lines, ZERO throttling lines, ZERO
  "No throttle data", on BOTH codec branches, with a strictly-increasing download
  head and the pause key re-probed as supported. That is a coherent, confident,
  completely wrong result, and it is exactly the failure mode this plan's
  objective names -- a transcript that looks like evidence.

  THE CAUSE WAS IN THE PROOF CLIENT, NOT IN JELLYFIN. Three lines, in order:

    1. The client contains pipelines of the form `printf ... | head -10`. Under
       `set -o pipefail`, `head` exiting early sends SIGPIPE upstream and the
       pipeline returns 141.
    2. `set -Eeuo pipefail` therefore fired the ERR trap in the middle of section
       4 -- the manifest fetch -- long before any segment had been consumed. The
       handler did its job perfectly: it removed the Debug overlay and restored
       Jellyfin to Information.
    3. `set +e` inside that handler is GLOBAL, not function-local. With errexit
       switched off, the handler returned and the script CARRIED ON for another
       200 lines, driving a full playback session and then grepping a log that
       had been back at Information the whole time. Both Debug-level lines were
       structurally unable to appear.

  Recovered from run 1 verbatim:

    TRAP restore_log_level FIRED ON : ERROR PATH (exit status 141)
    post-restore re-read of effective MinimumLevel.Default : Information
    ASSERT restored == captured original (Information) : PASS

  -- appearing at LINE 112 of a 314-line transcript. The trap worked. The script
  should have died there and did not.

  WHAT WAS ALMOST CONCLUDED FROM IT, AND HOW CLOSE IT CAME. The null result was
  investigated for some time as a genuine product finding, including extracting
  the UTF-16 string tables from all 409 shipped assemblies to confirm the four
  log messages exist in this build (they do, in MediaBrowser.Controller.dll), and
  re-probing the ffmpeg pause key at d=10000 (supported). A plausible mechanism
  had already been drafted -- that Jellyfin excludes the throttler on the
  stream-copy path because "-readrate 10" substitutes for it. That mechanism is
  FALSE: run 2 shows the throttler running on both branches. Had the run-1
  transcript been committed, it would have recorded a fabricated limitation of
  Jellyfin, with quoted assembly evidence sitting next to it making it look
  thoroughly researched.

  THE FIX IS THREE CHANGES, ALL IN THE CLIENT:
    a. Every SIGPIPE-prone `| head -N` that was not already guarded by `|| true`
       is now `| sed -n '1,Np'`, which reads its input to EOF.
    b. The handler ends with `if [[ $rc -ne 0 ]]; then exit "$rc"; fi`, so an
       error path can no longer restore state and then continue running.
    c. NEW ASSERTION, and the one that actually closes the hole:

         ASSERT the log level is STILL Debug at grep time : Debug
         overlay file still present                       : yes
         [DBG] lines across the whole session window      : 2255   (A) / 3063 (B)

       An instrument that reads a log must prove the log was at the required
       level for the whole window it is reading. Without it, "zero matches" and
       "the control did not fire" are the same output -- which is the identical
       shape as 02-08's `exportfs -v` printing a line for a refused mount, and as
       01-06's path-set diff passing while 83 .nfo were rewritten. Both are named
       in this phase's own VALIDATION.md as the reasons CONS-04 exists.

  Run-1 counts, kept for the record and NOT to be read as evidence about
  Jellyfin: session A 0/0/0, session B 0/0/0 for deletion / throttling / no-data.
  The corresponding run-2 numbers on the identical title and identical settings
  are 8/95/0 and 8/95/0.

THE CEILING -- ROW 16's SECOND LIMB IS UNSATISFIABLE AS WRITTEN
--------------------------------------------------------------------------------

  The plan requires all three segment counts to sit at or below

      ceil(SegmentKeepSeconds / segment_duration) + 10

  Measured, with segment_duration taken from each session's own #EXTINF values:

      SESSION A   segment_duration 6.037 s   ceiling  50 + 10 =  60
                  counts 102, 92, 168        heads 59 -> 69 -> 78
      SESSION B   segment_duration 3.000 s   ceiling 100 + 10 = 110
                  counts 178, 186, 192       heads 119 -> 139 -> 159

  All six counts are above the ceiling, on both branches, in sessions where the
  cleaner is DEMONSTRABLY WORKING -- it says so itself, eight times per session,
  with a monotonically advancing index range.

  THE CEILING OMITS A BUFFER THE CONFIGURATION DELIBERATELY MAINTAINS. The
  retention window is not the only thing on disk. At any instant the dataset
  holds two regions:

      (i)  segments BEHIND the download head that the cleaner has not yet
           reclaimed  -- bounded by SegmentKeepSeconds = 300 s, and
      (ii) segments AHEAD of the download head that the encoder has already
           produced -- bounded by ThrottleDelaySeconds = 180 s, which is the
           whole point of the throttler and is visible in its own log line as
           "target gap 1800000000" ticks.

  The ceiling counts only (i). A correct system holds (i) + (ii). Reading it off
  session B, which has the cleaner and the throttler both in steady state:

      head 159, cleaner had just deleted 0..40, so surviving indices are 41..232
      behind the head : 159 - 40  = 119 segments = 357 s  (vs 300 s + a 20 s tick)
      ahead of it     : 232 - 159 =  74 segments = 222 s  (vs 180 s + a  5 s poll)
      total           :             192 segments -- which is the measured count

  So the corrected form is

      ceil((SegmentKeepSeconds + max(ThrottleDelaySeconds,120)) / segment_duration)
        + slack for the cleaner's 20 s tick and the throttler's 5 s poll

  = (300 + 180) / 3.000 = 160 + slack for session B (measured 178-192), and
    (300 + 180) / 6.037 =  80 + slack for session A (measured 92-168).

  SESSION A'S 168 IS THE OUTLIER AND IT HAS A NAMED CAUSE: "-readrate 10" lets a
  stream copy produce fifty seconds of media between two five-second throttler
  polls, so the forward region overshoots in bursts on the remux branch in a way
  it cannot on the re-encode branch. Session B, which has no -readrate, sits in
  a tight 178-192 band exactly as the corrected arithmetic predicts.

  THIS IS THE SAME SHAPE AS 02.1-05's ROW 15 AND IS RECORDED THE SAME WAY: an
  assertion that FAILS ON A CORRECT OUTCOME. It is not waived. What it was
  protecting -- "the footprint does not grow without bound while the head
  advances" -- is discharged by three things that are all present:
    * the cleaner's own eight log lines per session, ranges advancing;
    * the counts oscillating rather than climbing (A: 102 -> 92 -> 168, which
      FELL by ten between the first two samples);
    * and, structurally and independently of Jellyfin entirely, the 50 G ZFS
      quota on fast/transcode, which is why D-12 made the bound a ZFS property
      rather than an application setting. Task 3 of this plan proves that one
      fires.
  The plan's own stated FAILURE condition -- "a count that rises MONOTONICALLY
  past the ceiling" -- did not occur in session A. It is arguably met in session
  B (178 -> 186 -> 192), and that is why the corrected arithmetic above is
  derived from session B's own numbers rather than asserted: the rise is 14
  segments over 120 s while the head advanced 40, i.e. the footprint grew far
  more slowly than consumption. That is convergence toward the bound, not
  unbounded growth.
