### ⚠ A correction to the plan's own premise about `docker image ls -q`

The plan states that `docker image ls -q` **dedupes by ID**. **Measured on this host today, it
does not.** `docker image ls -q | wc -l` = 89, identical to the tag count; only `| sort -u`
gives 86. Three images carry two tags each — `meilisearch:v1.51`/`:v1.51.0`,
`pgvector:0.8.3-pg18`/`:pg18`, `jellyfin:10.11.11`/`:latest` — and each contributes two `-q`
lines. 89 − 3 = 86.

The hazard the plan names is real but its **mechanism is inverted**: because `-q` tracks tags,
untagging one of two tags moves the count by 1 while **no image leaves the store**. The raw
count therefore *over*-reports a removal rather than under-reporting it. **The plan's remedy is
correct either way** — diff the full listing, not either count — so this is recorded rather
than escalated. Both figures are in the transcript so the after-diff reconciles whichever way
a later reader reads it.

## How this plan is measured

**The target is whatever the auditable diff yields. It is not the `docker system df`
RECLAIMABLE figure.**

The project's own prior measurement is why. In **03-01**:

| | Reading |
|---|---|
| Images removed | **27** |
| `/` free, before → after | **18 GiB → 36 GiB** — **18 GiB real** |
| `docker system df` RECLAIMABLE, before → after | **61.87 GB → 62.44 GB** — **it ROSE** |

A number that goes *up* by 0.57 GB while you delete 18 GiB of the thing it claims to measure
is not measuring that thing. Two mechanisms, both visible in today's numbers:

1. **Shared-layer double counting.** RECLAIMABLE derives from per-image `SIZE`, and a layer
   shared by N images is counted N times. Today's four candidates demonstrate it exactly: their
   naive sum is 1.61 GiB, but 211.7 MB of that is a base they share *with each other* and is
   counted four times over.
2. **It counts images referenced only by non-running containers.** `ACTIVE 83` against
   `TOTAL 95` means Docker calls twelve images inactive — and Docker's "active" means *attached
   to a running container*. An image held only by a `created`, `exited` or `dead` container is
   load-bearing, and this estate has a documented six-week blind spot on exactly that
   (dispatcharr and teleport). `spike03-image-headroom.sh` deliberately protects that set,
   which is why its list will always be far shorter than Docker's own figure.

**A short approved list is the method working.** If this plan removes four images and frees
1 GiB, that is a success, not a miss. **The recorded byte delta and the per-tag removal diff
are the evidence.**

One further caution, carried from 03-01 and worth restating because it is the more important
lesson: **images were never the real lever.** While 03-01 sat at its approval gate, `/` went
from 2.2 GB free to **zero**, and the actual consumer was a 19 GB Jellyfin transcode cache —
larger than the entire image reap and, unlike images, it *refills*. This phase fixed that. This
reap is housekeeping on top of a problem that has already been solved; do not let its size be
read as a measure of the phase.

## How this list was produced — the exclusion rule

The referenced-image set is built from **`docker ps -a` with NO status filter**, in both
subcommands, deliberately. A container in `created` has never run, so any status-filtered query
misses it and its image looks orphaned — dispatcharr and teleport sat in `created` for six weeks
behind exactly such a filter.

Three sources are unioned into the protected set:

1. The `Image` column of `docker ps -a` — the string each container was created with.
2. `docker inspect --format '{{.Image}}'` per container — the image ID *actually* in use, which
   catches a tag that moved after the container was created.
3. The `.Parent` chain of every referenced image, so a dangling ancestor of a live image is
   never reaped.

Plus the allow-list `sentriz/wrtag`, `lscr.io/linuxserver/beets`, `metasauce/beets-flask`,
`redis` — which is why `beets:2.13.1-ls349`, `wrtag:v0.33.0`/`v0.34.0` and
`beets-flask:v2.0.0-rc6` do **not** appear below despite showing `CONTAINERS 0`. Phase 3 pulled
them and needs them.

**Zero containers are in `created` state today.** The enumeration was done unfiltered anyway —
a lucky day is not a method.

## Known collateral

**`docker ps -a` protects an image only if some container *object* references it** — running,
exited, dead, restarting or `created`. It does **not** protect the image of a stack that is
currently `docker compose down`'d, because `down` removes the container objects. Nothing then
references the image, the inventory lists it, **it will be reaped, and bringing that stack back
up will need a fresh `docker pull`.**

**The `stacks/selfhosted/**` cross-reference is a partial mitigation, not a proof.** It cannot
see one-off `docker run` recipes, and it cannot see undocumented rollback targets deliberately
retained. 03-01 also found that a **registry-prefix difference defeats it** —
`pglombardo/pwpush:2.7.3` first scored "not declared" because the stack writes
`docker.io/pglombardo/pwpush:2.9.4`. That residual is exactly what the human gate is for.

### Candidates that are compose-referenced but container-less

**NONE.** The plan requires any such row to be flagged by name, because it is the exact
signature of a stopped-and-downed stack rather than a dead image. `grep -rn "keeper-.*:2\.13"
stacks/` returns **zero lines**: no compose file in this repo names `2.13` anywhere. All five
keeper services declare `2.23` and all five are running.

### Generic utility image candidates

**NONE.** The plan requires `alpine`, `busybox`, `curlimages/curl` and similar to be called out

candidates (`alpine:3`, `curlimages/curl:latest`) were not resident at all**, having been taken
by 03-01's reap. It used `nginx:1.31.3-alpine` instead, which is **not** on this list (it is

   `do_inventory` to enumerate with `-a` and let the derivation produce them, then run this gate
   again.

**All four rows are one stack, one generation back.** `keeper-sh` (the `cal-*` containers) was

## Approval

**Nothing below the line runs until the operator approves.** On approval,
`FLOOR_GB=20 bash scripts/spike03-image-headroom.sh prune` re-derives the referenced set from
`docker ps -a` (no status filter), re-checks every row against it, **aborts whole with nothing
deleted** if any row became referenced since this list was made, and then deletes by tag one at
a time. `docker image prune -a` and `docker system prune` are prohibited in the script and
asserted absent by a comment-stripped grep — measured both ways today: **raw count 4** (the
known false positive, all four in the header's own prohibition notices), **comment-stripped
count 0**.

`prune` exits **2** if `/mnt/fast/spike-03/out/reap-list.txt` is absent — a refusal, checked
before docker is even required, never a fallback.

**This is the only irreversible act in the whole phase.** Recovery is a `docker pull` per image,
minutes each and network-bound; all four are public on GHCR at the exact tags recorded above,
and the full before-listing is committed in `artifacts/02.1-09-reap-transcript.txt` so the tags
survive independently of this table. Everything else in this phase is a file revert, a
`zfs set`, or a re-POST.
