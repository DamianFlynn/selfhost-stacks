# Phase 02.1 Plan 12: Correct the false Jellyfin reachability claim (CR-02) Summary

Measured Jellyfin's admin API surface from three vantage points, found it LAN-wide reachable at
`172.16.1.76:8096` via `iot_macvlan` and the `ports:` mapping inert, corrected the false
"publishes no host port" claim at four sites, and re-derived PROJECT.md's residual-risk acceptance
for the write-scoped administrator-equivalent API key against the corrected reachability.

## Did the review's `docker-proxy` mechanism reproduce?

**No — and this matters more than the conclusion it was attached to.**

Four independent instruments say the same thing: `ss -tlnp` finds zero listeners on 8096 and 8920;
`docker inspect .NetworkSettings.Ports` reports every port bound to `null`; `docker ps` prints no
`0.0.0.0:8096->` arrow; and `curl` to `172.16.1.159:8096` fails to connect from the workstation,
from atlantis, and from LXC 100's own loopback.

**The code review was RIGHT ABOUT THE CONCLUSION and WRONG ABOUT ONE OF ITS TWO STATED
MECHANISMS.** The admin API surface genuinely is reachable far beyond one container — but the
route is the `iot_macvlan` LAN address alone, not a `docker-proxy` bind on LXC 100's host
interface. The `ports:` list at `jellyfin.yaml:89-93` is **inert** under macvlan attachment; the
compose file's own inline comment `# HTTP (accessible via macvlan and host)` is half wrong.

That distinction is recorded loudly because writing "it publishes 8096 on the host interface" into
the scripts would have replaced one false claim with another, and the next reader would have acted
on it. `grep -ic 'docker-proxy'` over both edited scripts returns **0** — deliberately.

## What the risk re-derivation changed, and what it deliberately did not

**Changed.** The blast radius of an **API-key leak** is estate-wide — the whole `172.16.1.0/24`
plus the tailnet via the estate's two subnet routers — rather than confined to a host an attacker
must already own. The "you must already be on LXC 100 to use it" mitigation **does not exist and
never did**.

**Deliberately not changed.** Reachability of the *endpoint* is not disclosure of the *key*.
Obtaining the key still requires root on LXC 100: `/mnt/fast/secrets/jellyfin-deercrest.env` is
mode `600 root`, asserted on **every** sourcing by both `check-music-consumers.sh` and
`check-jellyfin-transcode.sh`, which refuse to source on any other mode/owner.

**Also not changed by this phase at all.** `172.16.1.76:8096` being LAN-reachable is a
**pre-existing estate condition** long predating phase 02.1. What this phase changed is that the
key is now used for **write** (`POST /System/Configuration/encoding`) — not that the port opened.

**The withdrawn control is named, not dropped.** PROJECT.md's row states in-band that
"Jellyfin publishes no port reachable from outside LXC 100" was **measured false on 2026-09-03**,
citing the artifact. A control list that silently shortens reads as if the item was never there;
naming it is what makes the next security review meet a reasoned answer.

**The three surviving controls were verified and kept intact**: mode `600 root` re-checked on every
sourcing; the key passed to `curl` by **process substitution** so it never enters argv; never
written to this public repo, screened with a positive control on every plan that touches it.

## Remediation: deferred, and why

Dropping `ports:` from `jellyfin.yaml` is **near-cosmetic** given the measurement — those mappings
publish nothing. The real lever is **detaching `iot_macvlan`**, and that is a **behaviour change**,
not a cleanup: `172.16.1.76` is how LAN clients and the TV path reach Jellyfin, demonstrated live
by an operator streaming from exactly that address while this plan ran. The code review itself says
this "should be its own decision, not folded in here". Traefik already fronts Jellyfin via the
`t3_proxy` service label, so a route exists — but re-pointing the house at it is a separate piece
of work with its own failure modes.

Recorded in PROJECT.md as **deferred, not overlooked** — the same distinction D-22 draws for
scheduling. Jellyfin's network exposure is **unchanged** by this plan.
