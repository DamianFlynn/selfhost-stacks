<objective>
Close **CR-03**, found by the 02.1 gap-closure code review and independently reproduced on LXC 100.

`scripts/quick-health-check.sh:261` and `:267` bound their remote command with `timeout` inside a
pipeline whose last stage is `wc -l`. `timeout` signals only the first stage. `wc -l` then counts the
empty stream, prints `0`, and — with no `pipefail` in the remote shell — the pipeline exits `0`.

Reproduced live on LXC 100 before this plan was written:

```
$ timeout 1 sh -c "sleep 5; echo hi" | wc -l ; echo "rc=$?"
0
rc=0
$ timeout 1 sh -c "sleep 5" ; echo "rc=$?"                    # no pipe, for contrast
rc=124
$ set -o pipefail; timeout 1 sh -c "sleep 5; echo hi" | wc -l ; echo "rc=$?"
0
rc=124                                                        # <-- the fix
```

So on a wedged dockerd — **the 2026-08-31 amdgpu signature that 02.1-13 exists to defend against** —
the script prints `✅ No unhealthy containers` and leaves `EXIT_CODE` at 0. A green tick while blind:
this phase's own named central failure mode, reintroduced by the plan written to prevent it.

The guard at `:268` is unreachable for the case its own comment names. `wc -l` always emits a number,
so `grep -qE '^[0-9]+$'` always matches; the branch can only fire on ssh transport failure, which
`:211` already exits on. Line `:261` has the same defect, rendering a hang as `Containers running: 0`.

The `| wc -l` shape predates 02.1-13. What 02.1-13 added is a **new and likely route into it** plus a
comment asserting the case is handled — which is worse than leaving it alone, because it stops the
next reader from looking.

Also in scope, rolled in by operator decision: **WR-01** (two genuinely unbounded probes with a
factually wrong justification) and **WR-09** (four cross-file `file:line` references this phase's own
edits invalidated).

Purpose: 02.1-13's bound must actually bind. Output: a driven control proving it does.

  <name>Task 2: Bound the exempted probes, or re-justify them truthfully (WR-01)</name>

  <files>scripts/quick-health-check.sh</files>

  <action>
`:211` (`ssh ... true`) and `:224` (`ssh ... command -v timeout`) are unbounded. The in-file
justification at `:206-210` says the not-at-all case is "a dead transport, which ConnectTimeout above
does cover." **That is false.** `ConnectTimeout` bounds the TCP connect and in some OpenSSH versions
the banner exchange. It does not bound authentication, PAM, session setup, or the fork of the remote
shell. A host that completes the TCP handshake but cannot fork — PID exhaustion, memory pressure,
**a full `/`, which is the exact incident this phase exists to fix** — hangs both probes forever.

Two acceptable resolutions; pick one and say why:

  - **Bound them.** `-o ServerAliveInterval=5 -o ServerAliveCountMax=2` bounds a wedged session at
    roughly 10 s with no local `timeout` and no subshell. Alternatively a pure-bash watchdog
    (background the ssh, background a `sleep N; kill`, `wait` the ssh, reap the watchdog).
  - **Keep them unbounded** — but replace the false justification with a true one that names what is
    actually not covered, so the next reader is not misled.

Bounding is preferred: these two probes gate everything after them, so a hang here hangs the whole
check, and the failure mode is the phase's own incident.
