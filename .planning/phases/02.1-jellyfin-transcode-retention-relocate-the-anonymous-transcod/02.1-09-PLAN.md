<objective>
Reclaim the unreferenced Docker images sitting on LXC 100's root filesystem, through the approval gate
that already exists — and measure success by what the method actually yields.

D-28 pulls this into scope deliberately. It keeps its own human gate because the image reclaim is the
**one irreversible act in this whole phase**, which is exactly why it has one while the Jellyfin
recreate does not (D-27).

**Under D-31 this plan moved from the front of the phase to the tail, and its objective was restated.
Both changes are operator rulings taken after the cross-AI review; the scope is unchanged.**

*Why it moved.* In the reviewed order this plan sat in wave 1 with a **blocking human gate**, standing
between the incident and its fix. The anonymous volume kept receiving transcodes until wave 3 and was
not removed until wave 4, so a day spent sitting on this approval exposed the phase to a repeat of the
very failure it exists to prevent — `DeleteTranscodeFileTask` bounds an orphan at ~48 h, the same
window the original 19 GB accumulated in. It now runs after `/` is structurally protected, so the gate
can take as long as it needs to.

*Why the target was restated.* The reviewed objective read "Reclaim the ~62 GB". **The project's own
prior measurement contradicts that figure.** 03-01 removed 27 images and `/` went 18 → 36 GiB —
**18 GiB real** — yet `docker system df` reclaimable went **61.87 GB → 62.44 GB. It rose.** A 95-image
/ 66.54 GB total with 62.44 GB "reclaimable" implies roughly 4 GB of *active* image size across 103
running containers, which is not credible. Docker's RECLAIMABLE double-counts shared layers and counts
images referenced only by non-running containers — precisely the set `spike03-image-headroom.sh`
deliberately protects. The objective is therefore **"reclaim whatever the auditable diff yields"**, and
the 03-01 evidence is recorded in the reap list itself so that a short approved list reads as *the
method working* rather than as a shortfall. If this plan removes twelve images and frees 6 GiB, that is
a success, not a miss.

No new tooling. `scripts/spike03-image-headroom.sh` already has everything: its `inventory`/`prune`
split is joined by a **file on disk** specifically so the gate cannot be branch-skipped from inside one
process; it builds the referenced set from `docker ps -a` with **no status filter**, covering the
estate's documented `created`-state blind spot (dispatcharr and teleport sat there for six weeks behind
a filtered check); it re-validates the approved list against a freshly derived referenced set
immediately before deleting anything, because a container may have been created between approval and
now; and `docker image prune -a` / `docker system prune` are **prohibited by name**, with the
prohibition asserted by a comment-stripped grep — the banner deliberately says "reap" rather than the
prohibited word, because a banner string would satisfy a naive grep just as well as a real call.

**Ordering constraint (D-31, constraint 2).** This plan `depends_on` **02.1-07**, the
`disable-jellyfin-hwaccel.sh` hardening. That plan's sandboxed proof needs a resident container image,
and the candidates here are exactly the generic utility images you would reach for — `alpine:3` and
`curlimages/curl:latest` were rows 9 and 2 of 03-01's approved list. Running the proof first removes
the collision entirely.

Purpose: headroom on the filesystem this phase exists to protect, taken through a gate that cannot be
skipped.
Output: a reclaimed root filesystem, an approved reap list under `.planning/`, and before/after
free-space figures in bytes with a per-tag removal diff.
</objective>
