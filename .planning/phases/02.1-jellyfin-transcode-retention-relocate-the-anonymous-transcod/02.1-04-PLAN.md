<objective>
Move the bytes and change the declaration — everything up to, but not including, the recreate.

The `jellyfin/jellyfin` image declares `VOLUME /cache`. It is unbound, so Docker put it on `/` as an
anonymous volume, `d98b2ff94482…`. STATE.md names *"the volume being anonymous rather than a declared
bind mount"* as the root cause of `/` reaching zero bytes. That volume holds 392 MiB today: `images`
370 M (the artwork cache), `xmltv` 16 M (the TV guide), shader caches ~4 M, and `transcodes` 472 K —
but it held **19 GB** on 2026-09-01, from a single unbounded stream-copy HLS remux.

D-08 binds **all** of `/cache`, not only the transcodes path, because binding only `transcodes` would
leave the named root cause standing and would leave the 370 MB image cache — the other, slower grower
— on `/`. D-09 points `/cache` at `/mnt/fast/appdata/media/jellyfin/cache`, a **plain directory**
inside the already-mounted `fast/appdata/media` dataset; that is decisive rather than aesthetic,
because `infra/lxc-selfhost.tf:163-167` requires every child ZFS dataset to have its own explicit
`mount_point`, so a new dataset would mean editing the LXC resource that carries `prevent_destroy`
and `ignore_changes = [mount_point]`. D-01/D-03 then nest `/cache/transcodes` on top from
`/mnt/fast/transcode`, which plan 02.1-03 has already given `quota=50G` and proven `mounted=yes`.

D-10 copies the 392 MB first — preserving the artwork cache (no burst of re-fetching on a server the
house watches) and the xmltv cache (no blank TV guide on first load) — and deletes the anonymous
volume only **after** Jellyfin is proven running on the new path. That deletion is plan 02.1-06's
task, two plans away, and the ordering is not negotiable.

D-02 deletes `/dev/shm:/data/transcode` and its comment together. `/dev/shm` holds **0 bytes** and
always has, because `TranscodingTempPath` was never set to `/data/transcode`. Leaving it is a decoy:
it reads as "already solved", which is plausibly part of why 19 GB accumulated unnoticed.

**Two changes the cross-AI review made to this plan:**

- **The cache census gets a stated tolerance.** Jellyfin is live and serving throughout: it writes to
  the image cache on artwork fetch, xmltv sync and client browsing. An exact file-count-and-byte match
  between a census taken before the copy and one taken after is a **false-negative generator** — both
  reviewers reached that from opposite sides. The assertion becomes structural and sampled rather than
  exact, and — this is the part the reviewed version got wrong independently — the automated verify
  and the written acceptance criteria now say the **same thing**.
- **Under D-31 this plan no longer depends on the image reap.** The reap moved to the tail (02.1-09),
  so the headroom this copy needs is checked here explicitly rather than inherited from a plan that
  now runs later. 392 MB against ~33 GiB free is not a constraint; the check exists so that if it ever
  became one, this plan stops rather than discovering it mid-copy.

Purpose: this is the structural fix. Everything else in the phase bounds or detects; this is the part
that moves the write target off `/`.
Output: the cache copied and censused, `jellyfin.yaml` edited and documented, and the host checkout
carrying it all.
</objective>
