**Instrument note.** The script measures available space with `df -B1` and truncates to GiB,
**not** `df -BG`. GNU `df -BG` rounds *up*: on this host 2.2 GiB actually free reports as `3G`.
On an 8 GiB floor that is up to 1 GiB of optimism in exactly the wrong direction. The truncating
measure is strictly more conservative than the plan's external acceptance check
(`df -BG --output=avail / … -ge 8`), so anything passing this measure also passes that one.

**Why "upper bound".** Docker shares layers between images, so a shared layer is counted once per
image that uses it. Two rows below (`audiobookshelf:2.35.1` and `:latest`) are literally the same
image `a7befa7704bd` counted twice. The measured `df` delta after the prune is the real number;
18.1 GiB is the ceiling, not the promise. Even at a large discount it clears the ~8.3 GiB needed.

**Why this list is much smaller than docker's own 61.87 GB "reclaimable".** `docker system df`
computes reclaimable against its own notion of unused. This list is derived from an explicit,
auditable diff and additionally protects an allow-list and the parent chain of every referenced
image. The ~42 GB difference is the safety margin bought by not trusting a blanket sweep.

## How this list was produced — the exclusion rule

The referenced-image set is built from **`docker ps -a` with NO status filter**, in both
subcommands, deliberately.

This estate has a documented **`created`-state blind spot**: dispatcharr and teleport sat in
`created` — existing, having never run — for six weeks behind a check that filtered on
`status=restarting/dead/exited` and therefore never saw them. A container in `created` has never
run, so any status-filtered query misses it, and its image looks orphaned. Reaping that image
would silently break a container that already looks broken.

Three sources are unioned into the protected set:

1. The `Image` column of `docker ps -a` — the string each container was created with.
2. `docker inspect --format '{{.Image}}'` per container — the image ID *actually* in use, which
   catches the case where a tag moved after the container was created.
3. The `.Parent` chain of every referenced image — so a dangling `<none>:<none>` ancestor of a
   live image is never reaped.

Plus an allow-list: `sentriz/wrtag`, `lscr.io/linuxserver/beets`, `metasauce/beets-flask`,
`redis`. This is why **`sentriz/wrtag:v0.20.0` (172 MB) does not appear below** — plan 03-01 task 3
requires it to survive.

## Known collateral

**`docker ps -a` protects an image only if some container *object* references it** — running,
exited, dead, restarting or `created`. It does **not** protect the image of a stack that is
currently `docker compose down`'d, because `down` removes the container objects. Nothing then
references the image, the inventory lists it as reapable, **it will be reaped, and bringing that
stack back up will need a fresh `docker pull`.**

This is accepted deliberately, not discovered later. At 2.2 GiB free of 126 GB the trade is a
re-pull costing minutes against a full root filesystem taking the Docker host down for 103
containers. But it is the operator's cost to accept knowingly, which is what this section and the
approval prompt exist for.

**Partial mitigation:** every row below carries a cross-reference against the `image:` lines in
`stacks/selfhosted/**`, so a `compose down`'d stack's image is visibly distinguishable from a
genuinely orphaned layer.

**The limits of that cross-reference, stated honestly:**

- It cannot see **one-off `docker run` recipes** — an image pulled by hand and kept.
- It cannot see **undocumented rollback targets** — an old version deliberately retained.
- It matched on literal `image:` values, so a **registry-prefix difference defeats it**. This
  actually happened here: `pglombardo/pwpush:2.7.3` first scored *not declared* because the stack
  declares `docker.io/pglombardo/pwpush:2.9.4`. It is in fact a superseded tag of a live stack.
  Corrected in the table below rather than silently fixed.

No automated check can close the first two. That residual is exactly what the human gate is for.

### The headline finding

**Not one of the 27 is the exact image any *enabled* stack currently declares.** Twenty-two are
straightforwardly superseded tags — the residue of the documented Renovate deploy-drift pattern,
where a merged version bump pulls the new image and leaves the old one on disk forever. The
`compose down`'d-stack collateral this plan warned about **did not materialise in this list**.

### The three rows that deserve a deliberate answer

- **Row 23 — `karakeep-mcp:0.31.0`.** The only row declared at its *exact* tag. The declaration is
  commented out (disabled 2026-07-30, "karakeep-mcp is a STDIO MCP server, not an HTTP one"), so no
  container object exists and `docker ps -a` cannot protect it. This is the closest thing in the
  list to a deliberately-retained image. Re-pullable from GHCR if the decision is ever revisited.
- **Row 27 — `gcr.io/zenika-hub/alpine-chrome:124`.** ⚠ **This one is not re-pullable from where it
  came from.** `karakeep/compose.yaml:124` records that the GCR mirror is *gone*, which is why the
  stack moved to `zenika/alpine-chrome:124` on Docker Hub. The Docker Hub image is the one actually
  running and is unaffected; deleting the GCR copy loses only the dead-registry duplicate. Called
  out because "cannot be re-pulled" is normally the reason to keep something.
- **Rows 2 and 9 — `curlimages/curl:latest`, `alpine:3`.** Undeclared generic utility images,
  32 MB combined. These are the one-off-`docker run` class the cross-reference cannot see. Trivially
  re-pullable.

## Approval

**Nothing below the line runs until the operator approves.** On approval,
`bash scripts/spike03-image-headroom.sh prune` re-derives the referenced set, re-checks every row
against it, aborts whole if any row became referenced since this list was made, and then deletes
by tag (or by ID for untagged images) one at a time. `docker image prune -a` and
`docker system prune` are prohibited in the script and asserted absent by a comment-stripped grep.
