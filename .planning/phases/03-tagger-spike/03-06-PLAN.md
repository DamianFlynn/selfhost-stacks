<objective>
Build the instrument criteria 1 and 2 are measured with, and gate it behind a smoke test before it is
trusted on the sample.

`beet import --pretend` is **unusable** for this: `beets/importer/session.py` v2.13.1 replaces the
entire pipeline with a file lister when `pretend` is set, so it never calls `lookup_candidates`,
issues zero API calls and reports zero candidates. `beet import -q --log` records only the outcome
(`skip`/`asis`/`duplicate`), not the candidate set or its track counts, so it cannot satisfy D-05.
`beet import -t` needs a human keypress per folder and its transcript is not machine-parseable, so
it is kept as the **second** instrument on a three-folder subset, not the first.

The only mechanism that yields both the loose and the strict figure mechanically is a direct call to
`beets.autotag.match.tag_album()`, whose `AlbumMatch` carries the candidate's track list *and* the
item/track mismatch. Research assumption **A1** flags the plugin-bootstrap lines as the weak point,
so the smoke test in Task 2 is a **hard gate**: if it does not return a Discogs candidate on a
known-good album, stop.

Purpose: this is the number the whole phase produces. An instrument that under-reports because a
plugin quietly failed to load would disqualify the winner on a measurement artefact.
Output: `scripts/spike03-discogs-probe.py` and a recorded smoke-test verdict.
</objective>

Create `scripts/spike03-discogs-probe.py`. **Container-resident** — it runs inside `beets-spike` via
`docker exec beets-spike python3 /spike-scripts/spike03-discogs-probe.py …`, delivered by the
read-only `scripts/` mount (OD-6). State that in the header, with the reason: LXC 100 has no `pip3`,
no venv (`ensurepip` absent) and PEP 668 set, so beets and `python3-discogs-client` exist only inside
the image.

Header docstring in the repo's fixed section order, with a **READ-ONLY contract clause that is
narrower and stronger than `snapshot-music-tags.sh`'s** and stated *at the call site* as well as in
the header: `tag_album()` reads `Item`s and returns a `Proposal`; it opens no library database, runs
no importer stage, moves no file and writes no tag. Pitfall 5 in 03-RESEARCH.md is exactly this risk.

**Configuration, explicitly, never by default** (Pitfall 1 — a bare `beet` invocation opened the
default library and ran 11 migrations in Phase 1):
  - `config.set_file(os.environ["SPIKE_CONFIG"])` — the spike config, never the image default.
  - `config["library"] = os.environ["SPIKE_DB"]` — an explicit throwaway `.blb` under
    `/mnt/fast/spike-03/beets-config/`. **Not** under `/tmp`.
  - `config["discogs"]["user_token"] = os.environ["DISCOGS_USER_TOKEN"]` — injected in Python from
    the environment supplied by `env_file`. The token never appears in argv, never in a config file,
    never in the repo. Do not log the value; do not echo the environment.
  - `plugins.load_plugins(config["plugins"].as_str_seq())` then `plugins.find_plugins()`.

**Preconditions, all loud, all before any work:**
  1. Assert `musicbrainz` **and** `discogs` are both present in the loaded plugin set from
     `plugins.find_plugins()`. Exit 1 naming what is missing. A customised `plugins:` list that omits
     `musicbrainz` silently disables autotagging and presents as "no match found", not as a config
     error — that is the exact defect TAGR-05 exists to close.
  2. Probe Discogs auth once: `GET https://api.discogs.com/oauth/identity`. **Refuse the entire run**
     if it does not return 200, printing one unmissable statement. Record the
     `x-discogs-ratelimit` header value into the run banner — criterion 2's whole extrapolation
     rests on it (research assumption A6 says 60/min; verify, do not trust).
  3. Assert every required environment variable is set, naming any that is not.

**Per-folder work loop:**
  - Collect audio paths by extension (`.mp3`, `.flac`, `.wav`, `.m4a`), build `Item.from_path`
    objects, call `match.tag_album(items)`, and emit **one NDJSON line per candidate** carrying at
    minimum: `folder`, `tree`, `stratum`, `n_files`, `cur_artist`, `cur_album`, `source`
    (`m.info.data_source`), `album`, `album_id`, `n_tracks` (`len(m.info.tracks or [])`),
    `extra_items` (files with no matching track), `extra_tracks` (release tracks with no matching
    file), `distance`, `recommendation`, `index_tracks_setting`, `plugins_enabled`, and a per-folder
    UTC timestamp. Also emit a `candidates: 0` record for a folder that returns none, so a
    zero-candidate folder is distinguishable from a folder that was never probed.
  - Assemble every record with `json.dumps(dict)`. Never f-string a record: album titles in this
    collection contain `:`, quotes and trailing spaces (`Mastermix Crate 068 : …`,
    `Mastermix - Issue 413 `).

**Resume ledger, at folder granularity.** `<basename>.done` is loaded once into a set on start and
any folder already present is skipped. **Emit the NDJSON lines for a folder first, then append the
folder to `.done`** — a hard kill in that window re-emits one folder's records on the next run and
never loses one. This matters more here than it did in Phase 1: a rate-limited Discogs run stalls
invisibly for hours, the operator **will** interrupt it, and a 24-folder run that has to start over
burns another 150–260 API requests against a 60/min ceiling.

**Failure ledger, not a silent skip.** A folder whose `tag_album()` raises goes to `.failed` with
the exception class and is **not** written to `.done`, so a re-run retries it. It must **never** be
counted as "no Discogs candidate" — conflating an exception with a zero-candidate result would
corrupt the headline number this phase exists to produce.

**Signal handling at a clean boundary.** A `signal.SIGINT`/`SIGTERM` handler sets a flag checked at
the top of the folder loop; print `[signal received - stopping at the next folder boundary]`. Ctrl-C
must never land between the emit and the ledger append.

**Request counting — the independent second instrument.** Configure
`logging.getLogger("urllib3.connectionpool").setLevel(logging.DEBUG)` writing to **stderr**, so
`grep -c 'api\.discogs\.com'` on the stderr file counts what actually left the process, independently
of beets' own bookkeeping. Never set `http.client.HTTPConnection.debuglevel` — that logs request
headers, and the token travels in `Authorization`. Additionally maintain an in-process counter of
HTTP `429` responses and print it in the summary: Pitfall 4 means a rate-limited run does not fail,
it sleeps, so **429 count is recorded beside the timing or the extrapolation is uninterpretable**.

**A wall-clock ceiling.** Accept `--max-seconds` with a documented default and abort past it rather
than absorbing a `MAX_ATTEMPTS = 100` backoff chain silently.

**Summary block** printing, at minimum: folders probed, folders with ≥1 Discogs candidate
(**loose**), folders passing the track-count test (**strict**), **the gap between them** as a count
and a percentage, total Discogs requests, 429 count, wall-clock total and per-folder mean, the
`index_tracks` setting in force, and the `search_limit` in force. D-05 and the CONTEXT `<specifics>`
both make the loose/strict gap a deliverable in its own right — print it; do not make a reader
compute it.

**EXIT-CODE CONVENTION**, stated in the header: `0` = all folders probed with zero failures; `1` =
one or more folders in `.failed`, or the wall-clock ceiling was hit; `2` = usage error, a missing
environment variable, a plugin not loaded, or the Discogs identity probe not returning 200.

Cite `D-05`, `OD-6` and the Pitfall numbers inline at the lines they justify.
