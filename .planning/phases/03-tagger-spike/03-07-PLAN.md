<objective>
Produce criterion 1's and criterion 2's numbers, each with two independent instruments, and write
the T1 and T2 verdicts back into the pre-committed threshold table.

Criterion 1 requires a Discogs match rate over the normalised sample **with the un-normalised number
recorded beside it**, because beets builds its Discogs query from the existing `artist` and `album`
tags and a rate measured on raw tags under-reports. Criterion 2 requires the run timed and
extrapolated against the authenticated rate ceiling into a stated hours-for-the-backlog figure.

Two further rules were fixed before any of this ran and are executed, not chosen, here.

**The estimator (committed in plan 03-02, pushed to `origin` before this plan starts).** The sample
is stratified and deliberately never random: it over-weights minority variants so every convention is
exercised, and it excludes the scan-bearing folders. That makes it a **coverage sample**, built to
surface failure modes — and a coverage sample is not a population estimate. Request volume and match
likelihood vary by stratum by construction (a V3 folder with no `album` issues no Discogs query at
all; a V1 folder paginates), so an unweighted average over the 24 folders is skewed by the very
property that makes the sample useful. Therefore **every headline figure in this plan is a
per-stratum roll-up weighted by that stratum's prevalence across the committed 143-folder backlog**,
using the weights measured in `03-SAMPLE.md § Stratum prevalence`. The unweighted per-folder figure is
reported beside it, always, and is never the figure T1 is tested against. **The 40% threshold value
is unchanged**; only the estimator was specified, and it was specified before any weight or rate
existed.

**Custody (F-check before anything is measured).** Criterion 5's proof is a commit on a remote, not
an ordering on a local branch. Before this plan records a single number it re-asserts that the
plan-03-02 threshold commit is reachable from `origin/main`, and it reproduces that SHA verbatim in
the evidence file.

Two rules govern everything here. **D-05:** a "match" means a Discogs candidate appears **and** its
track count agrees with the folder — a confident wrong match is the worst possible outcome on this
content, and stub entries of 5–10 tracks against 15–20 track releases are exactly how that happens.
T1's 40% applies to that strict figure. **The paired-instrument rule:** every number gets two
independent readings before it is written down, and if the two disagree neither is recorded until
the disagreement is explained. Phase 1 produced six passes it had not earned, every one from partial
data stated as settled.

Purpose: this is the phase's headline number and the input to axis one.
Output: `03-DISCOGS-EVIDENCE.md`, and T1/T2 filled in `03-DECISION.md`.
</objective>
