pool can see them, and bounds Prometheus' growth.

## Decisions taken in this plan (Claude's discretion, each with its estate precedent)

- **Datasets.** One per app: `fast/appdata/{teslamate,trek,monitoring,airtrail,silo}` (R1). They
  inherit `fast/appdata` (posix ACLs, aclmode=discard, xattr=sa, lz4, atime=off), as the
  Proxmox-era siblings `agentic-os`/`mpe` do. posix + discard is also what Postgres wants: `chmod
  0700` on PGDATA works. Root owner `568:568 0755` on the host is the `agentic-os` precedent.
- **recordsize=16K on the three Postgres-dominated datasets** (teslamate, airtrail, silo). This
  follows `fast/appdata/immich/postgres`, the estate's only Postgres-tuned dataset. trek (SQLite,
  12M) and monitoring (Prometheus TSDB chunks, large sequential) keep the 128K default.
  recordsize affects only newly written blocks, so the fresh copy gets it.
- **The Postgres datasets are NOT split into `<app>/postgres` children** (unlike immich). Each
  child needs its own LXC mount and TF block, and R1 asks for one dataset per app.
- **quota=25G on `fast/appdata/monitoring` only**: about 15x today's 1.7G. This is the "quota'd
  dataset" fix shape that memory `fast-appdata-not-a-mountpoint` prescribes for the estate's one
  continuously-growing tenant. `quota`, not `refquota`, so the failure is ENOSPC, which is what
  the estate's log greps key on. No quota on the Postgres datasets, because ENOSPC under Postgres
  WAL is a PANIC, which is worse than unbounded growth at these sizes.
- **Mount indices mp32..mp36, appended**: teslamate=mp32, trek=mp33, monitoring=mp34,
  airtrail=mp35, silo=mp36. mp29/mp30 stay free on purpose. `mount_point` is a positional
  TypeList, and Recordings (mp31) is the last block in the TF file. Appending at indices above 31
  keeps the host index order and the TF block order identical without moving any existing block.
  Slots 29/30 would have to be inserted before Recordings and would depend on how the provider
  orders a gappy list.
- **Old copies are renamed** to `<path>.rootfs-pre-cg6` (dirs). Named volumes are simply left in
  place (R4). Nothing is deleted before T6.
- **The copy primitive is `cp -a` inside LXC 100, not rsync.** rsync is not installed there, and
  the tank workaround `rsync -rlt --no-p` must NOT be used, because it drops owner and mode.
  `fast/appdata` is posix/discard, so chmod and chown succeed, unlike tank's nfsv4/restricted.
  `automation` is nfsv4/passthrough, where chmod works (the immich postgres precedent).
- **Compose edits ride on a branch** `quick/261022-cg6-appdata-datasets` and are merged and pulled
  to the host only at the start of the migration window (T4 step 0). If a recreate happens on the
  host before the data copy, Postgres initdb's an EMPTY cluster on the new bind. A concurrent
  session pushing `main` early (memory `concurrent-session-push-defeats-deferred-deploy`) is the
  failure this avoids.

- Guards, each a refusal with exit 2 and a one-line reason (rule 1: a refusal is never a pass):
  - EUID must be 0.
  - SRC must be a directory. DST must be an existing, EMPTY directory.
  - `findmnt -no FSTYPE -T DST` must equal `zfs`. This is the R1 assertion that the bytes land on

  failure (exit 1), because `cp` reports dropped xattr/ACL preservation only as a warning.
