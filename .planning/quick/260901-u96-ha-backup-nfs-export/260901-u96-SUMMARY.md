# Quick Task 260901-u96 — read-write NFS export for Home Assistant backups

**Complete.** `/mnt/tank/backups/homeassistant` is exported `rw` to `172.16.1.31` and to nothing
else, Terraform-managed, and proven by a write round-trip from the NUC. Unblocks the
`home-assistant-os` project's RES-04 plans 02-10 and 02-13.

## The finding that shaped the design

`nfs-music-export.tf` argues that `ro` is *forced, not preferred*, because the library is `0777`,
knfsd does not export ZFS NFSv4 ACLs, and mode bits are therefore the only lever a client sees.
Taken at face value that argument forbids any writable export on `tank`.

It does not. It is a property of *those datasets*. `zfs get -s source` on atlantis:

| Dataset | acltype | source |
|---|---|---|
| `tank` | **posix** | local |
| `tank/media/Music` | nfsv4 | local |
| `tank/downloads` | nfsv4 | local |
| `tank/timemachine` | nfsv4 | local |

The `nfsv4` acltype is a TrueNAS-era setting applied *locally* to the migrated datasets. `tank`
itself is `posix`, so a **new** child of it has real, settable, enforceable mode bits — and `chmod`
works on it, which `CLAUDE.md` records failing `EPERM` even as real root on the nfsv4 ones.

So this export sits behind a genuine `0770` rather than the media tree's decorative `0777`, and
that — not a policy preference — is what makes `rw` defensible. The resource sets
`acltype=posix` **explicitly** rather than inheriting it, and asserts the *observed* `acltype` and
the *observed* `stat` mode on every apply, so a later `zfs set acltype=nfsv4 tank` cannot silently
convert a writable export into a world-writable one.

## What was built

- `infra/nfs-ha-backup-export.tf` — `null_resource.nfs_ha_backup_export`. Guarded
  `nfs-kernel-server` install, `zfs create -p` with explicit ACL/recordsize properties, an
  unconditional `zfs set` so a pre-existing dataset converges, ownership + mode, a whole-file
  `/etc/exports.d/ha-backup.exports` write, `exportfs -ra`, then the gates.
- `infra/variables.tf` — `ha_backup_export_path`, `ha_backup_refquota`. Reuses `ha_nuc_ip`,
  `apps_uid`, `apps_gid`.
- `NETWORK.md`, `infra/outputs.tf` — both exports documented; verification commands added.

`depends_on = [null_resource.nfs_music_export]` for ordering only (so two `apt` transactions never
race under `-parallelism=10`). The install guard is *repeated* rather than inherited, unlike
`nfs_music_temp_export`: this export serves a different project's requirement and should not fail
with "unit not found" because someone retired the music export. The `After=zfs-mount.service`
drop-in is **not** repeated — it is a property of the unit, and `nfs_music_export` owns it.

`local.exportfs_joined` is reused across files rather than copied; its own comment says it exists so
the gates needing it cannot drift apart.

## Gates on every apply

1. `acltype` is observed to be `posix` — the property the `rw` decision rests on.
2. `stat -c '%u:%g %a'` is observed to be `568:568 770` — asserts the *result*, not that `chown`
   and `chmod` were run.
3. `mountpoint -q` — never export an empty stub beneath an unmounted dataset.
4. Path **and** client matched on the same joined `exportfs -v` line (WR-04). `grep <ip>` alone
   would pass off the *music* export's line, which names the same client.
5. The effective options contain `rw` — a `ro` regression mounts perfectly and fails only on the
   first write.
6. `no_root_squash` absent, scoped to this file's own drop-in (WR-05). Deliberately **not** read
   from `/proc/fs/nfsd/exports`, which shows four auto-generated `v4root` traversal hits once a
   client mounts.

## HA-side facts, measured not recalled

- Supervisor hardcodes NFS options to `softerr,timeo=100,retrans=2` (+`port=`); `ha mounts add`
  cannot pass others. No `vers=`, so the kernel negotiates — the **live music mount reports
  `vers=4.2`**. (A manual `mount -t nfs4` probe pins 4.0; that is the probe, not Supervisor.)
- `ha mounts add --read-only` is documented by the CLI as "not available for backup mounts", so a
  writable export is Supervisor's requirement.
- `--path` is the NFS flag; `--share` is CIFS-only.
- `softerr` means a LAN stall during a write errors rather than hangs — a blip surfaces as a
  *failed* backup, not a retried one. The 02-13 restore drill should confirm the newest backup is
  complete, not merely present.
