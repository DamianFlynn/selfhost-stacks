# Quick Task 260901-u96 — read-write NFS export for Home Assistant backups

Requested by the `home-assistant-os` project, Phase 2 (Observable House), requirement **RES-04**
("daily automated backups stored off-NUC; a full restore tested and documented"). Its plans 02-10
(off-NUC target) and 02-13 (timed restore drill) are blocked on this.

Serve a **read-write** NFSv4 export from atlantis (`172.16.1.158`) to the HA NUC (`172.16.1.31`)
only, as a Supervisor backup target — Terraform-managed in the same shape as
`infra/nfs-music-export.tf`, never hand-edited.

## Facts established before planning (measured on atlantis, 2026-09-01)

| Fact | Value | Why it matters |
|---|---|---|
| `tank` acltype/aclmode/aclinherit | `posix` / `discard` / `discard`, **source `local`** | A new child of `tank` inherits **posix** ACLs, so `chmod` works normally. The `CLAUDE.md` "chmod fails EPERM on tank" constraint is scoped to `tank/media/*` and `tank/downloads`, which set `acltype=nfsv4` **locally**. This is the finding that makes a tight mode achievable and therefore makes `rw` safe. |
| `tank/timemachine` | `refquota=2T`, `recordsize=1M`, mode `0770` | Existing precedent for a bounded backup dataset on this pool. Followed. |
| `/etc/exports` | empty | Terraform owns `/etc/exports.d/*.exports` only; nothing else is exported. |
| `/proc/fs/nfsd/versions` | `+3 +4 +4.1 +4.2` | The client will negotiate NFSv4.2. |
| `/mnt/tank` | `drwxr-xr-x 0 0` | NFSv4 pseudo-root traversal works; the new parent dir must match. |
| Supervisor `NFSMount.options` | `softerr,timeo=100,retrans=2` (+`port=` if set) | Hardcoded — no `vers=`, and **not overridable** from `ha mounts add`. |
| `ha mounts add --read-only` | "not available for backup mounts" | Supervisor itself requires the export to be writable for `usage: backup`. |

## Design decisions

1. **`all_squash` + `anonuid`/`anongid` from `var.apps_uid`/`var.apps_gid`, never `no_root_squash`.**
   As requested, and it preserves `nfs-music-export.tf`'s invariant. HA's Supervisor writes as root
   inside its container; `all_squash` lands every one of those writes as `apps:apps` regardless.
2. **Its own ZFS dataset, `tank/backups/homeassistant`.** The export option list keeps `mountpoint`,
   and a plain directory is not a mount point — the same reasoning the temp export records. It also
   gives the backups their own snapshot/quota boundary.
3. **Mode `0770`, not `0777`.** The Music library is `0777` because its NFSv4 ACLs made mode bits
   unfixable. This dataset is `acltype=posix`, so the mode is real and enforceable — and unencrypted
   HA backups contain `.storage` secrets, so nothing outside `apps` should read them. The parent
   `/mnt/tank/backups` stays `0755 root:root` so NFSv4 pseudo-root traversal to the leaf works.
4. **`refquota`, not `quota`, defaulting to `50G`.** Matches `tank/timemachine`. At ~440 MB/backup
   that is ~113 retained backups — a real bound against a runaway retention setting eating a shared
   pool, and a one-variable change to lift.
5. **Its own file and its own resource.** `depends_on = [null_resource.nfs_music_export]` for
   ordering (so two `apt` transactions never race), but the guarded package install is repeated
   rather than inherited — this export serves a different project's requirement and should not be
   hostage to the music export continuing to exist.
6. **`local.exportfs_joined` is reused, not duplicated.** It is module-scoped, and its own comment
   says it exists so the gates that need it cannot drift apart.

Deliberately absent from the option list: `no_root_squash` (forbidden, and moot under `all_squash`),
`fsid=` (would relocate the NFSv4 pseudo-root and break the `server:/full/path` addressing both
consumers use), `crossmnt` (would silently export any child dataset created later), `async` (a
backup target must not acknowledge writes the server has not committed), `insecure` (Supervisor
mounts as root from a privileged port).

## Tasks

### Task 1 — variables + the export resource
- **files:** `infra/variables.tf`, `infra/nfs-ha-backup-export.tf`
- **action:** Add `ha_backup_export_path` and `ha_backup_refquota`. Create the export resource:
  guarded `nfs-kernel-server` install, `mkdir -p /etc/exports.d`, `zfs create -p` with explicit
  `acltype=posix`/`aclmode=discard`/`aclinherit=discard`/`recordsize=1M`, unconditional `zfs set`
  of the same plus `refquota` so a pre-existing dataset converges, parent dir `0755 root:root`,
  leaf `chown`/`chmod 0770`, a whole-file `/etc/exports.d/ha-backup.exports` write, then
  `exportfs -ra` and the gates.
- **verify:** `terraform fmt -check`, `terraform validate`.
- **done:** Both files present, formatted, valid.

### Task 2 — apply and prove it with a real client mount
- **action:** `terraform plan -target=null_resource.nfs_ha_backup_export` first and **read it** —
  this repo has a documented landmine where a bare apply in `infra/` planned `1 to destroy` on
  LXC 100. Confirm `0 to destroy` before applying. Then apply the same target.
- **verify:** STATE.md's standing rule — *never assert export health from `exportfs -v` alone*
  (02-08 measured it printing an intact line for an export that refused every client). The
  export-health check is a **real client mount from the NUC**: mount it, write a file, read the
  byte count back from atlantis, delete it, unmount.
- **done:** `exportfs -v` shows the line with `rw`, `no_root_squash` absent from the drop-in, and
  a file written from `172.16.1.31` lands on atlantis owned `568:568`.

### Task 3 — documentation
- **files:** `NETWORK.md`, `infra/outputs.tf`
- **action:** Extend the NFS server section with the second export, its options table, and the
  HA-side notes. Add verification commands to the `verify_commands` output.
- **done:** `NETWORK.md` describes both exports; `outputs.tf` covers the backup export.
