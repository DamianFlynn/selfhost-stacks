## Deviations from Plan

### 1. [Rule 1 — corrected fixture] The drift count is **14**, not 12

**Found during:** Task 1, first run against the live estate.

**Issue:** The plan states the fixture as exactly 12 and instructs that the result "must come out at
exactly 12 — not 0, not 13". The matcher, implemented exactly as the plan's step 3 mandates, finds
those twelve **and two more**.

**This is not a false positive. It is the plan's own stated hazard, caught in the wild:**

| Container | Running | Its project's pin | Also in the repo at the running tag |
|-----------|---------|-------------------|--------------------------------------|
| `n8n` | `ghcr.io/damianflynn/custom-n8n:2.11.1` | `2.22.0` via `stacks/selfhosted/automation/compose.yaml` → `n8n.yaml` | `stacks/mpe/n8n/n8n.yaml` |
| `socket-proxy` | `tecnativa/docker-socket-proxy:v0.4.2` | `v0.5.0` via `stacks/selfhosted/traefik/compose.yaml` → `socket-proxy.yaml` | `stacks/mpe/edge/socket-proxy.yaml` |

Both containers' `com.docker.compose.project.config_files` labels were read directly from the
daemon and point at the `stacks/selfhosted/...` projects. A matcher asking *"does this running
reference appear anywhere in the repo?"* answers yes for both and returns 12. A matcher asking
*"does it match the pin in this container's own project?"* answers no for both and returns 14.

The plan mandates the second question in as many words — *"the map is keyed per container by its
own label, never globally by image repo"* — so **12 is what the superseded method returned**. The
matcher was **not** bent to reproduce it.

**Fix:** none needed in code. The corrected fixture and the full evidence are recorded in-band in a
`MEASURED FIXTURE` block in `scripts/check-drift.sh`, so a reader who meets 14 finds the reason
without leaving the file. **Commit:** `924f272`.

### 2. [Rule 1 — bug in my own code] `tr -dc '0-9'` mangled the count on the green path

**Found during:** Task 3, driving the green path — **not** by reading the code.

**Issue:** The fold-in extracted counters with `sed 's/.*label: *//' | tr -dc '0-9'`. Every summary
line carries explanatory prose after the number, and that prose has digits:
`image drift:        14  (REPORTED, not asserted — v1 is ALERT-ONLY, D-01)` → `tr` keeps the `1`
from "v1" and the `01` from "D-01" and yields **14101**. The first run printed
`✅ Measured — 14101 drifted`.

It was still green and still correct about being green, which is what makes the class worth
recording: **a mangled number on the reassuring path is exactly what nobody re-reads.**

**Fix:** `grep -o '^[0-9][0-9]*'`, anchored, which also preserves the behaviour that matters — a
counter reading `UNKNOWN` yields the empty string rather than a plausible `0`, and empty is treated
as fatal. Reasoning written in-band. **Commit:** `f4ea351`.

### 3. [Rule 1 — bug in my own code] A missing host-side script produced a confident **wrong** diagnosis

**Found during:** Task 3, driving the end-to-end run against the real host state.

**Issue:** `bash <missing file>` writes *"No such file or directory"* to stderr, which `2>&1`
captures — so the output is **not** empty, the empty-output test did not fire, and the run fell
through to the summary-anchor branch and reported *"the section heading this fold-in anchors on has
changed"*. Red and exit 1, with a diagnosis pointing at a heading nobody had touched.

That is precisely the failure mode this file's own WR-10 notice condemns ("a confident and WRONG
diagnosis rather than UNKNOWN"). The three older fold-ins escape it only because their scripts have
been on the host for months — and `check-drift.sh` will be absent until G0, so this is the branch
the user hits **first**.

**Fix:** a presence test in the remote command string (`[ -r … ] || exit 7`, no pipe, so the
`REMOTE_TIMEOUT` bound is not laundered; `7` cannot collide with the check's own 0/1/2), plus its
own branch naming the real cause and the `git pull` that fixes it. The anchor-missing branch was
also softened to name **both** possible causes and print the output tail, rather than asserting the
one that happened to be wrong. **Commit:** `f4ea351`.

### 4. [Rule 2 — missing critical info] Added gated step **G0**

**Issue:** Failing closed on a not-yet-pulled script means **`quick-health-check.sh` exits 1 from

### 5. [Rule 3 — blocking] The Grafana datasource has no pinned UID

**Issue:** Provisioned alert rules can only reference a datasource by `uid`, and
`grafana/provisioning/datasources.yml` declares none, so Grafana generated one.

**Fix:** read the live value — `GET /api/datasources` returned `PBFA97CFB590B2093` — and pinned that
literal in `rules.yaml`, documenting where it came from. **Adding `uid:` to `datasources.yml` was
considered and declined:** provisioning matches an existing datasource by name and would *rewrite*
its uid, silently breaking every hand-imported dashboard referencing the old one. Pinning the
literal changes nothing already running. **Commit:** `2f19870`.
