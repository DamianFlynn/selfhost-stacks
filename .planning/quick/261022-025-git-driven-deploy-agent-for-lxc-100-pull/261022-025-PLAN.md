## Decisions taken by the planner (Claude's discretion), recorded so the executor does not re-open them

- **D-A Classifier reuse = run check-drift.sh, do not copy it.** deploy-stacks.sh runs
  `bash $REPO/scripts/check-drift.sh` in REPORT mode, strips ANSI, and consumes two documented
  anchors: the per-container `IMAGE_DRIFT  <name>  <running> -> <declared>` lines (check-drift.sh
  says the token "appears exactly once per drifted container and nowhere else") and the `📊 Summary`
  block's `image drift:`, `could-not-look:` and `FAILURES total:` labels — the same CROSS-FILE
  CONTRACT quick-health-check.sh already relies on. Its exit contract decides: rc 0 → no drift;
  rc 1 with `FAILURES total: 0` and `could-not-look: 0` → drift; anything else → fatal
  could-not-look (deploy nothing). Anchor guard (CONVENTIONS rule 11): heading missing, or the parsed
  IMAGE_DRIFT line count ≠ the `image drift:` number → fatal. This reuses `docker compose config`
  resolution, `.Config.Image`, the `created` handling, digest-pinned exclusion and normalisation
  WITHOUT a second implementation that could disagree. The only extra docker read is one
  `docker inspect` of the drifted names for four compose labels: `com.docker.compose.project`,
  `com.docker.compose.project.working_dir`, `com.docker.compose.project.config_files`,
  `com.docker.compose.service`.
- **D-B check-drift.sh code is untouched; IMAGE_DRIFT_AUTOAPPLY stays 0 forever.** Its D-01 header
  promised "a flag flip ... not a rewrite", but the constant's own block says the apply path "needs
  its own gate, its own dry-run and its own rollback before it is written. Do not write the apply
  path here". The new script IS that separate gate, so the header promise is now misleading: make a
  COMMENT-ONLY edit in check-drift.sh (the D-01 header paragraph and the AUTO-APPLY SEAM block) so
  it points at scripts/deploy-stacks.sh and says flipping the constant does nothing. Zero
  non-comment lines change (asserted).
- **D-C Compose invocation preserves the original project:** `docker compose -p <project>
  --project-directory <working_dir> -f <each config_file> ...`. Without `-p` a re-run from a
  different cwd can mint a second project and collide on `container_name`.
- **D-D Apply is switched on by a systemd drop-in that replaces ExecStart**, not by an env var. The
  repo ships `scripts/systemd/selfhost-deploy-apply.conf`; installing it to
  `/etc/systemd/system/selfhost-deploy.service.d/apply.conf` is the enable step, deleting it plus
  `daemon-reload` is the disable step, and `systemctl cat selfhost-deploy.service` shows which mode
  is live. The script has no env var that turns apply on — only the `--apply` flag acts.
- **D-E Timing arithmetic (one decision across three files).** Timer `OnCalendar=*:0/30`,
  `RandomizedDelaySec=5m`, `Persistent=true`. Service `TimeoutStartSec=60min`. The script stops
  STARTING new stacks once 20 min have elapsed (remaining deployable stacks become pending
  `deferred: run budget`, not failures; the next run takes them), and per-stack worst case is pull
  900 s + up 300 s + prune 300 s = 25 min, post-checks ≤ 15 min, so a run fits the 60-min cap.
  Worst gap between two healthy `last_run` writes = 35 min (period + jitter) + 60 min (runtime cap)
  = 95 min; plus one whole missed run (30 min) = **125 min = 7500 s** staleness threshold.
- **D-F Metric semantics.** `deploy.prom` is written on EVERY run that got past the classifier —
  dry-run included (so the user's observation period also proves the timer), refused included (the
  refused gauge must be visible). It is NOT written on a could-not-look (classifier red, docker
  down, hold-name verification failed, lock busy): the file is left byte-identical so it goes stale.
  `last_run_timestamp_seconds` = this run completed; `last_success_timestamp_seconds` = last run with
  zero failures and not refused — carried forward from the previous file when this run is not a
  success, so `max()` never goes no-data. Staleness alerts on `last_run`.
- **D-G Exit codes.** 0 = run completed, no failure (dry-run with pending drift is 0: the metric is
  the signal, as in check-drift `--prom`). 1 = any counted failure or could-not-look. 2 = usage /
  environment (bash < 4, non-GNU df, unknown flag, unknown `--stack`, malformed window). 3 = refused
  (dirty / not fast-forwardable). 4 = another run holds the lock (`flock -n` on
  `/run/selfhost-deploy.lock`).
- **D-H Rule noDataState.** The stale rule carries `noDataState: Alerting` (README Health Checks
  rule 4). The failed and refused rules carry `noDataState: OK` with an in-band comment: an absent
  `deploy.prom` is ONE condition and the stale rule owns it; three pages for one cause trains the
  reader to ignore all three. Task 2's verification proves every metric those two rules read is
  actually emitted, which is the failure `noDataState: OK` would otherwise hide.
